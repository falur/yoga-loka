# О проекте
YogaLoka — социальная сеть для йогов. PHP 8.5, Spiral Framework, PostgreSQL, RoadRunner.

# Формат ответа
- Отвечай очень просто — если надо дай немного контекста, твой ответ должен понимать человек с любой подготовкой. Термины, жаргон сокращение не используй. Термины если только совсем без них не обхяснить.
- Отвечай всегда на русском языке
- Не используй Markdown-таблицы в ответах пользователю. Если нужна таблица, рисуй ASCII-таблицу в блоке `text`, чтобы она нормально читалась в терминале.

# Важные файлы

- docs/arch.md — описание архитектуры
- docs/rules.md — правила для написания кода
- docs/code-examples.md — примеры кода

# Принципы работы

## 1. Думай перед тем, как писать код

**Не делай предположений. Не скрывай неуверенность. Озвучивай компромиссы.**

Перед реализацией:
- Явно сформулируй свои предположения. Если не уверен — спроси.
- Если есть несколько интерпретаций, перечисли их — не выбирай молча одну.
- Если существует более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то непонятно — остановись. Объясни, что именно вызывает путаницу. Спроси.

## 2. Простота прежде всего

**Минимум кода, который решает задачу. Ничего лишнего и спекулятивного.**

- Никаких возможностей сверх того, что было запрошено.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «конфигурируемости», если об этом не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если ты написал 200 строк, а можно было 50 — перепиши.

Спроси себя: «Сказал бы опытный инженер, что это переусложнено?» Если да — упрощай.

## 3. Точечные изменения

**Меняй только то, что необходимо. Убирай только собственный мусор.**

При редактировании существующего кода:
- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Следуй существующему стилю, даже если сам сделал бы иначе.
- Если заметил неиспользуемый код, не связанный с задачей — упомяни о нём, но не удаляй.

Если твои изменения создают «сиротский» код:
- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА ТВОИХ изменений.
- Не удаляй старый мёртвый код, если тебя об этом не просили.

Проверка: каждая изменённая строка должна напрямую относиться к запросу пользователя.

## 4. Работа от цели

**Определи критерии успеха. Повторяй цикл, пока они не выполнены.**

Преобразуй задачи в проверяемые цели:
- «Добавить валидацию» → «Написать тесты для невалидных входных данных и добиться их прохождения»
- «Исправить баг» → «Написать тест, воспроизводящий проблему, и добиться его прохождения»
- «Рефакторинг X» → «Убедиться, что тесты проходят до и после изменений»

Для многошаговых задач укажи краткий план:
```text
1. [Шаг] → проверка: [что проверить]
2. [Шаг] → проверка: [что проверить]
3. [Шаг] → проверка: [что проверить]
```

## 5. Проверки и тесты

- Тесты приложения всегда запускай через Docker: `make test`.
- Не запускай `composer test` с хоста. Часть тестов использует адрес `minio:9000`, а он доступен только внутри Docker-сети.
- PHPStan приложения запускай через Docker: `make phpstan`.
