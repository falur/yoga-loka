## Заметки

- Ветка выполнения: `main` (по входу пользователя «в ветке мейн», уже на main).
- Docker и инфраструктура (postgres, redis, minio, mailpit, rabbitmq, temporal, centrifugo) подняты на старте.
- **Расхождение списка переноса с фактом:** план перечисляет 7 файлов для переноса из `tests/Unit` в `tests/Kernel`, но фактически `Tests\TestCase` используют 8 файлов — добавился `tests/Unit/Shared/Infrastructure/Configuration/MediaConfigTest.php` (появился после планирования). План явно требует, чтобы в `Unit` остались только тесты на `PHPUnit\Framework\TestCase`, и закрепляет это проверкой `assert-unit-suite-is-light.sh`. Чтобы план прошёл собственную проверку, переношу все 8 файлов. Это устранение устаревшего перечня, а не отклонение от плана.

- **ВАЖНО — предсуществующий пробел покрытия (вне задачи, решение пользователя):** `make test-coverage`/`make qa` падают на `assert-coverage ... 100`, потому что репозиторий покрыт на **93.04% (2111/2269)**, а не на 100%. Это НЕ регрессия от PCOV/ParaTest: старый механизм (Xdebug, serial `phpunit`) на текущем коде даёт ровно те же 93.04% и тот же список из 29 недопокрытых файлов. Машинерия coverage (PCOV в воркерах + ParaTest, comma-suite, clover) проверена и работает корректно — покрытие совпадает с Xdebug бит-в-бит. 0%-файлы без тестов: `RedisCacheStorage` (CACHE_STORAGE=local в тестах → не исполняется), `OpenApiPublishAssetsCommand` (нет теста на `openapi:publish`), `SystemOutboxRelaySleeper`. Порог 100% и `docker/test/assert-coverage.php` не трогал (запрещено правилами/планом). Пользователь выбрал «считать пробел вне задачи» (это задача про скорость тестов, а не про покрытие). Доведение до 100% — отдельная задача по тестам (~158 строк в 29 файлах).
- **Исправление синтаксиса coverage-команды плана:** план предписывал `--testsuite Unit --testsuite Kernel --testsuite Feature` (три флага), но опция ParaTest `testsuite` — `VALUE_REQUIRED` (не массив), три флага дали бы только `Feature` (142 теста, неполное покрытие). Проверено через `phpunit --list-tests`: правильная форма — один флаг с запятыми `--testsuite Unit,Kernel,Feature` (334 теста). PHPUnit сплитит запятую, ParaTest реконструирует `--testsuite=<val>` для PHPUnit Builder. Это исправление ради явной цели плана «включать suite-ы Unit, Kernel и Feature».
- **PCOV в воркеры ParaTest:** план задавал PCOV только на главном процессе (`php -d pcov.enabled=1`), но воркеры ParaTest — отдельные процессы и не наследуют `-d`; coverage не собирался («MissingResultsException»). Добавлен `--passthru-php="'-d' 'pcov.enabled=1' '-d' 'pcov.directory=app/src'"`, чтобы каждый воркер включал PCOV. После этого clover генерируется корректно.
- **prepare-parallel-resources.sh чистит только БД (не bucket-ы):** план описывал один скрипт для очистки БД и bucket-ов, но в образе test-runner есть `psql`, но нет `mc`. Очистка БД — в `prepare-parallel-resources.sh` (test-runner, psql), очистка bucket-ов — в `ensure-buckets.sh` reset-test (minio-init, mc). Валидация `TEST_PARALLEL_PROCESSES` (1..4) в prepare выполняется первой в reset-test, поэтому при 5 reset падает до любой очистки (и БД, и bucket-ов). Все перечисленные ресурсы очищаются, единый safety-gate сохранён.
- **Перенос подшага из Фазы 4 в Фазу 2:** `Tests\TestCase::defineDirectories()` с `DirectoryAlias::Runtime` (= `runtime/testing` / `runtime/testing-{TEST_TOKEN}`) и `DirectoryAlias::Cache` сделан уже в Фазе 2. Причина: warmup из Фазы 2 проверяет `cache/cycle.php` «внутри текущего runtime-каталога», что требует, чтобы и warmup, и тесты использовали один и тот же runtime/cache. Логика worker-ветки (`TEST_TOKEN`) читает `getenv('TEST_TOKEN')` через общий помощник `Tests\TestRuntime` и forward-совместима: до появления `tests/bootstrap.php` (Фаза 4) `TEST_TOKEN` пуст → базовый `runtime/testing`. В Фазе 4 подшаг defineDirectories(Runtime) уже выполнен.
- В `DirectoryAlias` добавлен `Cache`, потому что Cycle schema cache пишется в `{cache}/cycle.php`, а по умолчанию `cache = runtime/cache` выводится из root, а не из переопределённого runtime; без переопределения `cache` файл `cycle.php` лежал бы вне `runtime/testing`.
- `make test-feature`: 1 PHPUnit Notice (не падение, не из изменений этой задачи) — оставлен, финальный `qa` сверит.

- **КЛЮЧЕВАЯ НАХОДКА — выключенный кэш токенайзера съедал ~2 с на каждый тест:** после первого прогона оказалось, что Feature-тесты идут ~2.6 с/тест (медиана), даже тривиальные. Профилировка: сам boot kernel прогретый = 0.16 с, но `boot` с `TOKENIZER_CACHE_TARGETS=false` = 2.1 с (сканирование `app/src`). Диагностика в реальном тесте показала `TokenizerConfig::isCacheEnabled()=false`, потому что `getenv('TOKENIZER_CACHE_TARGETS')='false'`. Причина: `.env` держит `TOKENIZER_CACHE_TARGETS=false` и `CYCLE_SCHEMA_CACHE=false` (dev-дефолты для автообновления схемы), docker-compose `test-runner` грузит `.env` через `env_file`, а phpunit.xml `<env value="true">` с `force=false` не перезаписывает уже существующую переменную окружения контейнера. Итог: кэш был выключен, каждый boot пере-сканировал `app/src`; warmup писал кэш-файлы (`runtime/testing/cache/listeners`, 30 шт), но тесты их не читали (`readCache=false`). **Фикс:** `tests/bootstrap.php` форсирует `TOKENIZER_CACHE_TARGETS=true` и `CYCLE_SCHEMA_CACHE=true` через putenv+$_ENV+$_SERVER до autoload. Дополнительно `migrate-test-databases.sh` экспортирует те же флаги (ускоряет boot app-kernel при миграциях ~20 с → ~4 с).
- **Результат ускорения:** Feature serial **534 с → 16 с** (медиана 2.6 с → 0.098 с/тест); полный `make test` (334 теста) **324 с → ~46 с**; сам ParaTest-прогон ~13 с. Тайминг стадий make test: reset-test 5 с, migrate base+4 4 с, warmup base+4 2 с, ParaTest 12–16 с, ~15 с — Docker-оркестрация (несколько `compose run`).

- **Оптимизация Docker-оркестрации:** основные прогоны (`make test/test-kernel/test-feature/test-coverage/qa`) запускали `run test-runner` без `--no-deps`, из-за чего compose повторно поднимал `postgres-init`/`minio-init` и ждал healthcheck, хотя `reset-test` уже всё подготовил. Добавлен `--no-deps` (сервисы уже подняты в reset-test) — `make test` 46–55 с → **36 с**.
