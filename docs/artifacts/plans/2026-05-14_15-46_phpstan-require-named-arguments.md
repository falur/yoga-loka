# План реализации

## Задача

Добавить проектное правило PHPStan: если вызов передаёт два и более аргумента, все обычные переданные аргументы должны быть именованными.

Готовый результат: правило живёт в пакете `tools/phpstan`, подключено через `tools/phpstan/extension.neon`, покрыто unit-тестами с fixtures, описано в `docs/rules.md`, а `composer phpstan` и тесты правил проходят.

## Контекст

| Факт | Источник |
|---|---|
| PHPStan tooling вынесен в отдельный Composer-пакет `tools/phpstan`. | `docs/rules.md`, `tools/phpstan/composer.json` |
| Правила регистрируются в `tools/phpstan/extension.neon` сервисами с тегом `phpstan.rules.rule`. | `tools/phpstan/extension.neon` |
| Уже есть примеры custom rules и тестов через `PHPStan\Testing\RuleTestCase`. | `tools/phpstan/src/Rules/*`, `tools/phpstan/tests/Unit/PHPStan/*` |
| Корневой `composer phpstan` подключает пакет правил через `vendor/yoga-loka/phpstan-rules/extension.neon`. | `phpstan.neon`, `composer.json` |
| PHPStan в пакете правил закреплён через существующий constraint `phpstan/phpstan:^2.1.54`; новые зависимости для задачи не нужны. | `tools/phpstan/composer.json`, `composer.lock` |
| В текущем коде уже есть многoаргументные позиционные вызовы в `app/src` и `tools/phpstan/src`; после регистрации нового rule их нужно исправить в той же фазе. | мета-ревью плана, точечный AST-скан |
| Архитектурный документ `docs/arch.md` отсутствует. | проверка файлов проекта |

## Принятые решения

- Реализовать новое custom rule внутри `tools/phpstan/src/Rules`, без установки новых пакетов. Источник: текущая структура PHPStan tooling и отсутствие необходимости в новой зависимости.
- Проверять call-site, то есть количество фактически переданных аргументов в вызове. Если в вызове два и более обычных аргумента, каждый такой аргумент должен иметь имя. Это закрывает исходное правило простым и проверяемым способом.
- Область действия правила: все PHP-файлы, которые анализируют корневой `composer phpstan` и `composer phpstan-rules:phpstan`, включая вызовы проектных классов, vendor API, PHP built-in functions и attributes. Источник: исходное правило проекта без исключений по типу вызываемого API.
- Покрыть function call, method call, nullsafe method call, static method call, constructor call и attribute arguments.
- Не пытаться по PHPStan reflection считать количество параметров в объявлении функции или метода. Такой вариант заметно расширит область правила, добавит риски на dynamic calls/vendor signatures и не нужен для формулировки “именованные аргументы обязательны при 2+ параметрах”.
- Для variadic unpack `...$args` не требовать имя у самого unpack-аргумента, потому что PHP не даёт ему обычное имя аргумента на call-site. Если вызов использует variadic API, которому нельзя безопасно передать все значения именованными аргументами, дополнительные значения передавать через unpack-массив, чтобы обычные аргументы остались именованными.
- Ошибка правила должна иметь отдельный identifier, например `project.namedArgumentsRequired`, чтобы её можно было точечно искать и тестировать.
- План короткий: одна фаза, ожидаемый объём 10-13 файлов и меньше 400 строк осмысленного diff. Количество файлов выше обычного ориентира short, потому что кроме rule/test/fixtures нужно однотипно переписать уже существующие нарушения в `app/src` и `tools/phpstan/src`; изменения остаются локальными и ревьюируемыми за один проход.

## Целевой алгоритм

1. PHPStan анализирует файл и передаёт AST-узлы проектным rules.
2. Новое правило получает узел вызова или атрибута с аргументами.
3. Правило считает обычные аргументы, не включая variadic unpack.
4. Если обычных аргументов меньше двух, правило ничего не сообщает.
5. Если обычных аргументов два или больше, правило проходит по каждому обычному аргументу.
6. Для каждого обычного аргумента без имени правило возвращает точную PHPStan-ошибку на строке аргумента или вызова.
7. Ошибка содержит стабильный identifier `project.namedArgumentsRequired` и короткое сообщение о том, что вызовы с двумя и более аргументами должны использовать именованные аргументы.
8. Диагностический вывод остаётся внутри PHPStan error message и identifier; отдельные runtime-логи не добавляются.

## Фазы выполнения

### 1. Добавить правило именованных аргументов

Цель: ввести один локальный quality gate для многопараметровых вызовов и закрепить его тестами.

Что сделать:
- Создать rule-класс в `tools/phpstan/src/Rules`, например `RequireNamedArgumentsRule`.
- В rule-классе обработать вызовы функций, методов, nullsafe-методов, статических методов, конструкторов и атрибутов.
- Считать только обычные аргументы; variadic unpack не должен сам по себе требовать имени.
- Для вызова с двумя и более обычными аргументами вернуть ошибку на каждый обычный аргумент без имени.
- Зарегистрировать правило в `tools/phpstan/extension.neon` рядом с существующими rules.
- Добавить unit-тест в `tools/phpstan/tests/Unit/PHPStan` через `RuleTestCase`.
- Добавить fixtures: допустимые вызовы с одним позиционным аргументом, допустимые вызовы с двумя именованными аргументами, недопустимые вызовы с двумя позиционными или смешанными аргументами, constructor/static/nullsafe/dynamic function call сценарии, attribute arguments и variadic unpack-комбинации.
- Исправить текущие нарушения нового правила в `app/src` и `tools/phpstan/src`. Ориентир по текущему скану: около 8 call-sites в `app/src` и около 12 call-sites в `tools/phpstan/src`.
- Для variadic функций вроде `sprintf`, где дополнительные значения нельзя безопасно назвать как обычные named arguments, оставить именованным первый обычный аргумент и передать остальные значения через unpack-массив.
- Обновить `docs/rules.md`: зафиксировать, что вызовы с двумя и более обычными аргументами должны использовать именованные аргументы.
- После реализации и тестов запустить проверки.

Результат: новый PHPStan rule стабильно ловит многопараметровые вызовы без имён и не ломает допустимые вызовы.

Сценарии тестирования:
- Вызов с одним позиционным аргументом проходит.
- Вызов с двумя именованными аргументами проходит.
- Вызов с двумя позиционными аргументами даёт `project.namedArgumentsRequired`.
- Вызов с одним именованным и одним позиционным обычным аргументом даёт ошибку на позиционный аргумент.
- Method, nullsafe method, static method и constructor call покрыты fixtures.
- Attribute arguments покрыты fixtures.
- Dynamic function call `$fn(...)` покрыт fixture.
- Variadic unpack не получает ошибку только из-за отсутствия имени, а смешанные варианты с обычными аргументами проверяют точные строки `project.namedArgumentsRequired`.
- Текущий код `app/src` и `tools/phpstan/src` не содержит нарушений нового identifier после миграции.

Проверка:
- `composer phpstan-rules:test -- --filter RequireNamedArgumentsRuleTest`
- `composer phpstan-rules:phpstan`
- `composer phpstan`
- `rg -n "RequireNamedArgumentsRule|project\\.namedArgumentsRequired|phpstan.rules.rule" tools/phpstan docs/rules.md`

## Тесты

Стратегия: `after_each_phase`. В фазе сначала реализуется правило и регистрация, затем добавляются fixtures и unit-тесты правила, затем запускаются точечные тесты пакета правил и общий `composer phpstan`.

Основной уровень тестирования: unit-тест PHPStan rule через `PHPStan\Testing\RuleTestCase`. Интеграционная проверка: `composer phpstan`, чтобы подтвердить, что правило подключено к корневому анализу и текущий код проекта либо проходит, либо даёт реальные нарушения, которые исполнитель должен исправить в рамках той же фазы.

## Логирование

Стратегия: `debug_precise`. Для PHPStan rule не добавлять runtime-логи. Вместо этого сделать диагностику точной: стабильный identifier `project.namedArgumentsRequired`, короткое сообщение, строка конкретного нарушающего аргумента или вызова и отдельные fixture-сценарии для каждого важного типа вызова.

## Документация и эксплуатация

- Обновить `docs/rules.md` правилом про именованные аргументы.
- Команда локальной проверки остаётся `composer phpstan`.
- Новые tests и fixtures должны остаться внутри `tools/phpstan`, потому что PHPStan tooling живёт отдельным Composer-пакетом.
- Если `composer phpstan` в локальном sandbox падает на `TcpServer EPERM`, повторить команду с доступной локальной настройкой окружения для PHPStan result cache или зафиксировать инфраструктурный сбой в журнале выполнения; сам план реализации от этого не меняется.

## Изменения после мета-ревью

### После моделей

- **+ Добавлено:** обязательная миграция текущих позиционных многoаргументных вызовов в `app/src` и `tools/phpstan/src`.
- **+ Добавлено:** явная область действия правила: все анализируемые файлы и все типы API, включая vendor, built-ins и attributes.
- **+ Добавлено:** тестовые сценарии для dynamic function call, attributes и variadic unpack-комбинаций с точными строками ошибок.
- **~ Изменено:** attribute arguments больше не условный пункт, а часть обязательной области rule.
- **~ Изменено:** ожидаемый объём short-плана уточнён до 10-13 файлов из-за однотипной миграции существующих call-sites.
- **~ Изменено:** handling variadic API уточнён: дополнительные значения передаются через unpack-массив, когда named arguments для них небезопасны.
- **Отклонено:** сужать правило только до проектных API не нужно, потому что исходное правило сформулировано как общий project quality gate без исключений.
