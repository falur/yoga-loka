# План реализации

## Задача

Дословный запрос пользователя: «Не хватает в модуле постс загрузки медия для постов у нас решено было что это в каждом модуле свой загрузчик».

Добавить в модуль `Posts` собственные HTTP-точки запроса и завершения загрузки медиа. `Posts` задаёт права, допустимые типы, размеры, срок действия ссылок и план обработки, а переиспользуемый модуль `Media` создаёт загрузку, проверяет загруженный объект и обрабатывает файл.

Результат считается готовым, когда авторизованный пользователь может получить одну ссылку либо набор ссылок для составной загрузки, напрямую загрузить проверяемый файл в объектное хранилище, подтвердить загрузку и запросить текущее состояние. Одиночная загрузка подтверждается синхронно, составная собирается через очередь. Изображения, видео и аудио затем обрабатываются существующей очередью, документы сохраняются без преобразований. Изображения записи получают строгую миниатюру и пропорциональную версию для просмотра без сохранения оригинала.

## Контекст

- Архитектура требует, чтобы внешний модуль обращался только к `Media/Application`; общего `POST /media/upload` быть не должно. Правила конкретной загрузки принадлежат модулю-потребителю.
- `Media` уже предоставляет `RequestMediaUpload` и `CompleteMediaUpload`, поддерживает одиночную и составную загрузку, проверяет владельца и размер объекта, сохраняет `MediaUploaded` в transactional outbox и обрабатывает файл через очередь. Domain уже содержит состояния и переходы `completingMultipartUpload`, `multipartCompletionFailedCanRetry` и `multipartCompletionFailedNeedReupload`, но текущий Application-путь собирает части синхронно и эти переходы не использует.
- `Posts` уже принимает до 10 готовых `mediaIds`, проверяет владельца и готовность через `CheckMediaAttachable`, переводит медиа в постоянное состояние и создаёт `post_media`. Новый загрузчик не прикрепляет файл к записи автоматически и не меняет контракт создания записи.
- Текущий `MediaImageProcessorContract` создаёт изображение точного размера с обрезкой. Для пропорциональной версии нужен явный режим уменьшения.
- Текущий постер видео имеет размер обработанного видео. Для отдельной границы `1280×1280` параметры постера должны войти в профиль видео, а результат процессора должен вернуть фактический размер постера отдельно от размера видео.
- `RemoveMediaOriginal` удаляет уже перенесённый оригинал после готовности, но не подключён к надёжному автоматическому запуску. Для нового сценария безопаснее вообще не копировать оригинал изображения в постоянное хранилище: после успешного создания версий зафиксировать `readyOriginalRemoved` и через outbox удалить временный исходник.
- Новые пакеты, таблицы и миграции не нужны. `app/config/queue.php` меняется только для регистрации новых Job и `OutboxQueueSerializer`; новых переменных окружения и typed config нет.
- Текущий `RateLimitMiddleware` считает запросы по IP и маршруту. Подтверждённое ограничение загрузчика должно считаться по авторизованному `authUserId`, поэтому для него нужен отдельный middleware на существующем Redis-кэше.
- Текущая проверка завершения сравнивает только заявленный размер и не проверяет фактический формат. Для публичных файлов нужен потоковый инспектор содержимого до перехода в `uploaded`.
- Обязательные проверки приложения выполняются только через Docker: `make test` и `make phpstan`. Каждый новый маршрут требует интеграционного HTTP-теста; покрытие должно остаться 100-процентным.

## Принятые решения

1. HTTP-контракт принадлежит `Posts`: `POST /api/v1/posts/media/upload-requests` создаёт запрос загрузки, `POST /api/v1/posts/media/upload-requests/<id>/complete` завершает её, `GET /api/v1/posts/media/upload-requests/<id>` показывает состояние. Источник: подтверждение пользователя.
2. Все три маршрута используют существующую цепочку авторизации `AuthTransportWithStorageMiddleware`, `AuthContextAttributeMiddleware`, `RequireAuthenticatedMiddleware`. Загружать, завершать и читать состояние может только текущий пользователь; повторная проверка владельца остаётся в `Media/Application`. Источник: подтверждённый контракт и действующий HTTP-образец `Posts`.
3. Политика `Posts`: изображения до 20 МиБ, аудио до 100 МиБ, документы до 100 МиБ, видео до 800 МиБ; публичная видимость; срок действия ссылок загрузки 40 минут. Размеры считаются в байтах: `20 * 1024 * 1024`, `100 * 1024 * 1024`, `800 * 1024 * 1024`. Источник: подтверждение пользователя.
4. `Posts` использует явный список форматов: JPEG, PNG, WebP, GIF; MP4, MOV, WebM; MP3, M4A/AAC, WAV, OGG/Opus, FLAC; документы из текущего безопасного списка `Media` (PDF, DOC/DOCX, TXT, RTF, ODT/ODS/ODP, XLS/XLSX, PPT/PPTX, EPUB, FB2, DJVU, CSV, Markdown). SVG и форматы Office с макросами запрещены. Один Application-сервис `Media` хранит соответствие расширений, заявленных MIME и допустимых фактических MIME, чтобы `Posts` не копировал правила. Источник: подтверждение пользователя после мета-ревью.
5. Изображение получает `thumbnail` строго `320×320` с обрезкой и `preview` в границах `1280×1280` с сохранением пропорций и без увеличения маленького изображения. После успешного создания обеих версий оригинал не переносится в постоянное хранилище, клиенту не выдаётся и временный исходник удаляется надёжной задачей. Источник: подтверждение пользователя.
6. Видео преобразуется в `normalizedMp4H264` в границах `1280×720` с сохранением пропорций, видеопоток — 1 000 000 бит/с, звук — 128 000 бит/с. Постер извлекается из исходного кадра отдельно и вписывается в `1280×1280` без обрезки и увеличения; для вертикального видео его высота может достигать 1280 пикселей независимо от ограничения видео в 720 пикселей. Источник: подтверждение пользователя.
7. Аудио преобразуется в `normalizedAacM4a`: 128 000 бит/с, 44 100 Гц, 64 точки формы волны. Документ не получает преобразований. Оригиналы видео, аудио и документов сохраняются. Источник: подтверждение пользователя.
8. В `MediaImageConversionSpec` добавляется совместимый режим изменения размера с безопасным значением по умолчанию для старых outbox-сообщений; в `MediaConversionPlan` — политика оригинала со значением `keep` по умолчанию. Новые поля профиля постера видео также имеют совместимые значения по умолчанию: при их отсутствии постер остаётся размера обработанного видео. Это позволяет дочитать события, записанные до выпуска изменения. Источник: `decision_mode: ask_each_time`, выбран минимальный обратно совместимый способ расширить подтверждённое поведение.
9. До создания загрузки `Posts` передаёт имя и MIME в публичный `ResolveMediaUploadFormat` Query модуля `Media`; Query проверяет подтверждённый список и возвращает заявленный `MediaType`. При завершении новый `GetMediaUploadContext` Query возвращает сохранённые `mediaId`, заявленные `type`/`mimeType`, владельца и состояние. Это не считается проверкой фактического содержимого: фактический формат отдельно определяет инспектор после загрузки. Окончательные проверки владельца, состояния, формата и плана остаются в Command модуля `Media`, поэтому гонка между Query и Command не ослабляет инварианты.
10. Удаление исходника изображения выполняется после сохранения готовых версий. `ProcessMediaHandler` при политике удаления не копирует исходник в постоянный bucket, переводит Entity в `readyOriginalRemoved`, сохраняет конверсии и outbox-сообщение очистки одним `EntityManager::run()`. Отдельный Job вызывает идемпотентную Application-команду, которая удаляет конкретный временный объект; ошибка приводит к повтору очереди, но ссылка на исходник не появляется. Источник: требование пользователя и обязательное правило архитектуры о надёжных действиях после commit.
11. Ответ запроса загрузки повторяет действующий `RequestMediaUploadResult` без раскрытия внутренних Entity. Ответ завершения содержит минимальный результат `mediaId`, `status`, `visibility`; создание/чтение самой записи остаётся отдельным сценарием.
12. Ожидаемые ошибки клиента остаются переводимыми 4xx: неверные поля и части — 422, неподдерживаемый/подменённый формат, неверное расширение, превышение размера или 40 миллионов пикселей — 422 для одиночной загрузки; отсутствующее медиа — 404; чужое медиа — 403; неверное состояние — 422. Ошибка, обнаруженная после асинхронной сборки частей, отражается состоянием `multipartCompletionFailedNeedReupload`, а не поздним HTTP 422. Ссылки загрузки и `eTag` в журналы не попадают.
13. Составная загрузка не собирается внутри HTTP-запроса. Завершение проверяет полный непрерывный набор частей `1..partsCount`, сохраняет части, переводит медиа в `completingMultipartUpload` и кладёт событие в outbox; HTTP возвращает `202`. Job собирает объект, проверяет размер и содержимое, затем транзакционно переводит его в `uploaded` и создаёт `MediaUploaded`. Временная ошибка даёт `multipartCompletionFailedCanRetry` и `RetryException`, постоянная — `multipartCompletionFailedNeedReupload`. Источник: подтверждение пользователя после мета-ревью и исходное исследование.
14. Добавляется `GET /api/v1/posts/media/upload-requests/<id>`, который доступен только владельцу и возвращает текущее `MediaStatus`. Клиент ожидает `ready` или `readyOriginalRemoved` перед передачей `mediaId` в создание записи; состояния ошибок сообщают о необходимости повтора либо новой загрузки. Источник: подтверждение пользователя после мета-ревью.
15. Фактический формат проверяется до `uploaded`: изображения — через безопасное чтение метаданных Imagick без полного декодирования, видео/аудио — через ffprobe, документы — через `finfo` и сигнатуры контейнера (для ZIP-форматов проверяется ожидаемая структура). Расширение, заявленный MIME и фактический формат должны относиться к одной разрешённой записи. Изображение не может превышать 40 000 000 пикселей и не загружается целиком в память до этой проверки. Источник: подтверждение пользователя после мета-ревью.
16. Маршрут запроса ссылки ограничивается 15 вызовами за 60 секунд по `authUserId` через Redis. Дополнительно `Media/Application` считает незавершённые непросроченные загрузки владельца; при 10 активных загрузках новый запрос получает 429 через новый переводимый `TooManyRequestsException`. Активны состояния `waitingUpload`, `completingMultipartUpload`, `multipartCompletionFailedCanRetry`, `uploaded` и `processing`; готовые и окончательно ошибочные состояния квоту не занимают. Проверка количества без ручного SQL имеет небольшой допустимый зазор при строго одновременных запросах, как существующий Redis rate limiter. Источник: подтверждение пользователя после мета-ревью.
17. `CheckMediaAttachableHandler` проверяет `isFinalized()`, а не только `isReady()`; `MakeMediaPermanentHandler` принимает `readyOriginalRemoved` и делает его постоянным без изменения статуса. Иначе изображение без оригинала невозможно прикрепить к записи. Источник: подтверждённое поведение и факт из кода, найденный мета-ревью.
18. Создание составной загрузки в S3 остаётся до DB flush из-за необходимости получить `uploadId`; при сбое сохранения `RequestMediaUploadHandler` выполняет best-effort `abortMultipartUpload`, логирует отдельный инфраструктурный сбой компенсации и пробрасывает исходную ошибку. Новая таблица ради строгой компенсации не вводится.

## Целевой алгоритм

1. Авторизация записывает `authUserId` в запрос. Пользовательский rate limiter проверяет 15 запросов за 60 секунд для маршрута получения ссылок.
2. Клиент отправляет имя файла, MIME и размер в `POST /api/v1/posts/media/upload-requests`. `Posts` валидирует форму, через `ResolveMediaUploadFormat` проверяет пару расширение/MIME, получает заявленный тип, проверяет лимит размера и квоту 10 активных загрузок.
3. `Posts` собирает `MediaUploadSpec` с публичной видимостью и сроком 2400 секунд и вызывает `RequestMediaUpload`. `Media` создаёт временную Entity, выбирает одиночный либо составной режим и возвращает подписанные ссылки. Если создание multipart в S3 удалось, а DB flush упал, Handler пытается отменить незарегистрированную составную загрузку.
4. Клиент загружает байты напрямую в объектное хранилище. Для составного режима сохраняет `partNumber` и `ETag` каждой части.
5. Клиент вызывает `POST /api/v1/posts/media/upload-requests/<id>/complete`. `Posts` валидирует UUID и вложенные части, получает сохранённый контекст через `Media/Application`, проверяет владельца и формирует подтверждённые спецификации проверки/обработки. Command `Media` повторяет все окончательные проверки.
6. Для одиночной загрузки оркестратор вне DB-транзакции проверяет наличие, размер и фактическое содержимое объекта. Затем короткий внутренний `FinalizeMediaUpload` Handler с `#[Transactional]` переводит медиа в `uploaded` и сохраняет `MediaUploaded` одним flush; HTTP возвращает `200`.
7. Для составной загрузки до вызова S3 проверяется точный набор частей `1..partsCount`. Короткий транзакционный Handler сохраняет части, ставит `completingMultipartUpload` и outbox-сообщение сборки; HTTP возвращает `202`.
8. Outbox Job составной загрузки вызывает S3 вне DB-транзакции, устойчиво обрабатывает повтор после возможного успешного `CompleteMultipartUpload`, проверяет размер и фактическое содержимое, затем через тот же `FinalizeMediaUpload` переводит медиа в `uploaded` и создаёт `MediaUploaded`. Временная ошибка сохраняет повторяемое состояние и бросает `RetryException`; постоянная фиксирует необходимость новой загрузки.
9. Outbox relay передаёт `ProcessMediaJob` в RabbitMQ. Обработчик создаёт только версии фактического подтверждённого типа.
10. Для изображения обработчик создаёт `thumbnail` и `preview`, не копирует исходник в постоянное хранилище, коротким DB flush фиксирует `readyOriginalRemoved`, конверсии и outbox очистки. Для остальных типов сохраняется перенос оригинала и состояние `ready`.
11. Задача очистки после commit удаляет временный исходник изображения. Повтор после успешного удаления безопасен; временная ошибка преобразуется в `RetryException`.
12. Клиент запрашивает `GET /api/v1/posts/media/upload-requests/<id>` до состояния `ready` или `readyOriginalRemoved`. Затем прикладывает `mediaId` к `CreatePost` или `RepostPost`; обновлённый `CheckMediaAttachable` принимает оба финализированных состояния, а `PostViewAssembler` отдаёт версии изображения без поля оригинала.

## Контракты реализации

### Данные и БД

Схема БД не меняется. Новых таблиц, колонок, индексов, связей, миграций и заполнения старых строк нет.

Используются существующие `media`, таблицы конверсий, `media_multipart_uploads` и `outbox_events`. Состояния составной загрузки и изображения без оригинала уже существуют в `MediaStatus`, поэтому миграция не нужна. В outbox добавляются сериализуемые DTO сборки multipart и очистки временного объекта. Очистка несёт `mediaId`, storage и path: путь нужен, чтобы удалить объект даже если Entity успели удалить до повторной доставки; сообщение создаётся только внутренним Handler-ом и не принимает данные HTTP.

В `MediaRepository` добавляется запрос количества непросроченных загрузок пользователя в активных состояниях. Ручной SQL не используется.

### API и внешние контракты

#### Запрос загрузки

- Метод и путь: `POST /api/v1/posts/media/upload-requests`.
- Авторизация: обязательный access token, текущая цепочка middleware модуля `Posts`.
- Тело:
  - `fileName: string` — обязательно, непустое, не длиннее 255 символов, с расширением;
  - `mimeType: string` — обязательно, непустое, не длиннее 255 символов;
  - `size: int` — обязательно, от 1 до 838 860 800 байт; точный лимит сначала проверяется по заявленному разрешённому типу, после загрузки тип подтверждается инспектором.
- Разрешённые пары:
  - изображения: `.jpg/.jpeg` → `image/jpeg`, `.png` → `image/png`, `.webp` → `image/webp`, `.gif` → `image/gif`;
  - видео: `.mp4` → `video/mp4`, `.mov` → `video/quicktime`, `.webm` → `video/webm`;
  - аудио: `.mp3` → `audio/mpeg`, `.m4a` → `audio/mp4|audio/x-m4a`, `.aac` → `audio/aac`, `.wav` → `audio/wav|audio/x-wav`, `.ogg/.oga` → `audio/ogg`, `.opus` → `audio/opus|audio/ogg`, `.flac` → `audio/flac|audio/x-flac`;
  - документы: расширения и MIME из текущего явного `MediaTypeResolver::DOCUMENT_MIME_TYPES`, включая `.pdf`, `.doc/.docx`, `.txt`, `.rtf`, `.odt/.ods/.odp`, `.xls/.xlsx`, `.ppt/.pptx`, `.epub`, `.fb2`, `.djvu`, `.csv`, `.md/.markdown`; форматы с макросами и SVG отсутствуют в списке.
- Успех: `200 DataResponse<PostMediaUploadRequestResource>`:
  - `mediaId: string`;
  - `uploadMode: 'single'|'multipart'`;
  - `expiresAt: DateTimeImmutable`;
  - `putUrl: string|null` — заполнено только для `single`;
  - `uploadId: string|null` — заполнено только для `multipart`;
  - `parts: list<PostMediaUploadPartResource>|null`, где элемент содержит `partNumber:int`, `url:string`.
- Ограничения: `AuthenticatedRateLimitMiddleware(maxAttempts:15, perSeconds:60)` после middleware авторизации; Application-квота — не больше 10 активных непросроченных загрузок.
- Ошибки: `401`, `422`, `429`; внутренние ошибки хранилища — `500` по действующей обработке ошибок. Неподтверждённый `403` для этого маршрута не объявляется.

#### Завершение загрузки

- Метод и путь: `POST /api/v1/posts/media/upload-requests/<id>/complete`.
- Авторизация: обязательный access token.
- Путь: `id` — UUID медиа.
- Тело:
  - `parts: list<CompletePostMediaUploadPartInput>` — необязательный список, по умолчанию пустой;
  - элемент: `partNumber:int` от 1 до 10 000, `eTag:string` непустой длиной до 512;
  - номера частей уникальны; для `single` список пуст, для `multipart` — непуст и далее сверяется с сохранённым составным запросом в `Media`.
- Успех для `single`: `200 DataResponse<PostMediaUploadStatusResource>`:
  - `mediaId: string`;
  - `status: 'uploaded'`;
  - `visibility: 'public'`.
- Успех для `multipart`: `202 DataResponse<PostMediaUploadStatusResource>` с `mediaId`, `status: 'completingMultipartUpload'` и `visibility: 'public'`.
- Ошибки: `401`, `403`, `404`, `422`; повторное завершение после постановки сборки остаётся 422. Подмена содержимого, найденная позже в multipart Job, отражается через status endpoint.

#### Состояние загрузки

- Метод и путь: `GET /api/v1/posts/media/upload-requests/<id>`.
- Авторизация: обязательный access token; читать состояние может только `uploadedById`.
- Путь: `id` — UUID медиа.
- Успех: `200 DataResponse<PostMediaUploadStatusResource>` с `mediaId`, `visibility` и `status` из закрытого набора `waitingUpload|completingMultipartUpload|multipartCompletionFailedCanRetry|multipartCompletionFailedNeedReupload|uploaded|processing|processingFailed|ready|readyOriginalRemoved`.
- Готовность для прикрепления: `ready` или `readyOriginalRemoved`.
- Повтор автоматически ожидается для `multipartCompletionFailedCanRetry`; новая загрузка нужна для `multipartCompletionFailedNeedReupload` и `processingFailed`.
- Ошибки: `401`, `403`, `404`, `422` для неверного UUID.

#### Внутренний Application-контракт Media

- `ResolveMediaUploadFormatQuery(fileName:string, mimeType:string) -> MediaUploadFormatResult{type, canonicalMimeType}` — единая публичная точка проверки подтверждённого списка расширений и заявленных MIME до создания Entity; не меняет состояние и не открывает Repository.
- `GetMediaUploadContextQuery(mediaId:string) -> MediaUploadContextResult{mediaId, declaredType, declaredMimeType, uploadedById, status, uploadMode}` — чтение без изменения состояния и без транзакции; имена полей честно показывают, что это ещё не проверка содержимого.
- `GetMediaUploadStatusQuery(mediaId:string, userId:string) -> MediaUploadStatusResult{mediaId,status,visibility}` — проверяет владельца и служит внутренним источником GET-маршрута `Posts`.
- `CountActiveMediaUploadsQuery(userId:string, now:DateTimeImmutable) -> int` — считает непросроченные активные загрузки без доступа `Posts` к Repository.
- `MediaContentInspectionSpec` содержит разрешённые пары расширение/фактический MIME и `maxImagePixels: 40_000_000`; `MediaContentInspectorContract` потоково возвращает фактический тип, MIME и размеры изображения при наличии.
- `MediaImageConversionSpec` получает `resizeMode`; старое сообщение без поля восстанавливается как строгая обрезка.
- `MediaVideoConversionSpec` получает `posterMaxWidth:int|null = null` и `posterMaxHeight:int|null = null`. Пара `1280/1280` означает отдельный пропорциональный постер без увеличения; пара `null/null` сохраняет старое поведение и размер обработанного видео; заполнение только одного поля отклоняется как 422.
- `MediaConversionPlan` получает `originalRetention`; старое сообщение без поля сохраняет оригинал.
- `CompleteMediaUpload` становится оркестратором без длинной DB-транзакции. `FinalizeMediaUpload` выполняет только короткий транзакционный переход `uploaded + MediaUploaded`; `RequestMultipartMediaCompletion` — короткий переход `completingMultipartUpload + outbox`.
- Outbox DTO сборки multipart несёт mediaId, план проверки и план обработки. DTO очистки несёт mediaId и внутренний адрес временного объекта. Оба регистрируются в `MediaBootloader`, а Job и `OutboxQueueSerializer` — в `app/config/queue.php`.

Новые и изменённые классы покрываются на 100 процентов. Все три маршрута получают интеграционные тесты успеха, авторизации, ограничения частоты/квоты, валидации, асинхронных состояний и ошибок смежного `Media`. Инфраструктурные инспектор и процессоры получают проверки сигнатур, размеров и режимов; сериализация outbox — проверку старой и новой формы сообщения; multipart и очистка — проверку повтора, временного и постоянного сбоя. Финальный `make qa` измеряет покрытие, а обязательные `make test` и `make phpstan` остаются отдельными воротами.

## Логирование

Стратегия: `debug_precise`.

- `RequestPostMediaUploadHandler`: debug с userId, типом, размером, режимом и mediaId.
- `CompletePostMediaUploadHandler`: debug с userId, mediaId, заявленным и проверенным типом, числом частей, количеством версий и политикой оригинала.
- Multipart Job: debug начала/успеха/повтора с mediaId, числом частей и безопасной категорией ошибки без `eTag`.
- `ProcessMediaHandler`: существующие debug-записи дополнить режимом resize, фактическими размерами версии/постера и решением о сохранении оригинала.
- Команда очистки: debug на успешном и повторном удалении; временная ошибка остаётся инфраструктурной проблемой и обрабатывается существующей очередью.
- Не логировать access token, подписанные ссылки, `uploadId`, `eTag`, содержимое и исходное имя файла. Ожидаемые 4xx не повышать до warning/error.

## Документация и эксплуатация

- Обновить `app/src/Modules/Media/README.md` и документацию `Posts` с подтверждённым потоком и параметрами.
- Обновить `public/openapi/openapi.yml` генератором, а не вручную.
- Новые переменные окружения, сервисы, зависимости и миграции не нужны; обновляется существующий `app/config/queue.php`.
- Для фактической обработки должны работать один `outbox:relay --loop` и текущий RabbitMQ consumer. Новая очистка использует тот же надёжный путь.
- Выпуск должен сохранить чтение старых `MediaUploaded`: новые поля Application DTO имеют значения по умолчанию. Перед удалением этих значений в будущем требуется убедиться, что старых pending/queued outbox-сообщений не осталось.

## Изменения после мета-ревью

### После моделей

- **+ Добавлено:** разрешение `readyOriginalRemoved` в `CheckMediaAttachable` и `MakeMediaPermanent`, без которого изображение нельзя было прикрепить к записи.
- **+ Добавлено:** асинхронная сборка multipart через существующие состояния Domain, outbox и Job, точная проверка частей, 202-ответ и GET состояния.
- **+ Добавлено:** явный список форматов, проверка фактического содержимого/расширения/MIME и предел изображения 40 миллионов пикселей.
- **+ Добавлено:** ограничение 15 запросов в минуту по пользователю, квота 10 активных загрузок и ответ 429.
- **+ Добавлено:** регистрация новых Job и сериализаторов в `app/config/queue.php`, проверка `PostsOpenApiGenerationTest` и финальный `make qa` с измерением покрытия.
- **~ Изменено:** формулировка «фактический тип из Query» заменена на честное разделение заявленного типа и последующей инспекции содержимого.
- **~ Изменено:** файловые операции оставлены вне длинных DB-транзакций; переходы состояния и outbox выполняются отдельными короткими транзакционными Handler-ами.
- **~ Изменено:** пустой `parts` явно превращается в `null` только для single, а multipart требует точный набор `1..partsCount`.
- **~ Изменено:** при сбое сохранения после создания multipart добавлена best-effort отмена S3 upload; исходная ошибка сохраняется.
- **Отклонено:** сократить outbox-сообщение очистки до одного `mediaId`. Storage/path оставлены во внутреннем DTO, чтобы повтор мог удалить объект после конкурентного удаления Entity; HTTP не может сформировать это сообщение.
- **Отклонено:** вводить новую таблицу или ручную блокировку ради абсолютно строгой квоты 10. Проект запрещает ручной SQL, пользователь не подтверждал новую схему; принят прикладной подсчёт с небольшим зазором только при одновременной гонке.
