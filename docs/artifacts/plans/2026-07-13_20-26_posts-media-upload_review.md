## Критическое ревью плана `docs/plans/2026-07-13_20-26_posts-media-upload.md`

Контекст проверки: изучены Media (`Domain/Entity/Media.php`, `MediaStatus`, `CompleteMediaUploadHandler`, `ProcessMediaHandler`, `RequestMediaUploadHandler`, `RemoveMediaOriginalHandler`, `MakeMediaPermanentHandler`, `CheckMediaAttachableHandler`, DTO/Message, `MediaTypeResolver`, `MediaUrlService`, `MediaFileServiceContract`, `ImagickMediaImageProcessor`, `AbstractFfmpegMediaProcessor`, `MediaRepository`, `MediaBootloader`, планировщик), Posts (`PostController`, `CreatePostHandler`, `PostContentComposer`, `PostViewAssembler`, `MediaView`/`MediaResource`), Outbox (`ValinorOutboxMessageSerializer`, `OutboxJobRegistry`, `OutboxQueueSerializer`, `ProcessMediaJob`), `app/config/queue.php`, `app/config/media.php`, `RateLimitMiddleware`, `ApiExceptionInterceptor`, `SpecBuilder`.

### Критичные (реализуемость под вопросом)

- **[скрытый риск] OpenAPI-генератор жёстко проставляет `200` (или `204` для `EmptySuccessResponse`) и не умеет `202`.** `packages/spiral-openapi/src/Spec/SpecBuilder.php:112` возвращает `['200' => …]` для любого непустого wrapper; механизма задать статус на метод нет, а на одну операцию — только один success-ответ. Рантайм-`202` через `->withStatus(HttpStatus::Accepted)` работает (`AbstractJsonResponse` тянет `HasHttpResponseMetadata`), но фаза 3 требует «OpenAPI содержит … 202» и «ответы 200/202» — это недостижимо, тест `PostsOpenApiGenerationTest` на 202 не пройдёт, а `openapi.yml` разойдётся с рантаймом. — Предлагаю: либо разнести single/multipart на два маршрута (200 и 202), либо multipart тоже отдавать `200` со `status` в теле; если 202 обязателен — вынести отдельным шагом расширение пакета `spiral-openapi` (per-method success status) и заложить его в объём/риски, а не считать «документацию из кода».

- **[скрытый риск] `Media::markUploaded()` не имеет guard'а — повторная доставка multipart-Job вернёт `processing`/`ready` обратно в `uploaded`.** `Domain/Entity/Media.php:162-167` безусловно ставит `Uploaded`. Сейчас метод вызывается один раз из `WaitingUpload`, но асинхронная сборка (Job → `FinalizeMediaUpload` из `CompletingMultipartUpload`) при повторе очереди после уже случившегося перехода дальше молча откатит состояние. `startCompletingMultipartUpload()` (строка 142) так же безгардовый. — Предлагаю: добавить доменные guard'ы (finalize — no-op, если статус уже `uploaded` или дальше; completing — только из `WaitingUpload`) и покрыть тестом повторной доставки Job после `processing`/`ready`.

- **[нарушение архитектуры / пропущенный шаг] новый переход в `readyOriginalRemoved` прямо из processing конфликтует с существующим доменным инвариантом.** `markReadyOriginalRemoved()` (`Media.php:281-296`) допустим только из `Ready`, а `persistReady()` в `ProcessMediaHandler` всегда делает `copyObject` + `markReadyMovedTo` (ставит storage/path на target). План хочет для изображений НЕ копировать оригинал и сразу финализировать в `readyOriginalRemoved`. Если ослабить guard `markReadyOriginalRemoved`, ломается инвариант и тесты `RemoveMediaOriginal`. — Предлагаю: завести ОТДЕЛЬНЫЙ доменный метод (например `markReadyWithoutOriginal()`, допустимый из `uploaded/processing/processingFailed`), сохранив `markReadyOriginalRemoved` и `RemoveMediaOriginalHandler` как есть; в `persistReady` развилка «keep → copy+markReadyMovedTo / removeAfterProcessing → без copy + новый метод + outbox очистки»; явно описать, что `Media.path/storage` остаётся указывать на staging.

- **[скрытый риск] инспекция фактического формата документов через `finfo` не различает большинство разрешённых типов.** DOCX/XLSX/PPTX/EPUB/ODT/ODS/ODP — это ZIP → `finfo` вернёт `application/zip`; DOC/XLS/PPT (OLE) → `application/x-ole-storage`/`CDFV2`; TXT/CSV/MD → все `text/plain`; RTF → `text/rtf`. Требование decision 15 «расширение + заявленный MIME + фактический формат относятся к одной разрешённой записи» приведёт к массовым ложным 422 для валидных документов. — Предлагаю: заменить строгий triple-match для документов на посемейственный (image/video/audio — точная проверка ffprobe/imagick; ZIP-контейнеры — чтение `[Content_Types].xml`/`mimetype` внутри архива; text/* — трактовать `text/plain` как валидное для txt/csv/md; OLE — семейство ms-office), описать по каждому контейнеру отдельный критерий и тест; иначе документная ветка нереализуема как заявлено.

### Существенные

- **[нарушение архитектуры] двойной источник истины по типу/формату.** План вводит каталог `ResolveMediaUploadFormat` (расширение+MIME), но `RequestMediaUploadHandler` (`RequestMediaUpload/RequestMediaUploadHandler.php:36`) продолжит резолвить тип через `MediaTypeResolver` по префиксам `image/*`,`video/*`,`audio/*` (`Service/MediaTypeResolver.php:52-64`), а `assertUploadAllowed` — по `spec->allowedMimeTypes`. Три разных проверки MIME, тип Entity берётся из префиксов, а не из каталога — риск расхождения (например, будущий `image/*`, не входящий в каталог, всё равно создаст `Image`). — Предлагаю: `RequestMediaUpload`/`MediaTypeResolver` должны потреблять тот же единый каталог, что и `ResolveMediaUploadFormat`; либо явно зафиксировать, что тип Entity берётся из результата каталога (передавать `MediaType` в spec), а префиксный резолвер убрать из нового пути.

- **[риск смежного кода] крупный рефактор `CompleteMediaUpload` — единственного публичного входа — ломает поведение и существующие тесты.** Сейчас это один `#[Transactional]`-handler со СИНХРОННОЙ сборкой multipart внутри транзакции (`CompleteMediaUpload/CompleteMediaUploadHandler.php:45-100`), требует `status === WaitingUpload`. Разбиение на оркестратор + `FinalizeMediaUpload` + `RequestMultipartMediaCompletion` меняет контракт и заденет `tests/Feature/Modules/Media/Application/CompleteMediaUploadHandlerTest.php` и сквозной `tests/Feature/Modules/Media/Flow/MediaProcessingFlowTest.php`. План упоминает разбиение, но не отмечает это как ломающее изменение с миграцией тестов. — Предлагаю: явно перечислить переработку этих тестов и не-регресс единственного sync-пути (single) как отдельный критерий фазы 1.

- **[зависимость / пропущенный шаг] контент-инспектор: не указан способ потокового чтения и жёсткие внешние зависимости.** В `MediaFileServiceContract` уже есть `downloadToFile()`/`uploadFromFile()` (строки 94, 100), но план не называет их источником для инспекции и не описывает удаление temp-файла (в `finally`). Для пиксель-проверки план требует именно Imagick, хотя драйвер может быть `gd` (`media.php:30`), а размеры дешевле и кросс-драйверно читает `getimagesize()`. Инспектор вводит жёсткую зависимость от ext-imagick и ffprobe в тест-окружении. — Предлагаю: явно опереть инспекцию на `downloadToFile` + `finally`-удаление; для размеров использовать `getimagesize()` (или задать поведение при `gd`); зафиксировать наличие ext-imagick/ffprobe/finfo как предусловие интеграционных тестов.

- **[скрытый риск / зависимость] backward-compat outbox держится только на том, что Valinor подставляет дефолты конструктора для отсутствующих ключей.** `ValinorOutboxMessageSerializer` (`allowPermissiveTypes()` + `allowScalarValueCasting()`) читает СТАРЫЕ payload'ы `MediaUploaded`/`MediaConversionPlan` без новых полей (`resizeMode`, `originalRetention`, `posterMaxWidth/Height`). Совместимость постулируется, но не проверяется. — Предлагаю: добавить тест десериализации зафиксированного СТАРОГО JSON-payload (без новых полей) для `MediaUploaded` и плана, чтобы дефолты (crop/keep/null) реально применялись; это единственная защита от «мёртвых» pending-сообщений.

- **[пропущенный шаг] двухзвенная outbox-цепочка multipart тянет два новых сериализуемых DTO и две регистрации, которые план перечисляет вскользь.** Цепочка: assembly-outbox → assembly Job → `FinalizeMediaUpload` (кладёт `MediaUploaded`) → `ProcessMediaJob`. Значит assembly-DTO должен нести сериализуемые `MediaContentInspectionSpec` + `MediaConversionPlan`; нужны два message→Job в `MediaBootloader` (сейчас там один — `MediaUploaded`, `Bootloader/MediaBootloader.php:38-44`) и по строке в `handlers`/`serializers` `app/config/queue.php:133-158` на каждый новый Job. — Предлагаю: явно перечислить оба новых message-класса (сборка, очистка), их DTO с примитив-дружественными полями, регистрацию в bootloader и queue.php, и тест реестра/сериализации на каждый.

### Умеренные

- **[риск смежного кода] `MakeMediaPermanentHandler` сейчас допускает `Uploaded` и `Ready` (`MakeMediaPermanent/MakeMediaPermanentHandler.php:36`), но не `readyOriginalRemoved`.** План (decision 17) требует добавить `readyOriginalRemoved`, но не отмечает, что `Uploaded` остаётся допустимым — то есть `attachMedia` через `CheckMediaAttachable(isFinalized)` гейтит по finalized, а `MakeMediaPermanent` шире (пропустит `uploaded`). Обновится и его тест. — Предлагаю: явно согласовать набор допустимых статусов в обоих (attach только из `isFinalized`), обновить тест `MakeMediaPermanent`, зафиксировать, что `makePermanent()` не меняет статус (для `readyOriginalRemoved` это ок).

- **[скрытый риск] порог multipart по умолчанию 16 МиБ (`media.php:24`), а лимит изображения — 20 МиБ.** Изображения 16–20 МиБ пойдут через multipart (async), значит «одиночная загрузка подтверждается синхронно, изображение получает thumbnail/preview» неверно для части изображений; Posts режим не контролирует (решает `MediaUploadPlanner`). — Предлагаю: либо согласовать лимит изображения с порогом (≤ порога → single), либо явно принять и задокументировать, что часть изображений проходит multipart, и тесты покрывают оба режима для image.

- **[риск смежного кода] `AuthenticatedRateLimitMiddleware` дублирует fixed-window логику `RateLimitMiddleware`.** Существующий middleware (`Shared/Infrastructure/Framework/Middleware/RateLimitMiddleware.php`) отличается только ключом (IP+path). Копия ради ключа по `authUserId` — дублирование инфраструктурного кода Redis-окна. — Предлагаю: вынести стратегию ключа (IP-based / user-based) как зависимость одного middleware, а не копировать весь класс; проверить, что новый middleware стоит строго после `AuthContextAttributeMiddleware`/`RequireAuthenticatedMiddleware` (атрибут `authUserId`).

- **[недостающие тесты] при требовании 100% покрытия не выделены сценарии, которые дают самые тонкие ветки.** Отсутствуют явно: повтор multipart-Job после `processing`/`ready` (unguarded-переходы), gd-ветка инспектора и `getimagesize`/imagick-развилка, конкурентный double-complete (два assembly-outbox → двойная обработка, идемпотентность по детерминированным путям), ffmpeg-постер fit без upscale на граничных размерах (горизонт/вертикаль/квадрат), десериализация старого payload. — Предлагаю: включить эти сценарии в план тестов фаз 1–2.

- **[без критериев готовности] шаги документации не имеют проверяемого критерия.** «Обновить `Media/README.md`», «Обновить документацию Posts / создать README», «Обновить `docs/arch.md`» — без measurable-условия (в отличие от остальных шагов с тест-сценариями). — Предлагаю: задать критерий вида «в README перечислены 3 маршрута + режимы resize + политика оригинала + порядок commit/outbox; в arch.md добавлены новые публичные сценарии Media» и упомянуть, что это не входит в `make qa`-гейт.

- **[нарушение архитектуры — мелкое] `ResolveMediaUploadFormat` как «Query» без обращения к Repository.** По CQRS Query читает данные (Repository/View), а тут — чистая проверка статического каталога без БД. — Предлагаю: оформить как stateless Application-сервис (`Application/Service`, рядом с `MediaTypeResolver`), а не Query, либо явно обосновать в плане это исключение.

### Замечания, снижающие риск (проверено — не дефекты плана)

- Read-модель ленты уже корректно отдаёт `original = null` + конверсии для `readyOriginalRemoved`: `MediaUrlService::getUrls` (`original: isReady() ? … : null`, строка 66), `PostViewAssembler::mediaItem` (мягкая деградация), `MediaView`/`MediaResource` (nullable `original`). Значит фаза 3 в части «изображение без оригинала» в основном УЖЕ поддержана — риск ниже, чем заявляет план; формулировка «лента сейчас отдаёт оригинал» неточна.
- 429 через доменное исключение реализуемо: `ApiExceptionInterceptor` принимает ЛЮБОЙ код 400–499, для которого есть case в `HttpStatus` (`supportedClientStatus`), а `HttpStatus::TooManyRequests` уже существует и используется в `RateLimitMiddleware`. Домен перевода `app.posts.*` → `posts.php` (файлы локали существуют). То есть `TooManyRequestsException` (429) — не блокер.
- `downloadToFile`/`uploadFromFile` и `runFfmpeg` (постер) уже есть — потоковая инспекция и извлечение постера технически возможны без новых методов файлового сервиса.
