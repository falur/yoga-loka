# План реализации

## Задача

Асинхронный обмен событиями переезжает с собственного модуля `app/src/Modules/Outbox` на пакет
`gian-tiaga/spiral-outbox` версии `v0.2.1`. Модуль удаляется целиком, его контракты, хранилище,
relay, сериализатор и очередной interceptor заменяются частями пакета. Модулей в проекте
становится восемь.

Готово, когда: каталога `app/src/Modules/Outbox` нет; `Auth`, `Media`, `Notifications` и `Posts`
пишут и читают события через контракты пакета; шесть маршрутов разведены по трём очередям с
собственной политикой повторов; постоянный `outbox:relay --loop` и `outbox:status` работают на
таблицах пакета; `make qa` зелёный при сохранённом покрытии 100%.

В задачу не входит: изменение бизнес-поведения, состава событий и их полей; изменение публичного
HTTP API; правка самого пакета (по `docs/rules.md` он правится в своём репозитории); выделение
отдельного процесса worker под тяжёлую обработку медиа.

## Целевой алгоритм

Событие пишется в бизнес-транзакции, доставляется отдельно от неё и повторяется самим outbox.

```text
Command handler (#[Transactional])
  меняет агрегаты своего модуля
  кладёт интеграционное событие в хранилище пакета    -> строка outbox_events, routed_at = null
  commit

outbox:relay, проход 1
  берёт события с routed_at = null
  по карте маршрутов создаёт строку доставки на каждый маршрут события
  ставит событию routed_at                            -> одним commit

outbox:relay, проход 2
  берёт готовые доставки в статусе pending
  ставит dispatched, dispatched_at, delivery_timeout_at, commit
  после commit отправляет Job в очередь своего маршрута

Worker очереди
  interceptor пакета сверяет доставку и текущую отправку, грузит событие
  Job модуля-потребителя вызывает свой Command или Query через шину
  успех -> completed; повторяемая ошибка -> pending и новое available_at; иначе -> failed
```

Повторами владеет только outbox: число повторов равно длине списка пауз маршрута, физического
возврата Job в RabbitMQ нет. Событие неизменяемо и общего статуса не имеет; успех одной доставки
не закрывает соседние доставки того же события. Доставка идемпотентна на стороне потребителя —
семантика остаётся at-least-once, как и сейчас в `docs/arch.md`.

Диагностический маршрут модуля (`OutboxDebugLogRequestedEvent` → `OutboxDebugLogJob`) исчезает
вместе с модулем: состояние обмена показывает команда `outbox:status`.

## Контракты реализации

### Данные и БД

Схему создают две миграции пакета из его каталога `migrations`, который bootloader пакета
дописывает в `migration.vendorDirectories`. Миграция модуля
`20260525.153700_0_create_outbox_events_table.php` удаляется вместе с модулем; своей миграции
перехода проект не пишет.

```text
outbox_events      id, event_type, payload, created_at, routed_at
outbox_deliveries  id, event_id, job_class, queue_name, снимок пауз и таймаута,
                   статус, попытки, dispatch_id, времена переходов, причина отказа
```

Имена таблиц остаются значениями пакета по умолчанию — `outbox_events` и `outbox_deliveries`.
Существующая таблица `outbox_events` модуля не переносится: база в dev пересоздаётся с нуля
(`AGENTS.md`, «Стадия проекта»). Откат изменения — откат ветки и повторное `make reset-test` плюс
пересоздание dev-базы.

Секция конфигурации `outbox` объявляется пакетом; приложение задаёт в ней `batchSize` и карту
`routes`. Типизированный Config на неё проект не заводит: секцией владеет пакет, и её разбирает
его собственная фабрика.

### API и внешние контракты

Публичный HTTP API и формы ответов не меняются.

Соответствие контрактов — старый тип модуля заменяется типом пакета:

```text
Outbox/Public/Contract/IntegrationEvent              -> GianTiaga\SpiralOutbox\IntegrationEventContract
Outbox/Public/Contract/IntegrationEventStoreContract -> GianTiaga\SpiralOutbox\OutboxEventStoreContract
Outbox/Public/Contract/IntegrationEventLoaderContract-> GianTiaga\SpiralOutbox\OutboxMessageLoaderContract
Outbox/Public/Contract/IntegrationEventRoutingContract -> карта routes секции config outbox
Outbox/Public/Dto/OutboxEnvelopeDto                  -> идентификатор доставки в полезной нагрузке Job
```

Job-потребитель перестаёт принимать конверт события и принимает идентификатор доставки, по
которому загрузчик пакета отдаёт событие ожидаемого класса. Событие модуля вместо маркера модуля
реализует `IntegrationEventContract`; поля событий не меняются.

Маршруты объявляются модулем-потребителем в его bootloader патчем секции `outbox`, ключ — класс
события, значение — непустой список маршрутов. Политика на маршрут:

```text
событие                          очередь        паузы повторов, с   таймаут доставки, с
LoginCodeRequestedEvent          mail           30, 120             300
MediaUploadedEvent               media          60, 300, 900        7200
MediaDeletedEvent                media          60, 300             600
NotificationRequestedEvent       notifications  60, 300             600
NotificationPushRequestedEvent   notifications  60, 300             600
NotificationRealtimeRequestedEvent notifications —                  120
```

Пустой список пауз у realtime-уведомления означает единственную попытку без повтора.

Транспорт: вместо одного pipeline `rabbitmq` объявляются три — `mail`, `media`, `notifications`.
Каждому соответствует своя очередь и exchange RabbitMQ с общим префиксом из окружения. Все три
читает существующий пул задач RoadRunner: отдельных пулов у плагина `jobs` нет, разделение даёт
независимую очередь и приоритет, а не отдельный процесс. `requeue_on_fail` остаётся `false`.

Из `app/config/queue.php` уходят `OutboxQueueStatusInterceptor` (вместе с модулем) и
`RetryPolicyInterceptor` (повторами владеет outbox). Остаётся `ErrorHandlerInterceptor` и
добавленный bootloader пакета interceptor доставки.

## Фазы выполнения

### 1. Объявить целевую форму в документах

Цель: закрыть расхождение, при котором `docs/arch.md` называет Outbox одним из девяти модулей, до
того как код перестанет ему соответствовать.

Что сделать: в `docs/arch.md` сократить состав модулей до восьми и убрать `Outbox` из перечня
названных инфраструктурных границ; в разделах «Взаимодействие модулей» и «Runtime» описать обмен
через пакет — событие пишется в транзакции, relay создаёт доставки и отправляет их в очередь
назначения, повторами владеет outbox; в «Направления зависимостей» добавить контракты
`GianTiaga\SpiralOutbox` к нейтральным контрактам собственных пакетов, доступным `Application` и
`Public`, а его runtime — к `Infrastructure/Spiral`; в «Осознанные отступления» ничего не
добавлять. Карточки `docs/references/integration-event.md` и `docs/references/job-consumer.md`
привести к новой форме: событие реализует контракт пакета, Job принимает идентификатор доставки и
загружает событие ожидаемого класса, маршрут объявляется в bootloader модуля-потребителя.

Результат: документы описывают целевую форму обмена, а код им пока не соответствует — это
единственная фаза, после которой расхождение допустимо и ожидаемо.

Проверка:
- в `docs/arch.md` нет модуля `Outbox` в составе модулей и в списке технических границ;
- обе карточки показывают форму с идентификатором доставки и маршрутом в bootloader.

### 2. Развести очереди по назначению

Цель: дать маршрутам три независимые очереди до того, как на них начнут ссылаться маршруты.

Что сделать: завести перечисление имён очередей приложения в общей части Spiral-инфраструктуры —
имя очереди нужно и конфигурации транспорта, и маршрутам разных модулей, владельца среди модулей у
него нет. Объявить в `app/config/queue.php` три pipeline по этим именам вместо одного `rabbitmq`,
каждый со своим коннектором AMQP, и те же три pipeline с их очередями и exchange в
`docker/rr/http-jobs.yaml` со списком `consume`. Имена очередей, exchange и routing key собрать из
общего префикса окружения, заменив им переменные одной очереди в `.env.sample` и `.env`. Старый
pipeline `rabbitmq` убрать: на него никто не ссылается по имени, отправка модуля идёт в очередь по
умолчанию.

Результат: приложение поднимается, RoadRunner читает три очереди, существующий обмен через модуль
продолжает работать без изменений в его коде.

Проверка:
- `make up` и `make test` зелёные;
- панель RabbitMQ показывает три очереди, каждая с потребителем;
- `make test-feature` проходит на существующих сценариях обмена.

### 3. Перевести код на пакет и удалить модуль

Цель: заменить собственную реализацию обмена пакетом одним неделимым изменением — контракты
хранения и загрузки меняются у всех потребителей сразу.

Что сделать: подключить `gian-tiaga/spiral-outbox: ^0.2.1` и зарегистрировать его bootloader в
Kernel после bootloader миграций; задать в `phpstan.neon` параметр `integrationEventInterface`
контрактом события пакета, чтобы правило проверяло форму полей событий. Шесть интеграционных
событий четырёх модулей перевести на контракт пакета; пять Command handler — на хранилище пакета;
шесть Job — на идентификатор доставки и загрузчик пакета, заменив собственный `RetryException`
повторяемой ошибкой пакета там, где повтор нужен, и обычным исключением там, где отказ
окончателен. Маршруты объявить в bootloader модулей-потребителей патчем секции `outbox` по
таблице контрактов; в ту же секцию задать размер пачки relay. Удалить каталог модуля целиком
вместе с его миграцией, конфигурацией, тестами и диагностическим маршрутом; убрать из
`app/config/queue.php` interceptor модуля и политику повторов Spiral; убрать переменные `OUTBOX_*`
из `.env.sample` и `.env`. В `deptrac.yaml` удалить слои и правила модуля, добавить контракты
пакета в нейтральный слой, доступный `Application` и `Public`, а его runtime — в слой, доступный
`Infrastructure/Spiral` и Kernel. Обновить общие тестовые помощники, чистящие и записывающие
outbox, под две таблицы и контракты пакета, а в `docker/README.md` — команды relay и новую
`outbox:status`.

Результат: обмен работает на пакете, модуля в проекте нет, границы и статический анализ зелёные.

Проверка:
- `make qa` зелёный, покрытие 100%;
- `grep -rF "Modules\Outbox" app/src tests app/config` ничего не находит;
- `php app.php outbox:relay` и `php app.php outbox:status` отрабатывают на пустых таблицах;
- сквозной сценарий: запрос кода входа кладёт событие, relay создаёт доставку и отправляет Job,
  доставка приходит в `completed`.

## Тесты

Тесты пишутся после реализации каждой фазы и живут внутри модуля-владельца проверяемого кода;
общие помощники — в корневом наборе. Покрытие приложения остаётся 100%.

Фаза 2 закрывается существующими интеграционными и feature-тестами обмена и проверкой формы
конфигурации очередей: три объявленных pipeline с ожидаемыми именами очередей.

Фаза 3 по каждому потребителю: положительный сценарий — Command handler в транзакции кладёт
событие, relay создаёт доставку на каждый маршрут события, Job выполняет сценарий и доставка
становится `completed`; отрицательный — отказ сценария не создаёт события и не трогает соседние
доставки; граничный — повторная доставка того же события не ломает состояние, а при пустом списке
пауз первая же ошибка даёт `failed`. Отдельно проверяется, что событие каждого модуля проходит
сериализацию и восстановление контрактом пакета без потери полей — это заменяет существующий
unit-тест сериализации события медиа. Маршруты проверяются интеграционно: объявленная в
bootloader карта содержит ожидаемую очередь, паузы и таймаут для каждого из шести событий.

Тесты приложения запускаются только в Docker, как требует `docs/rules.md`.

## Логирование

Стратегия точная отладочная: каждая запись обмена связывается идентификаторами `outboxEventId`,
`outboxDeliveryId` и `outboxDispatchId`, к ним добавляются класс события, класс Job, очередь,
статус и номер попытки. Записи relay, interceptor и присмотра за worker даёт сам пакет — проект их
не дублирует.

Собственные записи остаются только у Job-потребителей, там, где сбой внешней границы нужно
объяснить: уровень WARNING на повторяемый отказ, ERROR на окончательный. Из контекста записей
убираются адрес электронной почты и другие персональные данные — остаются идентификаторы и класс
ошибки, как требует `docs/rules.md`. Полезная нагрузка события, коды входа и тексты внешних
ответов в журнал не попадают.

## Документация и эксплуатация

`docs/arch.md` и две карточки-эталона обновляются в фазе 1, `docker/README.md` — в фазе 3 вместе с
командами `outbox:relay` и `outbox:status`. В `.env.sample` и `.env` переменные `OUTBOX_*`
удаляются, переменные одной очереди RabbitMQ заменяются общим префиксом имён.

Порядок развёртывания: миграции, затем HTTP и worker, затем постоянный `outbox:relay --loop`;
процесс relay по-прежнему должен быть один. Команда `outbox:status` даёт быстрый ответ о
состоянии обмена: немаршрутизированные события, доставки по статусам и возраст старейшей
незакрытой доставки.

## Принятые решения

- Модули работают с контрактами пакета напрямую, модуль-обёртка не создаётся, каталог
  `app/src/Modules/Outbox` удаляется целиком — ответ пользователя. Нейтральные контракты
  собственных Composer-пакетов в `Application` и `Public` уже разрешены `docs/arch.md`, так же
  подключён `gian-tiaga/spiral-cqrs`.
- Маршруты разводятся по трём очередям назначения `mail`, `media`, `notifications` — ответ
  пользователя. Отдельных пулов worker у плагина `jobs` RoadRunner нет, поэтому разделение даёт
  независимые очереди и приоритеты в общем пуле; отдельный процесс под медиа остаётся за рамками.
- Политика повторов и таймаут задаются на каждый маршрут по таблице в контрактах — ответ
  пользователя.
- База пересоздаётся на миграциях пакета, миграция перехода не пишется — ответ пользователя,
  опирается на раздел «Стадия проекта» в `AGENTS.md`.
- Имена очередей живут в перечислении общей Spiral-инфраструктуры: значение нужно конфигурации
  транспорта и маршрутам разных модулей, владельца среди модулей у него нет.
- Диагностический маршрут модуля удаляется вместе с ним: его роль закрывает команда
  `outbox:status` пакета.
- Версия пакета `^0.2.1` — последняя опубликованная на Packagist на 2026-09-23.
