## Детали правок

### 1 — Заголовок аутентификации Centrifugo v6
Заголовок `X-API-Key` заменён на `Authorization: apikey <key>` (`\sprintf('apikey %s', $apiKey)`)
в `CentrifugoClient::publish()`. Контракт подтверждён официальной докой Centrifugo через context7
(`/centrifugal/centrifugo`): POST `/api/publish` требует `Authorization: apikey <key>` либо
query-параметр `api_key`. Заодно поправлен вводящий в заблуждение комментарий в
`app/config/centrifugo.php`. Тест `CentrifugoClientTest` обновлён: проверка заголовка
`Authorization` = `apikey dev-key`.

### 2 — Разбор тела ответа Centrifugo (200 + error)
После 2xx добавлен `ensureNoApiError()`: тело парсится, и при наличии ключа `error` бросается
`CentrifugoPublishException::apiError(code, message)`. Классификация временного характера: внутренний код
Centrifugo `100` — временный (повтор), прочие коды (неизвестный канал/namespace, валидация,
лимиты) — терминальные. Пустое 2xx-тело считается успехом (guard `\trim($body) === ''`), чтобы не
ломать реальные ответы без тела и существующие фикстуры. Операционная часть: в
`docker/centrifugo/config.json` объявлен namespace `personal` (`allow_subscribe_for_client: true`),
иначе персональные публикации `personal:#user_{id}` отклонялись бы как «200 + error». Схема
namespace подтверждена через context7. Добавлены unit-кейсы: «200 + error код 102 → терминально»,
«200 + error код 100 → временный сбой», «200 + result → без исключения».

### 3 — Базовый класс исключений
`CentrifugoPublishException` и `FcmPushFailedException` переведены с `\RuntimeException` на
`\DomainException` (паттерн всех прочих модульных исключений проекта, `rules.md:45`). Сигнатуры
фабрик, конструктора и `isTransient()` не менялись; классификация Job (`instanceof` +
`isTransient()` → `RetryException`) сохранена.

### 4 — PSR-18 клиент без захвата глобального интерфейса (optional, принято)
Убран биндинг `ClientInterface::class => Client::class` из `SINGLETONS`. Вместо этого добавлена
фабрика `centrifugoClient(CentrifugoConfig): CentrifugoClient`, которая собирает выделенный
`new Client()` под Centrifugo — по образцу уже существующей фабрики `fcmMessaging()`. Модуль
больше не занимает общий PSR-18 интерфейс и не навязывает свою конфигурацию Guzzle другим модулям.
Поведение `CentrifugoClient` не изменилось. Добавлен unit-кейс на фабрику для сохранения 100%
покрытия.

### 5 — `equals()`/`\sort()` (optional, применено в минимальной форме)
Ревью само отметило, что это не баг (локальные копии, мутации нет) — только читаемость.
Предложенный вариант «нормализовать порядок в `of()`» отклонён как избыточный: он изменил бы порядок
в `jsonSerialize()` (сериализуемое/персистентное представление) ради косметики внутри одного
метода — лишний риск для сериализации. Вместо этого добавлен поясняющий комментарий к `equals()`,
который прямо закрывает заявленную претензию «непонятно, зачем сортировка», без изменения поведения
и порядка сериализации.

## Решения по optional

- **Принято:** 4 — низкий риск, явное улучшение (убирает скрытую связанность глобального
  интерфейса), следует уже принятому в этом же файле паттерну фабрики, поведение неизменно,
  покрыто тестом.
- **Принято частично:** 5 — претензия чисто про читаемость и не-баг по признанию ревью; применён
  дешёвый безопасный вариант (комментарий). Полный рефактор (нормализация в `of()`) отклонён:
  он меняет порядок сериализации (поведение-смежное) ради косметики — scope/риск не оправдан.
- **Отклонено:** 6 — предложенный `has(NotificationTypeCode): bool` требует строить VO из
  недоверенного пользовательского ввода через `NotificationTypeCode::fromString()`, который на
  невалидный формат бросает `InvalidDomainValueException` (500). Текущий линейный скан реестра на
  любой неизвестный/некорректный пользовательский `type` отдаёт `ValidationException` (422) — это
  корректный клиентский контракт. Замена превратила бы 422 в 500 для некорректных строк — регрессия
  HTTP-контракта. Скан хоть и линеен, но семантически верен и намеренно избегает 500 на вводе.
  Чисто-читаемостная польза не перевешивает риск регрессии. Чтобы следующие ревьюеры не повторяли
  пункт без новых аргументов: предложение валидно только если найти способ проверить наличие вида,
  не конструируя VO из untrusted-строки (например, отдельный реестр-предикат по «сырому» коду без
  format-валидации) — но это уже расширение контракта реестра.
