# Фиксы по ревью: Модуль Auth — беспарольный вход по email-коду (после правок)

Режим `apply-optional`. Обязательных замечаний в ревью нет — все три пункта помечены
«на усмотрение автора». По каждому решение принято самостоятельно.

## Применённые правки
| # | Замечание | Файлы | Тесты | Статус |
|---|-----------|-------|-------|--------|
| 1 | Рассинхрон контракта/PHPDoc рендерера `spiral-api-errors` (`firstMessage` принимает `string\|list<string>`, интерфейс/PHPDoc — `array<string,string>`) | — | — | ✗ отклонено (на усмотрение; причина ниже) |
| 2 | Фильтр-валидация `RegisterFilter` строже нормализации VO `UserName`/`UserNickname` на краевом вводе | `app/src/Modules/Auth/Presentation/Http/Filter/RegisterFilter.php` (комментарии-предупреждения у полей `name`/`nickname`) | существующие HTTP-тесты 422 (поведение не менялось) | ✓ применено частично (только документирование намеренной строгости, поведение не трогал) |
| 3 | Генератор OpenAPI (`SchemaBuilder::schemaForProperty`) теряет `nullable` для nullable-списочных свойств | `packages/spiral-openapi/src/Schema/SchemaBuilder.php`; фикстура `packages/spiral-openapi/tests/Fixtures/Endpoint/Api/V1/Resource/UserResource.php` | `packages/spiral-openapi/tests/Generator/OpenApiGeneratorTest.php` (нов. проверки `tags`: `type=array`, `nullable=true`, не в `required`) | ✓ применено |

## Решения по optional

### Принято
- **Пункт 3 (`spiral-openapi`, nullable-списки).** Дешёвая, локальная и низкорисковая правка в
  пакете, который правился в этом же диффе именно ради корректного `nullable`. Симметричный
  пробел к уже внесённой правке union `T|null`: ранний `return` в ветке `listItemType` не
  применял `nullable`, хотя `PropertyMetadata->nullable` для списка вычисляется корректно.
  Собрал array-схему в переменную и применяю `nullable` единым местом перед `return` — теперь
  ветка списков ведёт себя так же, как скаляры/ссылки. Добавил в фикстуру `UserResource`
  свойство `/** @var list<string>|null */ public array|null $tags` и проверки в
  `OpenApiGeneratorTest`: `nullable: true`, `type: array`, отсутствие в `required`. Закрывает
  латентный класс расхождения контракта молча.

### Принято частично (только документирование)
- **Пункт 2 (`RegisterFilter` vs VO).** Применил минимальный вариант, явно предложенный в
  ревью: комментарий-предупреждение у полей `name`/`nickname`, фиксирующий, что фильтр
  намеренно строже VO на ненормализованном вводе (даёт понятный 422, а не 500 из домена).
  Выравнивание нормализации (trim/Length по нормализованному значению) в фильтре **отклонено**:
  это расширяет scope HTTP-границы, дублирует доменную нормализацию в Presentation-слое и
  создаёт риск регрессии валидации ради краевого padded-входа, который и так корректно
  отклоняется 422. Поведение и тесты не менялись — дополнительные кейсы с padded-вводом не
  нужны, т.к. текущая (намеренно строгая) валидация уже покрыта.

### Отклонено
- **Пункт 1 (`spiral-api-errors`, контракт/PHPDoc рендерера).** Корень — узкий vendor-PHPDoc
  `Spiral\Filters\ErrorsRendererInterface::render(array<string,string>)`, который пакет не
  контролирует; собственный `render()` обязан совпадать с сигнатурой реализуемого интерфейса.
  Разбор списка сообщений в `firstMessage()` — это граница системы (выход Symfony-валидатора),
  где `rules.md` «Не заменять типизацию ручными проверками» прямо допускает сужение на границе;
  ветка уже задокументирована комментарием и помечена `@param string|list<string>`, рантайм
  корректен и покрыт двумя пакетными тестами (список и пустой список). Расширять value-тип в
  собственной сигнатуре до `string|list<string>` нельзя, не разойдясь с реализуемым
  vendor-интерфейсом; нормализовать список в строку до рендерера — лишний код на стороне
  приложения ради формальной чистоты PHPDoc без снижения реального риска. rules-check в самом
  ревью уже отклонил поднятие этого пункта до must-fix по той же причине (vendor-PHPDoc).
  Реального риска для приложения нет; повторно поднимать без новых аргументов не нужно.
