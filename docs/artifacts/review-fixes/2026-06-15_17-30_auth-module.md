# Правки по ревью: модуль Auth

Применены все обязательные замечания (1, 4, 6, 7, 8) и полезные optional-пункты
(план №1/№2/№3, замечания 2, 3, 5). Один optional-пункт отклонён с причиной (см. ниже).
Перед правками прочитаны `docs/rules.md`, `docs/arch.md`, `docs/code-examples.md`,
`AGENTS.md`.

## Обязательные (исправлены полностью)

### Замечание 1 — мёртвый VO `LoginCodeValue`
Удалён класс `app/src/Modules/Auth/Domain/ValueObject/LoginCodeValue.php` и его unit-тесты
(`testLoginCodeValueAcceptsSixDigits`, `testLoginCodeValueRejectsInvalidFormat` + провайдер)
из `tests/Unit/Modules/Auth/Domain/ValueObject/AuthValueObjectTest.php`. Формат «6 цифр»
закрыт `VerifyCodeFilter` (`#[Assert\Regex]`), хэшер работает со строкой — потребителя у VO
не было. Покрытие осталось 100%.

### Замечание 6 — невалидный ввод давал 500 вместо 422
Добавлены формат-констрейнты в фильтры, согласованные с валидацией соответствующих VO:
- `RequestCodeFilter`, `VerifyCodeFilter`: `#[Assert\Email]` + `#[Assert\Length(max: 254)]`
  на email (как `EmailAddress`).
- `RegisterFilter`: на `name` — `#[Assert\Length(max: 100)]` + регулярка `UserName`; на
  `nickname` — регистронезависимая регулярка `UserNickname` (3–30) + запрет двух точек подряд.
Никнейм нормализуется в VO (lower), поэтому констрейнт регистронезависимый, чтобы не
отбраковывать валидный ввод. Добавлены HTTP-тесты 422 на невалидный email
(`code/request`, `code/verify`) и невалидные `name`/`nickname` (`register`) в `AuthHttpTest`.

### Замечание 7 — OpenAPI-схема `VerifyResultResource` не отражала nullable
Корневая причина — в `packages/spiral-openapi` парсер
(`PhpAstParser::parseProperties`/`parseParameters`) определял nullable только по
`Node\NullableType` (`?T`) и не учитывал union с `null` (`T|null`). Добавлен помощник
`isNullableType()`, корректно распознающий обе формы; `baseTypeName()` теперь пропускает
часть `null` в union. Добавлен пакетный тест: фикстура `UserResource` получила поля
`string|null` и `HealthResource|null`, генератор-тест проверяет `nullable: true` и отсутствие
в `required`. Спецификация приложения перегенерирована (`openapi:generate`) —
`tokens`/`registrationTicket` теперь `nullable: true`, в `required` только `needsProfile`.
В `AuthOpenApiGenerationTest` добавлена проверка схемы `VerifyResultResource`.

### Замечание 8 — имя переменной `$result`
Переименовано в `verifyLoginCodeResult` в `AuthController::verifyCode` и в параметре
`VerifyResultResource::fromResult(...)`.

### Замечание 4 — правка переносимого пакета без пакетного теста (обязательная часть)
В `packages/spiral-api-errors/tests/Filter/ApiValidationErrorsRendererTest.php` добавлены два
кейса на ветку `is_array` метода `firstMessage`: вход `list<string>` (берётся первое сообщение)
и пустой список (fallback на пустую строку). Контракт `render(array<string,string>)` сохранён
(интерфейс `ErrorsRendererInterface` и правило «без вложенных массивов в PHPDoc»), список
скармливается через `json_decode(..., true)` с сужением `@var array<string,string>` на границе
— это допустимое сужение mixed, без inline-ignore и без расширения PHPDoc. Пакетные
`phpstan` + `test` зелёные.

## На усмотрение автора

### Применены

- **План №1 (чекбокс фазы 6).** Отмечен `[x]` в `docs/plans/...:736` — фаза rate limit реально
  выполнена; расхождение убирало ложную картину состояния.
- **План №2 (область OpenAPI-скана).** Оставлен общий scan всех модулей; неявный контракт
  «генератор обходит все модули по фильтру `#[Route]`, исключение — `#[OpenApi(ignore: true)]`»
  описан в `docs/arch.md` (раздел «API-документация»). Возврат к точечному списку namespace был
  бы откатом уже согласованного с пользователем решения без выгоды.
- **План №3 (зафиксировать решения в плане).** В план добавлен раздел «Принятые по ходу решения
  (зафиксированы после ревью)»: scan на все модули, ключ rate limit `path`, logout без
  `authUserId`, фиксированное окно rate limit.
- **Замечание 2 (rate limit — настоящее фиксированное окно).** `RateLimitMiddleware` переписан:
  момент истечения окна фиксируется один раз (`:reset`-ключ с TTL=perSeconds), счётчик пишется
  с оставшимся TTL и не продлевается. Время берётся из PSR-20 `ClockInterface` (биндинг
  `NativeClock` в `AppBootloader`; `psr/clock`/`symfony/clock` подняты до прямых зависимостей),
  что делает окно детерминированно тестируемым. Добавлены unit-тесты: TTL счётчика убывает
  `[60,40,20]` (а не сбрасывается на 60) и клиент под лимитом не блокируется после истечения
  окна; тестовый кэш `RecordingCache` использует общий `MockClock`.
- **Замечание 3 (нормализация `requestLocale`).** `CreateUserHandler` нормализует локаль через
  `resolveLocale()` (как `SendLoginCodeHandler`): неподдерживаемое значение → `LocaleConfig.default`,
  вместо `Locale::from()` с риском непойманного `\ValueError` (500) вне HTTP-потока. Добавлен тест
  `testFallsBackToDefaultLocaleForUnsupportedValue`. `LocaleConfig` инжектится в Application —
  явно разрешённое в `docs/arch.md` исключение для `TypedConfig`.
- **Замечание 5 (429-покрытие per-route).** В `AuthHttpTest` добавлен 429-кейс на `code/verify`
  (порог 10 vs 5 у `code/request`) — фиксирует, что middleware навешен и параметр читается именно
  для этого маршрута.

### Отклонено

- **Вынос правки пакета `spiral-api-errors` в отдельный коммит (часть замечания 4) — отклонено.**
  Причина: скилл `eda-fix-by-review` не коммитит (это зона `eda-commit`), поэтому разбиение на
  коммиты вне его ответственности и контроля. Обязательная часть замечания 4 (пакетный тест)
  выполнена. Решение о структуре коммитов остаётся за `eda-commit`/автором при фиксации:
  рекомендация — выделить изменения `packages/spiral-api-errors` и `packages/spiral-openapi`
  (правки переносимых пакетов) в отдельный коммит от прикладного модуля Auth. Ссылка для
  следующих ревьюеров: см. этот пункт, повторно поднимать без новых аргументов не требуется.
