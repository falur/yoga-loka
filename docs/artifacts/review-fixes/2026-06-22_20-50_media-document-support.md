## Решения по optional

### Принято

- **Замечание 1 — принято (уточнить комментарий, без новой ассерты).** Правка чисто текстовая,
  нулевой риск, повышает точность. Комментарий переписан так, чтобы он описывал именно то, что
  проверяет моковый кейс (ветка без конверсий: смена пути на `documents/` + storage по visibility),
  и явно отсылал к сквозному `MediaProcessingFlowTest::testCompleteThenRelayProcessesDocumentToReady`
  как к месту, где держится реальная перекладка оригинала. Вариант «добавить проверку аргументов
  `copyObject`» ревью пометило как необязательный — не делал, чтобы не дублировать в моковом тесте
  то, что уже закрыто Flow-тестом (это и есть смысл разделения мокового и сквозного теста).

- **Замечание 2 — принято в форме «тест-пин + комментарий о намеренно общей нормализации».** Это
  архитектурно корректный из двух предложенных ревью вариантов. Альтернатива «ограничить нормализацию
  документными типами» отклонена осознанно: `MediaMimeTypeCollection::containsMimeType()` — это
  общий метод доменной коллекции; чтобы нормализовать только документы, ему пришлось бы знать, какие
  MIME являются документами, то есть тянуть в коллекцию список `DOCUMENT_MIME_TYPES`/логику
  `MediaTypeResolver`. Это связало бы общую коллекцию с классификацией типов медиа (чужая
  ответственность) и сломало бы чистую семантику «сравнение по базовому MIME». Поведение «общая
  нормализация» уже задекларировано в докстринге `MediaMimeType::baseValue()` как намеренное.
  - Что сделано: в `containsMimeType()` добавлен докблок, что сравнение по `baseValue()` —
    умышленно общее для всех типов (для документов с charset обязательно, для image/video/audio с
    параметром тоже проходит спецификацию), а хранимое значение (`value()`) остаётся исходным.
  - Добавлен тест-пин `testContainsMimeTypeMatchesParametrizedImageByBaseValue`: `image/jpeg;charset=utf-8`
    проходит спецификацию `image/jpeg` — фиксирует осознанное поведение, чтобы оно не «уехало» молча.
  - Что НЕ трогал: путь конверсии (`ProcessMediaHandler:167` → `ImagickMediaImageProcessor:42`,
    `encodeUsingMediaType($value())`) и нормализацию хранимого MIME при записи. Это изменило бы
    поведение и расширило scope; ревью прямо помечает такой вариант как «необязательно». Практический
    риск низкий: спецификацию `allowedMimeTypes` задаёт потребитель, image-MIME с charset на практике
    почти не приходят, а поведение теперь зафиксировано тестом и комментарием.

- **Замечание 3 — принято для двух комментариев, названных в ревью.** Текстовые правки, нулевой риск,
  устраняют прямое нарушение правила `docs/rules.md` «Без англицизмов»:
  - `MediaTypeResolverTest`: «whitelist» → «список разрешённых».
  - `RequestMediaUploadHandlerTest` (комментарии document/charset, добавленные/тронутые этой задачей):
    «Спека…» → «Спецификация…», «…спека его не разрешает…» → «…спецификация его не разрешает…».

### Отклонено

- Отклонённых optional-замечаний нет: все три пункта применены.

## За рамками задачи (упомянуто, не правлено)

- В `RequestMediaUploadHandlerTest.php` строки 65 и 111 содержат ту же кальку «спеки» (и
  «конфиг-дефолта»), но это **предыдущий код** (коммит `9d25a51d` от 2026-06-10), не введённый
  задачей поддержки документов. Ревью назвало в замечании 3 только комментарии document/charset.
  По правилу «точечные изменения» (`AGENTS.md`/принципы проекта) соседний предыдущий код не правлю,
  чтобы не расширять scope задачи. Класс проблемы (англицизмы) стоит закрыть отдельно — это кандидат
  на правило линтера/`eda-automate`, а не на правку в рамках этого ревью.
