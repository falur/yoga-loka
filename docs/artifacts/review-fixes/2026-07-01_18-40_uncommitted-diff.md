# Фиксы по ревью: Рефакторинг Media URL-сервисов, RemoveMediaOriginal и config-independence (4-й круг)

Режим: `apply-optional`. Обязательных замечаний в ревью нет. Единственный пункт —
«на усмотрение автора» (тройное дублирование `existsReadyForMediaId`). Решение по нему
принято самостоятельно по строгим критериям запроса.

## Применённые правки
| # | Замечание | Файлы | Тесты | Статус |
|---|-----------|-------|-------|--------|
| 1 | Тройное байт-в-байт дублирование `existsReadyForMediaId` в `MediaImageConversionRepository` / `MediaVideoConversionRepository` / `MediaAudioConversionRepository` (`quality`, низкий риск, зеркалит принятый дубль `findByMediaId`) | — | — | ✗ отклонено (на усмотрение) |

## Решения по optional
- **Принято:** ничего.
- **Отклонено:** пункт 1 — консолидация `existsReadyForMediaId` не выходит чистой и
  консистентной ни одним из доступных способов, а буквальный вариант из ревью нарушает
  архитектуру. Причины ниже.

### Почему отклонён пункт 1 (подробно)

1. **Буквальный вариант из ревью — вынести общий метод в `AbstractRepository` — нарушает
   направление зависимостей.** `App\Shared\Infrastructure\Cycle\AbstractRepository` —
   кросс-модульный базовый класс: от него наследуются 20 репозиториев всех модулей
   (Posts, Tags, Notifications, Outbox, Media). Метод `existsReadyForMediaId(MediaId $mediaId)`
   тянет в `Shared` доменные типы модуля Media (`MediaId`, `MediaConversionStatus`) и навешивает
   Media-специфичный метод на репозитории чужих модулей. Это прямое нарушение arch.md
   («`Shared` — общий доменный и инфраструктурный код без привязки к одному модулю»; «Domain не
   зависит от других слоёв», правила зависимостей). Отклонено как архитектурно неверное.

2. **Консистентная консолидация обоих методов через модульный базовый класс/трейт не выходит
   чистой.** Запрос прямо запрещает устранять `existsReadyForMediaId`, оставляя параллельный дубль
   `findByMediaId`. Но:
   - `existsReadyForMediaId` возвращает `bool` без вариативности типов — переносится тривиально;
   - `findByMediaId` возвращает ТРИ РАЗНЫЕ конкретные `final`-коллекции
     (`MediaImageConversionCollection` / `MediaVideoConversionCollection` /
     `MediaAudioConversionCollection`).

   Свести `findByMediaId` в общий базовый метод можно только двумя путями, и оба плохи:
   - **Ослабить тип возврата** до абстрактной `TypedCollection` (или generic `TCollection`) —
     нарушает rules.md («методы репозиториев, возвращающие несколько элементов, должны возвращать
     конкретную типизированную коллекцию, а не голый `Collection`») и ухудшает публичный контракт
     трёх репозиториев.
   - **Оставить три override `findByMediaId`** с абстрактной фабрикой-шаблонным методом в базе —
     параллельная структура публичных методов при этом НЕ исчезает (экономия ~3 строк на класс
     ценой нового базового класса + generics-строительства). Это ровно «сомнительная
     связность/абстракция ради одного балла», которую запрос велит отклонять.

3. **Только `existsReadyForMediaId` устранять нельзя.** Это прямо помеченная запросом
   неконсистентность (дубль `findByMediaId` остался бы), и она противоречит осознанно принятому
   в прошлых кругах решению по `findByMediaId`.

4. **Нет прецедента модульного базового репозитория.** Все 20 репозиториев проекта наследуют
   `AbstractRepository` напрямую; введение `AbstractMediaConversionRepository` — новый паттерн
   без обоснования, вопреки AGENTS.md («не рефактори то, что не сломано»; «каждая изменённая
   строка относится к запросу»).

5. **Нулевая выгода.** Ревью само классифицирует пункт как `quality`, низкий риск и «на оценку не
   влияет» (score 94, status final). Балла за него нет — устранять дубль ценой архитектурного
   нарушения или сомнительной абстракции необоснованно.

Дубль `existsReadyForMediaId` оставлен как есть: он зеркалит принятый в прошлых кругах дубль
`findByMediaId`, соответствует локальному стилю модуля и держит репозитории read-only
(`->count()`, без гидрации).
