# Ревью: Ревью незакоммиченных изменений tools-мультиязычности

## Оценка

**72/100.** Основное поведение покрыто тестами и проходит проверки, но есть несколько существенных рисков: язык по умолчанию изменён без явного требования, контракт конструкторов разошёлся с планом, а bootstrap-файлы пакетов начали подключать тестовый код.

## Проблемы сверки с планом

### 1. Изменён язык по умолчанию, хотя план оставлял `LOCALE=en`

Статус: отклонение

Контекст:
План опирался на то, что язык по умолчанию остаётся английским, а русские тексты добавляются как отдельная локаль. Это важно, потому что пакеты должны читать уже выставленный язык, а не менять базовое поведение приложения.

Проблема:
Конфиг переводчика теперь использует `ru`, если переменная окружения `LOCALE` не задана. Это не было частью плана и меняет внешний контракт приложения в окружениях без явно заданного `LOCALE`.

Риск:
В окружении без явно заданного `LOCALE` API начнёт отдавать русские тексты вместо прежних английских. Это может неожиданно изменить внешний контракт и скрыться от тестов, потому что базовый тестовый класс вручную выставляет `en`.

Где:

- `docs/plans/2026-05-20_14-39_tools-multilingual.md:49` — план фиксирует, что `LOCALE` по умолчанию равен `en`
- `app/config/translator.php:11` — значение по умолчанию изменено на `ru`

### 2. Решение про обязательный переводчик не синхронизировано с планом

Статус: отклонение

Контекст:
План требовал добавить переводчик так, чтобы старый код продолжал работать. В журнале исполнения отдельно указано, что по замечанию пользователя переводчик сделан обязательным, но сам план всё ещё обещает обратную совместимость.

Проблема:
Фактический контракт конструкторов изменён, а план и часть проверочных сценариев не обновлены под это решение. В результате по артефактам проекта невозможно понять, это намеренное ломащее изменение или недоделка реализации.

Риск:
Локальные пакеты заявлены как переносимые библиотеки. Если обязательный переводчик принят намеренно, это нужно явно зафиксировать в плане и тестах. Если нет, старый код вне Spiral DI будет падать сразу при создании объекта.

Где:

- `docs/plans/2026-05-20_14-39_tools-multilingual.md:51` — план требует обратимое расширение конструкторов `tools/api-error`
- `docs/plans/2026-05-20_14-39_tools-multilingual.md:53` — план требует сохранить `new OpenApiGenerator()`
- `docs/plans/2026-05-20_14-39_tools-multilingual.md:159` — план повторяет требование про необязательный переводчик
- `docs/plans/2026-05-20_14-39_tools-multilingual.md:176` — план требует тест на работу `new OpenApiGenerator()` без DI
- `docs/executions/2026-05-20_16-23_tools-multilingual.md:19` — журнал фиксирует позднее решение сделать переводчик обязательным
- `tools/api-error/src/Middleware/RouteNotFoundMiddleware.php:19` — переводчик обязателен в конструкторе
- `tools/api-error/src/Filter/ApiValidationErrorsRenderer.php:17` — переводчик обязателен в конструкторе
- `tools/api-error/src/Interceptor/ApiExceptionInterceptor.php:21` — переводчик обязателен в конструкторе
- `tools/openapi/src/OpenApiGenerator.php:18` — `OpenApiGenerator` больше нельзя создать без переводчика

### 3. Bootstrap-файлы пакетов подключают тестовый класс

Статус: отклонение

Контекст:
Bootstrap-файлы пакетов используются для запуска тестов и статического анализа. Обычно они подключают автозагрузку, а тестовые помощники загружаются через `autoload-dev` или отдельный test bootstrap.

Проблема:
В оба package bootstrap добавлен прямой `require_once` на `tests/Support/FakeTranslator.php`. Это изменение не требовалось планом и смешивает общий bootstrap пакета с тестовой поддержкой.

Риск:
Общий запуск проверок пакета теперь зависит от конкретного файла из `tests`. Если этот bootstrap переиспользуют для проверки только рабочего кода или в другой сборке пакета, он может упасть до начала проверки. Кроме того, граница между рабочим кодом пакета и тестовой инфраструктурой становится менее понятной.

Где:

- `tools/api-error/bootstrap.php:6` — подключается тестовый `FakeTranslator`
- `tools/openapi/bootstrap.php:6` — подключается тестовый `FakeTranslator`
- `tools/api-error/phpstan.neon:9` — этот bootstrap используется статическим анализом пакета
- `tools/openapi/phpstan.neon:9` — этот bootstrap используется статическим анализом пакета

## Замечания

### 1. Конфиг меняет язык приложения по умолчанию

Тип: `bug`

Рекомендация: `править обязательно`

Контекст:
Добавление переводов должно менять текст в зависимости от текущего языка, но не должно само менять базовый язык приложения. Если базовый язык меняется, это уже отдельное изменение внешнего поведения.

Риск:
В окружении без `LOCALE` ответы API и генерация OpenAPI будут работать не так, как до задачи. Клиенты могут получить другой язык сообщений без явного включения, а тесты этого не поймают, потому что `tests/TestCase.php` после запуска приложения выставляет `en`.

Где:

- `app/config/translator.php:11` — fallback для `locale` изменён с `en` на `ru`
- `tests/TestCase.php:55` — тесты принудительно возвращают `en` и не проверяют реальный дефолт конфига
- `public/openapi/openapi.yml:16` — файл в репозитории сгенерирован с английским описанием
- `public/openapi/openapi.yml:19` — файл в репозитории сгенерирован с английским описанием ошибки

Детали:
План фиксирует, что при отсутствии пользовательского выбора используется `LOCALE`, а прежний дефолт был `en`. В коде дефолт стал `ru`. Отдельного артефакта с решением поменять базовый язык приложения в рамках этой задачи нет.

Как исправить:
Нужно не менять язык по умолчанию в рамках этой задачи. Если проект действительно должен перейти на русский по умолчанию, это стоит оформить отдельным решением и явно обновить план, документацию и проверки.

Конкретные шаги:

- Вернуть в `app/config/translator.php` значение `\env('LOCALE', 'en')`.
- Если нужен русский дефолт, добавить отдельный тест, который запускает приложение без принудительного `setLocale('en')` и проверяет новый ожидаемый язык.
- После выбора дефолта заново сгенерировать `public/openapi/openapi.yml` в том же языке, который должен попасть в репозиторий.

### 2. Контракт конструкторов разошёлся с планом и публичным примером

Тип: `bug`

Рекомендация: `править обязательно`

Контекст:
Пакеты из `tools/` можно использовать как отдельные библиотеки. Если контракт меняется и переводчик становится обязательным, это нужно явно синхронизировать с планом, тестами и публичными примерами использования.

Риск:
Код вне приложения, старые тесты или ручные CLI-сценарии, которые создают `OpenApiGenerator` или middleware напрямую, начнут падать сразу при создании объекта. Если это намеренное решение, без обновлённого плана и явного теста на новый контракт следующий исполнитель может вернуть fallback обратно или неправильно оценить задачу.

Где:

- `tools/openapi/src/OpenApiGenerator.php:18` — первый аргумент конструктора стал обязательным переводчиком
- `tools/api-error/src/Middleware/RouteNotFoundMiddleware.php:19` — прямое создание только с logger больше не работает
- `tools/api-error/src/Filter/ApiValidationErrorsRenderer.php:17` — прямое создание только с logger больше не работает
- `tools/api-error/src/Interceptor/ApiExceptionInterceptor.php:21` — прямое создание только с logger больше не работает
- `tools/openapi/tests/Generator/OpenApiGeneratorTest.php:24` — тесты теперь всегда передают fake-переводчик и не проверяют старый сценарий
- `tools/openapi/README.md:31` — публичный пример теперь показывает только сценарий с обязательным переводчиком

Детали:
Сигнатуры конструкторов требуют `TranslatorInterface`, а план всё ещё требует необязательный переводчик и fallback. Журнал исполнения говорит, что обязательный переводчик появился по замечанию пользователя, но это решение не перенесено в план как новый контракт.

Как исправить:
Нужно либо вернуть необязательный переводчик и английский fallback, либо явно зафиксировать, что принято ломащее изменение. Если выбрать ломающий вариант, план и тестовые сценарии должны быть обновлены так, чтобы не обещать `new OpenApiGenerator()` без DI.

Конкретные шаги:

- Если обязательный переводчик остаётся решением, обновить план и явно убрать требования про `?TranslatorInterface`, fallback и `new OpenApiGenerator()` без DI.
- Если обратная совместимость всё ещё нужна, сделать `TranslatorInterface` необязательным и вернуть fallback.
- Добавить тест, который фиксирует выбранный контракт: либо успешный `new OpenApiGenerator()` без переводчика, либо ожидаемый обязательный сценарий с переводчиком.

### 3. Bootstrap пакетов зависит от тестового helper-а

Тип: `architecture`

Рекомендация: `править обязательно`

Контекст:
Тестовые helper-классы должны оставаться частью тестовой инфраструктуры. Общий bootstrap пакета лучше держать минимальным: только подключение Composer autoload и подготовка окружения, которая нужна всем проверкам пакета.

Риск:
Bootstrap для PHPUnit и PHPStan теперь жёстко зависит от `tests/Support/FakeTranslator.php`. Это усложняет запуск анализа и тестов в разных окружениях и создаёт ненужную связь между рабочей проверкой `src` и тестовым классом.

Где:

- `tools/api-error/bootstrap.php:6` — общий bootstrap требует тестовый helper
- `tools/openapi/bootstrap.php:6` — общий bootstrap требует тестовый helper
- `tools/api-error/tests/Support/FakeTranslator.php:10` — тестовый класс подключается вручную
- `tools/openapi/tests/Support/FakeTranslator.php:10` — тестовый класс подключается вручную

Детали:
Для обоих пакетов уже есть `autoload-dev` в `composer.json`, где namespace тестов указывает на `tests`. Прямой `require_once` в bootstrap обходит эту границу и делает test helper частью обязательной загрузки пакета при проверках.

Как исправить:
Нужно оставить package bootstrap без знания о конкретных тестовых helper-ах. Тестовые классы должны грузиться через dev-autoload или через отдельный test bootstrap.

Конкретные шаги:

- Убрать `require_once __DIR__ . '/tests/Support/FakeTranslator.php'` из обоих `bootstrap.php`.
- Если текущий запуск PHPUnit или PHPStan после этого не видит тестовые классы, настроить dev-autoload для локального запуска пакета или вынести подключение helper-а в отдельный bootstrap только для PHPUnit.
- Проверить `composer -d tools/api-error test`, `composer -d tools/openapi test`, `composer -d tools/api-error phpstan` и `composer -d tools/openapi phpstan`.
