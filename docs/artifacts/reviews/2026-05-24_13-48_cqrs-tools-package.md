## Замечания

### 1. Часть новых вызовов не соблюдает правило именованных аргументов

Тип: `rules`

Рекомендация: `править обязательно`

Контекст:
В проекте именованные аргументы обязательны для вызовов с необязательными или булевыми параметрами, а также для неочевидных вызовов с несколькими параметрами. Это правило нужно соблюдать и в локальных tools-пакетах, иначе root-проверки или дальнейшие правки начнут расходиться со стилем проекта.

Риск:
Код может не пройти проектные проверки, когда root PHPStan снова будет доступен через Docker. Даже если package-local PHPStan проходит, пакет станет выбиваться из правил основного проекта.

Где:

- `tools/cqrs/src/Middleware/LoggingMiddleware.php:28` — `microtime(true)`
- `tools/cqrs/src/Middleware/LoggingMiddleware.php:30` — `round(..., 2)` и второй вызов `microtime(true)`
- `tools/cqrs/tests/Portability/PackagePortabilityTest.php:30` — вызов PHPUnit assertion с тремя аргументами
- `tools/cqrs/tests/Portability/PackagePortabilityTest.php:31` — вызов PHPUnit assertion с тремя аргументами

Детали:
В этих местах передаются булевые или необязательные параметры позиционно. Для этого проекта такие вызовы лучше писать явно: например, `microtime(as_float: true)` и `round(num: ..., precision: 2)`.

Как исправить:
Оставить поведение тем же, но назвать аргументы там, где правило проекта этого требует.

Конкретные шаги:

- Обновить вызовы `microtime()` и `round()` в `LoggingMiddleware`.
- Обновить assertion-вызовы в portability-тесте.
- После правки повторить package-local PHPStan и root `make phpstan`, когда Docker будет доступен.

### 2. Логика pipeline продублирована в двух классах шин

Тип: `quality`

Рекомендация: `на усмотрение автора`

Контекст:
`CommandBus` и `QueryBus` отличаются составом middleware, но сам алгоритм прохода по цепочке middleware у них одинаковый. Сейчас этот алгоритм скопирован в оба класса.

Риск:
Если поведение pipeline понадобится поменять, придётся править два места. При будущих изменениях легко обновить одну шину и забыть вторую.

Где:

- `tools/cqrs/src/CommandBus.php:21` — начало реализации `dispatch()`
- `tools/cqrs/src/CommandBus.php:36` — рекурсивный проход по middleware
- `tools/cqrs/src/QueryBus.php:21` — такая же реализация `dispatch()`
- `tools/cqrs/src/QueryBus.php:36` — такой же рекурсивный проход по middleware

Детали:
Методы `dispatch()` и `dispatchThrough()` в обоих классах почти полностью совпадают. Разница находится не в алгоритме, а только в том, какие middleware передаются в конструктор.

Как исправить:
Если автор считает риск сопровождения значимым, вынести общий pipeline в небольшой внутренний класс или trait внутри пакета. Если важнее оставить два класса максимально простыми, можно оставить как есть.

Конкретные шаги:

- Принять решение, стоит ли убирать это дублирование сейчас.
- Если да, покрыть общий pipeline существующими тестами `CommandBusTest` и `QueryBusTest`.

### 3. Имя операции в логах определяется по подстрокам в имени класса

Тип: `quality`

Рекомендация: `на усмотрение автора`

Контекст:
Логи шины должны помогать понять, какой сценарий выполнялся. Сейчас имя операции берётся из первого захваченного объекта, в имени класса которого есть `Command` или `Query`, но нет `Handler`.

Риск:
Если closure захватит вспомогательный объект с похожим именем, лог может показать не тот сценарий. Это не ломает выполнение, но может усложнить разбор проблем в эксплуатации.

Где:

- `tools/cqrs/src/Middleware/LoggingMiddleware.php:50` — проверка имени на `Command`
- `tools/cqrs/src/Middleware/LoggingMiddleware.php:54` — проверка имени на `Query`

Детали:
План осознанно оставляет `dispatch(callable)` без marker-интерфейсов, поэтому строгого типа Command или Query здесь нет. Но текущая эвристика всё равно может дать ложное совпадение по имени класса.

Как исправить:
Если точность логов важнее простоты, сделать извлечение имени более явным. Например, договориться о небольшом интерфейсе для логируемых операций или передавать имя операции отдельным способом.

Конкретные шаги:

- Решить, достаточно ли текущей эвристики для проекта.
- Если нет, обновить контракт логирования и добавить тест на ложное совпадение.
