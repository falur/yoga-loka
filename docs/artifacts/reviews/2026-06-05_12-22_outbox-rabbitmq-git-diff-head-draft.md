## Замечания

### 1. Job может выполниться без обновления статуса outbox

Если сообщение очереди придёт с разными данными в headers и payload, interceptor замечает несовпадение, но дальше запускает Job как обычную задачу. Причина в том, что `null` из `outboxEventIdFromParameters()` одновременно означает «это обычная Job» и «данные outbox повреждены или противоречат друг другу».

Практический риск: внешнее действие может выполниться, а outbox-событие останется без статуса `handled` или `failed`. При повторной ручной обработке это может привести к дублю внешнего действия. Это также ломает архитектурную гарантию outbox: внешние побочные эффекты должны идти через outbox-учёт, а не обходить его как обычные queue Job.

Технические детали:

- **Тип:** `bug`, `architecture`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxQueueStatusInterceptor.php:34` — `?OutboxEventId` не различает обычную Job и повреждённые outbox-данные
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxQueueStatusInterceptor.php:94` — ветка несовпадения headers и payload
- **Что подтверждает проблему:** при несовпадении метод возвращает `null`, а `process()` на строках 34-41 трактует `null` как обычную задачу без outboxId и вызывает `$core->callAction(...)`
- **Как исправить:** разделить состояния «outboxId отсутствует» и «outboxId повреждён или противоречив». Для второго состояния не запускать Job как обычный: либо бросать понятное исключение, либо брать один доверенный источник и всё равно проводить Job через outbox-учёт.
- **Тесты:** добавить тест, где headers содержат один `outboxId`, payload другой, и проверить, что Job не выполняется без фиксации статуса. После исправления выполнить итоговую проверку `make qa`.

### 2. Битая строка с пустым last_error может снова ломать relay

Восстановление outbox-события из базы считает пустую строку в `last_error` ошибкой, но предварительная проверка битых строк пропускает такую строку как допустимую. Это показывает более общую проблему: репозиторий вручную повторяет правила разбора outbox-строки, которые уже есть в value object и typecast, и эти два источника правил уже разошлись.

Практический риск: одна некорректная строка может остановить relay для всей пачки. Код пытается изолировать такие записи и переводить их в `failed`, но из-за расхождения контрактов между Repository и ORM typecast та же строка может снова попасть в выборку и снова уронить relay.

Технические детали:

- **Тип:** `bug`, `quality`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:142` — ручная проверка `last_error`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:92` — ручная проверка строки outbox дублирует правила гидрации
- **Где:** `app/src/Modules/Outbox/Infrastructure/Cycle/OutboxLastErrorTypecast.php:24` — typecast передаёт любую строку в `OutboxLastError::fromString()`
- **Что подтверждает проблему:** `OutboxEventRepository` валидирует `last_error` только если строка не пустая, а `OutboxLastErrorTypecast` передаёт пустую строку в `OutboxLastError::fromString()`, где пустая строка запрещена.
- **Как исправить:** привести ручную проверку к тем же правилам, что и typecast, или убрать расхождение через один общий механизм проверки. Важно выбрать один контракт: пустая строка либо ошибка строки, либо отсутствие ошибки.
- **Тесты:** добавить кейс в `OutboxEventRepositoryTest` для `pending`-строки с `last_error = ''`. После исправления выполнить итоговую проверку `make qa`.

### 3. Тестовый лимит цикла relay попадает в общий catch

В `runLoop()` тестовый ограничитель итераций бросает исключение внутри общего блока `try`, а общий `catch` считает его обычной временной ошибкой relay и продолжает цикл. Это смешивает боевую retry-логику и тестовый стоп-сигнал.

Практический риск: проверка устойчивости бесконечного режима становится ненадёжной. Такой тест должен быстро завершать цикл, а сейчас он может уйти на лишнюю итерацию и упасть уже из-за превышения ожиданий mock-объекта.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxRelayWorker.php:47` — исключение лимита внутри общего `try`
- **Что подтверждает проблему:** `tests/Unit/Modules/Outbox/Infrastructure/Outbox/OutboxRelayWorkerTest.php:20` ожидает ровно два вызова relay и на строках 46-49 ждёт исключение лимита, но `catch` на строке 50 перехватывает это исключение как обычную ошибку.
- **Как исправить:** проверять `maxLoopIterations` вне общего `try/catch`, либо бросать отдельное исключение и не перехватывать его в retry-логике.
- **Тесты:** после исправления выполнить итоговую проверку `make qa`; минимум должен стабильно проходить `OutboxRelayWorkerTest`.

### 4. Diff-check уже находит лишнюю пустую строку в новом PHP-файле

В одном новом файле есть лишняя пустая строка в самом конце. Это мелкая проблема, но она уже ловится стандартной проверкой diff и может создать шум в проверках перед коммитом.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Application/Command/Outbox/ProcessDebugLogMessage/ProcessOutboxDebugLogMessageHandler.php:46` — лишняя пустая строка после закрывающей скобки
- **Что подтверждает проблему:** `git diff --check HEAD` возвращает `new blank line at EOF`
- **Как исправить:** убрать лишнюю пустую строку в конце файла.
- **Тесты:** тест не нужен; достаточно повторить `git diff --check HEAD`. Перед завершением всей задачи всё равно выполнить итоговую проверку `make qa`.

### 5. Application-контракт сериализации раскрывает внутренние доменные типы outbox

Новый контракт сериализации находится в Application-слое, но принимает и возвращает доменные value object outbox. Из-за этого внутренние типы доменной модели становятся частью публичного Application API модуля.

Практический риск: другие модули или сценарии начнут зависеть не от устойчивого Application-контракта, а от деталей хранения outbox-событий. Потом будет сложнее менять формат хранения, typecast или внутреннюю доменную модель outbox без каскада правок.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Application/Contract/OutboxMessageSerializerContract.php:9` — контракт импортирует `OutboxEventPayload` из Domain
- **Где:** `app/src/Modules/Outbox/Application/Contract/OutboxMessageSerializerContract.php:10` — контракт импортирует `OutboxEventType` из Domain
- **Где:** `app/src/Modules/Outbox/Application/Outbox/SerializedOutboxMessage.php:7` — Application DTO хранит доменный payload
- **Где:** `app/src/Modules/Outbox/Application/Outbox/SerializedOutboxMessage.php:8` — Application DTO хранит доменный type
- **Что подтверждает проблему:** `docs/arch.md` описывает Application как границу модуля, через которую другие модули обращаются к outbox. В текущем контракте эта граница требует знать доменные VO outbox.
- **Как исправить:** либо убрать serializer из публичного `Application/Contract`, если это внутренняя инфраструктурная деталь, либо сделать контракт на Application DTO без доменных VO.
- **Тесты:** после изменения границы выполнить `make qa`, потому что правка может затронуть сериализацию, relay и Job.

### 6. Новые outbox-контракты используют запрещённые mixed и сложные массивы

В новых outbox-файлах появились явные `mixed` и PHPDoc вида `array<string, mixed>`. Правила проекта запрещают явный `mixed` в проектных контрактах и сложные массивы в PHPDoc; неизвестное значение нужно сужать на границе и дальше передавать именованный DTO, value object, enum или типизированную коллекцию.

Практический риск: такие контракты делают формат очереди и строк outbox неявным. Ошибки вроде пустого `last_error` или повреждённого payload обнаруживаются поздно и в разных местах по-разному.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:102` — `array<string, mixed>` для строки outbox
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:151` — параметр `mixed`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:218` — `list<array<string, mixed>>`
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxQueueHeaders.php:18` — `array<string, mixed>`
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxQueueStatusInterceptor.php:87` — `array<string, mixed>`
- **Где:** `app/src/Modules/Outbox/Infrastructure/Outbox/OutboxQueueSerializer.php:63` — параметр `mixed`
- **Как исправить:** вынести неизвестные данные в узкие DTO/value object на границе, а внутри outbox работать с именованными типами и простыми контрактами.
- **Тесты:** после изменения контрактов выполнить `make qa`.

### 7. В консольной команде продублирован разбор целых чисел

`integerArgument()` и `integerOption()` делают почти одинаковую проверку значения. Риск небольшой, но при следующем изменении правило для аргумента и опции легко может разойтись.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Presentation/Console/OutboxRelayCommand.php:43` — проверка аргумента
- **Где:** `app/src/Modules/Outbox/Presentation/Console/OutboxRelayCommand.php:58` — проверка опции
- **Как исправить:** оставить две публичные по смыслу обёртки, но вынести общую проверку значения в один приватный метод.
- **Тесты:** отдельный тест не обязателен, если поведение не меняется; после общей задачи выполнить `make qa`.
