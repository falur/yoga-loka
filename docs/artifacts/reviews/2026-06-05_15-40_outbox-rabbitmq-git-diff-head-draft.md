# Ревью: незакоммиченные изменения outbox RabbitMQ (git diff HEAD)

## Оценка

**94/100.** Архитектурный путь и большая часть алгоритма outbox сделаны последовательно: есть отдельный контракт для сообщений, relay с `publishing -> queued`, interceptor статусов и переключение очереди на RabbitMQ для dev. Является заметный риск в том, как валидируется тип сообщения в `OutboxEventType`, потому что план этого этапа требовал строгую проверку класса.

## Проблемы сверки с планом

### 1. `OutboxEventType` не валидирует, что тип реально существует и реализует контракт сообщения

План прямо задаёт, что тип сообщения в outbox должен быть не произвольной строкой, а именно полным именем класса с реализацией `OutboxMessage`. Сейчас это значение только проверяется на непустоту. Из-за этого в БД можно положить любой текст и довести до стадии десериализации уже в `relay`/`interceptor`, где ошибка всплывает позже и в более тяжёлой фазе потока.

Технические детали:

- **Статус:** отклонение
- **Где:** `app/src/Modules/Outbox/Domain/Outbox/ValueObject/OutboxEventType.php:15-22`, `tests/Unit/Modules/Outbox/Domain/Outbox/OutboxValueObjectTest.php:21-33`
- **Что подтверждает проблему:** из value object разрешён любой не пустой класс-строковый тип, и тест прямо закрепляет это поведение через `fromString('Old\\Removed\\Message')`.
- **Как исправить:** вернуть проверку существования класса и реализации интерфейса `OutboxMessage` внутри `OutboxEventType::fromString`, и скорректировать тесты: вместо «принимает любой текст» проверять допустимую пару `существует + реализует контракт`, и добавить провалы для `class_exists=false` и `не-implements OutboxMessage`.
- **Тесты:** обновить `tests/Unit/Modules/Outbox/Domain/Outbox/OutboxValueObjectTest.php` и добавить интеграционный кейс в репозиторий/relay, где в БД лежит некорректный `type` и событие корректно обрабатывается как ошибка, без неочевидного падения поздних слоёв.
