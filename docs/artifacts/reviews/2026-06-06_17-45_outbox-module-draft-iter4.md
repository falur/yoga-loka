# Ревью: модуль Outbox (итерация 4)

## Оценка

**93/100.** Свежее независимое ревью текущего состояния кода после применения фиксов
по итерации 3. Все шесть замечаний прошлой итерации закрыты корректно и
согласованно: уровни логирования реальных инфраструктурных сбоев теперь привязаны
к фактическому переходу статуса (`isFinal()` → ERROR, возврат в оборот → WARN/DEBUG)
единообразно и в relay, и в interceptor; recovery-выборка повреждённых строк
ограничена `batchSize`; введён VO `OutboxRelaySleepSeconds` (MIN=1) с вынесенным за
`OutboxRelaySleeperContract` сном, что закрывает busy-spin при `--sleep=0`; двойной
смысл колонки `available_at` зафиксирован комментарием рядом с константами;
recovery-выборка возвращает типизированную `OutboxPendingRowCollection`;
`RelayOutboxCommand` несёт только примитивы, а оба VO создаются в
`RelayOutboxHandler`.

Архитектура модуля выдержана: плоская структура `Command/`, relay как
инфраструктурный orchestrator со своими DB-переходами, единый источник трактовки
пустого `last_error` (`OutboxLastError::toDatabaseValue()` + парсер сырой строки +
typecast), разделение Domain/Application/Repository/Infrastructure, типизированный
`OutboxConfig` с авто-регистрацией. Доменная модель статусов, попыток и дат
консистентна, ручные CAS-UPDATE обоснованы комментариями (ORM Select не выражает
условный UPDATE по статусу).

Оставшиеся замечания мелкие, ничего из них не ломает основной сценарий доставки,
но одно из них — прямое нарушение правила, а не вкусовая правка: фабрика
`StoredOutboxEventId::fromString()` дублирует публичный конструктор без нового
смысла, что правило «Не дублировать конструктор фабриками без смысла» формулирует
как запрет (нужно закрыть конструктор или убрать фабрику; правка тривиальна и
не меняет поведение). Остальное — на усмотрение автора: корректность конфигурации
RabbitMQ при нестандартном vhost (проявляется только при ручной смене
`RABBITMQ_VHOST`), консистентность непубличности конкретного конструктора
`KnownOutboxEventDate` и мёртвые поля `createdAt`/`updatedAt` в
`ValidOutboxPendingRow`, которые сейчас не читаются ни в коде, ни в тестах.

## Замечания

### 1. Нестандартный `RABBITMQ_VHOST` без ведущего слэша даёт битый AMQP-адрес

RoadRunner подключается к брокеру по строке `amqp://user:pass@host:port${VHOST}`,
где значение vhost подставляется в URL сразу после порта. По умолчанию `VHOST=/`,
и адрес получается корректным (`...:5672/`). Но если кто-то задаст vhost без
ведущего слэша (например `RABBITMQ_VHOST=staging`), separator между портом и vhost
пропадёт и адрес станет `...:5672staging` — невалидный AMQP URL, соединение с
очередью не поднимется.

Риск низкий, но реальный и эксплуатационный: проявится не в коде, а при
развёртывании на стенде с отдельным vhost, и ошибка будет неочевидной (RoadRunner
не стартует jobs-консьюмер, outbox-события копятся в pending без явной причины в
логах приложения). Сейчас контракт «vhost обязан начинаться со слэша» нигде не
зафиксирован — ни валидацией, ни комментарием рядом с переменной.

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** на усмотрение автора
- **Где:** `docker/rr/http-jobs.yaml:40` (`addr: 'amqp://...:${RABBITMQ_PORT:-5672}${RABBITMQ_VHOST:-/}'` — vhost клеится к порту без разделителя). Значение по умолчанию задаётся в `.env.sample:29` (`RABBITMQ_VHOST=/`) и `docker/docker-compose.dev.yml:173`.
- **Что подтверждает проблему:** дефолт `/` маскирует проблему, потому что слэш уже есть в значении. Любой vhost без ведущего слэша ломает URL. В AMQP URI vhost — это path-сегмент после `/`, поэтому шаблон должен явно содержать разделитель и url-энкодить значение.
- **Как исправить:** либо закрепить контракт в шаблоне (`.../${RABBITMQ_PORT:-5672}/${RABBITMQ_VHOST:-}` и трактовать переменную как имя vhost без слэша, по умолчанию пустое = vhost `/`), либо оставить как есть, но добавить рядом с `RABBITMQ_VHOST` в `.env.sample` и в README модуля явный комментарий «значение должно начинаться со слэша». Тесты: инфраструктурная конфигурация RoadRunner юнит-тестами не покрывается; достаточно зафиксировать контракт документацией/дефолтом.

### 2. `StoredOutboxEventId::fromString()` дублирует публичный конструктор — прямое нарушение правила

`StoredOutboxEventId` имеет публичный конструктор, который валидирует пустоту, и
статическую фабрику `fromString()`, которая просто делает `new self($value)` без
нового смысла (нормализации, преобразования внешнего формата, дополнительной
валидации, отдельного доменного сценария). Правило проекта формулирует это не как
рекомендацию, а как запрет: «Если метод принимает те же данные, что и конструктор,
и просто вызывает `new self(...)` без нового смысла — он запрещён; используй
конструктор напрямую». Поэтому именно по `StoredOutboxEventId` это нарушение
правила, а не вкусовая правка: нужно либо убрать фабрику, либо закрыть конструктор.

Фактическая картина по коду: `new StoredOutboxEventId(...)` напрямую не вызывается
нигде, весь вход идёт через `fromString()` (`OutboxEventStore.php:34` и unit-тест).
То есть публичный конструктор — лишний параллельный вход, который правило и просит
устранить. Для `KnownOutboxEventDate` ситуация мягче и про консистентность: его
конкретный конструктор публичный, хотя единственный санкционированный вход —
абстрактная фабрика `OutboxEventDate::fromDateTime()`; прямой `new
KnownOutboxEventDate(...)` вне самой фабрики нигде не встречается.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** `StoredOutboxEventId` — править обязательно (прямой запрет правила); `KnownOutboxEventDate` — на усмотрение автора (консистентность).
- **Где:** `app/src/Modules/Outbox/Application/Message/StoredOutboxEventId.php:11-22` (публичный конструктор валидирует пустоту, `fromString()` лишь `new self($value)`; единственные вызовы — `OutboxEventStore.php:34` и `tests/Unit/Modules/Outbox/Application/Message/OutboxMessageSerializerTest.php:94`). `app/src/Modules/Outbox/Domain/ValueObject/KnownOutboxEventDate.php:9-11` — публичный конструктор; единственное создание — `OutboxEventDate::fromDateTime()` (`OutboxEventDate.php:16`).
- **Что подтверждает проблему:** `docs/rules.md` («Не дублировать конструктор фабриками без смысла») формулирует запрет, а не предпочтение. В `StoredOutboxEventId` `fromString()` не нормализует и не преобразует вход — вся валидация в конструкторе, а прямой `new` нигде не используется. В `KnownOutboxEventDate` конкретный конструктор публичный, хотя единственный санкционированный вход — `OutboxEventDate::fromDateTime()`.
- **Как исправить:** для `StoredOutboxEventId` — либо сделать конструктор приватным и оставить `fromString()` единственным входом (как в `OutboxLastError`/`OutboxAvailableAt` с приватным конструктором), либо убрать `fromString()` и звать конструктор напрямую. Любой из вариантов закрывает запрет правила. Для `KnownOutboxEventDate` рассмотреть непубличность/`internal` конкретного конструктора, чтобы единственным входом осталась абстрактная фабрика. Тесты: существующие unit-тесты VO покрывают поведение; при смене видимости конструктора обновить точки создания (`OutboxEventStore.php:34`, тест сериализатора).

### 3. `ValidOutboxPendingRow` отдаёт `createdAt`/`updatedAt` как голые `\DateTimeImmutable`

Типизированная строка `ValidOutboxPendingRow` сужает почти все поля в VO/enum, но
`createdAt` и `updatedAt` остаются публичными `\DateTimeImmutable`, тогда как
доменная дата в модуле уже выражена через `OutboxEventDate`/`OutboxAvailableAt`.
Это пограничный объект recovery (не Entity), поэтому формально запрет «Entity без
примитивов» сюда не распространяется. Ключевое: эти два поля сейчас не читаются
нигде — ни в коде приложения, ни в тестах. Их значения вытягиваются из БД
(`SELECT created_at, updated_at` в `pendingForRelayRows()`), парсятся в
`OutboxPendingRow::fromDatabaseRow()` и складываются в DTO, после чего ни один
потребитель к ним не обращается (recovery читает только `rawOutboxEventId` и
`lastError` у `InvalidOutboxPendingRow`). То есть это не просто непоследовательность
типов, а мёртвые данные: лишний столбец в выборке, лишний парсинг и лишний
аргумент конструктора, который правило «Нет мёртвого кода» просит убрать.

Если поля всё же планируются к использованию, остаётся вторичная проблема
консистентности: две даты пойдут голым `\DateTimeImmutable` рядом с доменными VO в
том же DTO.

Технические детали:

- **Тип:** `quality` (плюс затрагивает правило «Нет мёртвого кода»)
- **Рекомендация:** на усмотрение автора (по умолчанию — удалить неиспользуемые поля)
- **Где:** `app/src/Modules/Outbox/Repository/ValidOutboxPendingRow.php:29-30` (`public \DateTimeImmutable $createdAt`, `public \DateTimeImmutable $updatedAt`) против остальных полей того же класса, обёрнутых в VO/enum. Парсинг — `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:49-50`. Лишние столбцы в выборке — `OutboxEventRepository.php:81-82`.
- **Что подтверждает проблему:** соседние поля (`availableAt`, `queuedAt`, `lastError`, `status`, `attempts`) уже типизированы доменными типами, а две даты — нет. `createdAt`/`updatedAt` нигде не читаются: `grep` по `->createdAt`/`->updatedAt` в `app/src/Modules/Outbox` и `tests/**/Outbox` не находит ни одного обращения к полям `ValidOutboxPendingRow` (совпадения в тестах относятся к `OutboxMessage`/Command, не к этой строке). То есть поля сейчас лишние в DTO.
- **Как исправить:** по умолчанию — убрать `createdAt`/`updatedAt` из `ValidOutboxPendingRow`, из парсинга (`OutboxPendingRow.php:49-50`) и из выборки `pendingForRelayRows()` (`OutboxEventRepository.php:81-82`), чтобы не таскать неиспользуемые значения. Если поля нужны на будущее — обернуть обе даты в `OutboxEventDate`/`KnownOutboxEventDate` для единообразия и сразу подключить потребителя. Тесты: существующие repository-тесты покрывают парсинг; при удалении полей обновить ожидания.
