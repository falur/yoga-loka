# Ревью: модуль Outbox

## Оценка

**90/100.** Основной сценарий доставки рабочий, обязательных правок нет. Замечания
касаются удержания неиспользуемых полей в DTO валидной pending-строки, протекания
примитива в технический контракт паузы, попадания в target несвязанного с Outbox
глобального изменения mapper-а ORM и нескольких мест, где корректность модуля
держится на ручном синхронном поддержании двух файлов/двух реализаций разбора
строки. Часть из этих мест создаёт латентный риск зацикливания relay на
повреждённой строке. Все замечания — «на усмотрение автора», ни одно не ломает
основной сценарий доставки. Оценка снижена с 91 до 90 после мета-ревью: подтверждены
три дополнительных замечания, но несколько прежних формулировок были завышены и
смягчены.

## Проблемы сверки с планом

Проверка плана пропущена по явному указанию пользователя: ревью выполнено без
сверки с планом работ.

## Замечания

### 1. DTO валидной pending-строки восстановления удерживает поля, которые в коде нигде не читаются

Когда relay натыкается на повреждённые данные в outbox, он переходит в режим
восстановления: заново читает сырые pending-строки и парсит каждую в
типизированный объект. Сам разбор каждого поля — это механизм детекции порчи:
любое битое поле приводит к `InvalidOutboxPendingRow`, поэтому полный разбор
определяет классификацию «валидна / битая» и влияет на поведение. Проблема не в
разборе как таковом, а в том, что для валидной строки получается полноценный DTO
со всеми разобранными полями (тип, payload, статус, попытки, четыре даты, текст
ошибки), а восстановление реагирует только на битые строки и валидные молча
пропускает (`continue`).

В итоге публичные поля `ValidOutboxPendingRow` в продакшен-коде не читает никто:
ни `OutboxRelay`, ни `OutboxEventRepository`. Их читает только unit-тест парсера
(`OutboxPendingRowTest`), и то лишь часть — `status`, `attempts`, `queuedAt`,
`lastError`; поля `type`, `payload`, `availableAt`, `handledAt`, `failedAt` не
читаются нигде. То есть DTO валидной строки удерживает полностью разобранное
состояние, которое поведение не использует. Риск не в падении, а в лишней
сложности и стоимости поддержки: при изменении схемы кто-то будет чинить и
тестировать поля, не влияющие на поведение. Это же замечание поднималось в прошлой
итерации ревью и в текущем дереве всё ещё открыто.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:29-56` (сборка
  `ValidOutboxPendingRow`), `app/src/Modules/Outbox/Repository/ValidOutboxPendingRow.php`
  (DTO целиком), `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:142-169`
  (`markInvalidPendingRowsAsFailed` обрабатывает только `InvalidOutboxPendingRow`,
  валидные строки пропускает через `continue` на строках 149-151).
- **Что подтверждает проблему:** `markInvalidPendingRowsAsFailed` использует только
  `InvalidOutboxPendingRow` (`$pendingRow->rawOutboxEventId`, `$pendingRow->lastError`);
  публичные свойства `ValidOutboxPendingRow` не читаются ни в `OutboxRelay`, ни в
  `OutboxEventRepository`. В тестах их читает только парсерный
  `OutboxPendingRowTest` (`tests/Unit/Modules/Outbox/Repository/OutboxPendingRowTest.php`):
  `->status`, `->attempts->value()`, `->queuedAt->isEmpty()`, `->lastError`. Поля
  `type`, `payload`, `availableAt`, `handledAt`, `failedAt` не читаются нигде.
- **Как исправить:** свести валидную строку к факту «строка читается без ошибок».
  Варианты: возвращать из парсера только два состояния — «строка валидна» и
  «строка битая с id и ошибкой» — без сборки полного DTO; либо оставить полный
  разбор как зонд порчи, но тогда явно задокументировать, что `ValidOutboxPendingRow`
  — это маркер «строка распарсилась», и убрать из него удерживаемые поля, которые
  поведение не использует.
- **Тесты:** обновить `OutboxPendingRowTest` под выбранный контракт (например,
  проверять только различение валидной/битой строки); поведенческий тест
  восстановления в `OutboxRelayTest`/edge-тестах не меняется.

### 2. Контракт паузы relay принимает примитив, хотя для секунд паузы уже есть value object

Пауза между пустыми пачками relay выражена доменным value object, который
гарантирует минимум в одну секунду и тем самым защищает от busy-spin на пустой
очереди. Но технический контракт «поспать N секунд» и его системная реализация
принимают обычное целое число, а worker перед вызовом достаёт из value object
сырое значение и передаёт примитив. Из-за этого гарантия value object теряется на
границе контракта: реализация вынуждена сама повторно проверять «секунд больше
нуля», а любой будущий вызывающий может передать ноль или отрицательное число, и
ничто на уровне типа это не остановит.

Практический риск низкий, потому что единственный сегодняшний путь идёт через
value object. Правила проекта про «явные доменные типы вместо примитивов» scoped
на доменную модель и Entity, а этот контракт — технический системный таймер сна
процесса, поэтому это не нарушение правила, а дизайн-предпочтение по
консистентности. Дополнительно: guard `$seconds <= 0` в реализации (это не тот же
инвариант, что «минимум 1 секунда» в value object, а более слабая защита самого
вызова `\sleep()`) при текущих вызывающих недостижим — value object всегда отдаёт
значение ≥1, а `calculateRetryDelaySeconds` всегда возвращает ≥1. То есть это
недостижимая защитная ветка, которую по правилу «недостижимые ветки — удалять»
стоит либо убрать, либо обосновать как защиту будущих вызывающих.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Application/Contract/OutboxRelaySleeperContract.php:9`
  (`sleep(int $seconds)`), `app/src/Modules/Outbox/Infrastructure/SystemOutboxRelaySleeper.php:12-19`
  (повторный guard `$seconds <= 0`), `app/src/Modules/Outbox/Infrastructure/OutboxRelayWorker.php:37,48,76`
  (распаковка VO в `int` и передача примитива).
- **Что подтверждает проблему:** в `OutboxRelayWorker` есть и
  `OutboxRelaySleepSeconds` (с комментарием про запрет busy-spin), и передача
  голого `int` в `sleep()`; `SystemOutboxRelaySleeper` повторяет тот же инвариант
  guard-ом. Расчётная задержка ретраев (`calculateRetryDelaySeconds`) тоже
  возвращает `int`, который идёт в тот же примитивный контракт.
- **Как исправить:** либо принимать в контракте уже готовый
  `OutboxRelaySleepSeconds` (и завести отдельный VO/диапазон для задержки ретраев,
  если её диапазон шире паузы), чтобы гарантия минимума не терялась на границе
  контракта; либо осознанно оставить примитив как чисто системный таймер и тогда
  убрать недостижимый guard `$seconds <= 0` (или обосновать его как защиту будущих
  вызывающих). Выбор зависит от того, считается ли пауза доменным значением или
  чисто техническим параметром сна.
- **Тесты:** при переводе контракта на VO обновить `OutboxRelayWorkerTest`
  (моки/стабы `OutboxRelaySleeperContract`) под новую сигнатуру.

### 3. В target ревью попало изменение конфигурации ORM, не относящееся к Outbox

В заданном для ревью наборе изменений вместе с конфигом очередей оказался и конфиг
Cycle ORM. В нём включён нестандартный mapper по умолчанию для всех сущностей
приложения. Это изменение глобальное и не специфично для Outbox: оно влияет на
гидрацию любой entity проекта, а не только outbox-событий.

Риск здесь не в самом изменении, а в смешении областей: оно попало под ярлык
«связанные изменения Outbox», хотя на деле это отдельное инфраструктурное решение
по ORM. При раздельном коммите и ревью по областям такое изменение должно
оцениваться отдельно (влияние LazyGhost-маппера на все сущности, на schema cache и
на поведение ленивых полей), а не как часть outbox-фичи.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/config/cycle.php:25` — `SchemaInterface::MAPPER => LazyGhostMapper::class`
  (в diff вместо закомментированного дефолта).
- **Что подтверждает проблему:** `git diff HEAD -- app/config/cycle.php` содержит
  только смену mapper по умолчанию. Изменение глобальное и не outbox-специфично: оно
  меняет дефолтный mapper для всех сущностей проекта (включая `StoredOutboxEvent`,
  который тоже гидрируется этим дефолтным mapper-ом), а не только outbox. Уточнение:
  `typecast` `StoredOutboxEvent` отвечает за преобразование значений колонок, а не
  за выбор mapper, поэтому он не доказывает «вне Outbox» — доводом служит именно
  глобальность изменения.
- **Как исправить:** вынести изменение `cycle.php` в отдельный коммит/ревью с
  собственным обоснованием и проверкой влияния `LazyGhostMapper` на все сущности и
  на кэш схемы. В рамках outbox-ревью считать его вне области и не смешивать с
  оценкой модуля.
- **Тесты:** при отдельном рассмотрении — убедиться, что существующие
  feature/repository-тесты других модулей проходят с включённым LazyGhost-маппером.

### 4. Порядок очередных interceptor-ов и логика статусов держатся только на ручной синхронизации двух мест

Корректность модуля в части повторов и финальных статусов зависит от того, в каком
порядке перечислены consume-interceptor-ы в конфиге очередей. Interceptor статусов
outbox должен стоять снаружи политики ретраев, чтобы видеть уже преобразованное
исключение повтора и отличать «оставить на повтор» от «окончательно failed».
Порядок задокументирован в README модуля как шаг настройки, но README не объясняет,
что порядок критичен для корректности (именно почему статус-interceptor обязан
оборачивать политику ретраев), и ничто в коде/тестах не проверяет это требование.

Риск проявится при редактировании конфига очередей кем-то, кто не знает про эту
зависимость: перестановка interceptor-ов местами или удаление политики ретраев
тихо изменит классификацию ошибок (повтор начнёт записываться как окончательный
провал или наоборот), и это не поймает ни один тест, проверяющий outbox в
изоляции. Эффект сегодня латентен: единственный зарегистрированный Job
`OutboxDebugLogJob` не объявляет `#[RetryPolicy]` и не бросает retryable-исключение,
поэтому `RetryException` для него не создаётся и ветка `recordJobRetry` недостижима
вне зависимости от порядка; мис-классификация проявится только для будущих
retry-включённых Job. То же относится к парности записей «handler + serializer» для
каждого outbox-Job: пропуск одной из двух строк ломает доставку только в рантайме.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/config/queue.php:151-158` (порядок `ErrorHandlerInterceptor` →
  `OutboxQueueStatusInterceptor` → `RetryPolicyInterceptor`),
  `app/config/queue.php:128-143` (парность `handlers`/`serializers` для
  `OutboxDebugLogJob`), логика, зависящая от порядка —
  `app/src/Modules/Outbox/Infrastructure/OutboxQueueStatusInterceptor.php:171-212`
  (`recordJobFailure` различает `RetryException`).
- **Что подтверждает проблему:** `recordJobFailure` ветвится по
  `instanceof RetryException`; такое исключение появляется только если
  `RetryPolicyInterceptor` отработал внутри (ниже по стеку) статус-interceptor-а.
  Порядок и парность handler/serializer задокументированы в README
  (`app/src/Modules/Outbox/README.md:156-168, 180-188, 504-508`), но без объяснения,
  что порядок критичен, и без проверяемого теста; требование «один экземпляр relay»
  и контракт `RABBITMQ_VHOST` со слэшем тоже описаны в README/`.env.sample`.
- **Как исправить:** дополнить существующий раздел README рационализацией —
  явно указать, что политика ретраев должна стоять ниже (внутри) статус-interceptor-а,
  и описать ошибочную классификацию retry↔failed при обратном порядке; и/или покрыть
  требование тестом, который собирает контейнер с реальным `queue.php` и проверяет,
  что для outbox-Job статус-переходы retry/failed классифицируются верно при штатной
  конфигурации. Для парности handler+serializer — альтернатива в виде
  bootloader-уровневой регистрации пары, чтобы нельзя было добавить одну строку без
  другой.
- **Тесты:** добавить feature-тест на классификацию `RetryException` vs обычного
  исключения через реальную цепочку consume-interceptor-ов (сейчас это проверяется
  на самом interceptor-е напрямую, в обход порядка из конфига).

### 5. Recovery держится на согласованности двух независимых реализаций разбора строки

Восстановление повреждённых данных опирается на ручной парсер сырой строки
(`OutboxPendingRow::fromDatabaseRow`), а штатная выборка событий — на ORM-typecast
(`Infrastructure/Cycle/*`). Это две независимые реализации одной задачи «можно ли
разобрать строку». Если они разойдутся — например, ORM-typecast отвергнет строку,
которую ручной парсер считает валидной, — `markInvalidPendingRowsAsFailed` не
пометит такую строку failed, `failedRowsCount` останется `0`, `fetchPendingForRelay`
повторно пробросит `TypecastException`, повторная выборка снова упадёт той же
ошибкой, и relay застрянет на строке до остановки по
`MAX_CONSECUTIVE_RELAY_FAILURES`.

Риск практически низкий, пока обе реализации согласованы, но он реален и не покрыт
тестом: ничто не гарантирует, что ручной парсер и ORM-typecast принимают/отвергают
одинаковый набор строк. Это тот же класс «двух мест на ручной синхронизации», что и
замечание 4.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:37-160` (ручной
  парсер), `app/src/Modules/Outbox/Infrastructure/Cycle/*` (ORM-typecast),
  `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:104-139` (recovery,
  повторный проброс при `failedRowsCount === 0` на строках 129-131).
- **Что подтверждает проблему:** recovery считает «битой» только строку, которую
  ручной парсер вернул как `InvalidOutboxPendingRow`; строки, отвергнутые
  ORM-typecast но принятые ручным парсером, не попадают в `failedRowsCount`.
- **Как исправить:** свести разбор к одному источнику истины (например,
  переиспользовать typecast-логику в recovery), либо добавить тест, который
  фиксирует, что оба разбора согласованы на одном наборе данных.

### 6. Повреждённая строка с нестроковым `id` молча пропускается recovery

Парсер сырой строки возвращает `null`, если поле `id` не строка
(`OutboxPendingRow::fromDatabaseRow`), а репозиторий молча пропускает такие строки
при сборке коллекции pending-строк (`if ($pendingRow !== null)`), без лога и без
представления как `InvalidOutboxPendingRow`. В режиме восстановления такая строка
невидима для `markInvalidPendingRowsAsFailed`: она не попадёт в `failedRowsCount`.
Если повреждённая строка с нестроковым `id` окажется единственной причиной
`TypecastException`, recovery даст `failedRowsCount === 0` и пробросит исходное
исключение дальше — relay может зациклиться на сбое.

Практический риск низкий (`id` — это PK типа UUID, нестроковое значение в БД
маловероятно), но путь молчаливого пропуска реален и не задокументирован.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:31-35` (возврат
  `null` при нестроковом `id`),
  `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:100-104` (молчаливый
  пропуск `null`),
  `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:129-131` (повторный
  проброс при `failedRowsCount === 0`).
- **Что подтверждает проблему:** строка с нестроковым `id` не становится
  `InvalidOutboxPendingRow`, поэтому recovery не может её пометить failed.
- **Как исправить:** представлять такую строку как `InvalidOutboxPendingRow`
  (с сырым `id`, приведённым к строке, или с маркером отсутствия id) либо хотя бы
  логировать факт пропуска, чтобы recovery не молчал о неучтённой повреждённой
  строке.

### 7. `OutboxRelay::publish()` игнорирует переданное в `relay()` время

`relay()` принимает параметр `$now` и прокидывает его в этап захвата (`claimForRelay`),
но `publish()` создаёт собственное `$now = new \DateTimeImmutable()`. В результате
таймстемпы и backoff неудачной публикации (`recordPublishFailure`/`availableAt`) не
детерминированы относительно времени, переданного в `relay()`: в пределах одного
прогона захват и публикация работают с разными «текущими» моментами.

Риск не в падении, а в потере единого источника времени и в усложнении
тестируемости: тест, фиксирующий время через аргумент `relay($now)`, не управляет
временем шага публикации.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:42` (`relay()`
  принимает `$now`), `:173` (`publish()` создаёт собственное `$now`), `:205-210`
  (`recordPublishFailure`/`availableAt` от собственного времени).
- **Что подтверждает проблему:** `$now` из `relay()` доходит только до
  `claimForRelay`; в `publish()` он не передаётся.
- **Как исправить:** прокинуть `$now` из `relay()` в `publish()`, чтобы один прогон
  relay использовал единый источник времени.
