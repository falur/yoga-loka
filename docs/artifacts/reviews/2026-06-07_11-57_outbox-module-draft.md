## Замечания

### 1. `OutboxQueueStatusInterceptor` может повторно выполнить дубль Job и перезаписать финальный статус

`OutboxQueueStatusInterceptor` проверяет финальность события только до запуска Job: читает событие, вызывает `$core->callAction(...)`, а затем меняет уже загруженную Entity на `handled` или `failed`. Если в это время другой worker уже обработал тот же outbox event, текущий worker всё равно выполнит действие и сохранит статус из старого объекта.

Это опасно для внешних побочных эффектов: дубль задачи может повторно отправить письмо, push, webhook или другое внешнее действие. В тестах есть проверка случая, когда событие уже финальное до запуска Job, но нет проверки изменения статуса во время выполнения Job.

Технические детали:

- **Тип:** bug
- **Рекомендация:** править обязательно
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxQueueStatusInterceptor.php:55-76`, `app/src/Modules/Outbox/Infrastructure/OutboxQueueStatusInterceptor.php:171-191`
- **Что исправить:** перед финальным сохранением использовать повторную проверку или условное обновление статуса в репозитории, чтобы дубль не мог перезаписать уже финальное событие. Для самого внешнего действия нужен отдельный тест конкурентного изменения статуса во время `callAction`.

### 2. Инструкция подключения Outbox заставляет другие модули зависеть от `Infrastructure` Outbox

README показывает, что Job другого модуля должна принимать `OutboxQueueEnvelope` из `App\Modules\Outbox\Infrastructure`, а bootloader другого модуля должен инжектить `OutboxJobRegistry` из того же слоя. По архитектуре другие модули могут обращаться только к `Application` другого модуля, а `Infrastructure` остаётся внутренней технической деталью.

Из-за этого расширение Outbox новыми сообщениями закрепляет межмодульную зависимость на внутренние классы Outbox. При изменении транспорта очереди или registry ломаться будут внешние модули.

Технические детали:

- **Тип:** architecture
- **Рекомендация:** править обязательно
- **Где:** `app/src/Modules/Outbox/README.md:245-303`, `app/src/Modules/Outbox/README.md:314-346`, `app/src/Modules/Outbox/Infrastructure/OutboxJobRegistry.php`
- **Что исправить:** вынести внешний контракт регистрации и envelope в `Application` или дать другой Application-level способ подключать сообщения и загружать payload, чтобы внешние модули не импортировали `Infrastructure` Outbox.

### 3. `OutboxMessage` закрепляет ассоциативный массив как публичный контракт payload

`OutboxMessage` наследует `JsonSerializable`, а README требует от сообщений ручной `jsonSerialize(): array`. Для модульного Application-контракта это протаскивает наружу массивный формат payload и ручное описание ключей, хотя правила проекта требуют DTO и запрещают ассоциативные массивы в публичных контрактах.

Технические детали:

- **Тип:** rules
- **Рекомендация:** править обязательно
- **Где:** `app/src/Modules/Outbox/Application/Message/OutboxMessage.php`, `app/src/Modules/Outbox/Application/Message/OutboxDebugLogMessage.php:16-26`, `app/src/Modules/Outbox/README.md:219-237`
- **Что исправить:** сделать сообщение обычным типизированным DTO без обязательного `jsonSerialize()`, а сериализацию оставить инфраструктурному сериализатору.

### 5. Рабочее дерево Outbox находится в противоречивом состоянии после переноса файлов

В `git status --short` для старых Outbox-путей есть `AD`, а для новых путей — `??`. Это означает, что часть файлов была добавлена в индекс, потом удалена в рабочем дереве, а новые пути пока не добавлены. Для ревью это риск: `git diff HEAD` показывает удаление старых файлов, но не показывает содержимое новых untracked-файлов без отдельного чтения.

Технические детали:

- **Тип:** process
- **Рекомендация:** править обязательно
- **Где:** текущий `git status --short` по `app/src/Modules/Outbox` и `tests/Unit/Modules/Outbox`
- **Что исправить:** привести индекс и рабочее дерево к цельному состоянию перед финальным ревью или коммитом, чтобы target был однозначным.

### 6. Часть тестов Outbox привязана к приватным деталям через Reflection

Несколько тестов читают или вызывают приватные детали через Reflection. Это не ломает поведение сейчас, но делает тесты хрупкими: внутренний рефакторинг может ломать тест без изменения публичного поведения.

Технические детали:

- **Тип:** quality
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Outbox/Console/OutboxRelayCommandTest.php:105-149`, `tests/Feature/Modules/Outbox/Repository/OutboxEventRepositoryTest.php:214-288`, `tests/Unit/Modules/Outbox/Infrastructure/OutboxInfrastructureEdgeTest.php:112-124`, `tests/Feature/Modules/Outbox/Infrastructure/OutboxRelayPublishTest.php:81-90`
- **Что исправить:** по возможности проверять поведение через публичные методы, БД, очередь или явные тестовые заменители, а Reflection оставить только там, где публичной проверки реально нет.
