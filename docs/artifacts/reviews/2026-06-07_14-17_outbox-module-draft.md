## Замечания

### 1. Debug-Job делает действие сам, минуя Application Handler — и это расходится с собственным README модуля

Архитектура проекта описывает Job очереди как тонкий технический адаптер: он принимает payload, собирает Application Command и отправляет его в Application Handler, где и живёт сценарий. Собственный README этого модуля повторяет то же правило и даже показывает эталонный `SendWelcomeEmailJob`, который грузит сообщение и диспатчит команду через `CommandBusInterface`.

Реальный `OutboxDebugLogJob` так не делает: он сам грузит сообщение через loader и сам пишет лог прямо в Job, без Command и Handler. При этом раздел README «Как читать сообщение внутри Job» прямо ссылается на этот же Job как на пример правильного подхода и утверждает, что «Application Handler получает уже готовую команду» — хотя никакого Handler у debug-сценария нет. Получается внутреннее противоречие: документация описывает один поток, эталонный встроенный Job реализует другой.

Практический риск проявится, когда по этому встроенному примеру начнут писать реальные Job (email, push, Centrifugo): команда скопирует «как у debug» и протащит бизнес-логику в слой очереди, обойдя CQRS-шину, транзакционные и лог-атрибуты Handler-а. Удалённые из рабочего дерева `ProcessOutboxDebugLogMessageCommand`/`ProcessOutboxDebugLogMessageHandler` как раз были этим Application-слоем, поэтому их удаление нельзя считать исправлением — оно усилило расхождение.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Presentation/Job/OutboxDebugLogJob.php:15-31`; для сравнения — `app/src/Modules/Outbox/README.md:240-301` (эталонный `SendWelcomeEmailJob` через `CommandBusInterface`) и `app/src/Modules/Outbox/README.md:475-487` («Application Handler получает уже готовую команду» со ссылкой на debug-Job); `docs/arch.md:354-366` («Поток задачи очереди»).
- **Что подтверждает проблему:** в `OutboxDebugLogJob::invoke()` нет `CommandBusInterface`/Handler — есть только `OutboxMessageLoaderContract` и `LoggerInterface`, и действие (логирование) выполняется прямо в Job. В индексе при этом числятся как `AD` (добавлены в индекс, удалены из дерева) файлы `app/src/Modules/Outbox/Application/Command/ProcessDebugLogMessage/ProcessOutboxDebugLogMessageCommand.php` и `ProcessOutboxDebugLogMessageHandler.php`.
- **Как исправить:** либо вернуть/переписать Application Command + Handler для debug-сценария и оставить Job тонким адаптером (загрузить сообщение → создать команду → отправить через `CommandBusInterface`), как в эталоне README; либо, если для встроенного debug-примера осознанно решено держать действие в Job, явно описать это исключение в README и `docs/arch.md` и убрать из README ссылку на debug-Job как на образец «Job → Application Handler». Текущее состояние (код противоречит документации) оставлять нельзя.
- **Тесты:** обновить `tests/Unit/Modules/Outbox/Presentation/Job/OutboxDebugLogJobTest.php` под выбранный вариант — либо проверка делегирования в Handler через шину, либо явная фиксация выбранного исключения.

### 2. Доменный метод `StoredOutboxEvent::markQueued()` не вызывается из боевого кода

Сущность outbox содержит метод перехода в статус «queued», но в продакшен-коде его никто не вызывает: реальный переход publishing → queued выполняется атомарным CAS-апдейтом в репозитории (`markQueuedIfPublishing`), а не доменным методом. Метод остаётся только потому, что на него есть прямые вызовы из тестов.

Это мёртвый код по правилу проекта «Нет мёртвого кода». Риск практический: метод даёт ложное ощущение, что переход в queued — это доменная операция сущности, хотя источник правды по этому переходу — условный UPDATE в репозитории. Будущий разработчик может вызвать `markQueued()` в новом сценарии и получить неатомарный переход без CAS-защиты от гонок, который relay специально обходит.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Domain/Entity/StoredOutboxEvent.php:110-116`; реальный переход — `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:139-153`.
- **Что подтверждает проблему:** поиск по `app/src` находит `markQueued(` только в определении метода; все вызовы — в `tests/`.
- **Как исправить:** удалить метод `markQueued()` вместе с его прямыми тестами; если он нужен как часть доменного API на будущее, обосновать это явно и связать с реальным сценарием.
- **Тесты:** удалить прямые проверки `markQueued()` в `OutboxEventRepositoryTest` и фикстуре `OutboxQueueStatusInterceptorTestHelpers`; покрытие перехода в queued уже обеспечивает тест `markQueuedIfPublishing`.

### 3. VO-метод `OutboxAvailableAt::isAvailableAt()` не используется в боевом коде

Value object `OutboxAvailableAt` имеет метод-предикат «доступно ли событие сейчас», но боевой код этим методом не пользуется: проверка доступности события для relay делается через условие `available_at <= now` прямо в запросе репозитория, а не через VO. Метод существует только ради собственного unit-теста.

Это тоже мёртвый код, и правило проекта «Нет мёртвого кода» безусловно («неиспользуемые... — удалять»), поэтому формально это такое же нарушение, как в пункте 2, — отсюда и рекомендация «править обязательно». Runtime-риск ниже, чем у `markQueued()` (предикат чистый, без побочных эффектов), но логика дублирующая и неиспользуемая: рядом с реальным критерием в SQL есть второй критерий «доступности». Если кто-то начнёт принимать решение о доступности через VO, поведение может разъехаться с фактической выборкой relay (например, по границе равенства или по точности времени).

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Outbox/Domain/ValueObject/OutboxAvailableAt.php:23-26`; фактический критерий доступности — `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:88` и `:205` (`where('available_at', '<=', $now)`).
- **Что подтверждает проблему:** `isAvailableAt` встречается только в определении и в `tests/Unit/Modules/Outbox/Domain/OutboxValueObjectTest.php:138-140`; в `app/src` вызовов нет.
- **Как исправить:** удалить метод и его unit-проверки; либо, если предикат планируется использовать в relay как единый критерий доступности, перевести выборку на него и связать с репозиторием.
- **Тесты:** убрать соответствующие ассерты в `OutboxValueObjectTest`.

### 4. Ключи транспортного payload очереди заданы дважды

`outboxId` и `outboxType` — это один транспортный контракт очереди (и в заголовках, и в JSON-payload). Сейчас он задан в двух местах: публичными константами в `OutboxQueueHeaders` и отдельными приватными константами с теми же строками в `OutboxQueueSerializer`. Совпадение значений держится только на том, что обе строки написаны одинаково.

Риск проявится при правке контракта: если кто-то поменяет ключ в одном классе (например, заголовок), а во втором (JSON-payload) забудет, headers и payload начнут использовать разные ключи. Это тихо сломает сверку «header vs payload» в `OutboxQueueStatusInterceptor` и распознавание outbox-задачи. Пункт уже отмечался в предыдущей итерации ревью и пока не закрыт.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxQueueSerializer.php:14-15` (приватные `OUTBOX_ID`/`OUTBOX_TYPE`) и `app/src/Modules/Outbox/Infrastructure/OutboxQueueHeaders.php:9-10` (публичные `OUTBOX_ID`/`OUTBOX_TYPE`). Интерцептор уже строит payload по `OutboxQueueHeaders::OUTBOX_ID`/`OUTBOX_TYPE` (`OutboxQueueStatusInterceptor.php:163-175`), а сериализатор читает его по `self::OUTBOX_ID`/`self::OUTBOX_TYPE` — то есть один поток уже опирается на оба источника одновременно.
- **Что подтверждает проблему:** обе строки `'outboxId'`/`'outboxType'` объявлены независимо в двух классах.
- **Как исправить:** оставить единый источник имён ключей (например, публичные константы `OutboxQueueHeaders`) и переиспользовать их в `OutboxQueueSerializer`, если это не размывает ответственность сериализатора.
- **Тесты:** существующие тесты сериализатора и headers должны продолжать проходить без изменений.

### 5. В индексе остались «висящие» файлы удалённого debug Application-слоя

Два файла удалённого debug Command/Handler находятся в состоянии `AD`: они добавлены в индекс, но удалены из рабочего дерева. Это технический «хвост» предыдущих итераций, не относящийся к самому коду модуля, но он влияет на то, что попадёт в коммит: если коммитить из текущего индекса, в историю войдёт добавление файлов, которых уже нет на диске.

Это не баг рантайма, но перед фиксацией среза состояние индекса стоит привести к рабочему дереву, иначе коммит будет содержать противоречивый набор изменений. Пункт связан с замечанием 1: итоговое решение по debug Application-слою определит, должны эти файлы вернуться или окончательно исчезнуть.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `git status --short` → `AD app/src/Modules/Outbox/Application/Command/ProcessDebugLogMessage/ProcessOutboxDebugLogMessageCommand.php` и `...ProcessOutboxDebugLogMessageHandler.php`.
- **Что подтверждает проблему:** статус `AD` означает рассинхрон индекса и рабочего дерева по этим путям.
- **Как исправить:** после решения по замечанию 1 привести индекс к рабочему дереву (вернуть файлы либо снять их из индекса), чтобы `git status --short` не показывал `AD` по debug-handler-ам.
- **Тесты:** не требуется; достаточно проверки `git status --short` перед коммитом.
