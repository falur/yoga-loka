## Замечания

### 1. Иерархия «дат события» осталась единственным семейством VO модуля без строкового представления

Внутри модуля выдержана единая конвенция: простые скалярные value object умеют приводиться к строке —
строковые `OutboxEventType`, `OutboxLastError`, `OutboxEventPayload` реализуют `\Stringable` напрямую,
числовые и идентификаторы наследуют его от общих базовых классов, а `OutboxAvailableAt` в прошлой итерации
специально довели до этой же конвенции. Из общего ряда выпадает только семейство «дат события»: абстрактный
тип-обёртка времени и его «известный» вариант не объявляют строкового представления, хотя «известный»
вариант уже умеет отдавать дату в формате ATOM при сериализации в JSON.

Само по себе это не ломает рантайм: к строке эти объекты сейчас нигде не приводят. Но это именно та
неоднородность, которую цикл доводки последовательно вычищает — после правки `OutboxAvailableAt` данное
семейство стало единственным исключением. Риск практический и отложенный: когда кто-то по аналогии с
остальными VO напишет `(string) $event->queuedAt` (например, в логе или сообщении об ошибке), он получит
ошибку времени выполнения вместо ожидаемой строки.

Прошлая итерация осознанно вынесла этот случай за рамки обязательной правки из-за нюанса: «пустой» вариант
даты — это null-объект без естественного строкового представления, поэтому единый `__toString()` на всей
иерархии требует осмысленного решения для пустого случая (например, пустая строка, как уже делает
`jsonSerialize()` пустого варианта). Решение остаётся за автором, поэтому пункт — на усмотрение.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Domain/ValueObject/OutboxEventDate.php:7`
  (`abstract readonly class OutboxEventDate implements \JsonSerializable` — без `\Stringable`),
  `app/src/Modules/Outbox/Domain/ValueObject/KnownOutboxEventDate.php` (нет `__toString()`),
  `app/src/Modules/Outbox/Domain/ValueObject/EmptyOutboxEventDate.php` (`jsonSerialize()` уже отдаёт `''`
  для пустого варианта).
- **Что подтверждает проблему:** правило ValueObject в `docs/rules.md` для простого скалярного VO требует
  набор `readonly`, `Stringable`, `JsonSerializable`; `KnownOutboxEventDate::jsonSerialize()` отдаёт
  `format(\DateTimeInterface::ATOM)`, то есть безопасное строковое представление у «известной» даты есть;
  остальные скалярные VO модуля Stringable. Этот же пункт зафиксирован как «смежно (на усмотрение)» в
  ревью iter2 (`docs/reviews/2026-06-07_15-10_outbox-module-draft-iter2.md`, замечание №4) и пока не
  применён.
- **Как исправить:** объявить на абстракции `OutboxEventDate` `implements \JsonSerializable, \Stringable`
  и добавить `__toString()` в оба наследника: в `KnownOutboxEventDate` вернуть ATOM (как
  `jsonSerialize()`), в `EmptyOutboxEventDate` — пустую строку (как его `jsonSerialize()`), чтобы
  поведение совпало с уже существующей JSON-сериализацией. Либо осознанно оставить семейство без
  `\Stringable` (это составной/иерархический VO с null-объектом, а не простой скаляр) и зафиксировать
  это решение коротким комментарием, чтобы пункт не всплывал в следующих итерациях.
- **Тесты:** при добавлении `__toString()` — расширить `tests/Unit/Modules/Outbox/Domain/OutboxValueObjectTest.php`
  проверкой `(string) $knownDate` и `(string) $emptyDate` на совпадение с их `jsonSerialize()`.

### 2. Выборка pending-событий сортирует по `id`, а индекс заточен под другой порядок ключей

Relay выбирает события по двум критериям — статус из набора pending/publishing и наступивший
`available_at` — и упорядочивает их по идентификатору по возрастанию (UUID v7 хронологически сортируем).
Под эту выборку в миграции создан составной индекс, но порядок колонок в нём — `status`, `available_at`,
`id`, тогда как сортировка идёт только по `id`. Из-за этого индекс хорошо отбирает строки по статусу и
времени, но не отдаёт их уже в нужном порядке: на стороне БД остаётся отдельная сортировка выбранного
набора.

Риск низкий и проявляется только под нагрузкой: на большом backlog pending-событий и маленьком batch
size планировщику PostgreSQL придётся отсортировать промежуточный набор перед `LIMIT`, вместо того чтобы
взять первые строки напрямую из индекса. Это не ошибка корректности — relay всё равно вернёт правильную
пачку, — а вопрос эффективности горячего пути выборки, который в постоянном режиме выполняется в цикле.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** индекс — `app/database/migrations/20260525.153700_0_create_outbox_events_table.php:29`
  (`->addIndex(['status', 'available_at', 'id'])`); запросы — `OutboxEventRepository.php:198-208`
  (`pendingForRelayEventsQuery`: `where('status','in',...)->where('available_at','<=',$now)->orderBy('id','ASC')->forUpdate()`)
  и `OutboxEventRepository.php:66-104` (`pendingForRelayRows`: тот же фильтр + `orderBy('id','ASC')`).
- **Что подтверждает проблему:** оба запроса фильтруют по `status IN (...)` и `available_at <= now`, но
  сортируют по `id`, а не по `available_at`. Индекс `(status, available_at, id)` упорядочивает строки
  внутри статуса по `available_at`, затем по `id`, поэтому для `ORDER BY id` он не даёт готового порядка;
  фильтр по диапазону `available_at` дополнительно мешает использовать `id`-часть индекса как сортирующую.
- **Как исправить:** определить, что является намеренным порядком обработки. Если порядок «по времени
  доступности» (что естественно для relay) — поменять `orderBy` обоих запросов на `available_at` (с
  `id` как tie-breaker), это лучше согласует сортировку с порядком колонок индекса. Учесть нюанс: при
  `status IN (...)` по нескольким значениям и диапазоне по `available_at` PostgreSQL всё равно может не
  отдать полностью готовый порядок из одного прохода индекса (понадобится merge/частичная сортировка),
  поэтому реальный выигрыш стоит подтвердить через `EXPLAIN` на представительном объёме. Если порядок «по
  возрасту события» (по `id`) важен сознательно — рассмотреть индекс `(status, id)` под этот доступ или
  оставить как есть, признав сортировку допустимой ценой. Решение зависит от ожидаемого объёма backlog и
  принимается автором.
- **Тесты:** существующие тесты выборки (`OutboxRelayTest`, `OutboxEventRepositoryTest`) проверяют
  содержимое пачки и не зависят от плана запроса; при смене `orderBy` достаточно убедиться, что они
  по-прежнему проходят. Отдельный тест на план запроса не нужен.

### 3. В рабочем дереве остался незакоммиченный «хвост» тест-хелпера

Часть свежей правки тест-хелпера (тот самый фикс stale-heap через `cleanOrmState()`) лежит в рабочем
дереве как незакоммиченное изменение поверх уже застейдженной версии того же файла. То есть один и тот же
файл хелпера одновременно есть и в индексе (старая версия), и в рабочем дереве (с добавленным
`cleanOrmState()`).

Это не дефект кода и не влияет на поведение модуля, но влияет на то, что попадёт в коммит: при фиксации
из текущего индекса свежая правка хелпера в коммит не войдёт, и набор изменений окажется неполным
относительно того, что реально проверялось в этой итерации. Перед коммитом состояние индекса по этому
файлу стоит привести к рабочему дереву.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `git status` → `Changes not staged for commit: modified
  tests/Feature/Modules/Outbox/Infrastructure/Fixture/OutboxQueueStatusInterceptorTestHelpers.php`
  (тот же путь одновременно числится и в staged-изменениях).
- **Что подтверждает проблему:** `git diff` (unstaged) по этому файлу показывает добавление метода
  `cleanOrmState()` и его вызова в `persistQueuedEvent()`, которых нет в застейдженной версии.
- **Как исправить:** перед коммитом добавить файл в индекс (`git add` по этому пути), чтобы фикс
  stale-heap вошёл в коммит целиком.
- **Тесты:** не требуется; достаточно проверки `git status` перед коммитом.
