## Замечания

### 1. Recovery считает повреждённую строку обработанной, даже если её не удалось пометить failed

В relay есть защита от «отравленной» строки: если обычная выборка pending-событий падает на гидрации
повреждённой записи, relay переходит в восстановление, читает сырые строки, находит битые и помечает их
`failed`, после чего повторяет выборку уже без них. Логика опирается на счётчик: «сколько битых строк я
пометил». Если счётчик больше нуля — relay считает, что прогресс есть, и делает повторную выборку.

Проблема в том, что счётчик увеличивается на каждую распознанную битую строку безусловно, а не по факту
реально применённого изменения в БД. Пометка failed выполняется условным обновлением «обнови, только если
строка ещё pending/publishing и её id совпадает», и это обновление может не затронуть ни одной строки. Сам
контракт recovery при этом построен на ложной предпосылке «создал объект битой строки — значит, пометил её в
БД». Если условное обновление не затронуло строку, relay всё равно считает, что пометил битую запись, делает
повторную выборку, снова падает на той же записи, и это второе падение уже не перехватывается локальным
восстановлением — оно всплывает в общий обработчик ошибок цикла. В итоге «отравленная» запись не вычищается
никогда, а relay в постоянном режиме монотонно тратит лимит подряд идущих ошибок и в конце концов
останавливает цикл.

Важно честно оценить достижимость на текущей схеме. На сегодняшней структуре таблицы основной сценарий
расхождения «распознал, но не пометил» фактически недостижим:

- Колонка `id` объявлена `uuid NOT NULL`, поэтому PostgreSQL почти всегда отдаёт её строкой, а ветка
  «нестроковый id → `get_debug_type()`» (`OutboxPendingRow::rawIdToString`) на реальной строке БД не
  срабатывает; unit-тест `testNonScalarIdBecomesInvalidRowWithTypeName` проверяет этот код только в изоляции,
  не через настоящую выборку.
- Для всех остальных причин порчи (битый payload, дата, attempts и т.п.) `InvalidOutboxPendingRow.rawOutboxEventId`
  хранит настоящий строковый id строки, поэтому CAS-обновление матчит её и счётчик не расходится с фактом. Это
  поведение уже зафиксировано тестом `testManualParserAndOrmTypecastAgreeOnSameRows`
  (`failedRowsCount` не останется 0) и `testRelaySecondRunDoesNotRecaptureFailedInvalidRow` (битая строка
  реально переходит в failed).

Поэтому это не активный баг на текущей схеме, а хрупкость контракта recovery с одним реально достижимым уже
сейчас окном — гонка статуса между чтением сырых строк и CAS-записью (между ними нет блокировки строки), когда
строку успели перевести из pending/publishing: тогда CAS затронет 0 строк, а `failedRowsCount` всё равно
вырастет. Любой будущий сценарий, где условное обновление не затрагивает строку (другая первопричина порчи,
иной тип хранения id, ручная правка статуса), вернёт relay в тот же необслуживаемый цикл. Поэтому критерий
прогресса стоит привязать к фактическому числу обновлённых строк, а не к числу распознанных — это дешёвая
страховка, снимающая и текущую гонку, и будущие регрессии.

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:142-169`
  (`markInvalidPendingRowsAsFailed`: `$failedRowsCount++` на строке 158 — безусловно, для каждого
  `InvalidOutboxPendingRow`); `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:117-138`
  (`markRowFailedById` — условный `UPDATE ... WHERE id = ? AND status IN (pending, publishing)`,
  возвращает `void`, число затронутых строк наружу не отдаёт);
  `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:31-41,76-83`
  (`rawIdToString` для нестрокового id отдаёт `get_debug_type($rawId)`, который не совпадёт с реальным
  `uuid`-id строки).
- **Что подтверждает проблему:** в `OutboxRelay::fetchPendingForRelay` (строки 129-138) критерий выхода из
  recovery — `if ($failedRowsCount === 0) { throw $exception; }`, то есть `failedRowsCount > 0`
  безоговорочно ведёт к повторной выборке `findPendingForRelay`, которая на не вычищенной строке снова
  бросит `TypecastException`; этот второй вызов находится вне `try`, поэтому исключение пробрасывается в
  `claimForRelay` → `relay()` → `OutboxRelayWorker::runLoop` catch. `markRowFailedById` число затронутых
  строк не возвращает, и `markInvalidPendingRowsAsFailed` его не проверяет.
- **Как исправить:** вернуть из `markRowFailedById` число затронутых строк (`->run()` Cycle Database
  Query Builder отдаёт affected rows, как уже сделано в `markQueuedIfPublishing`) и увеличивать
  `failedRowsCount` только когда обновление реально затронуло строку. Тогда «отравленная» строка, которую
  не удалось пометить, не будет учтена как прогресс, и relay отдаст исходную ошибку гидрации в общий
  обработчик с понятной первопричиной, а не зациклится на повторных выборках. Дополнительно стоит решить,
  что делать с битой строкой, чей id вообще не матчится (например, отдельный лог-WARN «не смог пометить
  битую строку failed» с первопричиной), чтобы инцидент был виден, а не молча копился до остановки цикла.
- **Тесты:** recovery уже частично покрыт (`testRelayMarksInvalidPendingRowAsFailedAndKeepsProcessingValidEvents`,
  `testRelaySecondRunDoesNotRecaptureFailedInvalidRow`, `testManualParserAndOrmTypecastAgreeOnSameRows`), но
  нет кейса на расхождение «распознал, но CAS затронул 0 строк». При выносе фикса добавить в
  `tests/Feature/Modules/Outbox/Infrastructure/OutboxRelayTest.php` (или рядом) кейс «recovery не смог
  пометить битую строку (CAS затронул 0 строк) → relay не зацикливается на повторной выборке, а отдаёт
  исходную ошибку наверх»; проверить, что `markRowFailedById` на несовпадающем id даёт 0 затронутых строк и
  `failedRowsCount` не растёт.

### 2. Тайминги claim-lease и publish-backoff остались зашитыми константами, хотя соседние relay-пороги вынесены в конфиг

В прошлой итерации relay-пороги (лимит подряд идущих ошибок цикла, база и потолок экспоненциальной паузы)
осознанно вынесли в `OutboxConfig` и env, чтобы их можно было настраивать под окружение без правки кода.
При этом два других временны́х параметра самого relay — срок «аренды» захваченного события (после которого
упавший процесс отпускает событие обратно в выборку) и пауза перед повтором после неудачной публикации —
остались жёстко зашитыми константами по 60 секунд прямо в классе relay.

Само по себе это не баг: значения разумные, а рядом есть подробный комментарий, почему две константы
намеренно держат раздельно. Но это заметная неоднородность ровно того же класса, что цикл доводки уже
вычищал: часть relay-таймингов конфигурируема через env, а часть — нет, без видимой причины именно для этих
двух. На практике это проявится, когда на каком-то окружении понадобится другой срок аренды (например,
долгие push-операции, где 60 секунд мало) или другой backoff — это потребует изменения кода и релиза вместо
правки переменной окружения.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:30-31`
  (`CLAIM_TIMEOUT_SECONDS = 60`, `PUBLISH_RETRY_DELAY_SECONDS = 60`), используются на строках 53 и 206;
  для сравнения — уже вынесенные в конфиг пороги `app/src/Shared/Infrastructure/Configuration/Outbox/OutboxConfig.php:18-20`
  (`maxConsecutiveRelayFailures`, `baseRelayRetryDelaySeconds`, `maxRelayRetryDelaySeconds`) и
  `app/config/outbox.php:7-9`.
- **Что подтверждает проблему:** три relay-порога читаются из `OutboxConfig`/env, а два relay-тайминга —
  локальные `private const int`; оба класса параметров относятся к настройке поведения одного и того же
  relay в постоянном режиме.
- **Как исправить:** либо добавить два поля в `OutboxConfig`/`app/config/outbox.php`/`.env.sample`
  (`OUTBOX_CLAIM_TIMEOUT_SECONDS`, `OUTBOX_PUBLISH_RETRY_DELAY_SECONDS`) с `\max(1, ...)`-нормализацией,
  как у остальных, и пробросить их в `OutboxRelay` через конструктор, обернув в доменные VO секунд; либо
  осознанно оставить как константы и коротко зафиксировать решение в комментарии/README, чтобы пункт не
  всплывал в следующих итерациях. Если выносить — учесть, что claim-lease и backoff имеют разный
  доменный смысл (комментарий на строках 24-29), поэтому это две независимые настройки, а не одна.
- **Тесты:** при выносе в конфиг — расширить тест маппинга `OutboxConfig` (по аналогии с
  `tests/Unit/Shared/Infrastructure/Configuration/...`) новыми полями и при необходимости подкорректировать
  `ConfigShapeTest`. Если оставить константами — тесты не нужны.

### 3. Relay перечитывает свежий статус события из БД на каждой публикации даже вне sync-режима

При публикации каждого события relay в случае ошибки push проверяет, не записала ли уже ошибку синхронная
Job (sync-драйвер выполняет Job прямо в момент push, и тогда статус мог измениться). Проверка устроена
аккуратно — сначала смотрит, sync ли соединение, и только потом идёт в БД. Но на горячем пути это всё равно
дополнительное условие и потенциальный запрос на каждое событие пачки, и его легко случайно «утяжелить»
будущей правкой.

Это не дефект и не нарушение правил: запрос делается только в ветке ошибки и только при sync-соединении,
которое в проде не используется (прод — RabbitMQ). Замечание скорее про читаемость и про то, чтобы намерение
«это нужно только sync-драйверу» оставалось явным и не размывалось. Риск практический минимальный, поэтому
пункт на усмотрение.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxRelay.php:234-241` (`syncJobAlreadyRecordedFailure`)
  и `app/src/Modules/Outbox/Infrastructure/OutboxQueueStatusInterceptor.php:240-255` (`freshEventIsFinal`)
  — оба ходят в `OutboxEventRepository::findFreshStatusById`.
- **Что подтверждает проблему:** `findFreshStatusById` выполняет отдельный `SELECT status ... LIMIT 1` в
  обход identity map; в relay он вызывается из обработки ошибки каждого события, в interceptor — из
  пред/постобработки каждой Job. Для штатного async-пути (RabbitMQ) дополнительный SELECT в relay не нужен,
  и он отсекается ранним возвратом по `usesSyncConnection()` — то есть текущая реализация корректна, вопрос
  только в наглядности гарантии.
- **Как исправить:** оставить как есть (поведение верное) либо добавить короткий комментарий у
  `syncJobAlreadyRecordedFailure`, что лишний SELECT возможен только для sync-драйвера и в проде не
  выполняется, чтобы будущая правка не вынесла проверку статуса за пределы sync-гарда.
- **Тесты:** не требуется; существующие тесты relay/interceptor покрывают обе ветки.
