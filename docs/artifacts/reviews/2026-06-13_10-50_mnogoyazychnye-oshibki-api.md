# Ревью: Многоязычные ошибки API — перевод на границе + выбор языка по Accept-Language

## Оценка

**86/100.** Фича реализована целостно и соответствует архитектуре: перевод 4xx один раз на
границе, выбор локали по `Accept-Language` через middleware, типизированный конфиг, тесты на
все ветки. Замечания касаются мелкого мусора в артефактах (журнал выполнения и рабочий файл
`todo`, попадающие в коммит), недостающего каталога для одного из мигрированных исключений и
нескольких спорных деталей качества, которые стоит зафиксировать осознанно.

## Проблемы сверки с планом

Реализация в целом покрывает все 4 цели плана: исключения несут ключ+параметры, перевод на
границе, `LocaleMiddleware` из `Accept-Language ∩ supported → default`, каталоги заполнены,
гейт зелёный (по журналу — 424 теста, покрытие 100%). Ниже — только отклонения, которые важно
держать в поле зрения.

### 1. Дизайн перевода ушёл от «единого домена messages» к доменам по модулям — отклонение от плана, согласованное постфактум

План фиксировал интерфейс `TranslatableException` всего с двумя методами (`translationKey()` +
`translationParameters()`) и единый каталог `messages.php` с ключами `app.media.*`/`app.system.*`.
В коде интерфейс получил третий метод `translationDomain()`, а каталоги разбиты на
`media.php`/`system.php`, и интерсептор передаёт домен в `trans()`. Это более крупное изменение
публичного контракта пакета и структуры каталогов, чем описывал план.

Само по себе это не баг: журнал выполнения (шаги 5–6) явно помечает это как «дополнение по
запросу пользователя», `arch.md` обновлён под новую модель, тесты покрывают вывод домена из ключа.
Риск тут не в коде, а в рассинхроне артефактов: план остался описывать старую модель (раздел
«API и внешние контракты» и листинг интерфейса в плане показывают двухметодный интерфейс и
`messages.php`), поэтому при чтении одного только плана картина будет неверной. Это стоит держать
в голове, если по плану будут сверяться другие задачи или ревью.

Технические детали:

- **Статус:** отклонение (согласовано постфактум)
- **Где:** `packages/spiral-api-errors/src/Exception/TranslatableException.php` (3-й метод
  `translationDomain()`); `app/locale/{ru,en}/{media,system}.php` вместо `messages.php`;
  план `docs/plans/2026-06-11_22-30_mnogoyazychnye-oshibki-api.md:149-160,226-247`
- **Что подтверждает проблему:** журнал `docs/executions/2026-06-11_22-56_...md` шаги 5–6 фиксируют
  отклонение как одобренное пользователем; `arch.md:344-388` уже описывает доменную модель, а
  файл плана — нет.
- **Как исправить:** правок в коде не требуется. Опционально — дописать в план краткую пометку
  «контракт расширен `translationDomain()`, каталоги разбиты по модулям (см. журнал, шаги 5–6)»,
  чтобы план не вводил в заблуждение при последующей сверке.

### 2. `AuthenticationException` мигрирован, но каталога для домена `auth` нет — при первом реальном выбросе пользователь увидит сырой ключ

`AuthenticationException` теперь переводимый и в юнит-тесте сконструирован с ключом
`app.auth.required`, который выводит translation-домен `auth`. При этом файлов `app/locale/{ru,en}/auth.php`
не существует (исключение сейчас нигде в проде не бросается, что соответствует плану). Практический
риск проявится позже: когда кто-то впервые бросит `AuthenticationException('app.auth.required')`,
перевод молча вернёт сам ключ `app.auth.required` в теле ответа 401 — без ошибки, без падения теста,
просто пользователь получит технический ключ вместо текста. Такой регресс легко не заметить.

Это пограничный случай между «не править» и «на усмотрение»: в рамках текущей задачи исключение не
используется, поэтому формально всё корректно. Но это скрытая ловушка для следующей задачи по auth.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `tests/Unit/Shared/Domain/Exception/ApiDomainExceptionTest.php:35` (`app.auth.required`),
  `app/src/Shared/Domain/Exception/AuthenticationException.php`; каталогов `app/locale/*/auth.php` нет.
- **Что подтверждает проблему:** `translationDomain()` для `app.auth.required` вернёт `auth`, а
  каталога `auth.php` нет → `Translator::trans` отдаст сам ключ (поведение задокументировано тестом
  `testTranslatableExceptionWithoutCatalogueEntryReturnsKeyItself` в пакете).
- **Как исправить:** либо завести заглушку `app/locale/{ru,en}/auth.php` (даже с одним ключом
  `app.auth.required`), либо явно оставить как есть и завести задачу-напоминание на момент
  внедрения auth. Поскольку auth-флоу в проекте пока нет, заводить каталог сейчас не обязательно.
- **Тесты:** при добавлении каталога — короткий ассерт перевода ключа `app.auth.required` в ru/en;
  иначе тест не нужен.

### 3. `FakeTranslator` перестал быть `readonly` ради спая `lastDomain` — приемлемо для теста, но стоит понимать побочный эффект

Тестовый дублёр `FakeTranslator` лишился `readonly`-класса: добавлено публичное мутабельное
свойство `$lastDomain`, которое перезаписывается в `trans()`. Это сделано, чтобы один тест мог
проверить, какой домен интерсептор передал в переводчик. Запись в свойство внутри метода,
который по смыслу «только переводит», — лёгкий запах, но это изолированный тестовый fake, новый
инстанс на каждый тест, гонок нет.

Риск минимальный и проявится только если кто-то начнёт переиспользовать один и тот же инстанс
`FakeTranslator` между ассертами и забудет, что `lastDomain` хранит состояние последнего вызова.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `packages/spiral-api-errors/tests/Support/FakeTranslator.php:10,12,38`
- **Что подтверждает проблему:** класс был `final readonly`, стал `final` с публичным
  мутабельным `string|null $lastDomain`, присваивание в `trans()` (строка 38). При снятии
  `readonly` с класса конструкторные свойства `$locale`/`$messages` явно получили
  пер-property `readonly` — мутабельным стал только `$lastDomain`, то есть это минимальный
  diff для спая, а не «весь класс стал мутабельным».
- **Как исправить:** оставить как есть — для тестового спая это нормальный паттерн. Если хочется
  строже — фиксировать переданный домен через `createMock` с `expects()->with()` вместо мутабельного
  поля, но это усложнит существующий стиль fake-ов пакета без реальной выгоды.
- **Тесты:** не требуется.

### 4. `translationDomain()` берёт второй сегмент ключа без валидации формата ключа

Вывод домена `\explode('.', $key)[1] ?? 'messages'` молча полагается на конвенцию ключей
`app.{module}.{name}`. Для двухсегментного ключа (`app.media`) домен станет `media`, для
односегментного (`plainkey`) — `messages` (это покрыто тестом). Никакой ошибки при «неправильном»
ключе не будет — просто перевод уйдёт не в тот домен и вернётся сам ключ. Это сознательный
лёгкий контракт, риск — тихая опечатка в ключе приводит к не-переведённому сообщению вместо явного
сбоя.

Учитывая, что все ключи статичны и заданы в коде/каталогах, а тесты сверяют конкретные строки
ответов, практический риск низкий. Отмечаю как осознанный компромисс, а не дефект.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `не править`
- **Где:** `app/src/Shared/Domain/Exception/DomainTranslatableException.php:38-40`
- **Что подтверждает проблему:** домен выводится позиционно из ключа без проверки префикса `app.`
  или числа сегментов.
- **Как исправить:** правок не требуется. Защита от опечаток ключей и так обеспечивается тем, что
  каждый ключ заведён в каталоге и проверяется HTTP/feature-тестами на конкретный текст ответа.
- **Тесты:** существующего покрытия (`testTranslationDomainFallsBackToMessagesForKeyWithoutModuleSegment`)
  достаточно.

### 6. Сообщение `LocaleConfig`-исключения смешивает русский текст с английским словом `supported`

Сообщение валидации `LocaleConfig` собрано как `'одна из supported (%s)'`. По `rules.md:6`
(«Исключения пишутся на русском языке») в человеко-читаемой части сообщения должно быть русское
слово; `supported` здесь — не имя класса/метода, а просто английское слово в русской фразе. На
работу не влияет (исключение видит только разработчик при некорректном конфиге), но это явное
отступление от правила о языке исключений.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Shared/Infrastructure/Configuration/Locale/LocaleConfig.php:29`.
- **Что подтверждает проблему:** `\sprintf('одна из supported (%s)', \implode(...))` — русская
  фраза с вкраплением английского `supported`, тогда как `rules.md:6` требует русский текст
  исключений.
- **Как исправить:** заменить на `'одна из поддерживаемых (%s)'` (или иную полностью русскую
  формулировку); ассерт-тест валидации (`LocaleConfigTest`) проверяет факт исключения, не текст,
  поэтому правка не ломает тесты.
- **Тесты:** не требуются (текст сообщения не ассертится).

### 7. `LocaleMiddleware::matchSupportedLocale()` использует `foreach` для чистой трансформации вместо коллекционного пайплайна

`matchSupportedLocale()` — чистый поиск «первый item из отсортированного по quality списка, чей
primary-subtag входит в белый список»: побочных эффектов нет, результат — найденная локаль или
`null`. По `rules.md:19` (`foreach` — только при побочных эффектах; чистые трансформации —
collection-пайплайны) такой код ожидается выраженным через `filter`/`map`/`first`. Поведение
корректно и покрыто `LocaleMiddlewareTest`, поэтому риск — конформность со стилем проекта, а не баг.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Shared/Infrastructure/Framework/Middleware/LocaleMiddleware.php:50-64`
  (`matchSupportedLocale` через `foreach` + `continue` + ранний `return`).
- **Что подтверждает проблему:** метод не имеет побочных эффектов (только возвращает локаль),
  а `rules.md:19` предписывает для таких трансформаций коллекционные пайплайны вместо `foreach`.
- **Как исправить:** выразить через пайплайн над `AcceptHeader::fromString(...)->getAll()`
  (`->filter(quality > 0)->map(primarySubtag)->first(∈ supported)`), вернув `null` при отсутствии
  совпадений. Эквивалентно по поведению, существующие тесты остаются зелёными.
- **Тесты:** существующего `LocaleMiddlewareTest` достаточно — рефакторинг не меняет контракт.
