# Ревью: Модуль уведомлений (Notifications) — незакоммиченный diff (черновой круг)

## Оценка

**90/100.** Модуль зрелый и аккуратный: чистый DDD, корректный outbox-поток, null-object VO с
per-column typecast, тонкие контроллеры, идемпотентная рассылка. За три круга доводки закрыты все
ранее обязательные пункты — это подтверждается прямо в коде: IDOR удаления токена (поиск
`findByTokenForUser`), 500→422 на cursor (`#[Assert\Uuid]` в `ListNotificationsFilter`), Centrifugo
(`Authorization: apikey`, разбор тела при 2xx, namespace `personal` объявлен в конфиге),
инфраструктурные исключения переведены на `\DomainException`, фабрика `centrifugoClient` без занятия
глобального `ClientInterface`, `trim` в `NotificationTypeCode`.

Снижение на этом круге — за один реальный, ещё не закрытый пробел того же класса, что уже чинили для
cursor: маршрут отметки прочитанного принимает идентификатор уведомления прямо из пути и без
валидации передаёт его в доменный VO, который на некорректный UUID бросает внутреннюю ошибку 500
вместо клиентских 404/422. Этот путь (path-параметр) отдельный от уже исправленного cursor
(query-параметр) и тестами на некорректный ввод не покрыт. Остальные осмотренные места либо уже
исправлены, либо входят в список осознанно отклонённых решений — их не воскрешаю, новых аргументов
против зафиксированных причин нет.

## Проблемы сверки с планом

План выполнен по всем 7 фазам. Контракты БД и API совпадают с разделами «Данные и БД» и «API»:
3 таблицы с нужными индексами и unique-ограничениями, 8 роутов, outbox-сообщения и пары
message→Job зарегистрированы, OpenAPI расширен на namespace модуля. Явных невыполненных или
частично выполненных пунктов плана не найдено. Замечание ниже касается качества реализации внутри
выполненного плана (валидация входной границы), а не отклонения от плана: план для маршрута
`POST /notifications/{id}/read` фиксировал контракт «нет/чужое → 404», но способ валидации формата
`{id}` в плане не специфицирован, поэтому это не отклонение от плана, а недоведённая граница ввода.

## Замечания

### 1. Маршрут отметки прочитанного отдаёт 500 на некорректный идентификатор в пути вместо клиентской ошибки

Эндпоинт `POST /api/v1/notifications/{id}/read` берёт идентификатор уведомления прямо из сегмента
пути и без проверки формата передаёт его в команду. Внутри Handler этот идентификатор превращается
в доменный VO, который на строке, не являющейся корректным UUID v7, бросает внутреннюю доменную
ошибку. На границе API такая ошибка превращается в ответ 500 без понятного клиенту смысла, тогда как
для некорректного или несуществующего идентификатора клиент ожидает 404 (или 422 на явно битый
формат). На практике это срабатывает, когда клиент шлёт обрезанный, устаревший или подменённый
идентификатор: вместо предсказуемого «не найдено» он получает «внутренняя ошибка сервера», что
шумит в мониторинге как баг сервера и мешает клиенту корректно обработать ситуацию.

Важно, что это ровно тот же класс проблемы, который проект уже осознанно закрыл для курсора списка:
там добавили проверку формата UUID в фильтре, чтобы битый `cursor` давал 422, а не 500. Здесь
аналогичный path-параметр остался без такой защиты и без теста на некорректный ввод — покрыты только
валидный и «чужой» идентификаторы, но не «битый формат».

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Notifications/Presentation/Http/Controller/NotificationController.php:78-94`
  (`read()` принимает `string $id` из роута Spiral `'/api/v1/notifications/<id>/read'` — сегмент `<id>` без
  типа/паттерна — и кладёт его в `MarkNotificationReadCommand` без валидации формата);
  `app/src/Modules/Notifications/Application/Command/Notification/MarkNotificationRead/MarkNotificationReadHandler.php:29-32`
  (`NotificationId::fromString($command->notificationId)`).
- **Что подтверждает проблему:** `AbstractUuidV7Id::fromString()`
  (`app/src/Shared/Domain/ValueObject/AbstractUuidV7Id.php`) на невалидный UUID v7 бросает
  `InvalidDomainValueException`, а `InvalidDomainValueException`
  (`app/src/Shared/Domain/Exception/InvalidDomainValueException.php`) зашивает код 500 — на API это
  ответ 500 без исходного сообщения (`arch.md:352-363`). Сравнение с уже исправленным cursor:
  `ListNotificationsFilter::cursor` несёт `#[Assert\Uuid]`
  (`app/src/Modules/Notifications/Presentation/Http/Filter/Notification/ListNotificationsFilter.php:21-23`),
  у пути `<id>` аналогичной проверки нет. В HTTP-тестах
  (`tests/Feature/Modules/Notifications/Http/NotificationHttpTest.php:96-118`) маршрут `read`
  проверяется только валидным `id` и «чужим» `id` (404); кейса «битый формат `id`» нет.
- **Как исправить:** привести поведение к уже выбранному в проекте контракту для cursor. Варианты:
  (а) ограничить параметр роута шаблоном UUID в `#[Route(route: '/api/v1/notifications/<id:...>/read')]` —
  но встроенный паттерн `uuid` в Spiral матчит **любой** UUID (v1–v8) и версию не проверяет, поэтому он
  закрывает только «совсем не UUID» (→ 404 роутера), а валидный UUID не той версии (v4 и т.п.) всё равно
  пройдёт роутер и упадёт на `getVersion() !== 7` в `AbstractUuidV7Id::fromString()` — снова 500; для
  полного закрытия через роут нужен кастомный паттерн именно под UUID v7; либо (б) валидировать `{id}` как
  UUID на HTTP-границе фильтром (как сделано для cursor через `#[Assert\Uuid]`), чтобы битый формат давал
  422; либо (в) в Handler трактовать невалидный/несуществующий идентификатор как `NotFoundException` (404)
  через `check-then-act` (`Uuid::isValid()`/проверка версии перед `fromString`) — это не нарушает запрет
  try-catch в Handler-е (`rules.md:51`), но 404 на заведомо битый формат менее точен, чем 422. Вариант
  с фильтром (б) предпочтительнее: он симметричен уже принятому решению для cursor, держит проверку формата
  на границе и однозначно отделяет «битый формат» (422) от «не найдено/чужое» (404). Вариант (а) сам по
  себе неполон (см. оговорку про версию UUID).
- **Тесты:** добавить в `NotificationHttpTest` кейс «`POST /notifications/not-a-uuid/read` →
  ожидаемый клиентский код (404/422), не 500» — симметрично существующему
  `testListNotificationsReturns422ForInvalidCursor`.
