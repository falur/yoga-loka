# Ревью: Модуль Auth — беспарольный вход по email-коду (третий круг)

## Оценка

**90/100.** Третий круг ревью того же незакоммиченного диффа. Правки второго круга применены
корректно и подтверждаются кодом: в генераторе OpenAPI ветка `listItemType` теперь проходит
через единое присвоение `nullable` (`SchemaBuilder::schemaForProperty`), для этого заведена
фикстура `UserResource` с `@var list<string>|null public array|null $tags` и тест на
`nullable: true` + отсутствие в `required`; `RegisterFilter` получил подробные комментарии о
намеренной строгости фильтра относительно нормализации VO; рендерер `spiral-api-errors`
оставлен с контрактом `array<string,string>` и обоснованно отклонён в прошлом круге.

Найдено одно новое содержательное замечание с аргументом, которого не было в прошлых кругах:
вся ветка nullable в генераторе (включая только что добавленную обработку nullable-списков)
выражает необязательность ключевым словом `nullable: true`, тогда как сам документ объявлен
как `openapi: 3.1.0`, где это ключевое слово удалено из стандарта. То есть усилия второго и
третьего круга по корректному nullable пишут в спецификацию ключ, который валидатор 3.1
игнорирует. Все пять проверяющих (plan/architecture/rules/quality + кросс-CLI codex)
подтвердили фактологию замечания и его новизну относительно второго круга (там речь шла о
потере `nullable` у списков, здесь — о неверном для версии 3.1 способе выражения nullable).
По severity мнения разошлись: четыре субагента сочли это латентным дефектом переносимого
пакета (`на усмотрение автора`), а кросс-CLI codex — обязательной правкой контракта, потому
что фаза 7 плана прямо требовала проверить «корректность схемы `VerifyResultResource` с
nullable-полями», а опубликованная под `openapi: 3.1.0` спецификация всё ещё описывает
обнуляемость не по стандарту. Аргумент codex принят: 3.1-валидатор/codegen молча проигнорирует
`nullable`, и типобезопасный клиент получит non-nullable `tokens`/`registrationTicket` — тот же
класс клиент-видимого расхождения контракта, что второй круг закрывал как must-fix. На сам
сервер Auth и текущие тесты это не влияет (сервер отвечает корректно), поэтому замечание
переведено в `править обязательно`, но с минимальным практическим риском (нужен внешний
строгий потребитель спеки). Остальные два пункта прошлого круга (контракт рендерера,
выравнивание фильтра под VO) уже осознанно отклонены с обоснованием и без новых аргументов не
поднимаются.

## Проблемы сверки с планом

Все семь фаз реализованы, пять маршрутов на месте, отклонения предыдущих кругов (scan OpenAPI
на все модули, ключ rate limit по `path`, `logout` читает только `authSessionId`, фиксированное
окно через PSR-20 clock) зафиксированы в разделе плана «Принятые по ходу решения» и в
`docs/arch.md`. Ветка nullable-списков из правок второго круга (план не требовал её отдельно —
это инициатива по итогам мета-ревью) добавлена в переносимый пакет с фикстурой и тестом.

Единственная неполнота по плану: фаза 7 (`docs/plans/2026-06-15_13-25_auth-module.md:579`)
требовала проверить «корректность схемы `VerifyResultResource` с nullable-полями». Серверная
семантика схемы выполнена (поля помечены nullable и убраны из `required`), но способ выражения
nullable (`nullable: true`) не валиден для объявленной версии `openapi: 3.1.0` — то есть
требование плана выполнено лишь формально для строгого 3.1-потребителя. Это и есть замечание 1
ниже (`править обязательно` по аргументу кросс-CLI codex).

## Замечания

### 1. Признак nullable пишется ключом OpenAPI 3.0 в документ, объявленный как 3.1

Генератор спецификации помечает необязательные/обнуляемые поля ключом `nullable: true`, и
именно этот механизм во втором круге чинил схему `VerifyResultResource`, а в третьем —
распространён на nullable-списки. Однако сам документ в шапке объявлен версией `3.1.0`, а в
OpenAPI 3.1 ключевого слова `nullable` больше нет: оно удалено из стандарта, и обнуляемость
выражается иначе (тип-объединение с `"null"` либо `anyOf`/`oneOf` с `{"type":"null"}`). В
результате строгий клиент или валидатор 3.1, прочитавший спеку, проигнорирует `nullable` и
будет считать поля `registrationTicket`, `tokens` и новые nullable-списки не-обнуляемыми —
ровно то расхождение контракта, которое правки второго и третьего круга пытались устранить.

Практический риск проявится у внешнего потребителя, который сгенерирует типобезопасный клиент
из этой 3.1-спеки: он получит non-nullable поля и сломается на реальном ответе, где одно из
`tokens`/`registrationTicket` равно `null`. На сам сервер и текущие тесты Auth это не влияет —
поведение приложения корректно, а пакетный тест проверяет наличие ключа `nullable`, но не его
валидность для заявленной версии. Раз переносимый пакет в этом круге правился именно ради
корректного nullable, версия документа и способ его выражения логично свести воедино, иначе
доработка достигает цели лишь формально.

Дополнительный нюанс той же природы: для поля-ссылки (`tokens`) ключ `nullable` соседствует с
`$ref`. Даже в 3.0 соседи `$ref` игнорируются, а в 3.1 это решается оборачиванием в `allOf`/
`oneOf`. Это часть того же корня — выражение nullable не согласовано с версией документа.

Технические детали:

- **Тип:** `architecture` / `quality`
- **Рекомендация:** `править обязательно` (по аргументу кросс-CLI codex: фаза 7 плана требовала
  корректную nullable-схему, а опубликованная под 3.1 спека выражает nullable не по стандарту —
  тот же класс клиент-видимого расхождения контракта, что второй круг закрывал как must-fix).
- **Где:** `packages/spiral-openapi/src/Config/OpenApiGeneratorConfig.php:14`
  (`openApiVersion = '3.1.0'` по умолчанию; `app/config/openapi.php` его не переопределяет —
  дефолт пакета проходит насквозь); `packages/spiral-openapi/src/Spec/SpecBuilder.php:54`
  (пишет `'openapi' => $config->openApiVersion`); `packages/spiral-openapi/src/Schema/SchemaBuilder.php:56-60`
  (единое `$schema['nullable'] = true` на `:57-58` для скаляров, ссылок и теперь списков); итог —
  `public/openapi/openapi.yml:1` (`openapi: 3.1.0`), `:155-160`
  (`tokens: {$ref: ..., nullable: true}`, `registrationTicket: {type: string, nullable: true}`);
  прочие места генератора тоже эмитят `nullable` (`SpecBuilder.php:120` ErrorResponse.code,
  `:184` meta.nextCursor).
- **Что подтверждает проблему:** шапка `openapi: 3.1.0` против эмита `nullable: true`; в 3.1
  (JSON Schema 2020-12) `nullable` не является валидным ключевым словом схемы и молча
  игнорируется. Тест генератора проверяет лишь наличие ключа `nullable`
  (`OpenApiGeneratorTest.php:109-110,113`, метод `assertUserResourceNullableSchema` на `:102`),
  при этом сам жёстко фиксирует `assertSame('3.1.0', ...)` на `:70`, но никогда не проверяет
  допустимость `nullable` для этой версии — поэтому пробел не подсвечивается.
- **Как исправить:** выбрать одно из двух согласованных решений на уровне пакета.
  Вариант А (минимальный) — понизить дефолт `openApiVersion` до `3.0.3`, тогда `nullable`
  валиден для скаляров; для ветки `$ref` всё равно потребуется обернуть ссылку в `allOf`,
  чтобы `nullable` не оказался соседом `$ref`. Вариант Б (каноничный для 3.1) — оставить
  `3.1.0` и эмитить обнуляемость через `type: [<type>, "null"]` для скаляров/массивов и
  `oneOf: [{$ref:...}, {type:"null"}]` для ссылок, убрав ключ `nullable`. Решение зафиксировать
  в коде пакета и обновить пакетный тест под выбранный способ.
- **Тесты:** в `OpenApiGeneratorTest` проверять не наличие ключа `nullable`, а фактический
  способ выражения обнуляемости, соответствующий объявленной версии (для 3.1 — `type` с
  `"null"`/`oneOf`; для 3.0 — `nullable: true` без соседства с `$ref`). Добавить кейс на
  nullable-ссылку (`HealthResource|null`) — сейчас он есть, но проверяет лишь `nullable`.
