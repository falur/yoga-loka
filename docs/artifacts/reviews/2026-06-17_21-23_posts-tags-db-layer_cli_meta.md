# Кросс-CLI мета-ревью (codex, gpt-5.5) — strict-режим

Соседний CLI (`codex exec`, модель gpt-5.5) проверил
`docs/reviews/2026-06-17_21-23_posts-tags-db-layer.md` против обоих планов, правил,
архитектуры и реального кода. Ниже — итоговые выводы (формат `+`/`−`/`~`/`?`). Полный
сырой транскрипт прогона не сохраняется; здесь зафиксирован итог.

## Итог

`+` **Обязательное замечание:** `Post::create()` не держит инвариант взаимоисключающего
вложения. Он просто записывает `attachmentType`, `lesson`, `practice`, `original`, поэтому
можно создать `AttachmentType::Lesson` с `PostLesson::none()` или одновременно заполнить
`lesson` и `practice`. План 1 требует, чтобы домен держал «при Lesson/Practice заполнен
ровно один id». Это реальный баг доменной сущности, не optional. Нужны guard-проверки и
unit-тесты на невалидные сочетания.

`+` Score 90 завышен: с обязательным багом в `Post::create()` оценку следует снизить
(~82-85), пока инвариант не закрыт.

`−` Не убирать ни одно из пяти optional-замечаний целиком: все подтверждаются кодом, часть
надо смягчить/уточнить.

`−` Не добавлять как проблему отсутствие tag-классов в `Posts`: это правильный результат
плана extract-tags (`TagId` в `Shared`, зависимости `Posts\Domain → Tags\Domain` нет).

`−` Не добавлять проблемы про FK, имена колонок `unblocked_*`, порядок миграции, транзакции
или записи в репозиториях: явных нарушений по коду нет.

`~` Замечание про счётчики: не советовать класть `zero()/increment()/decrement()` прямо в
общий `AbstractIntegerValue` (от него наследуются и не-счётчики) — лучше отдельный базовый
класс для счётчиков.

`~` Замечание про typecast: не писать «байт-в-байт идентичный `uncastValue()`» — сигнатуры
и типы отличаются, идентична именно структура логики.

`~` Замечание `tags.text=64` vs `TagText::MAX_LENGTH=50`: не ошибка реализации (оба числа
зафиксированы планом), оставить как слабый optional-риск — документировать запас БД либо
синхронизировать.

`~` Замечание про `Post HasMany PostTag`: unit-тест пустой `$post->tags` есть,
`PostTagRepository` покрыт; пробел именно в feature-тесте ORM-гидрации связи после чтения
из БД.

`~` Замечание про широкий `\Throwable` оставить optional — это текущий проектный канон,
обязательным без смены общего стиля constraint-тестов делать нельзя.

`?` Фактический класс исключения БД для замены `\Throwable` через Docker не проверялся —
не советовать конкретный класс как гарантированный без отдельной проверки.
