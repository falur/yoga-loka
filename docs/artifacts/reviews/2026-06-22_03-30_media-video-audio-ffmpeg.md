# Ревью: Media — реальная нарезка видео и аудио на ffmpeg (третий круг)

## Оценка

**89/100.** Это третий круг по тем же изменениям. Главный функциональный пробел прошлого круга
закрыт корректно: целевая частота дискретизации профиля теперь реально применяется к выходу.
`NativeAacAudioFormat::getExtraParams()` отдаёт `['-ar', <rate>]`, а php-ffmpeg в `Audio::buildCommand()`
добавляет эти параметры через `SimpleFilter` до пути выходного файла — то есть `-ar` применяется к
кодируемому потоку, а не к входу. Это подтверждается и юнит-тестом на состав `getExtraParams()`, и
интеграционным сценарием «вход 48000 → профиль 44100 → выход 44100», где вход намеренно отличается от
профиля. Усиленные ассерты видео-теста тоже на месте: рамка профиля, чётность сторон и сохранение
пропорций 4:3 действительно фиксируют контракт транскода, а не просто `> 0`.

Остальные применённые правки корректны и регрессий не внесли: недостижимые guard-ветки переведены на
`MediaProcessorFailedException::permanent(...)`, добавлен симметричный тест повторного прогона аудио
после `ProcessingFailed`, остаточный англицизм «Payload» в докблоке убран. Структурно план выполнен по
всем пяти фазам: полный аудио-стек, таблица `media_audio_conversions`, реальные ffmpeg-процессоры,
ветвление исчерпывающим `match` по типу, выдача URL на три типа и отдельная волна. Осознанное упрощение
относительно плана — логирование уровня `debug_precise` не доведено до DEBUG **внутри** процессоров
(план требовал «оригинал скачан / результат probe / транскод готов / постер-волна извлечены / временные
файлы удалены»); это часть осознанно отклонённого optional про инъекцию логгера, поэтому повторно не
открывается, но как «полное соответствие плану» это не описывается.

Новых блокирующих проблем нет — все замечания «на усмотрение автора». Мета-ревью третьего круга вскрыло
несколько мелких пунктов, которые черновик не зафиксировал: чистый подсчёт через `foreach` в
`ProcessMediaHandler::countByClass` (нарушение правила «`foreach` только при побочных эффектах»),
дублирование запуска внешнего ffmpeg между извлечением волны и постера, которое заодно обходит
настройку `ffmpegThreads`, и два плановых пробела в тестах (нет 422-сценария на несколько аудио-профилей,
хотя для видео он есть; интеграционный видео-тест не закрепляет кодеки H.264/AAC). Прежние пункты —
пустой PCM-буфер (переформулирован: вопрос явного выбора «ошибка процессора или документированная
тишина», аргумент про покрытие убран как неверный для PCOV/строчного покрытия), несимметричная проверка
дубликатов в валидации плана (читаемость, не баг) и зависимость ассерта пропорций видео-теста от версии
ffmpeg (риск будущей смены фикстуры, не текущий дефект) — остаются мягкими. Осознанно отклонённые в
прошлых кругах optional (typecast `\InvalidArgumentException`, возврат `MediaWaveform` из Query,
дедупликация `encode()`/`probeDurationMs()` в Abstract, инъекция логгера в процессоры/Query, `first()`
без фильтра по типу + `match (true)` без `default`, rotation-фикстура видео) повторно не открываю —
новых аргументов нет.

## Проблемы сверки с планом

Структурно план выполнен по всем пяти фазам. Расхождения, за которые снижалась оценка во втором круге,
устранены: профиль аудио (`sampleRate`) теперь соблюдается, повторный прогон аудио после
`ProcessingFailed` покрыт тестом, видео-контракт (пропорции/чётность/рамка) частично зафиксирован
усиленными ассертами. Часть «rotation-фикстура видео» осознанно отклонена в прошлом круге (поведение
ffmpeg на повёрнутом входе на образе не подтверждается без запуска кода) — повторно не открываю.

Остаются расхождения с планом, которые черновик не называл:

- **Логирование `debug_precise` не доведено до процессоров** (см. «Оценка»): план требовал DEBUG на
  каждом шаге внутри процессоров (скачивание, probe, транскод, постер/волна, удаление временных файлов),
  но логгер в `AbstractFfmpegMediaProcessor`/`FfmpegMediaVideoProcessor`/`FfmpegMediaAudioProcessor` не
  инжектится, логирует только handler. Это часть осознанно отклонённого optional (инъекция логгера),
  повторно не открываю — но это сознательное упрощение, а не «полное соответствие».
- **Пробелы плановых тест-сценариев** (замечания 6 и 7): план (фаза 4) требует для **video и audio**
  сценарий «несколько профилей → 422» — для видео он есть (`testRejectsMultipleVideoProfiles`), для
  аудио аналога нет; план (фаза 3) требует реальный транскод в mp4/**H.264+AAC** — интеграционный
  видео-тест проверяет MIME/размеры/пропорции, но не `codec_name` потоков.

## Замечания

### 1. Построение волны молча превращает пустой PCM-буфер в плоскую тишину вместо явного решения

При извлечении волны массив сэмплов получается из распакованного PCM. Если PCM окажется пустым (ноль
сэмплов), цикл по интервалам отработает с `start === end === 0`, защитный сдвиг
`$end = \min($start + 1, $sampleCount)` не сработает (он включается только при `$sampleCount > 0`), и для
каждого интервала вернётся амплитуда 0. То есть аномальный пустой результат ffmpeg тихо станет валидной
«плоской тишиной» из нулей, а не сигналом об ошибке. Это та же категория, что и уже закрытый guard
«короткое аудио» рядом: там пустые интервалы обработали явно, а случай полностью пустого буфера остался
без явного решения — «ошибка процессора» или «документированная тишина».

Практический риск низкий: волна строится из того же `$sourceFile`, который выше уже успешно прошёл
`open()` как аудио, поэтому пустой PCM — теоретический случай. Деталь, подтверждающая безвредность:
второй операнд guard `&& $sampleCount > 0` поведенчески избыточен — при `$sampleCount === 0` даже без него
`$end = \min($start + 1, 0) = 0`, внутренний цикл пуст и пик всё равно 0; ноль приходит из пустого
интервала, а не из guard. Аргумент про покрытие здесь неприменим: гейт меряет строчное покрытие (PCOV),
а под-условие `$sampleCount > 0` отдельной непокрытой строки не создаёт, поэтому «непокрываемой ветки»
как явления нет — остаётся только семантический выбор.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/FfmpegMediaAudioProcessor.php:152-186`
  (`buildWaveform`: `$sampleCount = \count($samples)`, guard `if ($end === $start && $sampleCount > 0)`).
- **Что подтверждает проблему:** при `$sampleCount === 0` все интервалы дают 0, и
  `MediaWaveform::fromPeaks([0, 0, ...])` вернёт «тихую» волну вместо сигнала об ошибке; явного решения
  на пустой буфер нет.
- **Как исправить:** сделать выбор явным — либо коротким комментарием зафиксировать, что после
  успешного `open()`/транскода буфер непуст и пустая волна не считается аномалией; либо, если пустой
  выход трактуется как сбой, бросить `MediaProcessorFailedException::permanent(...)`. Второй вариант
  создаст недостижимую строку, которую придётся закрывать `@codeCoverageIgnore` (как `audioStream === null`
  рядом), поэтому комментарий предпочтительнее, если пустой буфер не считается ошибкой.
- **Тесты:** если добавляется guard-исключение — юнит-тест `buildWaveform('')` через наследника-fixture
  (`WaveformExposingAudioProcessor`); если оставляется как есть/с комментарием — тест не нужен.

### 2. В валидации плана аудио/видео нет проверки дубликатов типов, в отличие от image — асимметрия, не баг

Валидация плана проверяет дубликаты профилей по типу только для изображений (`assertImagePlan`); для
видео и аудио такой проверки нет. Сейчас это безопасно и корректно: для video и audio отдельно
требуется `count(...) === 1`, поэтому два профиля одного типа физически не пройдут — список из двух
элементов отвергается раньше как «нужен ровно один профиль». То есть дубликат в этих списках уже
невозможен, отдельная проверка была бы мёртвой.

Замечание чисто про читаемость и единообразие: три метода валидации выглядят почти симметрично, но
image защищается от дублей явным блоком, а video/audio — неявно через счётчик. Человек, читающий код,
может не сразу понять, почему защита от дублей есть только в одном из трёх. Это не требует правки кода —
скорее короткий комментарий в `assertVideoPlan`/`assertAudioPlan`, что проверка `count === 1` уже
исключает дубликаты, снял бы вопрос на будущих ревью.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/CompleteMediaUpload/CompleteMediaUploadHandler.php:130-192`
  (`assertImagePlan` имеет блок проверки уникальности типов; `assertVideoPlan`/`assertAudioPlan` — нет).
- **Что подтверждает проблему:** для image дубли отсеиваются через сравнение `count()` и `unique()->count()`;
  для video/audio той же проверки нет, она покрыта косвенно требованием ровно одного профиля.
- **Как исправить:** оставить логику как есть (она верна) и при желании добавить однострочный комментарий
  в `assertVideoPlan`/`assertAudioPlan`, что `count === 1` уже исключает дубликаты типа. Дублировать саму
  проверку уникальности не нужно — она стала бы недостижимой.
- **Тесты:** не требуется; поведение «ровно один профиль» уже покрыто.

### 3. Ассерт пропорций в интеграционном тесте видео завязан на поведение масштабатора конкретной версии ffmpeg

Усиленный видео-тест сравнивает округлённое до двух знаков соотношение сторон выхода с соотношением
входа (4:3). Для входа 320x240, масштабируемого inset в рамку 640x480, это сейчас даёт точное 4:3 и
проходит. Но точное равенство соотношений после inset-масштаба с округлением сторон до чётных — это
свойство конкретной реализации `ResizeFilter` php-ffmpeg и версии бинаря ffmpeg в образе. При другой
рамке профиля или другом входе (например, нечётное исходное соотношение) округление сторон до чётных
может слегка сдвинуть соотношение, и сравнение с точностью до двух знаков может стать хрупким.

Сейчас риск минимальный — вход и рамка подобраны так, что соотношение совпадает идеально, и тест
зелёный. Замечание про устойчивость теста к будущим изменениям фикстуры/профиля, а не про текущий
дефект. Если фикстуру оставляют 320x240 в рамке 640x480 — всё в порядке.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Infrastructure/FfmpegMediaProcessorIntegrationTest.php:75-78`
  (сравнение `\round(320 / 240, 2)` с `\round($result->width / $result->height, 2)`).
- **Что подтверждает проблему:** точное равенство соотношений сторон после inset + округления до чётных
  гарантировано только для конкретной комбинации вход/рамка; на других значениях чётность может слегка
  изменить соотношение.
- **Как исправить:** оставить как есть для текущей фикстуры (она корректна), либо при будущем расширении
  набора входов сравнивать соотношения с допуском (`assertEqualsWithDelta` по соотношению) вместо точного
  округления до двух знаков, чтобы тест не падал от законного округления стороны до чётной.
- **Тесты:** само замечание про устойчивость существующего теста; новый тест не нужен.

### 4. `countByClass` считает конверсии через `foreach`-счётчик вместо collection-пайплайна

В `ProcessMediaHandler::countByClass` число конверсий каждого типа для контекста итогового DEBUG-лога
считается циклом `foreach` с инкрементом `$count++`. Это чистая трансформация (подсчёт), а не побочный
эффект, тогда как rules.md прямо требует «`foreach` — только при побочных эффектах», а для чистых
выборок/трансформаций — collection-пайплайны. Логики это не ломает (счётчик корректен), но стиль кода
расходится с правилом — это единственное новое нарушение правил в diff, которое черновик не зафиксировал.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/ProcessMedia/ProcessMediaHandler.php:137-147`
  (`countByClass`: `foreach ($conversions as $conversion) { if (...) { $count++; } }`).
- **Что подтверждает проблему:** rules.md «Collection-пайплайны … `foreach` — только при побочных
  эффектах»; здесь `foreach` используется ради чистого подсчёта без побочного эффекта.
- **Как исправить:** свести к пайплайну — например
  `\count(\array_filter($conversions, static fn(...): bool => $conversion instanceof $conversionClass))`
  (или `Collection::make($conversions)->filter(...)->count()`), убрав ручной счётчик.
- **Тесты:** не требуется (поведение `countByClass` уже покрыто проверкой счётчиков лога в существующих
  тестах handler-а; поведение не меняется).

### 5. Запуск внешнего ffmpeg для волны и постера дублируется и обходит настройку `ffmpegThreads`

Извлечение волны (`FfmpegMediaAudioProcessor::extractWaveform`) и извлечение постера
(`FfmpegMediaVideoProcessor::extractPoster`) оба строят `new Process([...])` напрямую, затем
`setTimeout((float) $this->mediaConfig->ffmpegTimeoutSeconds)` и `mustRun()`. Это мелкое дублирование
шаблона (бинарь + таймаут + запуск), не пересекающееся с уже осознанно отклонённой дедупликацией
`encode()`/`probeDurationMs()`.

Сопутствующий, более содержательный аспект: оба прямых вызова берут только `ffmpegBinaryPath` и таймаут,
но **не передают `-threads`**, тогда как основной путь через `FFMpeg::create([... 'ffmpeg.threads' => ...])`
настройку `ffmpegThreads` учитывает. То есть часть ffmpeg-вызовов обходит конфигурируемое ограничение
числа потоков. Если `ffmpegThreads` задаётся ради ограничения нагрузки, для волны/постера оно молча не
действует.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/FfmpegMediaAudioProcessor.php:123-133`
  (`extractWaveform`) и `app/src/Modules/Media/Infrastructure/FileService/FfmpegMediaVideoProcessor.php:147-154`
  (`extractPoster`); сравнить с `AbstractFfmpegMediaProcessor::ffmpeg()` (`:29-37`), где `ffmpeg.threads`
  передаётся.
- **Что подтверждает проблему:** оба прямых `Process` собирают аргументы без `-threads`; единая точка
  установки таймаута/потоков отсутствует, поэтому `ffmpegThreads` для этих двух вызовов игнорируется.
- **Как исправить:** вынести запуск в защищённый хелпер `AbstractFfmpegMediaProcessor`
  (`runFfmpeg(list<string> $arguments): void`), который ставит таймаут и при `ffmpegThreads > 0`
  добавляет `-threads <n>` — это убирает дублирование и распространяет настройку потоков на все
  ffmpeg-вызовы. Альтернатива (если потоки для коротких операций намеренно не ограничивают) —
  зафиксировать это комментарием.
- **Тесты:** при добавлении `-threads` покрыть, что аргумент попадает в команду при `ffmpegThreads > 0`
  (через подменяемый запуск процесса), иначе новая ветка просадит 100% порог.

### 6. Нет 422-сценария на несколько аудио-профилей, хотя для видео он есть (пробел плана)

План (фаза 4) требует для **video и audio** сценарий «пустой, дублирующий или множественный профиль →
422». Для видео покрыты пустой план (`testRejectsEmptyVideoPlanForVideoMedia`) и несколько профилей
(`testRejectsMultipleVideoProfiles`). Для аудио покрыт только пустой план
(`testRejectsEmptyAudioPlanForAudioMedia`) — теста на несколько аудио-профилей нет, хотя код отвергает
их через `\count($plan->audio) !== 1`. Ветка `!== 1` срабатывает и при пустом, и при множественном
списке, поэтому строчное покрытие держится за счёт пустого случая, но плановый сценарий «несколько
профилей» для аудио тестом не закреплён — асимметрично с видео.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Application/CompleteMediaUploadHandlerTest.php` —
  есть `testRejectsMultipleVideoProfiles` (`:185`), аудио-аналога нет; валидация —
  `CompleteMediaUploadHandler::assertAudioPlan` (`\count($plan->audio) !== 1`).
- **Что подтверждает проблему:** в тесте нет метода вроде `testRejectsMultipleAudioProfiles`, тогда как
  для видео симметричный сценарий присутствует, а план требует его для обоих типов.
- **Как исправить:** добавить тест «два аудио-профиля → 422» (по образцу видео-аналога), чтобы плановый
  сценарий для аудио был закреплён симметрично.
- **Тесты:** см. выше — это само замечание про недостающий тест.

### 7. Интеграционный видео-тест не закрепляет кодеки H.264/AAC (пробел плана)

План (фаза 3, решение 3) требует реальный транскод видео в **mp4/H.264+AAC**. Интеграционный тест
`testVideoProcessorTranscodesToMp4WithPoster` проверяет MIME (`video/mp4`), размеры, чётность сторон и
пропорции, но не `codec_name` потоков выхода. Код задаёт `X264` и нативный AAC, поэтому фактически
кодеки, скорее всего, верны, но контракт «именно H.264 + AAC» тестом не зафиксирован: смена формата
(например, на другой кодек видео) прошла бы при тех же MIME/размерах незамеченной.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Infrastructure/FfmpegMediaProcessorIntegrationTest.php:64-85`
