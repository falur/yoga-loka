# Ревью: Media — реальная нарезка видео и аудио на ffmpeg (четвёртый круг)

## Оценка

**90/100.** Это четвёртый круг по тем же изменениям. Все семь optional-замечаний третьего круга
обработаны корректно, и применённые правки сами по себе чистые, без регрессий. Оценка снижена с
черновых 94 после кросс-CLI: вскрыты два не зафиксированных ранее пробела в ffmpeg-процессорах —
аудио со встроенной обложкой терминально отклоняется как «не аудио», хотя приём разрешает любой
`audio/*` (замечание 3, поведенческий баг для штатного входа), и контракт «mp4/H.264+AAC» не
гарантирован для немого видео при отсутствующем тесте на этот случай (замечание 4). Ни одно из них не
рушит существующие зелёные тесты, поэтому это не блокеры, но замечание 3 затрагивает обычные
аудиофайлы с обложкой, поэтому его фактически лучше править. Подсчёт конверсий для
итогового лога переведён с `foreach`-счётчика на collection-пайплайн (`Collection::make(...)->filter(...)->count()`),
что прямо соответствует правилу «`foreach` только при побочных эффектах»; единственное новое нарушение
правил из прошлого круга закрыто. Прямые вызовы ffmpeg для волны и постера сведены в единый защищённый
`AbstractFfmpegMediaProcessor::runFfmpeg()`, который добавляет `-threads <n>` при `ffmpegThreads > 0` —
это убрало дублирование и распространило лимит потоков на вызовы, которые раньше его обходили; новая ветка
покрыта двумя юнит-тестами на состав команды (с потоками и без). Плановые тест-пробелы аудио закрыты:
`testRejectsMultipleAudioProfiles` симметричен видео-аналогу, а интеграционный видео-тест теперь
закрепляет кодеки выхода (`h264`/`aac`) через ffprobe, фиксируя контракт «mp4/H.264+AAC». Комментарии про
пустой PCM-буфер и про то, что `count === 1` уже исключает дубликаты типа, добавлены и читаются по делу.

Структурно план выполнен по всем пяти фазам: полный аудио-стек, таблица `media_audio_conversions`,
реальные ffmpeg-процессоры, ветвление исчерпывающим `match` по `MediaType`, выдача URL на три типа и
отдельная волна. Осознанное упрощение относительно плана сохраняется и в этом круге — логирование
`debug_precise` не доведено до DEBUG ни **внутри** процессоров (план требовал «оригинал скачан /
результат probe / транскод готов / постер-волна извлечены / временные файлы удалены»), ни в Query-хендлерах
(план требовал отдельным пунктом DEBUG на резолв с `mediaId` и выбранным типом в `GetMediaUrlHandler`/
`GetAudioWaveformHandler` — но они логгер вообще не инжектят). Фактически логируют только command-хендлеры
(`ProcessMediaHandler`, `CompleteMediaUploadHandler`), поэтому «логирует только handler» точнее читать как
«логируют только command-хендлеры». Всё это — часть осознанно отклонённого optional (инъекция логгера в
процессоры и Query): не «полное соответствие плану», но и не дефект, и повторно я этот пункт не открываю.

Новых блокирующих проблем нет. Остаётся один мягкий пункт «на усмотрение автора» — устойчивость ассерта
пропорций видео-теста к версии ffmpeg, который и в прошлом круге был осознанно отклонён (фикстура
фиксирована, даёт точное 4:3); привожу его ниже только для полноты картины, без нового аргумента, поэтому
он не должен открываться как обязательная правка. Отдельно фиксирую внеплановое изменение в файле `todo`,
не относящееся к задаче Media. Все осознанно отклонённые в прошлых кругах optional (typecast
`\InvalidArgumentException`; возврат `MediaWaveform` из Query; дедупликация `encode()`/`probeDurationMs()`
в Abstract; инъекция `LoggerInterface`/DEBUG плана в процессоры/Query; `first()` без фильтра по типу +
`match (true)` без `default`; rotation-фикстура видео; допуск `assertEqualsWithDelta` для соотношения
сторон) повторно не открываю — новых аргументов нет.

## Проблемы сверки с планом

Структурно план выполнен по всем пяти фазам; расхождения, за которые снижалась оценка в прошлых кругах,
устранены. Прежние optional-пробелы плановых тест-сценариев закрыты в этом круге:

- **Сценарий «несколько аудио-профилей → 422»** теперь есть (`testRejectsMultipleAudioProfiles`) —
  симметрично видео; плановое требование фазы 4 для обоих типов закрыто.
- **Контракт «mp4/H.264+AAC»** теперь зафиксирован интеграционным тестом через `codec_name` потоков
  выхода (`h264` + `aac`) — плановое требование фазы 3/решения 3 закрыто.

Остаётся одно сознательное упрощение, которое не является дефектом, но и не описывается как «полное
соответствие плану»:

- **Логирование `debug_precise` не доведено до процессоров и Query-хендлеров.** План требовал DEBUG на
  каждом шаге внутри процессоров (скачивание, probe, транскод, постер/волна, удаление временных файлов),
  но логгер в `AbstractFfmpegMediaProcessor`/`FfmpegMediaVideoProcessor`/`FfmpegMediaAudioProcessor` не
  инжектится. Кроме того, план логирования отдельным пунктом требовал DEBUG на резолв (`mediaId`,
  выбранный тип) в `GetMediaUrlHandler`/`GetAudioWaveformHandler`, но оба Query-хендлера логгер вообще не
  инжектят и `->debug()` не вызывают. Фактически логируют только command-хендлеры (`ProcessMediaHandler`,
  `CompleteMediaUploadHandler`). Оба пробела — часть осознанно отклонённого optional (инъекция логгера в
  процессоры и Query), повторно не открываю.

## Замечания

### 1. Ассерт пропорций в интеграционном тесте видео завязан на поведение масштабатора конкретной версии ffmpeg

Усиленный видео-тест сравнивает округлённое до двух знаков соотношение сторон выхода с соотношением входа
(4:3). Для текущего входа 320x240, масштабируемого inset в рамку 640x480, это даёт точное 4:3 и проходит.
Но точное равенство соотношений после inset-масштаба с округлением сторон до чётных — свойство конкретной
реализации `ResizeFilter` php-ffmpeg и версии бинаря в образе. При другой рамке профиля или другом входе
округление сторон до чётных может слегка сдвинуть соотношение, и сравнение с точностью до двух знаков
может стать хрупким.

Это тот же пункт, что и замечание 3 третьего круга, и он там был осознанно отклонён: фикстура
фиксирована, риск касается гипотетической будущей смены входа/рамки, а не текущего дефекта. Привожу для
полноты, новых аргументов нет — пункт остаётся мягким и не требует правки сейчас.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Infrastructure/FfmpegMediaProcessorIntegrationTest.php:75-78`
  (сравнение `\round(320 / 240, 2)` с `\round($result->width->value() / $result->height->value(), 2)`).
- **Что подтверждает проблему:** точное равенство соотношений сторон после inset + округления до чётных
  гарантировано только для конкретной комбинации вход/рамка; на других значениях чётность может слегка
  изменить соотношение.
- **Как исправить:** оставить как есть для текущей фикстуры (она корректна), либо при будущем расширении
  набора входов сравнивать соотношения с допуском (`assertEqualsWithDelta`) вместо точного округления до
  двух знаков. В этом круге правка не нужна — пункт ранее уже отклонён с обоснованием.
- **Тесты:** само замечание про устойчивость существующего теста; новый тест не нужен.

### 2. В рабочем дереве есть внеплановое изменение файла `todo`, не относящееся к задаче Media

- **Рекомендация:** на усмотрение автора
- **Где:** `todo` (отслеживаемый файл, `git diff` показывает правку 2 строк, вне области модуля Media).

### 3. Аудиофайл со встроенной обложкой отклоняется как «не аудио», хотя приём разрешает любой `audio/*`

`FfmpegMediaAudioProcessor::runEncoding` открывает оригинал через php-ffmpeg и сразу отвергает результат,
если это `Video`: `if ($audio instanceof Video) { throw MediaProcessorFailedException::permanent('Загруженный
файл не является аудио.'); }`. Но php-ffmpeg возвращает `Video` всегда, когда ffprobe видит **любой**
видеопоток — а у обычных `audio/mpeg`/`audio/mp4` со встроенной обложкой (attached picture, поток
`mjpeg`/`png`) такой видеопоток есть. Приём при этом разрешает любой `audio/*` (`MediaTypeResolver::resolve`
возвращает `MediaType::Audio` для всего с префиксом `audio/`, собственного whitelist у `MediaMimeType` нет).
В результате очень распространённый реальный вход — mp3/m4a с обложкой альбома — проходит приём (загрузка в
`uploaded` + outbox), но на обработке терминально падает «Загруженный файл не является аудио», и медиа
никогда не станет `ready`. Это поведенческий пробел для штатного входа, а не для аномалии.

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** на усмотрение автора (по сути — лучше править: затрагивает обычные аудиофайлы)
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/FfmpegMediaAudioProcessor.php:88-91`
  (`$audio = $ffmpeg->open(...)`; `if ($audio instanceof Video) throw ...permanent(...)`); приём —
  `app/src/Modules/Media/Application/Service/MediaTypeResolver.php:30-32` (любой `audio/*` → Audio).
- **Что подтверждает проблему:** php-ffmpeg классифицирует медиа как `Video`, если ffprobe видит видеопоток
  (а cover art в mp3/m4a даёт поток `attached_pic`); кросс-CLI (Codex) подтвердил это чтением vendor-кода
  php-ffmpeg и локальным прогоном ffmpeg вне сьюта. Проверка `instanceof Video` отклоняет такой файл,
  хотя это валидное аудио, разрешённое приёмом.
- **Как исправить:** не считать «есть видеопоток» = «не аудио». Различать реальное видео и аудио с обложкой
  по факту наличия настоящего аудиопотока (probe `audios()->first()` на входе) и/или игнорировать потоки
  `attached_pic`/`mjpeg`/`png` как обложку; при транскоде брать только аудиодорожку (`-map a` / `-vn`).
- **Тесты:** интеграционный (реальный ffmpeg в Docker) — аудио с прикреплённой обложкой
  (`lavfi sine` + одиночный кадр как attached picture) проходит обработку в m4a + волну; либо unit на
  ветке-различении, если она выделена.

### 4. Контракт «mp4/H.264+AAC» не гарантирован для видео без аудиодорожки, и нет теста на немое видео

`FfmpegMediaVideoProcessor` транскодирует через `X264` с `setAudioKiloBitrate(...)`, но php-ffmpeg добавляет
аудио-выход только если у входа есть аудиопоток. Для немого видео (`video/*` без звука — штатный вход,
приём его разрешает) выход получит только H.264-видеопоток без AAC. Декларированный планом и решением 3
контракт — именно «mp4/**H.264+AAC**»; для немого входа `+AAC` не соблюдается. Интеграционный тест
`testVideoProcessorTranscodesToMp4WithPoster` создаёт вход всегда со звуком (`lavfi sine`), поэтому этот
пробел не ловится — `assertContains('aac', $codecs)` проходит лишь потому, что у фикстуры есть аудиодорожка.

Практический риск ниже, чем у замечания 3: mp4 без AAC всё равно валиден и воспроизводится; вопрос — нужно
ли формально соблюсти «H.264+AAC» (например, добавив тихую дорожку `anullsrc`) или сузить контракт до
«H.264, AAC при наличии звука». Это решение по контракту, а не явный баг.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/FfmpegMediaVideoProcessor.php:107-114`
  (`X264` + `setAudioKiloBitrate`, `save()` — без принудительной аудиодорожки для немого входа);
  тест-пробел — `tests/Feature/Modules/Media/Infrastructure/FfmpegMediaProcessorIntegrationTest.php`
  (фикстура всегда со звуком).
- **Что подтверждает проблему:** кросс-CLI (Codex) локальным прогоном ffmpeg показал, что для входа без
  аудио выход содержит только `h264,video`; код тихую дорожку не добавляет и немое видео не отклоняет.
- **Как исправить:** определиться с контрактом — либо принудительно добавлять тихую AAC-дорожку
  (`anullsrc`) для немого входа, либо явно сузить контракт до «AAC при наличии аудиопотока» в плане/README;
  в любом случае закрепить выбор интеграционным тестом на немое видео.
- **Тесты:** интеграционный тест видео без аудиодорожки (`lavfi testsrc` без `sine`), фиксирующий
  выбранный контракт (наличие/отсутствие AAC).
