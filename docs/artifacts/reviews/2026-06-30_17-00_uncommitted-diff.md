## Замечания

### 1. Показ аватаров стал в несколько раз тяжелее по запросам к базе

Раньше, чтобы получить ссылку на аватар пользователя, система делала один запрос — брала запись о медиа и строила ссылку. Теперь тот же путь всегда дополнительно подгружает все варианты-превью медиа (картиночные, видео и аудио), хотя для аватара нужна только ссылка на оригинал — превью сразу выбрасываются.

Это особенно заметно на списках профилей: для каждого пользователя в списке сборка профиля вызывается отдельно, и на каждого теперь уходит примерно четыре запроса вместо одного, причём три из них загружают данные, которые тут же игнорируются. На ленте авторов или списке участников это умножается на число пользователей и бьёт по скорости. Иронично, что вся затея с прямой связью на медиа задумывалась именно ради устранения лишних запросов, а здесь, наоборот, добавляется лишняя нагрузка.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Media/Application/Query/FindMediaUrl/FindMediaUrlHandler.php:32` (вызывает `findByIdWithConversions`), `app/src/Modules/User/Application/Profile/UserPublicProfileAssembler.php:47` (использует только `->original`), `app/src/Modules/User/Application/Query/GetUserPublicProfiles/GetUserPublicProfilesHandler.php:38` (вызов в `->map()` по списку).
- **Что подтверждает проблему:** `FindMediaUrlHandler` безусловно зовёт `MediaRepository::findByIdWithConversions()`, которая делает `->load('imageConversions')->load('videoConversions')->load('audioConversions')` (основной запрос плюс до трёх relation-load запросов Cycle), а потребитель аватара читает только `$mediaUrls->original->url`. Конверсии в этом пути не нужны.
- **Как исправить:** дать потребителю аватара путь без подгрузки конверсий. Варианты: (а) в `FindMediaUrl` грузить конверсии лениво/опционально (например, отдельный лёгкий запрос только оригинала для аватара), или (б) для аватара использовать запрос, который возвращает только оригинал без `->load(...)` конверсий. Ключ — не загружать три relation, результат которых сразу отбрасывается.
- **Тесты:** добавить тест, фиксирующий число выборок на сборку профиля (или хотя бы что конверсии не подгружаются для аватар-пути), чтобы регрессия по запросам ловилась.

### 2. Верхняя граница срока presigned-ссылки скачивания не проверяется в конфиге

Для приватного медиа ссылка на скачивание живёт ограниченное время. Срок по умолчанию задаётся в настройке через переменную окружения. В комментарии к настройке и в документации указано, что допустимый диапазон — от 1 секунды до 7 суток (604800), но сам конфиг обрезает только снизу: гарантирует «не меньше 1», а слишком большое значение пропускает как есть.

Проблема проявится при неудачной настройке окружения: если кто-то выставит значение больше 7 суток, приложение спокойно стартует, но при первом же построении ссылки на любое приватное медиа упадёт с внутренней ошибкой 500 — и так для всех приватных файлов, пока настройку не поправят. То есть ошибка вскроется не при запуске, а уже на боевом запросе пользователя.

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/config/media.php:18` (`'presignedTtlSeconds' => \max(1, (int) \env('MEDIA_PRESIGNED_TTL_SECONDS', 3600))`), валидация диапазона — `app/src/Modules/Media/Domain/ValueObject/MediaPresignedTtl.php` (`MIN = 1`, `MAX = 604_800`), использование — `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php:79` (`MediaPresignedTtl::fromInt($presignedTtlSeconds ?? $this->mediaConfig->presignedTtlSeconds)`).
- **Что подтверждает проблему:** `\max(1, ...)` ограничивает только нижнюю границу; `.env.sample` и `README.md` заявляют «диапазон 1..604800». При значении из конфига > 604800 `MediaPresignedTtl::fromInt()` бросит `InvalidDomainValueException` (500) на каждом построении URL приватного медиа.
- **Как исправить:** ограничить значение в конфиге сверху (`\min(604_800, \max(1, ...))`) либо проверять диапазон при старте в конструкторе `MediaConfig` (как уже сделана проверка порога multipart), чтобы неверная настройка падала на запуске, а не на пользовательском запросе.
- **Тесты:** тест маппинга `MediaConfig`, что значение зажимается/валидируется по верхней границе.

### 3. Проверка «есть ли хоть одна конверсия» поднимает из базы все конверсии целиком

Перед удалением оригинала команда проверяет, что у медиа осталась хотя бы одна конверсия (иначе после удаления оригинала не останется доступного контента). Сейчас эта проверка для каждого вида конверсий выгружает из базы все строки целиком и потом смотрит, пуст ли результат, хотя достаточно было бы спросить у базы только «есть/нет».

Это не ошибка поведения — команда удаления оригинала вызывается редко, и автор честно отметил в комментарии, что агрегирующего метода в репозиториях нет. Но это лишняя гидрация сущностей ради булева ответа; на крупных наборах конверсий это заметная трата. Помечаю как место для улучшения, а не как блокер.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php:63` (вызов `hasConversion()`), тело метода — `:85`, проверка `findByMediaId(...)->isNotEmpty()` по трём репозиториям — строки `:89-91`.
- **Что подтверждает проблему:** `findByMediaId()` возвращает гидрированную коллекцию сущностей, а используется только `isNotEmpty()`; для ответа на вопрос наличия достаточно `exists`/`count`-запроса.
- **Как исправить:** добавить в репозитории конверсий доменный метод вида `existsForMediaId(MediaId): bool` (на `select()->...->limit(1)` или count) и использовать его в `hasConversion()`. Ранний выход по `||` сохранить.
- **Тесты:** покрыть новый метод репозитория (есть/нет конверсии) и сохранить существующий тест ветки 422 `no_conversions_to_keep`.

### 4. Сборка ленты строит и подписывает URL всех конверсий, хотя берётся только оригинал

При сборке вложений ленты для каждого медиа строится полный набор URL — оригинал и все конверсии (картиночные, видео, аудио), — но в ответ берётся только ссылка на оригинал, а конверсии тут же отбрасываются. Для приватного медиа на каждую отброшенную конверсию впустую вычисляется presigned-ссылка. На странице ленты это умножается на число постов, вложений и конверсий: десятки лишних presigned-подписей и объектов на запрос.

Это та же первопричина, что и в замечании №1 (`MediaUrlService::getUrls()` всегда собирает все конверсии, даже когда потребителю нужен только оригинал), но в другом месте и с другой ценой: здесь конверсии уже загружены eager (это сознательный выбор), лишней нагрузкой становится подписание URL, а не запросы в БД. Поэтому отмечаю отдельно и мягче, чем №1.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/View/PostViewAssembler.php:273-285` (`mediaItem()` зовёт `getUrls()`, читает только `$mediaUrls->original->url`), `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php:60-63` (`getUrls()` всегда строит `conversions`), `:85-117` (`conversionUrls()` резолвит каждую конверсию), `app/src/Modules/Media/Infrastructure/FileService/PresignedMediaUrlResolver.php:22-28` (`resolve()` → `presignGet()` на каждую конверсию).
- **Что подтверждает проблему:** `mediaItem()` вызывает `$this->mediaUrlService->getUrls(media: $postMedia->media)` и использует только `original`; `getUrls()` безусловно заполняет `conversions: $this->conversionUrls(...)`, а для приватного медиа `PresignedMediaUrlResolver::resolve()` делает `presignGet()` на каждую конверсию. В самом `mediaItem()` есть комментарий, что конверсии в ленте сейчас не используются — значит результат `conversions` гарантированно отбрасывается.
- **Как исправить:** дать потребителям, которым нужен только оригинал (лента и аватар из №1), путь без построения конверсий — например, опциональный режим/отдельный метод `MediaUrlService`, строящий только `original`, или ленивое построение конверсий. Общий с №1 фикс закрывает оба места.
- **Тесты:** тест, фиксирующий, что для лента-/аватар-пути конверсии не резолвятся (число вызовов `presignGet`/построений URL не растёт с числом конверсий).

### 5. В набор изменений попало несвязанное правило форматирования

Вместе с функциональными правками включено новое правило линтера для всего репозитория — приведение строк к одинарным кавычкам. Это правка инструмента форматирования, а не части про медиа, и она затрагивает стиль во многих местах. Изменение расширяет область коммита за пределы заявленной задачи. Отдельного правила про «точечные изменения» в `docs/rules.md` нет (есть только требование к языку коммитов), поэтому это рекомендация хорошего тона, а не нарушение нормы: общие правки стиля лучше выделять отдельным коммитом/PR, чтобы дифф задачи оставался про задачу. К тому же `single_quote` входит в общий прогон форматирования (`composer cs`), поэтому корректно либо прогнать форматирование по всему репозиторию одним махом, либо вынести само правило отдельно — иначе одинарные кавычки окажутся применены неравномерно.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `.php-cs-fixer.dist.php:12` (`'single_quote' => true`).
- **Что подтверждает проблему:** правило относится к стилю всего проекта и не связано с логикой медиа/локали; смешано с функциональным изменением.
- **Как исправить:** либо вынести правило линтера и связанную переформатировку в отдельный коммит/PR, либо явно отметить в сообщении коммита, что включено общерепозиторное правило стиля.
- **Тесты:** не требуются — изменение конфигурации линтера.
