## Замечания

### 1. Тип `kind` у ссылки конверсии шире, чем реальность: допускает `Document`, которого у конверсии не бывает

Новый DTO ссылки на конверсию хранит «вид для рендера на клиенте» в поле `kind` типом `MediaType`. Но
у `MediaType` четыре варианта (image/video/audio/document), а конверсия по своей природе бывает только
image, video или audio — документ не конвертируется. То есть тип поля допускает значение `document`,
которое в это поле никогда не попадёт.

Практический риск отложенный и небольшой, но реальный именно из-за правил проекта: правила требуют
исчерпывающего `match` по enum без `default`. Любой будущий потребитель, который захочет разобрать
`kind` через `match`, будет вынужден добавить ветку `Document` — заведомо мёртвую — только чтобы
удовлетворить исчерпывающность, либо нарушить правило и поставить `default`. То есть слишком широкий тип
создаёт будущим вызывающим лишнюю мёртвую ветку. Пункт необязательный: переиспользование `MediaType`
прагматично и явно описано в докблоке (постер видео имеет `kind = image`), а заведение отдельного
3-вариантного enum можно счесть переусложнением. Решение — сознательно подтвердить переиспользование
`MediaType` либо сузить тип.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Dto/MediaConversionUrl.php:21` (`public MediaType $kind`); значения проставляются только image/video/audio в `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php:112,122,132` (`kind: MediaType::Image/Video/Audio`); enum — `app/src/Modules/Media/Domain/Enum/MediaType.php` (4 варианта, включая `Document`).
- **Что подтверждает проблему:** `conversionUrls()` создаёт `MediaConversionUrl` ровно с тремя видами (Image/Video/Audio), `Document` не используется и появиться не может; при этом тип поля его допускает.
- **Как исправить:** вариант А — оставить как есть (переиспользование `MediaType` осознанно, докблок это поясняет), тогда пункт просто подтвердить. Вариант Б — завести узкий enum «вид конверсии» с тремя вариантами (image/video/audio) и типизировать `kind` им; тогда исчерпывающий `match` у потребителя не тянет мёртвую ветку `Document`. Если объём фичи не оправдывает новый enum, оставить вариант А.
- **Тесты:** при варианте Б — обновить ожидания `kind` в `FindMediaUrlHandlerTest` (`assertSame(MediaType::Image, ...)` → новый enum); новые тесты не требуются.

### 3. `RemoveMediaOriginalHandler` — семь зависимостей, три репозитория ради единственной проверки существования конверсии

Конструктор обработчика держит семь зависимостей; три из них (`MediaImageConversionRepository`,

масштабировании паттерна. Альтернатива — вынести проверку существования конверсий в отдельный
Application-сервис/Query модуля Media (`CheckMediaHasConversions`) либо в единый метод с cross-type
EXISTS, чтобы обработчик не зависел от каждого типа конверсии напрямую.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php:38-46` (конструктор, 7 зависимостей), `:92-99` (`hasConversion()` через три репозитория).

- **Как исправить:** инкапсулировать «существует ли хотя бы одна конверсия медиа» в один Application-сервис/Query модуля Media и инжектить его вместо трёх репозиториев.

### 4. Инвариант согласованности `partSize()`/`partsCount()` в `MediaUploadPlannerContract` держится только докблоком

Контракт требует, чтобы `partsCount(size)` делил размер именно на то значение, которое возвращает
`partSize()` (докблок, строки 26-31). Тип системы это не защищает: будущая реализация (продакшн-вариант
с другим алгоритмом или тест-двойник) может рассчитать `partsCount` иначе без ошибки компиляции — и
`MediaMultipartUpload` соберётся с несогласованной парой `(partsCount, partSize)`. Сейчас реализация одна,
поэтому риск отложенный — он материализуется только при появлении второй реализации контракта.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Contract/MediaUploadPlannerContract.php:21-34` (`partSize()`/`partsCount()` + докблок-инвариант).
- **Что подтверждает проблему:** `partsCount(MediaFileSize)` и `partSize()` — независимые методы; связь между ними выражена только текстом докблока, не сигнатурой.
- **Как исправить:** либо передавать `partsCount` уже полученный `MediaMultipartPartSize` аргументом (тогда деление гарантированно на то же значение), либо объединить оба в один метод, возвращающий согласованную пару.
- **Тесты:** при изменении сигнатуры — обновить `MediaUploadPlannerTest`; новых сценариев не требуется.

### 5. `AppBootloaderTest` слабо проверяет сборку `LocaleResolver` из конфига

что fallback равен именно значению по умолчанию из `LocaleConfig`. Тест пройдёт, даже если бутлоадер
соберёт резолвер с неверным default (например, `'en'`, когда в конфиге `'ru'`), поэтому он не валидирует
заявленное «собран из конфига» до конца.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `tests/Kernel/Shared/Infrastructure/Framework/Bootloader/AppBootloaderTest.php:20`.

- **Как исправить:** получить фактический default из `LocaleConfig` (через контейнер) и сравнить `resolve('zz') === $config->default` (а supported-локаль — проверить отдельным `resolve($supported) === $supported`).

### 6. Прямое чтение статуса вместо доменного предиката в `RemoveMediaOriginalHandler`

Обработчик читает `$media->status === MediaStatus::ReadyOriginalRemoved` напрямую (строка 58), хотя у
`Media` есть предикаты `isReady()` и `isFinalized()`, инкапсулирующие сравнение с конкретными статусами,
но нет `isOriginalRemoved()`. Из-за этого Application знает конкретный вариант enum — ровно та деталь,
которую предикаты `isReady()`/`isFinalized()` существуют, чтобы прятать. Оговорка (architecture-check): это
консистентный pre-changeset паттерн — `DeleteMediaHandler:46` (уже в HEAD, вне diff) точно так же читает
`$media->status === MediaStatus::WaitingUpload`. То есть это не уникальная регрессия данного changeset-а, а
согласованность с существующим кодом, поэтому пункт мягкий.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php:58`; отсутствует предикат в `app/src/Modules/Media/Domain/Entity/Media.php` (есть `isReady()`/`isFinalized()`, нет `isOriginalRemoved()`).
- **Что подтверждает проблему:** ранний no-op (строки 58-64) сравнивает публичное enum-свойство напрямую, минуя доменный предикат, в отличие от `isReady()`-guard ниже (строка 66).
- **Как исправить:** при желании выровнять домен — добавить `Media::isOriginalRemoved()` и использовать его здесь; для полной консистентности заодно перевести `DeleteMediaHandler` на аналогичный предикат для `WaitingUpload`.
- **Тесты:** существующие ветки `RemoveMediaOriginalHandlerTest` остаются; новых сценариев не требуется.

### 7. Тройное дублирование map-блоков в `MediaUrlService::conversionUrls()`

Метод содержит три почти идентичных блока `->toBase()->map(...)` (строки 110-138), отличающихся только

добавление четвёртого вида конверсии потребует ещё одного копипаст-блока. Обобщение ограничено типизацией
PHP (три разных Entity-класса и три типизированные коллекции), поэтому пункт минорный.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php:110-138` (`conversionUrls()`).
- **Что подтверждает проблему:** три `map`-блока совпадают по структуре и различаются лишь коллекцией, типом элемента и `kind`.
- **Как исправить:** при появлении 4-го вида конверсии — рассмотреть вспомогательный приватный метод с union-типом коллекции/элемента; до этого дублирование терпимо и явно ограничено типизацией.
- **Тесты:** изменение внутреннее, поведение прежнее — новых тестов не требуется.
