# Переезд кодовой базы на целевую архитектуру

## Контекст

Roadmap нужен команде разработки. Он перечисляет задачи, после выполнения которых кодовая база целиком соответствует `docs/arch.md` и продолжает работать.

Горизонт — одна большая миграция, разбитая на последовательные шаги. Каждая задача описана как проверяемое состояние проекта: её можно выполнить и проверить отдельно, а проект между шагами остаётся рабочим.

Текущее состояние отличается от целевого по всем крупным границам: ни у одного модуля нет слоя `Public`, соседи обращаются друг к другу напрямую к сценариям, представлениям и доменным значениям; доменные сущности несут разметку хранения и ссылаются на инфраструктуру; реализации хранения лежат в отдельной верхнеуровневой папке модуля; чтения под ответ собираются промежуточными представлениями вместо Reader и Data; у семи модулей есть верхнеуровневый слой `Presentation`; миграции, переводы, шаблоны, конфигурация и тесты вынесены из модулей в общие папки; у трёх модулей нет собственного bootloader; общая часть содержит код модуля `Media`.

## Предположения

- Roadmap опирается на фактическую структуру проекта, потому что пользователь прямо попросил привязку к текущему состоянию.
- Формулировки задач используют словарь целевой архитектуры (модули, слои, роли классов), так как именно они и есть предмет переезда. Способ выполнения, конкретные классы и порядок правок остаются за планом реализации.
- Состав модулей не меняется: переезд не добавляет и не удаляет предметные области.
- Внешнее поведение не меняется: публичный HTTP API, схема базы, формат событий и доставка остаются прежними; исключения возможны только там, где текущее поведение прямо противоречит целевой архитектуре, и согласуются отдельно.
- Сценарный слой у модулей, где его сейчас нет, создаётся минимально и только там, где он нужен для обслуживания публичного контракта или уже существующего поведения.
- Модуль `Access` сейчас фактически не используется остальным кодом; переезд приводит его к целевой форме и подключает к объявлению требований доступа, а не расширяет его возможности.
- Переезд идёт одной веткой с последовательными шагами, каждый шаг завершается рабочим проектом и зелёными проверками.

## Задачи

| # | Задача | Описание |
|---|---|---|
| 1 | Карта расхождений | Зафиксирован полный перечень отклонений кодовой базы от целевой архитектуры по модулям и слоям, с владельцем каждой таблицы, каждого перевода, шаблона, секции конфигурации и группы тестов. Дальнейшие шаги опираются на этот перечень, а его пункты закрываются по мере переезда. |
| 2 | Общая часть переименована по целевой схеме | Общая инфраструктура приведена к целевому виду: композиционный корень и общие адаптеры фреймворка лежат там, где их ожидает целевая структура, верхнеуровневого слоя представления в общей части нет. Приложение запускается и проходит проверки. |
| 3 | Общая часть свободна от кода модулей | Представления и ответы, относящиеся к медиа, переданы модулю-владельцу, общая часть содержит только примитивы без владельца и не импортирует бизнес-модули. |
| 4 | У каждого модуля один свой bootloader | Все девять модулей имеют собственный bootloader, включая те, у которых его сейчас нет; композиционный корень перечисляет только модули и не повторяет их внутреннюю настройку. |
| 5 | Интеграционные события в публичном слое | Сообщения, которые модуль публикует наружу, лежат в его публичном слое как интеграционные события; внутренние доменные события остаются внутри домена. Обмен через очередь работает как прежде. |
| 6 | Синхронные обращения через публичный контракт | Каждое синхронное межмодульное обращение объявлено публичным контрактом модуля-владельца, реализовано входным адаптером публичного API и выражено через сценарий владельца. Прямых вызовов чужих сценариев в коде нет. |
| 7 | Межмодульные ответы в публичных DTO | Данные, которые модуль отдаёт соседям, описаны публичными DTO и их типизированными списками; чужие внутренние представления и результаты сценариев соседями не используются. |
| 8 | Требования доступа объявляются публичными атрибутами | Маршрут объявляет нужный доступ публичным атрибутом модуля-владельца сессий или прав, общий HTTP-адаптер применяет его до контроллера. Бизнес-модули не импортируют чужие middleware. Поведение защищённых и публичных маршрутов не меняется. |
| 9 | Ссылки на чужие сущности без навигации | Чужие доменные значения и сущности заменены собственными объектами-ссылками; межмодульных связей уровня хранения и чтения чужих таблиц нет. Проверка и дочитывание чужих данных идут через публичный слой соседа. |
| 10 | Доменные исключения и события у владельца | Ожидаемые ошибки бизнес-смысла и внутренние доменные события каждого модуля описаны в его домене; в общей части остаются только исключения без владельца. Ответы об ошибках и их переводы не меняются. |
| 11 | Интерфейсы Repository в домене | У каждого корня агрегата есть доменный интерфейс Repository, сценарии зависят только от него, реализация на ORM живёт в инфраструктуре модуля. Верхнеуровневой папки хранения у модулей больше нет. |
| 12 | Массовая запись — отдельный порт | Прямая массовая запись выполняется отдельным инфраструктурным портом с явным именем и не маскируется под Repository агрегата. |
| 13 | Домен отделён от хранения в простых модулях | В модулях с небольшим числом сущностей доменная сущность не знает о хранении: форма хранения описана отдельной моделью, преобразование — mapper, имена таблиц и колонок — каталогом, преобразования значений — своими классами. Данные и запросы работают как прежде. |
| 14 | Домен отделён от хранения в остальных модулях | То же состояние достигнуто в модулях с большим числом сущностей и связей. После шага ни одна доменная сущность не содержит разметки хранения и не ссылается на инфраструктуру. |
| 15 | Чтение под ответ выполняет Reader | Там, где ответу нужны признаки вне агрегата, чтение выполняет Reader своего модуля и возвращает типизированные данные чтения. Промежуточные представления и их сборщики удалены, форма ответа сценария лежит рядом со сценарием, переиспользуемые части — в общем месте сценарного слоя. |
| 16 | Сценарии разложены по целевым папкам | Сценарный слой каждого модуля содержит только целевые разделы: команды и запросы по папкам действий, порты технических зависимостей, данные чтения, части результата и ошибки сценариев. Прочих разделов в сценарном слое нет. |
| 17 | HTTP-адаптеры внутри инфраструктуры | Контроллеры, фильтры, middleware, ресурсы и ответы каждого модуля живут в его инфраструктурной границе фреймворка. Маршруты, формы запросов и ответов не меняются. |
| 18 | Остальные входные адаптеры внутри инфраструктуры | Обработчики очереди, консольные команды и Temporal-адаптеры перенесены в инфраструктурную границу фреймворка; верхнеуровневого слоя представления у модулей больше нет. |
| 19 | Технические границы разложены по владельцам | Хранение, файлы, кэш, внешние клиенты, почта, push и realtime собраны каждый в своей явно названной инфраструктурной границе модуля-владельца. |
| 20 | Миграции внутри модулей | Каждая миграция лежит у модуля-владельца таблиц и меняет только его таблицы, путь регистрирует bootloader модуля, единый порядок имён в рамках приложения сохранён. Применение миграций с нуля и на существующей базе даёт прежний результат. |
| 21 | Переводы внутри модулей | Пользовательские сообщения модуля лежат внутри модуля и подключаются его bootloader; в общих переводах остаются только тексты без владельца. Многоязычные ответы не меняются. |
| 22 | Шаблоны внутри модулей | Шаблоны писем и служебных страниц лежат внутри модуля-владельца и подключаются его bootloader; общая папка шаблонов не содержит модульных файлов. |
| 23 | Конфигурация модулей внутри модулей | Секция конфигурации модуля и её типизированное представление принадлежат модулю и регистрируются его bootloader; в общей конфигурации остаются только секции без владельца. Переменные окружения и значения по умолчанию не меняются. |
| 24 | Тесты модулей внутри модулей | Проверки модуля лежат внутри него и разделены на быстрые доменные и сценарные, интеграционные и сквозные; в корневом наборе остаются только межмодульные и общесистемные проверки. Полное покрытие кода сохранено. |
| 25 | Имена классов соответствуют конвенции | Имена классов во всех модулях называют роль и слой по таблице ролей целевой архитектуры, поэтому граница видна без перехода к определению. |
| 26 | Структура модулей совпадает с целевым деревом | Дерево каждого модуля совпадает с целевым: лишних и устаревших разделов нет, а созданы только те разделы, для которых есть код. |
| 27 | Самодостаточность модуля подтверждена | Для каждого модуля подтверждено: подключение сводится к регистрации его bootloader, а его файлы не остаются в чужих папках при отключении. Глобальными остаются только части без владельца. |
| 28 | Инструменты проекта настроены на новое дерево | Автозагрузка, статический анализ, запуск тестов и покрытия, генерация спецификации API и сборка окружения работают с новой структурой без ручных исключений. |
| 29 | Границы проверяются автоматически | Направления зависимостей между слоями и модулями, запрет фреймворка в домене, сценариях и публичном слое, а также обращение к соседу только через публичный слой проверяются автоматически и падают при нарушении. |
| 30 | Статус архитектуры обновлён | Документ архитектуры отражает, что кодовая база соответствует целевому состоянию, а известные отступления перечислены явно с причиной и сроком. |

## Не входит

- Новая продуктовая функциональность и изменение бизнес-правил.
- Изменение публичного HTTP API, схемы базы данных и формата интеграционных событий, кроме согласованных отдельно случаев.
- Разделение монолита на отдельные сервисы, смена брокера, хранилища или фреймворка.
- Переход на event sourcing и отдельную базу чтения.
- Изменения в собственных Composer-пакетах проекта: они правятся в своих репозиториях и подключаются выпущенной версией.
- Оптимизация производительности, если она не следует из самого переезда.
