# План реализации

## Задача

Сделать локальный цикл тестов быстрым, не нарушая правило проекта о Docker-запуске проверок. Готовый результат: `make test-unit` запускает только настоящие unit-тесты без Spiral kernel, container, БД и storage; kernel/integration-тесты вынесены в отдельный suite; полный `make test` и `make qa` остаются чистыми Docker-проверками, но используют ParaTest и PCOV без двойного запуска одного и того же набора тестов.

## Контекст

Проект требует запускать тесты приложения через `make test`, а PHPStan через `make phpstan`. Правила также требуют 100 процентное покрытие тестами и интеграционный тест для каждого роута.

Текущий `make test-unit` запускает `vendor/bin/phpunit --testsuite Unit`, а suite `Unit` в `phpunit.xml` указывает на весь каталог `tests/Unit`. В этом каталоге есть тесты, которые импортируют `Tests\TestCase`, вызывают `getContainer()` и поднимают `Tests\App\TestKernel`, поэтому они не являются лёгкими unit-тестами.

Текущий `make test` всегда зависит от `reset-test`, поднимает PostgreSQL, Redis, MinIO и Mailpit, сбрасывает schema `yoga_loka_test`, очищает bucket `yoga-loka-test`, затем запускает `test-runner`. Текущий `make qa` тоже зависит от `reset-test`, запускает `test-runner` с `--build` и внутри `docker/test/run-qa.sh` выполняет обычные тесты, а затем второй раз тесты с покрытием.

Сейчас в `composer.lock` зафиксированы `phpunit/phpunit` 13.1.8 и `phpunit/php-code-coverage` 14.1.8. По Packagist для этого набора подходит `brianium/paratest` 7.22.4: эта версия требует `phpunit/phpunit:^13.1.8` и `phpunit/php-code-coverage:^14.1.8`. Более новая ветка ParaTest не берётся в этой задаче, чтобы не расширять работу обновлением PHPUnit.

PCOV актуален как `pecl/pcov` 1.0.12. В Ubuntu 26.04 для текущего Docker image доступен пакет `php8.5-pcov` версии `1.0.12-1ubuntu1`, поэтому расширение ставится через apt рядом с `php8.5-xdebug`. PCOV должен быть выключен по умолчанию и включаться только для coverage-команд, потому что PCOV не совместим с включённым Xdebug.

Соседний проект `../novostroikino-spiral` уже применял похожее ускорение, но его нельзя переносить один в один: там multi-tenant схема с platform DB и tenant DB, а в YogaLoka одна тестовая PostgreSQL БД и отдельный MinIO bucket. Из соседнего проекта берутся только подходы, которые подходят YogaLoka: строгий pure `Unit`, `tests/warmup.php` для Cycle schema cache, транзакционный rollback для обычных DB-тестов, per-worker ресурсы для ParaTest и fake storage по умолчанию там, где storage не является предметом теста.

Официальные источники, проверенные при планировании:

- Packagist `brianium/paratest`: https://packagist.org/packages/brianium/paratest
- GitHub README ParaTest: https://github.com/paratestphp/paratest
- Packagist `pecl/pcov`: https://packagist.org/packages/pecl/pcov
- PECL PCOV: https://pecl.php.net/package/pcov

## Принятые решения

Режим плана: normal. Источник подтверждения: ответ пользователя `Normal`.

Dev-инструменты добавляются. Источник подтверждения: research содержит ответ пользователя `Да вариант 2 нравится`, где вариант 2 означает ParaTest + PCOV.

`brianium/paratest` фиксируется как точная dev-зависимость `7.22.4`, потому что она совместима с текущими `phpunit/phpunit` 13.1.8 и `phpunit/php-code-coverage` 14.1.8. PHPUnit в рамках этой задачи не обновляется.

PCOV ставится в Docker image через apt-пакет `php8.5-pcov` версии `1.0.12-1ubuntu1`. В базовом окружении остаётся `ENV XDEBUG_MODE=off`; для PCOV добавляется настройка, которая выключает PCOV по умолчанию, а coverage-команда включает его через параметры PHP.

Быстрый unit suite означает только тесты на `PHPUnit\Framework\TestCase`, без `Tests\TestCase`, `getContainer()`, Spiral kernel, БД, MinIO, Redis, RabbitMQ, Temporal и RoadRunner. Это правило закрепляется отдельной проверкой, чтобы новые kernel-тесты не возвращались в `tests/Unit`.

Kernel suite всегда запускается после `reset-test`, потому что перенесённый `OutboxDebugLogJobTest` использует `EntityManager` и outbox store.

Параллельный запуск поддерживает только `TEST_PARALLEL_PROCESSES` от `1` до `4`, значение по умолчанию `4`. Если передано другое значение, скрипт подготовки падает до очистки БД и bucket-ов.

`make test-coverage` является полным тестовым запуском с покрытием и обязан включать suite-ы `Unit`, `Kernel` и `Feature`. `make qa` использует этот один полный coverage-run вместо отдельного `composer test` перед покрытием.

`composer test` остаётся простым запуском `phpunit`. `composer qa` обновляется и больше не дублирует `test` перед `test-coverage`: он запускает стиль, PHPStan и один полный coverage-run.

Для `TEST_TOKEN` добавляется конкретный bootstrap `tests/bootstrap.php`. `phpunit.xml` меняет `bootstrap` с `vendor/autoload.php` на `tests/bootstrap.php`, а новый bootstrap выставляет worker-переменные окружения до подключения `vendor/autoload.php`.

Namespace перенесённых kernel-тестов меняется с `Tests\Unit\...` на `Tests\Kernel\...`, чтобы путь и namespace совпадали.

PostgreSQL template database не используется в этой задаче. Причина: текущая главная задержка связана с лишним kernel boot, пересборкой Cycle schema и работой DB-тестов, а не с созданием тестовой БД перед каждым отдельным тестом. Миграции остаются production-like проверкой и выполняются один раз перед suite или worker.

Для Cycle schema добавляется явный warmup: новый `tests/warmup.php` поднимает `Tests\App\TestKernel`, форсирует получение `Cycle\ORM\SchemaInterface` и проверяет наличие `cache/cycle.php` внутри текущего runtime-каталога. Warmup запускается перед `Kernel`, `Feature`, `test`, `test-coverage` и `qa`, чтобы worker-ы не компилировали schema параллельно и чтобы первый тест не платил цену прогрева.

Для обычных DB-тестов добавляется `Tests\DatabaseTestCase`: он открывает транзакцию в `setUp()` и откатывает её в `tearDown()`. Это ускоряет очистку данных между тестами и убирает ручные `delete()` там, где тест не проверяет commit/relay/инфраструктурные побочные эффекты.

Не все DB-тесты переводятся на общий rollback. Outbox relay, queue status, console-команды, тесты транзакций, storage-интеграции и тесты, где нужно проверить состояние после commit-а, остаются без общего rollback через `useDatabaseTransaction(): false` или отдельный базовый класс `Tests\NonTransactionalDatabaseTestCase`.

Для storage вводится правило: если storage не является предметом теста, `DatabaseTestCase` подменяет `StorageInterface` fake-реализацией. Тесты, которые реально проверяют MinIO/S3, используют отдельный `Tests\RealStorageTestCase`.

Текущие файлы из `tests/Unit`, которые используют `Tests\TestCase`, переносятся в новый каталог `tests/Kernel` с сохранением внутренней структуры:

- `tests/Unit/DemoTest.php`
- `tests/Unit/Modules/Outbox/Presentation/Job/OutboxDebugLogJobTest.php`
- `tests/Unit/Shared/Infrastructure/Configuration/CacheConfigBindingTest.php`
- `tests/Unit/Shared/Infrastructure/Configuration/ComplexConfigBindingTest.php`
- `tests/Unit/Shared/Infrastructure/Configuration/ConfigShapeTest.php`
- `tests/Unit/Shared/Infrastructure/Configuration/MediaStorageConfigTest.php`
- `tests/Unit/Shared/Infrastructure/Configuration/SimpleConfigBindingTest.php`

`test_strategy: after_each_phase` применяется так: каждая фаза заканчивается своим ограниченным запуском, а полный `make test`, `make phpstan` и `make qa` выполняются в финальной фазе.

`logging_strategy: debug_precise` применяется к tooling-скриптам: новые и изменённые shell-команды печатают короткие русские сообщения о старте, параметрах запуска, suite, количестве процессов, coverage driver, имени тестовой базы и bucket-а. Логи не должны раскрывать секреты из `.env`.

Один владелец миграций для полного тестового окружения — `docker/test/migrate-test-databases.sh`, который вызывается после `reset-test` и очистки ресурсов. `reset-test` поднимает сервисы и очищает тестовые БД/bucket-ы, но не запускает миграции. Runner-скрипты не дублируют `php app.php migrate --force` напрямую.

## Целевой алгоритм

Финальное поведение строится вокруг двух режимов: быстрый unit-цикл без kernel и полный Docker-gate с подготовленной БД, warmup и изоляцией worker-ов.

Подготовка полного тестового окружения работает так:

- `reset-test` проверяет, что `TEST_PARALLEL_PROCESSES` равен `1`, `2`, `3` или `4`; при другом значении команда падает до очистки данных.
- `reset-test` поднимает только нужные test-сервисы: PostgreSQL, Redis, MinIO и Mailpit.
- `reset-test` очищает только разрешённые тестовые ресурсы: `yoga_loka_test`, `yoga_loka_test_1` ... `yoga_loka_test_4`, `yoga-loka-test`, `yoga-loka-test-1` ... `yoga-loka-test-4`.
- После очистки `docker/test/migrate-test-databases.sh` выполняет миграции один раз на базовой БД и один раз на каждой активной worker-БД.
- После миграций запускается `make warmup`: он удаляет старые `cache/cycle.php` из тестовых runtime-каталогов, поднимает тестовый Spiral kernel, форсирует сборку Cycle schema и проверяет, что новый cache-файл создан в каждом прогретом runtime.

Выбор ресурсов внутри тестового процесса работает так:

- Без `TEST_TOKEN` тесты используют базовые ресурсы: `yoga_loka_test`, `yoga-loka-test`, `runtime/testing`.
- При `TEST_TOKEN=1` тесты используют worker-ресурсы: `yoga_loka_test_1`, `yoga-loka-test-1`, `runtime/testing-1`.
- При `TEST_TOKEN=2` тесты используют worker-ресурсы: `yoga_loka_test_2`, `yoga-loka-test-2`, `runtime/testing-2`.
- `tests/bootstrap.php` разрешает пустой `TEST_TOKEN` и значения `1`, `2`, `3`, `4`; любое другое значение завершает bootstrap русской ошибкой до подключения `vendor/autoload.php`.
- `tests/bootstrap.php` выставляет только worker-зависимые переменные `DB_DATABASE`, `S3_BUCKET` и `S3_TEST_BUCKET` до подключения `vendor/autoload.php`. Остальные переменные testing-env остаются в `phpunit.xml` или переносятся без потери значений.
- `Tests\TestCase::defineDirectories()` задаёт отдельный runtime-каталог для базового режима и каждого worker-а.
- Активные worker-ресурсы определяются через `TEST_PARALLEL_PROCESSES`: при значении `1` подготавливается worker `1`, при `4` подготавливаются worker-ы `1..4`. Обычный PHPUnit без ParaTest и без `TEST_TOKEN` использует только базовые ресурсы.

Поведение test suite-ов:

- `Unit` содержит только тесты на `PHPUnit\Framework\TestCase`. Он не поднимает Spiral kernel, не использует container, БД, MinIO, Redis, RabbitMQ, Temporal и RoadRunner.
- `Kernel` содержит тесты на `Tests\TestCase`, которым нужен Spiral kernel или container. Команда `make test-kernel` всегда идёт через `reset-test`, миграции и `make warmup`.
- `Feature` содержит тесты с БД. Обычный DB-тест наследуется от `Tests\DatabaseTestCase`: в `setUp()` открывается транзакция, в `tearDown()` она откатывается, ORM heap очищается, storage по умолчанию заменён fake-реализацией.
- Тесты, которым нужен реальный commit, outbox relay, queue status, console flow или проверка транзакционного поведения, используют `Tests\NonTransactionalDatabaseTestCase` и чистят свои данные явно.
- Тесты, где MinIO/S3 является предметом проверки, используют `Tests\RealStorageTestCase` и работают с реальным test bucket.

Публичные команды работают так:

- `make test-unit` запускает только проверку лёгкого `Unit` suite через Docker `test-runner --no-deps`; `reset-test`, миграции и warmup не выполняются.
- `make test-kernel` выполняет `reset-test`, `docker/test/migrate-test-databases.sh`, `make warmup` и запускает только `Kernel`.
- `make test-feature` выполняет `reset-test`, `docker/test/migrate-test-databases.sh`, `make warmup` и запускает `Feature`; при включённом ParaTest worker-ы получают ресурсы по `TEST_TOKEN`.
- `make test` выполняет один `reset-test`, один `docker/test/migrate-test-databases.sh`, один `make warmup`, затем запускает `Unit`, `Kernel` и `Feature`.
- `make test-coverage` выполняет один `reset-test`, один `docker/test/migrate-test-databases.sh`, один `make warmup`, удаляет старый `runtime/coverage/clover.xml`, запускает `Unit`, `Kernel` и `Feature` с PCOV и проверяет новый Clover-файл через `docker/test/assert-coverage.php`.
- `make qa` выполняет стиль, PHPStan и один полный `test-coverage`; отдельный обычный запуск тестов перед coverage не выполняется.
- `make qa-build` делает то же, что `make qa`, но сначала пересобирает Docker image.

## Контракты реализации

### Данные и БД

Схема приложения и миграции не меняются.

Для тестового запуска добавляются служебные тестовые базы PostgreSQL:

- базовая база остаётся `yoga_loka_test`;
- worker-базы называются `yoga_loka_test_1`, `yoga_loka_test_2`, `yoga_loka_test_3`, `yoga_loka_test_4`;
- количество процессов задаётся переменной `TEST_PARALLEL_PROCESSES`, допустимые значения `1`, `2`, `3`, `4`, значение по умолчанию `4`;
- при значении вне диапазона `1..4` подготовительный скрипт падает до любых destructive-операций;
- активные worker-БД — это диапазон от `yoga_loka_test_1` до `yoga_loka_test_${TEST_PARALLEL_PROCESSES}`;
- `reset-test` удаляет и заново создаёт schema `public` в базовой базе и каждой worker-базе;
- миграции выполняет только `docker/test/migrate-test-databases.sh`: один раз для базовой базы и каждой активной worker-базы до параллельного запуска тестов;
- обычные миграции приложения не меняются.

PostgreSQL template database не создаётся. Если после остальных изменений миграции останутся главным bottleneck по замерам, template DB можно планировать отдельной задачей.

Для MinIO добавляются служебные тестовые bucket-ы:

- базовый bucket остаётся `yoga-loka-test`;
- worker bucket-ы называются `yoga-loka-test-1`, `yoga-loka-test-2`, `yoga-loka-test-3`, `yoga-loka-test-4`;
- `reset-test` очищает базовый bucket и каждый worker bucket;
- `tests/bootstrap.php` выбирает bucket по `TEST_TOKEN`: без `TEST_TOKEN` используется `yoga-loka-test`, с `TEST_TOKEN=1` используется `yoga-loka-test-1`, с `TEST_TOKEN=2` используется `yoga-loka-test-2`;
- `tests/bootstrap.php` выбирает БД по `TEST_TOKEN`: без `TEST_TOKEN` используется `yoga_loka_test`, с `TEST_TOKEN=1` используется `yoga_loka_test_1`, с `TEST_TOKEN=2` используется `yoga_loka_test_2`;
- `tests/bootstrap.php` падает с русской ошибкой при `TEST_TOKEN` вне диапазона `1..4`, до загрузки приложения.

Runtime-файлы покрытия остаются в `runtime/coverage/`. Clover-файл остаётся `runtime/coverage/clover.xml`, чтобы не менять `docker/test/assert-coverage.php`. Перед coverage-run файл удаляется, чтобы старый отчёт не мог считаться успешным результатом.

Для kernel/feature runtime используется отдельный каталог на worker: `runtime/testing` без `TEST_TOKEN` и `runtime/testing-{TEST_TOKEN}` при ParaTest. `Tests\TestCase::defineDirectories()` должен явно задавать `DirectoryAlias::Runtime` в этот каталог.

Для DB-тестов добавляются тестовые базовые классы:

- `Tests\DatabaseTestCase` — открывает транзакцию на `DatabaseInterface` в `setUp()`, откатывает её в `tearDown()`, очищает ORM heap, fake-ит `StorageInterface` по умолчанию;
- `Tests\NonTransactionalDatabaseTestCase` — для тестов, где общий rollback ломает проверку commit, relay, queue status, console flow или транзакционных сценариев;
- `Tests\RealStorageTestCase` — для тестов, где реальный MinIO/S3 является предметом проверки.

`DatabaseInterface` в этих базовых классах используется только в тестовой инфраструктуре для границы транзакции и отключения соединения. Ручной SQL в `app/` и `tests/` не добавляется.

Fake storage живёт в тестовом namespace `Tests\Storage` и подменяет `Spiral\Storage\StorageInterface` через test container перед началом DB-теста. Минимальный контракт fake-реализации: bucket-ы хранят файлы в `runtime/testing-storage` или `runtime/testing-storage-{TEST_TOKEN}`, поддерживают методы, которые реально используют текущие тесты (`write`, `exists`, `getContents`, `delete`), и очищаются между тестами вместе с runtime теста. `Tests\RealStorageTestCase` явно отключает эту подмену и использует реальный `s3-test` bucket.

### API и внешние контракты

HTTP API, OpenAPI, очереди, внешние события и публичные контракты приложения не меняются.

Меняются только команды разработки:

- `make test-unit` запускает быстрый unit suite без reset и без внешних зависимостей;
- добавляется `make test-kernel`, команда всегда выполняет `reset-test`;
- `make test-feature` остаётся отдельным запуском feature suite после reset;
- `make test` остаётся полной Docker-проверкой тестов после reset;
- `make test-coverage` остаётся проверкой покрытия после reset, но использует PCOV и ParaTest;
- добавляется `make warmup`, который пересобирает `cache/cycle.php` внутри тестовых runtime-каталогов после изменений Entity или Cycle config;
- `make qa` остаётся полным quality gate без принудительного `--build`;
- добавляется `make qa-build` для явного запуска QA с пересборкой image;
- `make phpstan` не меняет смысл и остаётся Docker-запуском PHPStan.

## Фазы выполнения

### 1. Разделить быстрые unit-тесты и kernel-тесты

Цель: убрать загрузку Spiral kernel из `make test-unit` и закрепить правило, что unit suite остаётся лёгким.

Что сделать:

- В `phpunit.xml` добавить suite `Kernel`, который указывает на каталог `tests/Kernel`.
- Перенести перечисленные в разделе `Принятые решения` файлы из `tests/Unit` в `tests/Kernel` с сохранением структуры.
- У перенесённых файлов поменять namespace с `Tests\Unit\...` на `Tests\Kernel\...`.
- Оставить в `tests/Unit` только тесты, которые используют `PHPUnit\Framework\TestCase` и не вызывают `getContainer()`.
- Добавить скрипт проверки лёгкого unit suite `docker/test/assert-unit-suite-is-light.sh`.
- В проверке запретить в `tests/Unit` строки `Tests\TestCase`, `getContainer(`, `Tests\App\TestKernel` и `Spiral\Testing\TestCase`. Запрет должен ловить alias-импорты вроде `use Tests\TestCase as KernelTestCase`.
- Подключить эту проверку к `make test-unit` перед запуском PHPUnit.
- Обновить `Makefile`: `test-unit` должен запускать `docker compose --profile test run --rm --no-deps test-runner bash -lc 'bash docker/test/assert-unit-suite-is-light.sh && vendor/bin/phpunit --testsuite Unit'`.
- Добавить цель `test-kernel`, которая зависит от `reset-test`, выполняет миграции и запускает suite `Kernel` через Docker.
- Убедиться, что все новые shell-сообщения написаны по-русски и показывают suite, режим и причину запуска.

Результат: `Unit` и `Kernel` разделены физически и логически; быстрый unit suite больше не может случайно поднять container.

Сценарии тестирования:

- Временная проверка запрета: если в `tests/Unit` есть импорт `Tests\TestCase`, скрипт падает с понятным русским сообщением.
- `make test-unit` проходит без поднятия `postgres`, `redis`, `minio` и `mailpit`.

## Тесты

Стратегия: `after_each_phase`.

После первой фазы запускаются `make test-unit` и `make test-kernel`, чтобы сразу проверить разделение suite-ов.

После второй фазы запускаются `make warmup`, `make test-kernel` и `make test-feature`, чтобы проверить Cycle schema cache, транзакционный rollback, исключения для outbox/commit-сценариев и fake/real storage.

После третьей фазы запускаются `make composer-install`, build `test-runner`, проверка `php -m | grep -E '^pcov$'` внутри `test-runner` и `make test-unit`, чтобы проверить совместимость ParaTest, PCOV и старого unit gate без полного coverage.

После четвёртой фазы запускаются `make test-feature` и `make test-coverage`, чтобы проверить изоляцию worker-БД и worker bucket-ов.

После пятой фазы запускаются `make test-unit`, `make test`, `make qa` и `make qa-build`, чтобы проверить новые публичные команды.

В финале обязательно запускаются `make test`, `make phpstan` и `make qa`.

## Логирование

Стратегия: `debug_precise`.

Изменения касаются tooling, поэтому нужно использовать shell-логи, а не приложение. Все новые и изменённые скрипты должны печатать русские сообщения:

- старт и конец каждого этапа;
- suite: `Unit`, `Kernel`, `Feature`, `Coverage`;
- количество ParaTest-процессов;
- тестовые базы и bucket-ы, которые будут очищены или использованы;
- runtime-каталоги worker-ов;
- результат warmup Cycle schema cache;
- coverage driver `PCOV`;
- путь `runtime/coverage/clover.xml`;
- порог покрытия `100`.

Логировать включение rollback и fake/real storage из каждого PHP-теста не нужно: это проверяется тестами поведения, а не шумом в консоли.

В логах запрещено печатать пароли, секреты, DSN с паролями и значения из `.env`, которые могут быть секретами.
