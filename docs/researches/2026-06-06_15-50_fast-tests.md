# Быстрые тесты приложения

## Суть

Исследовали, почему проверки приложения выполняются долго и как сделать локальный цикл тестов очень быстрым без отказа от Docker-проверок. Проект требует запускать тесты приложения через `make test`, PHPStan через `make phpstan`, а полный Composer QA через Docker-команду `make qa` (`docs/rules.md:101`, `docs/rules.md:102`, `AGENTS.md`).

Главная причина медленных unit-тестов оказалась не в запуске Docker-инфраструктуры. `make test-unit` показывает около минуты, потому что в suite `Unit` лежат не только настоящие unit-тесты, но и тесты, которые наследуются от `Tests\TestCase`, вызывают `getContainer()` и поднимают весь Spiral kernel (`tests/TestCase.php:19`, `tests/TestCase.php:21`, `tests/TestCase.php:41`, `tests/App/TestKernel.php:17`). Эти тесты должны считаться kernel/integration-тестами, даже если физически лежат в `tests/Unit`.

Дополнительные тормоза полного QA тоже есть: перед `make test` всегда сбрасываются PostgreSQL schema и MinIO bucket (`Makefile:27`, `Makefile:71`), `make qa` тоже делает полный reset и запускает test-runner с `--build` (`Makefile:52`), а внутри QA обычные тесты запускаются один раз без покрытия и затем второй раз с покрытием (`docker/test/run-qa.sh:13`, `docker/test/run-qa.sh:16`). Покрытие собирается через Xdebug, потому что Docker image ставит `php8.5-xdebug`, а PCOV в image не установлен (`docker/Dockerfile:30`, `composer.json:103`).

## Решение

Выбранный вариант нужно уточнить: для быстрого `Unit` главным решением является отделение настоящих unit-тестов от kernel/integration-тестов. ParaTest и PCOV остаются выбранными инструментами для полного ускорения `make test` и `make qa`, но они не должны маскировать неправильную классификацию тестов.

Архитектурный слой приложения не меняется. Это tooling-изменение вокруг тестового запуска: `Domain`, `Application`, `Repository`, `Infrastructure` и HTTP-слой остаются как есть (`docs/arch.md:40`, `docs/arch.md:235`). Меняются только dev-зависимости, Docker image, тестовый bootstrap/config и Make/Composer-команды.

Рекомендуемая рамка:

```text
Быстрый локальный цикл
  -> make test-unit
  -> только тесты на PHPUnit\Framework\TestCase
  -> docker compose run --no-deps test-runner ...
  -> цель: около 1 секунды PHPUnit-времени

Kernel/integration цикл
  -> make test-kernel или make test-integration
  -> тесты на Tests\TestCase
  -> разрешено поднимать Spiral kernel, container, БД и storage

Полная проверка / QA
  -> make qa
  -> reset-test один раз для набора worker-ресурсов
  -> cs + phpstan
  -> один запуск тестов с покрытием через ParaTest + PCOV
  -> без второго обычного запуска тех же тестов
```

Почему нужны отдельные ресурсы на worker: ParaTest запускает несколько процессов, а feature-тесты проекта используют общие PostgreSQL и MinIO (`phpunit.xml:29`, `phpunit.xml:42`, `tests/Feature/Shared/Infrastructure/DockerRuntimeSmokeTest.php:21`). Если параллелить feature-тесты на одной базе и одном bucket, тесты могут мешать друг другу. ParaTest даёт `TEST_TOKEN` с разным значением для параллельных процессов, и это можно использовать для отдельных баз или bucket-ов (https://github.com/paratestphp/paratest, раздел `Test token`). Это снимает главный риск параллельного запуска.

Итоговая форма команд для будущего плана:

```text
make test-unit
  Только настоящие unit-тесты без Tests\TestCase, container, БД, storage и kernel.
  Цель: около 1 секунды PHPUnit-времени.

make test-kernel
  Тесты, которым нужен Spiral kernel/container/config binding.
  Сюда уходят текущие тяжёлые файлы из tests/Unit.

make test
  Чистый полный запуск через Docker: unit + kernel + feature.
  Для feature и coverage можно использовать ParaTest после подготовки worker-БД/bucket.

make test-coverage
  Один coverage-run через ParaTest + PCOV с Clover и проверкой 100%.

make qa
  Docker QA: cs, phpstan, один coverage-run; без отдельного composer test перед coverage.

make qa-build
  Отдельная цель, если нужно явно пересобрать image перед QA.
```

## Итог

Дальше нужно планировать не просто «поменять команду PHPUnit», а перестроить тестовый запуск вокруг двух режимов: быстрый локальный режим и полный строгий QA. Выбранный подход: ParaTest 7.22.4 для параллельного запуска без обновления PHPUnit, PCOV 1.0.12 для быстрого покрытия, отдельные test-БД и MinIO bucket на worker через `TEST_TOKEN`, и удаление двойного запуска тестов из `make qa`.

Главный вывод после уточнения: текущий `Unit` suite медленный, потому что внутри него есть kernel/container-тесты. Настоящие unit-тесты уже проходят примерно за секунду. Поэтому первым делом нужно сделать быстрый Unit suite строгим: в нём запрещён `Tests\TestCase`, `getContainer()`, БД, storage и загрузка Spiral kernel. Тяжёлые config binding/job tests должны уйти в отдельный kernel/integration suite.
