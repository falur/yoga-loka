## Детали правок

### П1 — явная форма нормализации FORM_C (обязательно)
В `UserName::normalize()` и `UserSpiritualName::normalize()` вызов `\Normalizer::normalize(\trim($value))` заменён на `\Normalizer::normalize(\trim($value), \Normalizer::FORM_C)`. Поведение не изменилось (FORM_C — форма по умолчанию), контракт стал явным.

**Всплывший конфликт тулчейна.** Явный второй аргумент включил strict-правило `gianTiaga.phpstanStrictRules.namedArgumentsRequired` (2+ обычных аргумента требуют именования). Именовать аргументы нельзя: имя первого параметра расходится между нативным `ext-intl` (`$string`) и стабом `symfony/polyfill-intl-normalizer`, который PHPStan резолвит для глобального `\Normalizer` (`$s`). Любой выбор имени ломает либо рантайм, либо статический анализ. Поэтому аргументы оставлены позиционными, рядом — комментарий-пояснение, а named-arguments-правило для этих двух строк точечно погашено в `phpstan.neon` (`ignoreErrors` с `identifier` + сообщением, scoped по двум путям). Ревью не предполагало этот конфликт (считало правку чисто косметической); погашение — минимальный и документированный способ применить обязательный фикс, сохранив PHPStan зелёным.

### П2 — полный `\p{Cc}` в `UserBio` (принято)
Регэксп `'/[\x00-\x09\x0B-\x1F\x7F]/u'` (только ASCII C0 + DEL) заменён на `'/(?!\n)\p{Cc}/u'` — блокирует весь Unicode-диапазон управляющих символов `\p{Cc}` (включая C1 U+0080–U+009F), кроме `\n`. Добавлен unit-тест `testBioRejectsUnicodeC1ControlCharacter` на C1-символ (`\u{0085}` NEL). Правка приводит код в соответствие записанному контракту плана и дёшева.

### З2 — устранение дублирования валидации UUID v7 (принято)
В `AbstractUuidV7Id` выделен `public static function isUuidV7(string): bool`; приватный `assertUuidV7()` теперь делегирует в него. `UserAvatar::pointingTo()` использует `AbstractUuidV7Id::isUuidV7()` вместо собственной копии проверки `Uuid::isValid()` + версия 7, сохраняя свой доменный текст исключения. Инвариант «строка обязана быть UUID v7» теперь живёт в одном месте. Тесты не менялись, остаются зелёными.

## Решения по optional
- **Принято:** П2 (`UserBio`/`\p{Cc}`) — устраняет под-реализацию контракта плана, риск низкий, добавлен покрывающий тест. З2 (дублирование UUID v7) — минимальный DRY-фикс, единый источник инварианта версии, без нового helper-класса, тесты не меняются.
- **Отклонено:**
  - **З1 (`isDeleted()` единый источник истины)** — само ревью фиксирует, что на уровне данных/домена `OR` безопасен, а допустимость переходов `ban()/unban()` после `markDeleted()` план явно вынес в Application-слой. Выбор канона (`status` vs `deletion`) — продуктово-архитектурное решение, которым владеет Application-план; менять предикат сейчас значит принять это решение преждевременно и рискнуть рассогласованием с будущими сценариями. Вне текущего скоупа слоя данных.
  - **З3 (дублирование `normalize()`/`fromString()` в именах)** — структурный рефактор (общий `abstract readonly class` или статический хелпер) на два VO с расходящимися деталями (nullable у `UserSpiritualName`, разные тексты исключений). Ревью само помечает его «при желании» и подтверждает функциональную корректность. Извлечение общей базы ради двух почти-одинаковых, но не идентичных VO — риск преждевременной абстракции и расширение scope при спорной выгоде.
