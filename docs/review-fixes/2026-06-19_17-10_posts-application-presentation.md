## Решения по optional

- **Принято:**
  - **Проблема сверки 2** — дефект публичного контракта, рекомендован приоритетно. Корень не в коде
    ресурса, а в генераторе `packages/spiral-openapi`: `PhpAstParser::parseProperties()` извлекал
    `listItemType` только из PHPDoc на обычных свойствах, но не из `@param list<T> $name` для
    promoted-параметров конструктора (а `PostResource` использует именно их). Добавил извлечение
    `listItemType` для promoted-параметров по конкретному имени параметра (`paramListItemType`).
    Теперь `schemaForProperty`/`schemaForType` разрешают элемент списка-объекта в `$ref`. YAML
    регенерирован: `media` → `$ref PostMediaItemResource`, `tags` → `$ref TagResource`. Добавлены
    тесты в пакете (fixture с `@param list<HealthResource>`) и в приложении (контракт `media`/`tags`).
  - **Замечание 6** — реальный hot-path-риск. Добавил батч-методы `findByPostIds` в
    `PostMediaRepository`/`PostTagRepository` (по образцу `findByUserAndPostIds`), листинг собирает
    медиа и теги одним запросом каждый и один батч GetTags на страницу вместо `2*limit` обращений.
  - **Замечание 8** — реальный prod-риск (одна удалённая картинка роняла целую страницу ленты в 500).
    `PostViewAssembler::mediaItem()` переведён на не бросающий `FindMediaUrlHandler` (тот же паттерн,
    что для аватара в `UserPublicProfileAssembler`); недоступное медиа исключается из ответа.

- **Отклонено:**
  - **Проблема плана 1** — осознанное отклонение по решению 21 плана (тип следует из наличия медиа,
    lesson/practice отложены); ревью помечает правку «не обязательной» и требует продуктового
    согласования контракта с фронтом, а не правки кода.
  - **Замечание 1** — проверка видимости записи в лайке комментария требует продуктового решения
    («разрешены ли реакции на исторические комментарии»). Выравнивание guard-ов снятия лайка меняет
    идемпотентную семантику: план (решение 15) задаёт guard только для лайка/коммента/репоста, не для
    снятия; риск ревью оценило как низкий. Не правлю без продуктового решения.
  - **Замечание 2** — ревью само помечает поведение спорным и зависящим от продуктовой политики
    (сокрытие vs идемпотентность); коды на краевом сценарии, данные не затрагиваются.
  - **Замечание 3** — соответствует решению 11 «счётчики не ниже нуля»; ревью рекомендует «оставить
    как есть».
  - **Замечание 4** — вынос общего сервиса трогает DI-проводку и оба composer-а ради ~20 совпадающих
    строк; расширяет scope при модерной пользе и риске регрессии.
  - **Замечание 5** — число запросов ограничено доменом (актор/автор/упомянутые ≤50); выигрыш заметен
    лишь под нагрузкой; ревью «не обязательно».
  - **Замечание 7** — широкий рефакторинг трёх Query-Handler-ов и двух ассемблеров при риске регрессии
    и модерной пользе; ревью «не обязательно».
