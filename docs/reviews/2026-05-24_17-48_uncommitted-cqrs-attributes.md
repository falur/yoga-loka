# Ревью: Незакоммиченные изменения CQRS

## Оценка

**72/100.** Основной контракт CQRS-пакета выглядит рабочим, и package-local проверки проходят. Но есть риск, что новое PHPStan-правило не защищает код приложения, а реализация расширила публичный API сверх плана.

## Проблемы сверки с планом

### 1. CQRS-правило PHPStan не применяется к коду приложения

Статус: не проверялось

Контекст:
План добавляет PHPStan-правило внутри `tools/cqrs` и называет это PHPStan-контрактом проекта. Самые важные будущие вызовы `dispatch()` будут появляться в коде приложения: контроллерах, консольных командах и других входных точках.

Проблема:
Правило добавлено и подключено только внутри package-local конфигурации `tools/cqrs`. Корневая проверка `make phpstan` читает `phpstan.neon`, а там подключены только общие правила `yoga-loka/phpstan-rules`. Поэтому неверный `dispatch(..., handler: ...)` в `app/src` может не ловиться общей проверкой приложения.

Риск:
Разработчик может написать в приложении closure, array-callable или Query Handler с `#[Transactional]`, а общая проверка приложения это не остановит. Для Query Handler-а с `#[Transactional]` ошибка может дойти до runtime, потому что `QueryBus` технически прочитает атрибут, а `TransactionalMiddleware` выбросит `LogicException`.

Где:

- `docs/plans/2026-05-24_14-26_cqrs-handler-attributes.md:149` — план требует PHPStan-проверку формы handler-а до запуска
- `docs/plans/2026-05-24_14-26_cqrs-handler-attributes.md:220` — план описывает это как PHPStan-контракт проекта
- `phpstan.neon:1` — корневая конфигурация не включает CQRS extension
- `tools/cqrs/phpstan.neon:1` — CQRS extension подключён только внутри пакета
- `tools/cqrs/extension.neon:1` — само правило существует отдельно от корневого PHPStan

Детали:
Сейчас `composer -d tools/cqrs phpstan` проверяет пакет `tools/cqrs/src`, а `make phpstan` проверяет `app/src`. Так как корневой `phpstan.neon` не включает `vendor/yoga-loka/cqrs-tools/extension.neon` или аналогичный путь, правило `RequireCqrsHandlerCallableRule` не участвует в проверке приложения.

Как исправить:
Нужно решить, должно ли CQRS-правило защищать код приложения. Если да, подключить extension в корневую конфигурацию. Если нет, явно записать в документации, что правило проверяет только сам пакет.

Конкретные шаги:

- Добавить CQRS extension в `phpstan.neon` или явно зафиксировать отказ от root-подключения.
- Если extension подключается в root: проверить, что `make phpstan` видит правило после установки path-пакета.

### 2. Реализация добавила публичный общий middleware-механизм сверх плана

Статус: отклонение

Контекст:
План специально ограничил первую версию двумя атрибутами: `#[Transactional]` и `#[LogOperation]`. Он также требовал внутренний stateless executor без публичного middleware API, чтобы не расширять контракт пакета раньше времени.

Проблема:
В пакете появился публичный базовый атрибут `HandlerMiddlewareAttribute`, публичный `HandlerMiddlewareInterface` и pipeline, который выполняет любой атрибут-наследник через контейнер. README и `docs/arch.md` тоже описывают это как возможность пакета, а тест закрепляет выполнение произвольного middleware-атрибута.

Риск:
Пакет получает незапланированный внешний контракт. Его начнут использовать для произвольных middleware вокруг Handler-а, и потом будет трудно убрать или изменить этот API. Это также размывает принятое решение "только два атрибута" и может снова привести к скрытым побочным действиям вокруг CQRS-bus.

Где:

- `docs/plans/2026-05-24_14-26_cqrs-handler-attributes.md:86` — план разрешает только два атрибута
- `docs/plans/2026-05-24_14-26_cqrs-handler-attributes.md:190` — план требует убрать публичный middleware API
- `docs/plans/2026-05-24_14-26_cqrs-handler-attributes.md:193` — план требует внутренний executor без публичного middleware API
- `tools/cqrs/src/Attribute/HandlerMiddlewareAttribute.php:9` — публичный базовый атрибут для произвольных middleware
- `tools/cqrs/src/HandlerMiddlewareInterface.php:9` — публичный middleware-интерфейс
- `tools/cqrs/src/HandlerMiddlewarePipeline.php:80` — pipeline берёт все атрибуты-наследники
- `tools/cqrs/README.md:10` — README документирует общий middleware-механизм
- `tools/cqrs/tests/Bus/CommandBusTest.php:171` — тест закрепляет выполнение любого middleware-атрибута
- `docs/arch.md:443` — архитектура теперь описывает общий механизм атрибутов

Детали:
Это уже не просто внутренняя реализация двух атрибутов. Пользователь пакета может создать свой атрибут, вернуть из него middleware-класс, и bus выполнит его вокруг Handler-а. Так отклонение от плана закреплено как внешний контракт, а не как закрытая техническая деталь.

Как исправить:
Нужно либо вернуться к закрытой реализации только для `Transactional` и `LogOperation`, либо явно перепланировать и принять новый публичный extension API отдельным решением.

Конкретные шаги:

- Если extension API не нужен: убрать `HandlerMiddlewareAttribute`, `HandlerMiddlewareInterface`, общий pipeline и тест `testExecutorRunsAnyMiddlewareAttribute()`.
- Сделать executor, который явно обрабатывает только `Transactional` и `LogOperation`.
- Если extension API нужен: обновить план и архитектурные правила отдельным решением, описать границы API и запретить использовать его для внешних побочных эффектов.

Детали:

Как исправить:
Нужно отделить изменение инструкций от CQRS-работы или явно зафиксировать решение в отдельном плане/документе.

Конкретные шаги:
