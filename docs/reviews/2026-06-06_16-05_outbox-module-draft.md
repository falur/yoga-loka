# Ревью: модуль Outbox

## Оценка

**88/100.** Реализация цельная и хорошо соответствует разделу «События и outbox» в `docs/arch.md`: transactional outbox, relay-orchestrator, queue-interceptor, envelope с подгрузкой настоящего payload из БД, типизированные VO и typecast. PHPStan (level max) и php-cs-fixer по модулю проходят без ошибок. Главное замечание — пункт 1: репозиторий выходит за свою роль (try-catch + переход состояния `failed` внутри слоя доступа к данным), это сразу два формальных запрета из `docs/rules.md` плюс реальный риск зацикливания relay на повреждённых строках. Остальные замечания мягче и в основном про консистентность и поддерживаемость: дублирование общего трейта `HasTimestamps` и одна бизнес-дата без VO, непоследовательное моделирование «отсутствия значения», near-dead-code throw с голым `\RuntimeException` и недокументированные raw-операции query builder. Кроме пункта 1, всё локализовано и не ломает основной сценарий, поэтому остаётся на усмотрение автора.

## Замечания

### 1. Репозиторий ловит исключения и помечает «битые» строки failed внутри себя

Репозиторий outbox при выборке pending-событий ловит ошибку приведения типов и сам, через отдельный проход, помечает повреждённые строки как `failed`, после чего повторяет выборку. Проблема в том, что проектные правила прямо запрещают try-catch вне инфраструктурной границы (interceptor, middleware, Job) и запрещают репозиторию выполнять обновления-«переходы состояния», не относящиеся к конкретному запросу. Здесь репозиторий взял на себя роль orchestrator-а: он решает, что строка невалидна, и сам её «гасит».

Практический риск двойной: во-первых, это размывает границу ответственности — логика восстановления после повреждённых данных оказывается спрятана в слое доступа к данным, и её сложно заметить и протестировать как отдельный сценарий relay. Во-вторых, при ошибке приведения по любому полю (не только `type`) поведение становится трудно предсказуемым, и если валидация в `OutboxPendingRow` не покроет конкретную причину, та же строка может снова попасть в выборку и зациклить relay. Проявится это на реально повреждённых данных в проде (ручные правки, неудачная миграция, рассинхрон схемы).

Технические детали:

- **Тип:** `architecture | rules`
- **Рекомендация:** править обязательно (самое серьёзное замечание ревью: два формальных запрета сразу плюс риск зацикливания relay)
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:41-90` — `findPendingForRelayAndMarkInvalidRowsAsFailed()` и `markInvalidOutboxRowsAsFailed()`.
- **Что подтверждает проблему:** `try { ... } catch (TypecastException) { $this->markInvalidOutboxRowsAsFailed(...) ... }`; внутри — `$this->database->update('outbox_events')->values([...])->run()`, то есть переход статуса в `failed` выполняется прямо в репозитории. Правила `docs/rules.md`: «Запрет try-catch в контроллерах, Handler-ах и бизнес-логике … try-catch допустим только в инфраструктурном коде (interceptor-ы, middleware, Job-обработчики)» и «Repository отвечает только за конкретные запросы и сохранение переданных сущностей». Репозиторий не относится к инфраструктурной границе из списка правила, при этом сам решает «строка битая → failed».
- **Как исправить:** вынести обнаружение и пометку невалидных строк в orchestrator (`OutboxRelay` — он уже инфраструктурный и держит транзакцию `claimForRelay()`, а raw-переход статуса уже делегирует репозиторию через `markQueuedIfPublishing`). Репозиторий пусть предоставляет два чистых метода-запроса: «выбрать pending-строки как `OutboxPendingRow`» и «пометить строку failed по id с last_error». Решение «строка битая → failed» и try-catch держать в `OutboxRelay`. Тесты переходов в `failed` по битым полям уже есть (`testFindPendingForRelayAndMarkInvalidRowsAsFailedMarksRowsWithInvalidAttemptsAsFailed`, `...EmptyLastError...`) — их нужно перенести на новый orchestrator-метод и добавить недостающую проверку: после пометки строки `failed` повторная выборка не захватывает её снова (защита от зацикливания relay).

### 2. Сущность outbox-события дублирует трейт `HasTimestamps` и держит бизнес-дату `availableAt` без VO

Сущность outbox-события объявляет `createdAt`/`updatedAt` как голые `public private(set) \DateTimeImmutable` с `typecast: 'datetime'` и вручную реализует `initializeTimestamps()`/`touch()`. Это полностью повторяет общий трейт `App\Shared\Domain\Trait\HasTimestamps`, который уже даёт ровно эти два поля и эти два метода и используется в `Media`, `MediaImageConversion`, `MediaVideoConversion`, `MediaMultipartUpload`. Отдельно стоит бизнес-дата `availableAt` (момент, когда событие можно публиковать / claim-timeout): она тоже голый `\DateTimeImmutable`, но, в отличие от `createdAt`/`updatedAt`, не относится к стандартным timestamp-полям и не имеет своего VO, хотя модуль уже умеет оборачивать даты (`OutboxEventDate`/`KnownOutboxEventDate`).

Риск не функциональный, а в поддерживаемости: дублирование общего трейта расходится с проектным паттерном timestamp-полей (правка трейта не доедет до этой сущности), а доменно значимая `availableAt` без VO теряет валидацию/семантику на фоне того, что прочие даты модуля уже типизированы. Проявится при ревью и расширении модуля, а не в рантайме.

Технические детали:

- **Тип:** `rules | quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Outbox/Domain/Entity/StoredOutboxEvent.php:47-48,62-66` (`availableAt`, `createdAt`, `updatedAt`) и `:183-192` (`initializeTimestamps()`/`touch()`).
- **Что подтверждает проблему:** голые `createdAt`/`updatedAt` с `typecast: 'datetime'` НЕ являются нарушением проектного паттерна — это в точности канон `App\Shared\Domain\Trait\HasTimestamps` (`public private(set) \DateTimeImmutable $createdAt/$updatedAt`, `typecast: 'datetime'`), который другие сущности подключают через `use HasTimestamps;`. Проблема в том, что сущность не переиспользует трейт, а копирует его поля и методы. Для `availableAt` применяется правило «Entity без примитивов … single value -> ValueObject»: это доменное значение, для которого VO отсутствует.
- **Как исправить:** заменить ручные `createdAt`/`updatedAt`/`initializeTimestamps()`/`touch()` на `use HasTimestamps;` (поведение идентично, дублирование уходит). Для `availableAt` — ввести VO «обязательной» даты (например `OutboxAvailableAt` с фабрикой и typecast по образцу `OutboxEventDateTypecast`) либо осознанно зафиксировать исключение в README/`docs/rules.md`. Тесты: typecast/гидрация уже частично покрыты; при вводе VO для `availableAt` добавить round-trip-проверку.

### 3. `OutboxLastError` выражает «нет ошибки» пустой строкой и nullable-геттером

VO ошибки моделирует отсутствие через `none()` с пустой строкой внутри и геттер `value(): string|null`, возвращающий `null`, когда строка пустая. Это противоречит правилу «Явные типы вместо `null`» (отсутствие выражать отдельным типом, как сделано для `OutboxEventDate` через Empty/Known), и создаёт внутреннюю несогласованность модуля: даты получили честную дихотомию состояний, а ошибка — нет.

Практический риск низкий, но это ловушка читаемости: один и тот же модуль учит двум разным подходам к «отсутствию значения», и `value()` с union-возвратом заставляет каждого потребителя помнить про `null`. Проявится при чтении и сопровождении кода.

Технические детали:

- **Тип:** `quality | rules`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Outbox/Domain/ValueObject/OutboxLastError.php:17-20,44-47` — `none()` создаёт `new self('')`, `value(): string|null` возвращает `null` при пустой строке.
- **Что подтверждает проблему:** правила: «Отсутствие, неизвестность или особое состояние выражать отдельным типом/value object/enum … а не `?string`». В этом же модуле есть готовый эталон — `OutboxEventDate` с `EmptyOutboxEventDate`/`KnownOutboxEventDate`.
- **Как исправить:** либо привести `OutboxLastError` к той же Empty/Known-схеме (как `OutboxEventDate`) с методами `isEmpty()`/явным значением без nullable, либо оставить пустую строку как валидное доменное значение и убрать union из `value()` (всегда `string`), а пустоту читать через `isEmpty()`. Тесты `OutboxValueObjectTest` обновить под выбранный вариант.

### 4. Завершение цикла relay через голый `\RuntimeException` в near-dead-code ветке

Воркер relay в постоянном режиме имеет return type `never` и после `while ($this->outboxRelayLoopControl->shouldContinue())` бросает голый `\RuntimeException` на случай выхода из цикла. В проде `InfiniteOutboxRelayLoopControl::shouldContinue()` всегда возвращает `true`, поэтому строка достижима только в тестах с подменённым loop-control — это фактически guard-throw ради контракта `never`.

Замечание мягче, чем выглядит: правило `docs/rules.md` про `\RuntimeException` сформулировано как «запрещено использовать голый `\RuntimeException` **с HTTP-кодом**» и нацелено на HTTP-сценарии; здесь это инфраструктурный код без HTTP-кода, поэтому буквального нарушения нет. Остаётся стилевой момент: голый `\RuntimeException` менее информативен, чем типизированный, и при добавлении реального graceful-shutdown loop-control эта ветка станет рабочей.

Технические детали:

- **Тип:** `rules | quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Outbox/Infrastructure/OutboxRelayWorker.php:76` — `throw new \RuntimeException('Outbox relay loop остановлен внешним контролем.');`.
- **Что подтверждает проблему:** правило: «запрещено использовать голый `\RuntimeException` с HTTP-кодом … Типизированные доменные исключения вместо `RuntimeException`». Буквальный запрет тут не срабатывает (нет HTTP-кода, инфраструктурный путь), но общий посыл «типизированное исключение вместо голого» применим.
- **Как исправить:** либо завести типизированное инфраструктурное исключение (например `OutboxRelayStoppedException`) и бросать его, либо, если штатная остановка по внешнему контролю — допустимый сценарий, пересмотреть сигнатуру `runLoop(): never` так, чтобы корректный выход не требовал throw. Если оставляется как guard ради `never` — оставить как есть допустимо. Тест на остановку цикла обновить под выбранный вариант.

### 5. Внутренний DTO строки хранит ассоциативный массив `mixed`

DTO «сырой строки» outbox хранит весь ряд БД в `private array $fields` (ассоциативный массив `mixed`) и достаёт значения по строковым ключам через приватный геттер. Правила проекта запрещают ассоциативные массивы для передачи данных и `array<string, mixed>` в контрактах, отдавая предпочтение типизированным DTO/VO.

Риск ограниченный: это инфраструктурный helper на самой границе с БД, где данные действительно имеют неизвестный тип до валидации, поэтому формально это «граница системы». Но конструктор всё же сохраняет нетипизированный массив как состояние объекта и тащит его дальше, что делает DTO полу-типизированным и усложняет рассуждение о его инвариантах.

Технические детали:

- **Тип:** `quality | rules`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Outbox/Repository/OutboxPendingRow.php:14-39,124-127` — `private array $fields`, `field(string): mixed`.
- **Что подтверждает проблему:** правила: «Запрет ассоциативных массивов … `array<string, mixed>` в публичных контрактах — нарушение» и «Именованные типы для сложных данных». Объект не только принимает массив на границе, но и хранит его как поле.
- **Как исправить:** в `fromDatabaseRow()` сразу извлечь и провалидировать нужные поля в типизированные свойства (`id`, `type`, `payload`, `status`, `attempts`, даты, `lastError`) и хранить именно их, а не сырой массив; `assertExpectedTypes()` тогда работает с уже типизированными полями. Тесты на повреждённые строки сохранить, привязав к новым полям.

### 6. Несколько raw-операций query builder в репозитории без явного обоснования причины

Помимо пункта 1, репозиторий использует прямой query builder ещё в нескольких местах: атомарный условный UPDATE статуса, чтение «свежего» статуса в обход identity map и чтение сырых pending-строк. Часть из них действительно нельзя выразить через ORM Select (условный UPDATE, обход identity map), и для чтения свежего статуса есть поясняющий комментарий. Но правило требует, чтобы причина использования query builder вместо ORM Select была понятна из кода для каждого такого места, а для условного UPDATE и для чтения сырых строк комментария-обоснования рядом нет.

Риск низкий и в основном про поддерживаемость: без явной причины следующий разработчик может либо «починить» оправданный raw-запрос на ORM (сломав атомарность), либо наоборот растащить raw query builder туда, где он не нужен. Проявится при доработке модуля.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Outbox/Repository/OutboxEventRepository.php:97-110` (`markQueuedIfPublishing`), `:112-131` (`findFreshStatusById` — комментарий есть), `:136-177` (`pendingForRelayRows`).
- **Что подтверждает проблему:** правила: «Query Builder допустим только для операций, которые ORM Select не умеет выразить, и причина должна быть понятна из кода». У `markQueuedIfPublishing` (условный UPDATE по `status = publishing`) и у `pendingForRelayRows` (raw-чтение для пред-валидации типов) нет поясняющего комментария о причине, в отличие от `findFreshStatusById`.
- **Как исправить:** добавить короткий комментарий-обоснование рядом с `markQueuedIfPublishing` (атомарный CAS-переход статуса, ORM Select не выражает) и `pendingForRelayRows` (чтение сырых строк до ORM-гидрации для отлова битых данных — связано с пунктом 1). Тесты не требуются: изменение документирующее.
