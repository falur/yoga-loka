# Ревью: Media upload pipeline — незакоммиченный diff (третий цикл)

## Оценка

**90/100.** Реализация полностью покрывает план: переиспользуемый Application-API без собственного
HTTP, presigned/multipart через `Aws\S3\S3Client`, асинхронная обработка через outbox,
идемпотентный `ProcessMedia`, санитизация ошибок и классификация транзиентных/постоянных сбоев.
Правки двух предыдущих циклов подтверждаются в рабочем дереве: `$result` устранён, чистые
трансформации переведены на `->map()`, добавлен guard инварианта конфига
`multipartThresholdBytes >= multipartPartSizeBytes`, логирование на DEBUG, оригинал читается в
память только при наличии конверсий, README дополнен про осиротевшие конверсии и S3-I/O в
транзакции.

Блокеров нет. Новое в этом цикле, что заслуживает внимания: `DeleteMedia` для готового медиа
удаляет из S3 только оригинал, оставляя объекты конверсий в целевом бакете осиротевшими (это
отдельный сценарий от уже разобранного «осиротевшие при повторе с другим набором» — там речь о
reprocessing, здесь о delete). И ещё: доменный переход `markReadyMovedTo` теперь разрешён из
`ProcessingFailed` (восстановление после транзиентной ошибки) — переход покрыт unit-тестом, но
сквозного интеграционного теста «транзиентный сбой → успешный ретрай → ready» нет. Оба пункта
неблокирующие, на усмотрение автора.

## Проблемы сверки с планом

Явных проблем по плану не найдено. Все шесть фаз выполнены, контракт публичного Application-API
соответствует разделу «Контракты реализации», доменные методы/фабрики добавлены как описано.

Ранее зафиксированные осознанные отклонения остаются в силе и не ухудшены: глобальный
coverage-gate `make qa` красный из-за пред-существующего долга чужих файлов (новый media-код на
100%); уровень лога «media готова» приведён к DEBUG по `rules.md:84` вместо INFO из плана; guard
`markReadyMovedTo` расширен до `ProcessingFailed` относительно буквы плана (`uploaded`/`processing`)
— это осознанная правка ради корректного ретрая, разобрана и принята в первом цикле. Повторно их
не поднимаю.

## Замечания

### 1. `DeleteMedia` для готового медиа оставляет объекты конверсий осиротевшими в S3

Когда удаляют готовое (`ready`) медиа, из хранилища физически удаляется только сам оригинал. Все
сгенерированные превью/конверсии этого медиа, которые лежат в том же постоянном бакете
(`media-public`/`media-private`), из S3 не удаляются. При этом строки конверсий в БД исчезают
каскадом, поэтому после удаления остаются файлы в объектном хранилище, на которые уже ничто не
ссылается.

Практический риск — не корректность, а медленный рост мусора и расходов на хранение: чем больше
медиа с конверсиями удаляют, тем больше «висячих» файлов в публичном/приватном бакете. В отличие от
staging-оригиналов (которые чистятся по expiry), у конверсий в постоянном бакете нет ни expiry, ни
другого механизма уборки. README уже честно фиксирует похожий случай для повторной обработки с
другим набором конверсий, но именно про `DeleteMedia` там ничего нет, и читатель легко решит, что
удаление медиа освобождает и место в S3.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/Media/DeleteMedia/DeleteMediaHandler.php:45`
  (`deleteObject` только для `$media->path`); каскад БД —
  `app/database/migrations/20260521.184100_0_create_media_domain_tables.php:56` (`media_image_conversions ... 'delete' => 'CASCADE'`).
  То же относится и к видео-конверсиям: `MediaVideoConversion` имеет собственные `storage`/`path`
  (`app/src/Modules/Media/Domain/Entity/MediaVideoConversion.php:48-52`) и тот же `fkOnDelete: 'CASCADE'`
  (там же:72). Сейчас процессор создаёт только image-конверсии (`ProcessMediaHandler::buildConversions`),
  видео-конверсии в этом scope не генерируются, поэтому в проде осиротевают пока только image-объекты;
  но при включении видео-конверсий проблема распространится на них без изменений в `DeleteMedia`.
- **Что подтверждает проблему:** Handler не загружает и не удаляет объекты конверсий из S3 — нет
  ни `findByMediaId` по `MediaImageConversionRepository`/`MediaVideoConversionRepository`, ни цикла
  `deleteObject` по их путям; при этом FK на `media_image_conversions`/`media_video_conversions` имеет
  `ON DELETE CASCADE`, поэтому строки конверсий уходят, а файлы остаются.
- **Как исправить:** один из вариантов — до `entityManager->delete($media)` загрузить конверсии
  (`MediaImageConversionRepository::findByMediaId`; при появлении видео — и
  `MediaVideoConversionRepository`) и выполнить `deleteObject` по каждому
  `conversion->storage`/`conversion->path` (404 уже игнорируется сервисом). Либо осознанно оставить
  как есть и описать это в README рядом с заметкой про осиротевшие конверсии, отнеся уборку S3 к той
  же будущей задаче по очистке хранилища, что и staging-оригиналы.
- **Тесты:** при удалении конверсий из S3 — feature-кейс «delete готового медиа с конверсией →
  объект конверсии в бакете отсутствует» (по образцу `DeleteMediaHandlerTest`). Если решение «не
  чистим» — тест не нужен, достаточно записи в README.

### 2. Нет интеграционного теста на восстановление: транзиентный сбой → успешный ретрай → `ready`

В этом цикле `markReadyMovedTo` стал допускать переход из `ProcessingFailed` — это и есть
поддержка повторной обработки после транзиентной ошибки (Job фиксирует `ProcessingFailed`, бросает
`RetryException`, и при повторе медиа приходит в обработку уже из `ProcessingFailed`). Сам доменный
переход покрыт unit-тестом, а у Job покрыта классификация транзиентных ошибок и переход в
`ProcessingFailed`. Но цельного сценария «сбой зафиксирован → повторная доставка обрабатывается
успешно → медиа становится `ready`» в интеграционных тестах нет.

Замечание точнее квалифицировать не как нарушение плана, а как тест-долг, возникший из осознанного
отклонения от плана. План (после plan-polish, итерация 4) закрепил guard `markReadyMovedTo` как
`uploaded`/`processing`; расширение до `ProcessingFailed` принято осознанно в первом цикле ревью ради
корректного ретрая, но соответствующего требования к интеграционному тесту восстановления в план не
добавляли. Поэтому пробел не виден ни по букве плана, ни по существующим тестам.

Риск в том, что именно эта связка — единственная причина, по которой guard был расширен. Если в
будущем кто-то снова ужесточит guard до `uploaded`/`processing` (как написано в плане), ни один
тест не покажет, что ретрай после транзиентного сбоя начал падать в 500: unit-тест проверяет только
изолированный переход, а feature-тесты идут по happy-path и по терминальному провалу, минуя
успешное восстановление. Это пробел в защите регрессии, а не текущий баг.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** домен — `app/src/Modules/Media/Domain/Entity/Media.php:192-208` (`markReadyMovedTo`
  допускает `ProcessingFailed`); существующее покрытие —
  `tests/Unit/Modules/Media/Domain/Entity/MediaEntityTest.php`
  (`testMarkReadyMovedToAllowsRetryFromProcessingFailed`),
  `tests/Feature/Modules/Media/Flow/MediaProcessingFlowTest.php:86-104` (только провал),
  `tests/Feature/Modules/Media/Flow/ProcessMediaJobTest.php` (только классификация).
- **Что подтверждает проблему:** во flow-тестах есть `testProcessingFailureRecordsErrorAndFailsOutbox`
  (медиа остаётся `ProcessingFailed`), но нет кейса, где после фиксации `ProcessingFailed` повторный
  `ProcessMedia` доводит медиа до `ready`.
- **Как исправить:** добавить feature-кейс: создать медиа в `ProcessingFailed` (через
  `recordTemporaryProcessingError` или первый сбойный прогон), затем выполнить `ProcessMediaHandler::handle`
  с валидным оригиналом и проверить `status === Ready`, наличие конверсий и перекладку оригинала.
- **Тесты:** см. выше — это и есть добавляемый тест.

### 3. Нет Handler-теста `ProcessMedia` для неверного статуса (`WaitingUpload`)

План (фаза 4) требует для каждого Handler покрыть и ошибочные ветки, явно называя «неверный
статус». У `ProcessMediaHandler` неверный статус — `WaitingUpload`: загрузка ещё не подтверждена,
поэтому доменный `markReadyMovedTo` для такого медиа бросит `InvalidDomainValueException`. В
`ProcessMediaHandlerTest` этот кейс отсутствует: есть happy-path с конверсиями и без, no-op на уже
`ready` и `NotFound` на отсутствующем медиа, но нет теста, где `ProcessMedia` для медиа в
`WaitingUpload` приводит к доменному отказу. Сам доменный guard покрыт на unit-уровне
(`MediaEntityTest`), но связка Handler → guard для запрещённого входного статуса не зафиксирована.

Риск — не текущий баг (поток приходит из `Uploaded`/`ProcessingFailed`), а пробел в защите
регрессии на Handler-границе: если изменят порядок проверок или резолв статуса в `ProcessMediaHandler`,
ни один Handler-тест не покажет, что обработка медиа в неподтверждённом статусе перестала корректно
отклоняться.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/Media/ProcessMedia/ProcessMediaHandler.php:71`
  (`markReadyMovedTo` для медиа в `WaitingUpload` бросит `InvalidDomainValueException`); существующее
  покрытие — `tests/Feature/Modules/Media/Application/ProcessMediaHandlerTest.php`
  (`testProcessesMediaWithConversions`, `testProcessesMediaWithoutConversionsMovesOriginalOnly`,
  `testIsNoOpWhenMediaAlreadyReady`, `testRejectsMissingMedia` — кейса `WaitingUpload` нет).
- **Что подтверждает проблему:** ни один метод в `ProcessMediaHandlerTest` не создаёт медиа в
  `WaitingUpload` и не проверяет отказ; план фазы 4 требует покрыть «неверный статус» для каждого
  Handler.
- **Как исправить:** добавить feature/Handler-кейс: медиа в `WaitingUpload` → `ProcessMediaHandler::handle`
  → ожидать `InvalidDomainValueException` (или принять как осознанное сужение — guard покрыт на
  domain-уровне, а Handler-уровень тогда зафиксировать решением). Альтернатива — Handler сам отклоняет
  невалидный статус ранней проверкой с типизированным `ValidationException`, тогда тест на эту ветку.
- **Тесты:** см. выше — это и есть добавляемый тест.
