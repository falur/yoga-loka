## Оценка

для запрещённого статуса `WaitingUpload`. README дополнен явной записью про удаление объектов
конверсий. Регрессий в media-коде нет.

Блокеров нет. Все ранее найденные мелкие нарушения правил (`$result`, `foreach` для чистых
трансформаций, guard инварианта конфига) исправлены и не вернулись. Новый код по-прежнему на 100%
покрыт; красный глобальный coverage-gate — пред-существующее осознанное отклонение, разобранное в
прошлых циклах, повторно не поднимаю.

Новых наблюдений этого цикла два, оба узкие и неблокирующие, оба «на усмотрение автора». Первое:
`RecordMediaProcessingFailure` записывает сбой без проверки текущего статуса медиа, поэтому
теоретически может «откатить» уже `ready`-медиа в `ProcessingFailed`; в текущем потоке это
недостижимо из-за раннего `isReady()`-guard'а в `ProcessMediaHandler` (структурная защита) поверх
контракта single-relay/single-Job, поэтому пункт — защита команды на будущее, а не баг. Второе:
`MediaImageConversion` сохраняется с фактическими размерами процессора, тогда как план предписывал
размеры из `spec`; расхождение, вероятно, осознанное (фактические точнее), но нигде не зафиксировано —
стоит либо задокументировать выбор, либо вернуть spec-размеры.

## Проблемы сверки с планом

Все шесть фаз выполнены, контракт публичного Application-API соответствует разделу «Контракты
реализации», доменные методы/фабрики добавлены как описано, проводка outbox (bootloader,
`queue.php`, Kernel) на месте. Единственное незафиксированное расхождение с буквой плана — размеры
`MediaImageConversion` берутся из фактического результата процессора, а не из `spec.width/spec.height`
(план, строка 241). Это узкое и, вероятно, осознанное улучшение; вынесено как замечание №2
(`на усмотрение автора`) с рекомендацией задокументировать выбор либо выровнять на spec.

Ранее зафиксированные осознанные отклонения остаются в силе и не ухудшены: глобальный
coverage-gate `make qa` красный из-за пред-существующего долга чужих файлов (новый media-код на
100%); уровень лога «media готова» приведён к DEBUG по `rules.md:84` вместо INFO из плана; guard
`markReadyMovedTo` расширен до `ProcessingFailed` относительно буквы плана — осознанная правка ради
корректного ретрая, теперь под защитой нового интеграционного теста. Повторно их не поднимаю.

## Замечания

### 1. `RecordMediaProcessingFailure` записывает сбой без проверки статуса — теоретически может откатить `ready`-медиа в `ProcessingFailed`

Команда фиксации ошибки обработки всегда переводит медиа в `ProcessingFailed` и инкрементит счётчик
попыток, не глядя на текущий статус. Сейчас это безопасно по двум причинам, и главная из них —
структурная, а не только контрактная. **Структурная (первый эшелон):** `RecordMediaProcessingFailure`
вызывается исключительно из `catch`-ветки `ProcessMediaJob`, то есть только когда
`ProcessMediaCommand` бросил исключение. А `ProcessMediaHandler::handle()` начинается с раннего
guard'а `if ($media->isReady()) { return; }` (`ProcessMediaHandler.php:46`): для уже `ready`-медиа
обработка завершается без исключения, `catch` не входит, и фиксация ошибки не вызывается в принципе —
независимо от числа ретраев. **Контрактная (второй эшелон):** в потоке гарантирован один relay и один
Job на одно событие, поэтому запоздалой/повторной доставки, минующей этот guard, не возникает. Но
сама доменная команда инвариантом не защищена: если в будущем `RecordMediaProcessingFailure`
начнут диспатчить из другого места (минуя `ProcessMediaJob` и его `isReady()`-guard) либо появится
повторная/запоздалая доставка (несколько relay, ручной перезапуск Job, дубликат в очереди) после
того, как другой проход уже довёл медиа до `ready`, — фиксация ошибки молча переведёт готовое медиа
обратно в `ProcessingFailed` и обнулит инвариант «ready без ошибки».

Риск — не текущий баг (поток детерминирован), а хрупкость относительно будущих изменений
доставки/конкурентности. В отличие от forward-перехода `markReadyMovedTo`, у которого есть явный
guard «на `ready` → no-op», у обратного перехода в `ProcessingFailed` guard отсутствует. Проявится
только при появлении повторной доставки, которой в текущем контракте нет.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/Media/RecordMediaProcessingFailure/RecordMediaProcessingFailureHandler.php:33`
  (безусловный `recordTemporaryProcessingError`); домен —
  `app/src/Modules/Media/Domain/Entity/Media.php:164-178` (`recordTemporaryProcessingError`/
  `recordPermanentProcessingError` без guard по статусу).
- **Что подтверждает проблему:** `RecordMediaProcessingFailureHandler` не проверяет
  `$media->isReady()` (или иной терминальный статус) перед записью сбоя; доменные методы тоже
  безусловны. Единственная защита сейчас — guard `if ($media->isReady()) { return; }` в
  `ProcessMediaHandler.php:46`, который не даёт дойти до `catch`→`RecordFailure` для готового медиа;
  но этот guard живёт в другом Handler'е, а не в самой команде фиксации сбоя. `markReadyMovedTo` для
  сравнения имеет собственный `if ($this->status === MediaStatus::Ready) return;`.
- **Как исправить:** один из вариантов — в Handler добавить ранний `return`/no-op, если медиа уже
  `ready` (готовое медиа не может «сломаться» задним числом), либо вынести guard в доменный метод
  записи ошибки (`ProcessingFailed` допустим только из `Uploaded`/`Processing`/`ProcessingFailed`).
  Либо осознанно оставить как есть и зафиксировать, что инвариант «один Job на событие» держит
  корректность, по аналогии с уже принятым ограничением «один relay» в `arch.md`.
- **Тесты:** при добавлении guard — Handler-кейс «`RecordMediaProcessingFailure` для уже
  `ready`-медиа → статус остаётся `Ready`, `processingError` пуст». Если решение «не трогаем» —
  тест не нужен, достаточно записи рядом с заметкой о single-relay/single-Job контракте.

### 2. `MediaImageConversion` хранит фактические размеры от процессора вместо `spec.width/spec.height` — недокументированное расхождение с буквой плана

`ProcessMediaHandler::buildConversions` создаёт `MediaImageConversion` с `width: $conversionResult->width`,
`height: $conversionResult->height` — то есть фактическими размерами, которые вернул процессор. План
(шаг 6, «Целевой алгоритм», строка 241) явно предписывает `MediaPixelDimension из spec.width/spec.height`,
то есть размеры из запрошенной спецификации конверсии. При сохранении пропорций Imagick фактический
выход может отличаться от запрошенного (запрошено `100×100`, при letterbox/aspect-fit выдано `100×56`):
в БД ляжет `100×56`, а не `100×100` из spec.

Семантически фактические размеры точнее (отражают реальный объект, а не запрос), поэтому это, вероятно,
осознанное улучшение, а не баг. Но расхождение с явным контрактом плана нигде не зафиксировано —
ни в коде, ни в README, ни в журнале исполнения. Следующий ревьюер/сопровождающий, сверяясь с планом,
будет вынужден заново выяснять, намеренно это или регрессия.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/Media/ProcessMedia/ProcessMediaHandler.php:131-132`
  (`width: $conversionResult->width, height: $conversionResult->height`); контракт плана —
  `docs/plans/2026-06-08_22-56_media-upload-pipeline.md:241` (`MediaPixelDimension из spec.width/spec.height`).
- **Что подтверждает проблему:** Handler передаёт в `MediaImageConversion::create` поля
  `$conversionResult->width/height`, тогда как `MediaConversionSpec` несёт собственные `width/height`,
  которые план назначал источником размеров записи конверсии.
- **Как исправить:** один из вариантов — осознанно оставить фактические размеры и зафиксировать это
  одной строкой (комментарий у вызова `create` и/или запись в README/журнале «храним фактический выход
  процессора, а не запрошенный spec»), сняв расхождение с планом; либо, если контракт хранимых данных
  должен совпадать с запросом, вернуть `MediaPixelDimension` из `spec.width/spec.height`.
- **Тесты:** при выборе «храним фактические» — добавить/усилить кейс, где процессор возвращает размеры,
  отличные от spec (aspect-fit), и проверить, что в `MediaImageConversion` сохранены именно фактические
  значения; это закрепит выбранный контракт от регрессии.
