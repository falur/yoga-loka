# Ревью: медиа-пайплайн загрузки (цикл 8)

## Оценка

**96/100.** Восьмой цикл доводки: код отвердел, план выполнен по всем шести фазам,
правила и архитектура соблюдены. Набор тестов покрывает ключевые ветки нового кода (обе

этим ревью не переисполняли — она опирается на прошлые прогоны `make test`/coverage внутри

и пара совсем мелких шероховатостей — ни одна не блокирует. Все ранее разобранные за 7 циклов

## Проблемы сверки с планом

Все шесть фаз помечены выполненными и подтверждаются кодом: конфиг `media.php` + `MediaConfig`
с guard инварианта, Application-DTO и контракты, `S3MediaFileService` с резолвом бакета/префикса
из `StorageConfig`, `ImagickMediaImageProcessor`, полный набор CQRS-сценариев, `ProcessMediaJob`
с классификацией ошибок, проводка outbox (bootloader, queue, Kernel) и согласование документации
(arch.md/rules.md). Отклонения от буквы плана есть, но обоснованы; одно из них не задокументировано
(см. замечание 3).

Менее значимо и кода не требует: Handler-тесты лежат в `tests/Feature/Modules/Media/...`
(реальная БД + моки file service/процессора), тогда как план относил их к unit в
`tests/Unit/Modules/Media/...`. На покрытие это не влияет (ветки те же), отдельным замечанием
не выношу.

## Замечания

### 1. Image-конверсии для видео-медиа приведут к терминальному сбою обработки

Резолвер mime разрешает загрузку видео (`video/*` → `MediaType::Video`), и весь сценарий
до обработки видео отрабатывает штатно. Но при обработке для каждой конверсии безусловно
вызывается обработчик изображений, которому отдаётся оригинал и целевой mime-тип самого
медиа. Если потребитель подтвердит видео-загрузку с непустым списком image-конверсий,
обработчик упадёт уже на `decodeBinary($originalContents)` (`ImagickMediaImageProcessor.php:39`),
пытаясь раскодировать видео-байты как изображение, — до ветки `encodeUsingMediaType('video/*')`
дело не дойдёт. Исключение Intervention не является `MediaFileServiceFailedException`, поэтому
`ProcessMediaJob` классифицирует сбой как `isTransient=false` и уводит медиа в терминальный
`ProcessingFailed` без повтора.

Это не дефект для текущего scope (план явно ограничивает конверсии изображениями, видео
проходит как «оригинал без конверсий»), и при пустом списке конверсий видео корректно
доходит до `ready`. Риск чисто контрактный: будущий потребитель не имеет в коде/типах
сигнала, что image-конверсии валидны только для image-медиа, и узнает об ошибке лишь
асинхронно. Поскольку HTTP-границы у Media нет, защита уместна именно на Application-границе
`CompleteMediaUpload` (там же, где уже валидируются размеры конверсий). Рекомендация —
на усмотрение автора: либо явный guard, либо явная фиксация инварианта «image-конверсии только
для image-медиа» в README. Сейчас в README:95-96 есть лишь строка про оптимизацию
(«для видео/без конверсий — лишь server-side `copyObject`»), которая описывает happy-path
чтения оригинала, но не фиксирует запрет сочетания `video + непустые conversions`; README-вариант
означает усилить эту строку до явного инварианта, а не считать его уже описанным.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/Media/ProcessMedia/ProcessMediaHandler.php:104-110` (безусловный `mediaImageProcessor->resize` для каждой spec); `app/src/Modules/Media/Application/Command/Media/CompleteMediaUpload/CompleteMediaUploadHandler.php:55,107` (`assertConversionsValid` проверяет только диапазон width/height, не сочетание type+conversions); `app/src/Modules/Media/Application/Service/MediaTypeResolver.php:26` (video разрешён).
- **Что подтверждает проблему:** `buildConversions` не ветвится по `$media->type`; `MediaUploaded` несёт `conversions` без привязки к типу медиа; единственная валидация конверсий — `MediaPixelDimension::supports` по границам пикселей.
- **Как исправить:** в `CompleteMediaUploadHandler::assertConversionsValid` (или рядом) добавить guard «если `conversions !== []`, то медиа должно быть image» с `ValidationException` 422 — тогда невалидное сочетание отсекается синхронно на границе, а не падает в `ProcessMedia`. Минимальный вариант — задокументировать инвариант в `Media/README.md`.
- **Тесты:** добавить unit `CompleteMediaUploadHandler`: видео + непустые conversions → `ValidationException`. Если выбран только README — тест не нужен.

### 2. Параметр `isTransient` в `RecordMediaProcessingFailureCommand` используется только для лога

Команда фиксации ошибки несёт флаг транзиентности, но Handler записывает на сущность один
и тот же `ProcessingFailed` независимо от него (всегда `recordTemporaryProcessingError`,
`RecordMediaProcessingFailureHandler.php:33`) и использует флаг лишь в debug-контексте лога —
отдельной «ветки записи» по `isTransient` в Handler нет. Это осознанное решение плана (оба
доменных метода идентичны, различие влияет только на ретрай Job) и зафиксировано в комментарии
Handler-а, поэтому это не баг. Точка возможного будущего упрощения — конкретно: доменный двойник
`Media::recordPermanentProcessingError` (`Media.php:186-196`) байт-в-байт совпадает с
`recordTemporaryProcessingError` и в production не вызывается ни разу (только в `MediaEntityTest`);
плюс постоянный сбой пишется методом с именем «Temporary», что слегка вводит в заблуждение на
call-site. Сворачивать/удалять методы сейчас не нужно и в этом ревью не предлагается: оба метода
пред-существуют в HEAD (коммит `f235578`), в текущем незакоммиченном изменении к ним лишь добавлен
ready-guard, поэтому их рефакторинг — за пределами scope этого diff. Отмечаю как ориентир: если
различение transient/permanent на самой Media так и не появится, дубль и misleading-имя станут
кандидатами на чистку отдельной задачей.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/Media/RecordMediaProcessingFailure/RecordMediaProcessingFailureHandler.php:33,39` — флаг попадает только в лог-контекст.
- **Что подтверждает проблему:** `recordTemporaryProcessingError` вызывается всегда; `command->isTransient` не влияет на состояние Entity; доменный `Media::recordPermanentProcessingError` (`Media.php:186-196`) идентичен и в production не вызывается (grep: только `MediaEntityTest:89,100`).
- **Как исправить:** оставить как есть (поведение совпадает с планом, комментарий объясняет инвариант). Чистка дубля/misleading-имени — за пределами этого diff (методы пред-существуют в HEAD), отдельной задачей, если различение transient/permanent так и не появится.
- **Тесты:** не требуется; поведение покрыто `ProcessMediaJobTest` и `RecordMediaProcessingFailureHandlerTest`.

### 3. Отклонение от буквы плана по логированию «media готова» не задокументировано

План дважды требует уровень INFO для ключевого события «media готова» (фаза 4, строка 421;
раздел «Логирование», строки 491-495). Фактически `ProcessMediaHandler.php:79` пишет это
событие на DEBUG, и во всём модуле нет ни одного `logger->info` (подтверждено grep). Само
решение корректно и согласовано с `rules.md` («Логирование: DEBUG по умолчанию», INFO — только
для ключевых бизнес-событий регистрации/сброса пароля) — это осознанное отклонение цикла 8
(«лог DEBUG для success»), код менять не нужно. Проблема в другом: в отличие от отклонения
width/height-из-результата-процессора (зафиксировано в README:104-110, комментарии :123-127 и
тесте), это отклонение нигде не задокументировано как сознательное, поэтому будущему читателю
неочевидно, расхождение это с планом или упущение.

Технические детали:

- **Тип:** `plan`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Command/Media/ProcessMedia/ProcessMediaHandler.php:79` (событие «Медиа готово.» на DEBUG); план — фаза 4 / раздел «Логирование».
- **Что подтверждает проблему:** в модуле Media нет ни одного `logger->info` (grep), план предписывает INFO для «media готова».
- **Как исправить:** добавить короткую строку в `Media/README.md` (например, рядом с заметкой про DEBUG-логи), что «media готова» логируется на DEBUG по `rules.md`, осознанно расходясь с буквой плана. Поднимать до INFO не нужно — это нарушило бы `rules.md`.
- **Тесты:** не требуется (документационное уточнение).
