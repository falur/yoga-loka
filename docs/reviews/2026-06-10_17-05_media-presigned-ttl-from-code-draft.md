## Замечания

### 1. Невалидный TTL для public-медиа молча проходит как успех

Для public-медиа срок presigned-ссылки осознанно не применяется и доменный тип срока вообще не строится. Из-за этого потребитель, который передал заведомо мусорный срок (0, отрицательное число, миллион суток), для public-медиа получит нормальный ответ без ошибки, а для точно такого же private-медиа — внутреннюю ошибку 500. Один и тот же неверный ввод даёт два разных исхода в зависимости от видимости медиа.

Это поведение прямо заложено планом (VO строится только в private-ветке, для public TTL игнорируется), и формально это не баг. Риск проявится не сейчас (реальных потребителей ещё нет), а позже — когда модуль `User`/аватары начнёт звать `GetMediaUrl` и в коде потребителя проскочит неверный срок: на public он не будет замечен, на private «внезапно» даст 500. Стоит осознанно подтвердить, что молчаливое игнорирование неверного срока для public — желаемое поведение, либо задокументировать это ограничение в README рядом с сигнатурой `GetMediaUrl`.

Технические детали:

- **Тип:** `behavior` (не нарушение CQRS-правила: требование `arch.md` «Handler создаёт VO до `Entity::create()`/доменных методов» относится к Command-хендлерам; для Query-хендлеров тайминг построения VO не регламентирован, поэтому построение VO в private-ветке `buildUrl` — осознанный поведенческий компромисс, а не отступление от arch.md).
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Query/Media/GetMediaUrl/GetMediaUrlHandler.php:70-79` — ветка `MediaVisibility::Public` возвращается до построения `MediaPresignedTtl`; `GetMediaUrlQuery.php:13` — `presignedTtlSeconds` принимается сырым `int` без guard.
- **Что подтверждает проблему:** `buildUrl()` строит `MediaPresignedTtl::fromInt(...)` только внутри private-ветки (строка 78), public-ветка (строки 70-74) к сроку не обращается. Тест `testReturnsDirectPublicUrlForPublicMedia` передаёт валидный `presignedTtlSeconds: 300`, но кейс с невалидным сроком на public-медиа отсутствует, то есть текущее поведение «public игнорирует мусорный TTL» нигде не зафиксировано тестом.
- **Как исправить:** ничего менять в коде не обязательно. Если поведение оставляем — добавить в README в описание `GetMediaUrl` строку, что для public-медиа `presignedTtlSeconds` игнорируется и не валидируется, и при желании закрепить это тестом (public + заведомо невалидный TTL → успех, `presignGet` не зовётся). Если поведение нежелательно — строить VO в начале `handle()` для единообразной валидации обоих путей (но это противоречит явному решению плана, поэтому только по согласованию).
- **Тесты:** опционально добавить кейс в `GetMediaUrlHandlerTest`, фиксирующий, что для public невалидный TTL не приводит к ошибке.

### 2. Дублирование преобразования «секунды → DateTimeImmutable» в двух хендлерах

Логика «прибавить N секунд к текущему моменту через `new \DateInterval(sprintf('PT%dS', ...))`» теперь существует в двух местах независимо. В хендлере загрузки она вынесена в приватный метод `expiresIn()`, а в хендлере скачивания записана инлайном внутри `buildUrl()`. Это маленькое, но точное дублирование одной и той же неочевидной конструкции построения интервала.

Риск низкий и проявится только при будущем изменении формата (например, если понадобится учитывать миллисекунды или иной базовый момент времени): легко поправить одну копию и забыть про вторую. Сейчас на корректность не влияет.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `RequestMediaUploadHandler.php:159-162` (`expiresIn()`) и `GetMediaUrlHandler.php:77-79` (инлайн `new \DateTimeImmutable()->add(new \DateInterval(sprintf('PT%dS', ...)))`).
- **Что подтверждает проблему:** оба места строят `\DateTimeImmutable` смещением на N секунд тем же способом; в одном это именованный приватный метод, в другом — инлайн-выражение. Это два разных стиля для одной операции в одном модуле.
- **Как исправить:** текущее состояние двух локальных копий — корректное по правилам проекта, а не вынужденный компромисс: вынос построения интервала в shared-утилиту ради двух строк прямо нарушил бы `rules.md` «Не плодить технические константы/обёртки» (хендлеры в разных слоях CQRS, общего базового класса нет). Если всё же хочется единообразия, есть два варианта, оба на усмотрение автора: (а) привести оба места к одному стилю, вынеся построение в приватный метод и в `GetMediaUrlHandler`; (б) изменить сигнатуру `buildUrl(MediaPresignedTtl $presignedTtl)` и строить VO в `handle()` (где по духу CQRS-стиля `RequestMediaUploadHandler` уже работает с `$command->spec->presignedTtl->value()`), убрав inline-цепочку `fromInt(...)->value()` из private-метода — это снимает и дублирование стиля, и неявный inline-guard внутри `buildUrl`.
- **Тесты:** дополнительных тестов не требуется — поведение уже покрыто захватом `$expiresAt` в обоих feature-тестах.

### 3. Широкий diff выходит за рамки ревьюируемого плана

Ревью запрошено для плана о presigned-TTL, но незакоммиченное рабочее дерево содержит весь модуль Media целиком (S3-сервис, обработка изображений, ProcessMedia/CompleteMediaUpload/DeleteMedia и т.д.) плюс правки `docs/arch.md` и `docs/rules.md`. Это не дефект кода, а замечание о границах: сверка с планом покрывает только TTL-часть, а остальной объём проверен лишь обзорно на грубые проблемы.

Практический риск — при коммите всё это уедет одним набором изменений, и крупная часть (пайплайн загрузки медиа) формально останется без прицельной сверки с её собственным планом. Стоит убедиться, что широкий Media-diff покрыт отдельным ревью своего плана (`docs/plans/...media-upload-pipeline...`), прежде чем считать всё рабочее дерево готовым к коммиту.

Технические детали:

- **Тип:** `docs`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `git diff HEAD --stat` — 107 файлов; TTL-плану соответствуют только `MediaPresignedTtl.php`, `MediaUploadSpec.php`, `RequestMediaUploadHandler.php`, `GetMediaUrlQuery/Handler.php`, `MediaConfig.php`, `media.php`, `.env.sample`, `phpunit.xml`, `MediaFileServiceContract.php` (докблок), `README.md` и затронутые тесты. Остальное (`S3MediaFileService`, `ProcessMediaHandler`, `ProcessMediaJob`, `CompleteMediaUploadHandler`, изменения `arch.md`/`rules.md` и пр.) — отдельный объём.
- **Что подтверждает проблему:** в репозитории уже есть серия ревью `docs/reviews/...media-upload-pipeline-uncommitted-draft.md`, что указывает на отдельный поток работ, влитый в то же рабочее дерево.
- **Как исправить:** при коммите либо разделить изменения по логическим коммитам (TTL отдельно от пайплайна), либо убедиться, что широкая часть закрыта своим ревью. Для текущего ревью это лишь предупреждение о границах, кода менять не нужно.
- **Тесты:** не применимо.
