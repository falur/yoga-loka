# Ревью: Слой данных/домена модулей User и Access (повторный круг)

## Оценка

**95/100.** Второй круг доводки в целом прошёл чисто, но мета-проверка нашла одну реальную дыру в применённом фиксе `UserBio`. Три замечания прошлого ревью применены: `\Normalizer::FORM_C` теперь передаётся явно в `UserName`/`UserSpiritualName` с поясняющим комментарием; инвариант «строка обязана быть UUID v7» вынесен в единственный публичный `AbstractUuidV7Id::isUuidV7()` и переиспользован в `UserAvatar`; запрет управляющих символов в `UserBio` расширен до полного `\p{Cc}` (кроме `\n`) с покрывающим C1-тестом. Оговорка по последнему: новый запрет — это *негативный* блок-лист (`preg_match(...) === 1` → бросить), а не якорный whitelist, как у остальных текстовых VO. На невалидном UTF-8 `preg_match(..., /u)` возвращает `false`, проверка не срабатывает, и `UserBio` молча принимает битую строку — единственный текстовый VO без защиты от невалидного UTF-8 и без соответствующего теста (см. Замечание 3). `make phpstan` (level max) перепроверен — зелёный; это подтверждает, что точечный scoped-ignore в `phpstan.neon` реально совпадает и не маскирует ничего лишнего *сейчас* (при дефолтном `reportUnmatchedIgnoredErrors=true` несовпадение упало бы сразу), хотя сам ignore scoped по двум файлам, а не по двум строкам (см. Замечание 1). Слой целиком соответствует плану и эталону `Media`: границы модулей соблюдены, репозитории read-only с доменными методами и типизированными коллекциями, VO не зависят от ORM, миграции точно повторяют схему из «Контрактов». Осознанно отклонённые в прошлом круге optional-пункты (`isDeleted()` как `OR`, дублирование `normalize()/fromString()` между именами) не поднимаю — новых аргументов нет, оба явно переданы в Application-план. Прочие наблюдения мелкие и не блокируют слой данных.

## Проблемы сверки с планом

Все четыре фазы реализованы; контракты данных/БД, набор VO/enum/typecast/репозиториев и сценарии тестирования соответствуют плану. Контрактное отступление прошлого круга по `FORM_C` закрыто. Отступление по `UserBio`/`\p{Cc}` закрыто частично: полный диапазон `\p{Cc}` теперь блокируется для валидного UTF-8, но реализация через негативный блок-лист оставила дыру на невалидном UTF-8 (см. Замечание 3) — план («без `\p{Cc}` кроме `\n`») молчаливо подразумевает валидный текст, а другие текстовые VO (`UserName`/`UserSpiritualName`/`UserLocation`) этот ввод отбивают якорным whitelist'ом.

## Замечания

### 1. Гашение named-arguments в phpstan завязано на текст сообщения правила

Обязательный фикс `FORM_C` потребовал точечно погасить strict-правило named-arguments, потому что именовать позиционные аргументы `\Normalizer::normalize()` нельзя (имя первого параметра расходится между нативным `ext-intl` — `$string` — и polyfill-стабом `symfony/polyfill-intl-normalizer` — `$s`, который PHPStan резолвит для глобального `\Normalizer`). Само решение корректно и задокументировано. Две тонкости. Первая: ignore сматчен не только по идентификатору правила, но и по регулярке текста сообщения; если апстрим-правило переформулирует текст, ignore перестанет совпадать — но это безопасный режим отказа: при дефолтном `reportUnmatchedIgnoredErrors=true` (в проекте параметр не переопределён) сборка PHPStan просто покраснеет и укажет на это место, а не пропустит реальную ошибку. Вторая, более существенная: ignore scoped через `paths` по двум *файлам* целиком, а не по двум конкретным строкам. `reportUnmatchedIgnoredErrors` защищает только от полного несовпадения, но не от лишних совпадений — если в `UserName.php`/`UserSpiritualName.php` позже появится другой позиционный вызов с 2+ аргументами, named-arguments-правило для него тоже молча погасится. То есть это не риск тихого пропуска по `\Normalizer`, а точка хрупкости при апгрейде тулчейна плюс чуть более широкий, чем нужно, scope.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `phpstan.neon:19-24` — блок `ignoreErrors` с `identifier: gianTiaga.phpstanStrictRules.namedArgumentsRequired`, `message: '#Calls with two or more ordinary arguments must use named arguments\.#'` и `paths` на два файла VO имён (комментарий-пояснение — строки 15-18).
- **Что подтверждает проблему:** ignore сматчен по паре `identifier` + `message` + per-file `paths`; `message` дублирует человеческий текст правила из пакета `packages/phpstan-strict-rules`. `make phpstan` (level max) перепроверен в этой мета-проверке — зелёный, значит совпадение есть и ничего лишнего сейчас не маскируется.
- **Как исправить:** ничего срочного. Чтобы убрать хрупкость по тексту — оставить только `identifier` без `message` (он привязан к scoped `paths`, проверено: identifier-only вариант остаётся зелёным). Чтобы сузить scope до самих вызовов — `path` (один файл) или сужение `message` под `Normalizer`. Тесты и поведение не меняются.

### 2. Имя публичного предиката `isUuidV7()` не консистентно с уже принятым `supports()` на базовых VO

Дедупликация проверки UUID v7 сделана аккуратно и решает замечание прошлого круга. Появившийся публичный статический предикат `isUuidV7(string): bool` существует ради `UserAvatar::pointingTo()` — места, где «голую» строку нужно провалидировать как UUID v7 до построения полноценного id-VO. Это **не** размывание правила «доменные примитивы — через VO» и не архитектурный риск: в проекте уже есть благословлённый прецедент того же паттерна — `AbstractIntegerValue::supports(int): bool` (`app/src/Shared/Domain/ValueObject/AbstractIntegerValue.php:36-39`) с docblock, прямо санкционирующим «проверить значение на границе Application без создания VO». `isUuidV7()` — структурный близнец `supports()`, приватная валидация по-прежнему инкапсулирована в `fromString()`/`assertUuidV7()`. Единственное мелкое наблюдение: два базовых id/value-VO называют один и тот же по смыслу предикат по-разному (`supports` vs `isUuidV7`) — локальная неконсистентность имени, не дефект.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Shared/Domain/ValueObject/AbstractUuidV7Id.php:50` (`public static function isUuidV7`); ср. прецедент `app/src/Shared/Domain/ValueObject/AbstractIntegerValue.php:36-39` (`public static function supports`). Единственный внешний потребитель — `app/src/Modules/User/Domain/ValueObject/UserAvatar.php:23`.
- **Что подтверждает проблему:** оба класса предоставляют публичный статический предикат для проверки примитива до построения VO, но с разными именами. Поиск по `tests/` и `app/src/` показывает один внешний вызов `isUuidV7`.
- **Как исправить:** оставить как есть — функционально корректно, паттерн каноничен. При желании выровнять имя предиката между базовыми VO (например `supports(string)` и здесь), чтобы инвариант читался единообразно. Helper-класс заводить не нужно.

### 3. `UserBio` молча принимает невалидный UTF-8 (дыра в применённом фиксе `\p{Cc}`)

Фикс прошлого круга заменил проверку `UserBio` на блокировку всего `\p{Cc}` кроме `\n`, но реализовал её *негативным* блок-листом: `if (\preg_match('/(?!\n)\p{Cc}/u', $bio) === 1) { throw … }`. На невалидном UTF-8 `preg_match` с модификатором `/u` возвращает **`false`**, а не `0` или `1`. Условие `=== 1` не срабатывает, других guard'ов нет — и битая по UTF-8 строка проходит как валидное bio. Проверено исполнением: `UserBio::fromString("\xC3\x28")` создаёт VO, тогда как `UserName`/`UserSpiritualName`/`UserLocation` ту же строку отбивают, потому что используют *якорный whitelist* `/^[...]+$/u` с требованием `=== 1` (на `false` он не равен `1` → исключение). `UserBio` — единственный текстовый VO без этой защиты, и в отличие от `UserName`/`UserSpiritualName` (где есть `testNameRejectsInvalidUtf8`/`testSpiritualNameRejectsInvalidUtf8`) для него нет теста на невалидный UTF-8. Практический риск умеренный (поле декоративное, на HTTP-границе ввод обычно валидный UTF-8), но это реальная брешь инварианта VO, которую прошлый фикс внёс незаметно, а прошлое ревью описало как «без побочных эффектов».

Технические детали:

- **Тип:** `quality` (корректность инварианта VO)
- **Рекомендация:** `на усмотрение автора` (склоняется к «править»: дёшево и убирает реальную брешь)
- **Где:** `app/src/Modules/User/Domain/ValueObject/UserBio.php:30`.
- **Что подтверждает проблему:** `preg_match(..., /u)` на `"\xC3\x28"` → `false`; условие `=== 1` не ловит, VO создаётся. Аналог `UserName.php:25`/`UserSpiritualName.php:30`/`UserLocation.php:30` через `!== 1` корректно отвергает тот же ввод. Теста `testBioRejectsInvalidUtf8` нет.
- **Как исправить:** обрабатывать `false` явно — например `$matched = \preg_match('/(?!\n)\p{Cc}/u', $bio); if ($matched === false || $matched === 1) { throw … }`, либо добавить отдельный guard на валидность UTF-8 (`\preg_match('//u', $bio) === false` / `mb_check_encoding($bio, 'UTF-8')`). Добавить unit-ветку на `"\xC3\x28"` по образцу теста имён.
