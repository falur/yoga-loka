# Ревью: Модуль уведомлений (Notifications) — незакоммиченный diff (второй круг)

## Оценка

**86/100.** Модуль аккуратно следует плану и правилам: чистый DDD, корректный outbox-поток,
null-object VO и per-column typecast, тонкие контроллеры, идемпотентная рассылка. Прошлый круг
закрыл IDOR удаления токена, 500→422 на cursor и rename репозитория — всё подтверждено в коде.

Снижение в этом круге — за реальный риск в realtime-доставке: HTTP-клиент Centrifugo шлёт ключ
API в нестандартном заголовке (`X-API-Key` вместо документированного для Centrifugo v6
`Authorization: apikey`) и считает успех только по HTTP-статусу, тогда как Centrifugo на
логические отказы публикации отвечает кодом 200 с `error` в теле. В связке это даёт тихую потерю
realtime-уведомлений в проде, не покрытую тестами (клиент тестируется только против фейкового
PSR-18). Мета-ревью добавило третий обязательный пункт: два инфраструктурных исключения модуля
(`CentrifugoPublishException`, `FcmPushFailedException`) наследуют голый `\RuntimeException` —
нарушение `rules.md:45` и расхождение со всеми остальными исключениями проекта, которые наследуют
`\DomainException` (включая соседнее `NotificationTypeRegistryException` того же модуля). Остальные
замечания — мелкие, на усмотрение автора. Ранее отклонённые пункты (`__toString()` для none()-VO,
батчинг mark-all, enum в Filter, collection-пайплайн вместо `array_map`) не повторяю — новых
аргументов против зафиксированных причин нет.

## Проблемы сверки с планом

План выполнен по всем 7 фазам, контракты БД/API соответствуют разделам «Данные и БД» и «API».
Явных невыполненных пунктов плана не найдено: реализация точно следует плану. Замечания ниже
касаются качества реализации внутри выполненного плана, а не отклонений от него. Важная оговорка:
по заголовку Centrifugo реализация следует плану корректно — это сам план зафиксировал неверную
деталь HTTP-протокола (решение 15 и фаза 6 явно прописали `X-API-Key`), поэтому ошибка унаследована
из плана/research, а не является отклонением реализации от плана (см. «Замечания», пункт 1).

## Замечания

### 1. HTTP-клиент Centrifugo шлёт API-ключ в нестандартном заголовке — realtime может не аутентифицироваться в проде

Клиент realtime-доставки кладёт ключ API в заголовок `X-API-Key`. Документация Centrifugo v6
(сервис в dev-стенде — `centrifugo/centrifugo:v6.7.2`) для HTTP API описывает аутентификацию как
заголовок `Authorization: apikey <key>` либо query-параметр `api_key=<key>`; заголовок `X-API-Key`
в актуальной документации v6 не упоминается. Если v6 не принимает легаси-заголовок, каждый publish
будет отвергнут как неаутентифицированный, и ни одно realtime-уведомление до клиента не дойдёт.

Риск не виден ни в одном тесте: `CentrifugoClientTest` проверяет только, что заголовок `X-API-Key`
выставлен на исходящем PSR-18 запросе, но запрос уходит в фейковый HTTP-клиент, а не в настоящий
Centrifugo. То есть тест фиксирует текущее (потенциально неверное) поведение, а не контракт сервера.
Проявится при первом реальном realtime-уведомлении в окружении с включённой проверкой ключа.

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Notifications/Infrastructure/Centrifugo/CentrifugoClient.php:32-35`
  (заголовок `'X-API-Key' => $this->config->apiKey`); план фаза 6 тоже зафиксировал `X-API-Key`,
  так что ошибка унаследована из плана.
- **Что подтверждает проблему:** документация Centrifugo v6 (context7 `/centrifugal/centrifugo`):
  «Requires `Authorization: apikey <key>` header or query param `api_key=<key>`». Все примеры
  publish/broadcast используют `Authorization: apikey`. `X-API-Key` — формат старых версий
  Centrifugo (v1), в v6 не гарантирован.
- **Как исправить:** заменить заголовок на `Authorization` со значением `\sprintf('apikey %s',
  $this->config->apiKey)` (или добавить query-параметр `api_key`). Заодно поправить вводящий в
  заблуждение комментарий в `app/config/centrifugo.php:12` («заголовок X-API-Key»). Перед фиксом
  подтвердить против живого `centrifugo:v6.7.2` (smoke-публикация) — это снимет и неопределённость,
  и риск пункта 2.
- **Тесты:** обновить `CentrifugoClientTest` под новый заголовок; добавить интеграционную
  smoke-проверку против поднятого Centrifugo (publish → 200 без `error`), чтобы тест проверял
  контракт сервера, а не только форму исходящего запроса.

### 2. Клиент Centrifugo считает успехом любой ответ 2xx/3xx, а логические отказы publish приходят как 200 с `error` в теле

`CentrifugoClient::publish()` решает об успехе только по HTTP-статусу: ≥500 — временный сбой, ≥400 —
терминально, иначе считается, что сообщение доставлено. Но HTTP API Centrifugo на логические
отказы публикации (неизвестный namespace канала, превышение лимитов, отклонение proxy и т.п.)
отвечает кодом **200** и кладёт объект `error` в JSON-тело. Тело ответа клиент не читает вообще.

Практический эффект: при таком отказе publish тихо считается успешным, outbox-событие помечается
handled, и realtime-уведомление безвозвратно теряется без следа в логах и без повтора. Это особенно
вероятно в проде, потому что персональный канал `personal:#user_{userId}` использует namespace
`personal`, которого нет в dev-конфиге Centrifugo (`docker/centrifugo/config.json` не объявляет
`channel.namespaces`) — публикация в необъявленный namespace и есть классический «200 + error».

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Notifications/Infrastructure/Centrifugo/CentrifugoClient.php:45-54`
  (проверяется только `getStatusCode()`, тело не парсится); канал собирается в
  `PublishRealtimeNotificationHandler.php` (`personal:#user_%s`); namespace `personal` не объявлен в
  `docker/centrifugo/config.json`.
- **Что подтверждает проблему:** документация Centrifugo v6 (context7 `/centrifugal/centrifugo`):
  успешный ответ — `{"result": {...}}` с кодом 200; пример proxy-обработчика возвращает
  `{"error": {"code": ..., "message": ...}}` именно с HTTP 200. Клиент это тело игнорирует.
- **Как исправить:** после получения 2xx распарсить тело и, если присутствует ключ `error`,
  бросить `CentrifugoPublishException` — терминальную для ошибок запроса (неизвестный канал,
  валидация) и при необходимости временную для внутренних кодов. Отдельно (эксплуатация):
  объявить namespace `personal` в конфиге Centrifugo для dev и прода, иначе все персональные
  публикации будут отклоняться.
- **Тесты:** добавить юнит-кейс «ответ 200 с телом `{"error": {...}}` → `CentrifugoPublishException`»;
  зафиксировать поведение по коду ошибки (терминально/временно).

### 3. Инфраструктурные исключения модуля наследуют голый `\RuntimeException` — нарушение `rules.md:45`

`CentrifugoPublishException` и `FcmPushFailedException` наследуют `\RuntimeException`. Это прямое
нарушение `rules.md:45` («Типизированные доменные исключения вместо `RuntimeException`: запрещено
использовать голый `\RuntimeException`») и расхождение со сложившимся паттерном проекта: все
остальные модульные исключения наследуют `\DomainException` — `OutboxJobRegistryException`,
`OutboxRelayStoppedException`, `OutboxMessageLoadingException`, `MediaStorageNotConfiguredException`,
`MediaImageProcessorException`, `MediaFileServiceFailedException` и, что особенно показательно,
соседнее `NotificationTypeRegistryException` (`Application/Exception`) того же модуля. Два новых
исключения — единственные модульные исключения на `\RuntimeException` во всём `app/src` (вне их
остаётся лишь изолированный `Shared/Infrastructure/Exception/ConfigMappingException`, который
прецедента для нового кода не создаёт).

Технические детали:

- **Тип:** `bug`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Notifications/Infrastructure/Exception/CentrifugoPublishException.php:11`
  (`extends \RuntimeException`) и
  `app/src/Modules/Notifications/Infrastructure/Exception/FcmPushFailedException.php:12`
  (`extends \RuntimeException`).
- **Что подтверждает проблему:** инвентаризация всех `*Exception`-классов в `app/src` (Outbox,
  Media, Notifications/Application) показывает единый паттерн `extends \DomainException`; правило
  `rules.md:45` запрещает голый `\RuntimeException`. Оба исключения — инфраструктурные (не HTTP,
  не доменное значение), `isTransient()` для классификации повтора `\DomainException` не мешает.
- **Как исправить:** заменить базовый класс обоих на `\DomainException`; сигнатуры конструктора,
  фабрик и `isTransient()` не меняются. Поведение Job-классификации (`isTransient()` →
  `RetryException`) сохраняется — `instanceof CentrifugoPublishException` остаётся валидным.
- **Тесты:** существующие тесты (`CentrifugoClientTest`, push-handler) не зависят от базового
  класса; правка инфраструктурная, новые тесты не требуются.

### 4. Глобальный PSR-18 `ClientInterface` биндится синглтоном в модульном бутлоадере

`NotificationsBootloader` биндит общий интерфейс `Psr\Http\Client\ClientInterface` на конкретный
`GuzzleHttp\Client` синглтоном в контейнере приложения. Сейчас это единственный потребитель PSR-18
в коде, поэтому работает. Но биндинг глобального интерфейса из модульного бутлоадера — скрытая
связанность: как только другому модулю понадобится свой PSR-18 клиент (иные таймауты, базовый URL,
middleware), он молча получит Guzzle, сконфигурированный для Centrifugo, либо возникнет конфликт
регистраций между бутлоадерами. Проявится при добавлении второго HTTP-интеграционного модуля.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Notifications/Infrastructure/Bootloader/NotificationsBootloader.php:44-48`
  (`SINGLETONS`: `ClientInterface::class => Client::class`).
- **Что подтверждает проблему:** в коде приложения нет другого биндинга
  `Psr\Http\Client\ClientInterface` (проверено по `app/`, `packages/`), то есть глобальный интерфейс
  занимает один модуль. `CentrifugoClient` принимает `ClientInterface` в конструкторе.
- **Как исправить:** либо инжектить в `CentrifugoClient` свежесозданный `new Client(...)` через
  фабрику-метод бутлоадера (как уже сделано для `Messaging::fcmMessaging`), не занимая глобальный
  интерфейс; либо биндить PSR-18 на уровне Shared-инфраструктуры, если он осознанно общий для всех
  модулей. Поведение CentrifugoClient при этом не меняется.
- **Тесты:** не требуется — внутренняя проводка DI; существующие тесты подменяют `ClientInterface`
  напрямую.

### 5. `equals()` у `NotificationChannelDefaults` сортирует через `\sort()` ради порядко-независимого сравнения — хрупко и неочевидно

Сравнение двух наборов дефолтных каналов сортирует оба массива через `\sort()` и затем сравнивает
через `===`. Массивы — локальные копии из `jsonSerialize()`, так что мутации состояния VO здесь нет
(это **не** баг). Замечание — про читаемость: из тела `equals()` неочевидно, зачем вообще нужна
сортировка, а сама нормализация порядка делается «на лету» при каждом сравнении вместо однократной
нормализации при создании. Это хрупкий паттерн — логика «порядок каналов не важен» размазана между
`of()` (хранит как есть) и `equals()` (сортирует).

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Notifications/Domain/ValueObject/NotificationChannelDefaults.php:46-53`
  (`$mine = $this->jsonSerialize(); \sort($mine); ...`).
- **Что подтверждает проблему:** `equals()` зависит от сортировки массивов, чтобы сравнение не
  зависело от порядка каналов; при этом `of()` уже хранит каналы как уникальный список, но порядок
  не нормализует.
- **Как исправить:** нормализовать порядок один раз при создании в `of()` (например, сортировать
  каналы по `value` сразу), тогда `equals()` сведётся к прямому `===` сериализаций без `sort()`.
  Альтернатива — сравнивать через множества без мутации (`array_diff`). Поведение не меняется.
- **Тесты:** существующий тест на `equals()` сохранить; при нормализации в `of()` добавить кейс
  «разный порядок каналов → equals === true».

### 6. `UpdateNotificationSettingsHandler::resolveType()` проверяет существование вида перебором `all()->first()` вместо lookup по реестру

Чтобы вернуть 422 на неизвестный вид, `resolveType()` перебирает весь реестр через
`registry->all()->first(fn => $candidate->code()->value() === $type)`. У реестра уже есть
`get(NotificationTypeCode)` с O(1)-lookup, но он бросает `NotificationTypeRegistryException` (500),
а хендлеру нужен `ValidationException` (422), и try-catch в хендлере запрещён (`rules.md:51`).
Поэтому перебор — рабочий обходной путь, но он прячет намерение («проверить, что вид существует»)
за линейным сканом и сравнением строк, и масштабируется хуже при росте реестра. Замечание про
читаемость и единообразие, не про баг.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Notifications/Application/Command/Setting/UpdateNotificationSettings/UpdateNotificationSettingsHandler.php:85-92`.
- **Что подтверждает проблему:** `NotificationTypeRegistryContract` уже даёт `get()`/`all()`;
  существование вида проверяется через полный обход коллекции вместо прямого lookup. Имя
  `resolveType()` к тому же не отражает, что метод валидирует наличие вида и бросает 422.
- **Как исправить:** добавить в `NotificationTypeRegistryContract` non-throwing предикат
  `has(NotificationTypeCode): bool` (check-then-act, как требует `rules.md:51`) и проверять им,
  либо переименовать метод так, чтобы намерение «валидировать вид → 422» читалось из имени.
- **Тесты:** существующий кейс «неизвестный вид → 422» сохранить; при добавлении `has()` покрыть
  его прямым unit-тестом реестра.

Обязательные пункты 1, 2, 3 применены полностью. Optional 4 принят, optional 5 применён в
минимальной безопасной форме (комментарий), optional 6 отклонён.

### Отклонённые optional-решения
- **6 (`resolveType()` — lookup вместо скана):** отклонён. Предложенный `has(NotificationTypeCode)`
  требует строить VO из недоверенного пользовательского `type` через
  `NotificationTypeCode::fromString()`, который на невалидный формат бросает
  `InvalidDomainValueException` (500). Текущий линейный скан реестра на любой неизвестный/некорректный
  `type` отдаёт `ValidationException` (422) — корректный клиентский контракт. Замена превратила бы
  422 в 500 для некорректных строк (регрессия HTTP-контракта). Не повторять пункт без нового
  способа проверить наличие вида без конструирования VO из untrusted-строки.
- **5 (`equals()`/`\sort()` — нормализация в `of()`):** полный рефактор отклонён, претензия не-баг
  (по признанию ревью). Нормализация порядка в `of()` изменила бы порядок `jsonSerialize()`
  (сериализуемое представление) ради косметики — лишний риск. Применён дешёвый безопасный вариант:
  поясняющий комментарий в `equals()`, закрывающий заявленную претензию читаемости.
