# Ревью: Модуль Auth — беспарольный вход по email-коду (четвёртый круг)

## Оценка

**94/100.** Четвёртый круг доводки того же незакоммиченного диффа. Единственное обязательное
замечание третьего круга (способ выражения обнуляемости не соответствует объявленной версии
`openapi: 3.1.0`) закрыто реально, а не на бумаге, и закрыто чисто: вся эмиссия nullable теперь
проходит через один version-aware класс `NullableSchema`, в опубликованной спецификации ноль
ключей `nullable`, обнуляемость для скаляров/массивов выражается типом-объединением
`type: [<T>, "null"]`, а для ссылок и составных схем — `oneOf: [<схема>, {type: "null"}]`.
Покрытие соответствует правкам: новый `NullableSchemaTest` проверяет обе версии (3.1 и 3.0,
включая `allOf`-обёртку для `$ref` в 3.0), `OpenApiGeneratorTest` через фикстуру `UserResource`
проверяет все три формы обнуляемости (скаляр/ссылка/список), а app-тест
`AuthOpenApiGenerationTest` проверяет фактический YAML `VerifyResultResource`.

По существу реализация чистая, но мета-ревью нашло одно пропущенное обязательное замечание,
не связанное с поведением: новые тесты используют запрещённые правилом «Конкретные имена
переменных» абстрактные имена `$handler` и `$result` (`docs/rules.md`). Правило не делает
исключения для тестов, а PHPStan их не сканирует, поэтому нарушение проскочило (замечание 2).
Ранее осознанно отклонённые пункты (контракт/PHPDoc рендерера `spiral-api-errors`, полное
выравнивание `RegisterFilter` с нормализацией VO) не возвращаю — новых фактов по ним нет
(подтверждено кросс-CLI codex). Остаётся также одно мелкое замечание `на усмотрение автора`
про неполноту покрытия 3.0-ветки генератора (она проверена только на уровне unit, но не
сквозным прогоном генератора), не влияющее на текущий сервер и текущую спеку (замечание 1).

## Проблемы сверки с планом

Явных проблем по плану не найдено. Все семь фаз реализованы, пять маршрутов Auth присутствуют
в `public/openapi/openapi.yml` (`/auth/code/request`, `/auth/code/verify`, `/auth/register`,
`/auth/refresh`, `/auth/logout`). Требование фазы 7 — «корректность OpenAPI-схемы
`VerifyResultResource` с nullable-полями» — теперь выполнено не только по серверной семантике
(поля `tokens`/`registrationTicket` обнуляемы и убраны из `required`), но и по способу выражения
для объявленной версии `3.1.0`: `tokens` сериализуется как
`oneOf: [{$ref: TokenPairResource}, {type: 'null'}]`, `registrationTicket` — как
`type: [string, 'null']`, `required` содержит только `needsProfile`. Это закрывает единственную
неполноту, отмеченную в ревью третьего круга. Отклонения предыдущих кругов (scan OpenAPI на все
модули, ключ rate limit по `path`, `logout` читает только `authSessionId`, фиксированное окно
через PSR-20 clock) зафиксированы в разделе плана «Принятые по ходу решения» и в `docs/arch.md`.

## Замечания

### 1. Ветка генерации nullable для OpenAPI 3.0 покрыта только unit-тестом, без сквозной проверки

Класс `NullableSchema` теперь умеет две версии: для `3.1.x` он выдаёт тип-объединение и `oneOf`,
а для остальных версий (`3.0.x`) — ключ `nullable: true` с обёрткой ссылок в `allOf`. Приложение
сейчас использует только 3.1, причём 3.0 из приложения вообще недостижима обычной конфигурацией:
у `OpenApiConfig` нет поля версии OpenAPI, а `toGeneratorConfig()` не передаёт `openApiVersion`,
поэтому всегда проходит дефолт пакета `3.1.0`. Чтобы вызвать 3.0-ветку из приложения, пришлось бы
менять код конфигурации. Из-за этого 3.0-ветка вживую генератором не вызывается, а её корректность
подтверждается только изолированным `NullableSchemaTest`, который проверяет один метод в отрыве от
остального конвейера сборки спецификации.

Практический риск возникнет, если кто-то в будущем переключит пакет на 3.0 (например, ради
совместимости с инструментом, не понимающим 3.1): сквозная сборка спецификации с 3.0-формой
nullable ни разу не проверялась целиком, и регрессия в интеграции `SchemaBuilder` ↔ `SpecBuilder`
↔ `NullableSchema` для 3.0 не будет поймана существующими тестами. На текущий сервер Auth, на
опубликованную 3.1-спеку и на текущие тесты это никак не влияет — это запас прочности
переносимого пакета, а не дефект приложения.

Технические детали:

- **Тип:** `tests` / `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `packages/spiral-openapi/src/Schema/NullableSchema.php:60-69`
  (метод `makeNullableForOpenApi30`, ветка `$ref` → `allOf`); юнит-проверка —
  `packages/spiral-openapi/tests/Schema/NullableSchemaTest.php:39-55`; сквозной генератор-тест
  `packages/spiral-openapi/tests/Generator/OpenApiGeneratorTest.php:100-130`
  (`assertUserResourceNullableSchema`) жёстко завязан на 3.1 и не параметризован по версии.
- **Что подтверждает проблему:** 3.0-ветка `NullableSchema` достижима только при
  `openApiVersion`, не начинающемся с `3.1`; в коде приложения такой конфигурации нет и завести
  её без правки кода нельзя (`packages/spiral-openapi/src/Config/OpenApiGeneratorConfig.php`
  дефолт `3.1.0`; `app/config/openapi.php` версию не задаёт; `OpenApiConfig` не имеет поля версии
  OpenAPI, а `OpenApiConfig::toGeneratorConfig()` не передаёт `openApiVersion`), поэтому
  генератор-тест её не проходит — покрыт только прямой вызов метода.
- **Как исправить:** добавить в `OpenApiGeneratorTest` (или отдельный кейс рядом) сквозную
  генерацию той же фикстуры `UserResource` при `openApiVersion = '3.0.3'` и проверить
  фактический результат: `nullable: true` у скаляра/списка, `allOf` + `nullable: true` у ссылки,
  отсутствие `type: [..., null]`. Это закрывает интеграцию обеих веток одним конвейером, а не
  только изолированный метод.
- **Тесты:** см. выше — параметризованный по версии генератор-кейс. Юнит-тест `NullableSchemaTest`
  оставить как есть.

### 2. Запрещённые абстрактные имена переменных `$handler` и `$result` в новых тестах

Правило `docs/rules.md` «Конкретные имена переменных» прямо перечисляет `$handler` и `$result`
как запрещённые абстрактные имена и требует имя, отражающее суть (`$requestLoginCodeHandler`,
`$verifyResult` и т.п.). В новых тестах эти имена используются для локальных переменных. Правило
не делает исключения для тестов, а PHPStan тесты не сканирует (`paths: [app/src]`), поэтому
нарушение прошло мимо автопроверки. Это не runtime-баг — поведение и покрытие не страдают, —
но нарушение обязательного правила проекта в новом коде.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** `править обязательно` (правило формулирует имена как «запрещены», без
  исключения для тестов; риск низкий и неповеденческий)
- **Где:**
  - `tests/Feature/Modules/Auth/Application/RequestLoginCodeHandlerTest.php:38` — `$handler`
    (используется на `:40`, `:41`).
  - `tests/Feature/Modules/Auth/Application/LoginCodeVerificationTest.php:26` — `$result`
    (также `:38`, `:45`).
  - `tests/Feature/Modules/User/Application/CreateUserHandlerTest.php:30` — `$result`
    (также `:51`).
- **Что подтверждает проблему:** правило `docs/rules.md` «Конкретные имена переменных»
  («запрещены абстрактные имена вроде `$handler`, `$service`, `$manager`, `$data`, `$result`,
  `$item`»); подтверждено двумя независимыми проверяющими (rules-check sonnet и кросс-CLI codex)
  прямым чтением файлов.
- **Как исправить:** переименовать `$handler` → `$requestLoginCodeHandler`, `$result` →
  конкретное имя по сути возвращаемого значения (`$verifyResult`, `$createUserResult` и т.п.).
- **Тесты:** правка чисто косметическая (переименование локальных переменных), новые тесты не
  требуются.
