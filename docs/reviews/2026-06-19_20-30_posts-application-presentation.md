# Ревью: Модуль Posts/Tags/User — прикладной и презентационный слой (4-й круг)

## Оценка

**93/100.** Реализация полностью соответствует плану (все 5 фаз, 15 сценариев, 7 видов
уведомлений, межмодульные точки входа, чтение с cursor-пагинацией), правилам и архитектуре проекта;
после трёх кругов доводки обязательных дефектов нет, и ни одно из найденного не воспроизводится на
текущей модели данных. Найдены шесть «на усмотрение»: (1) рассылка упоминаний при публикации черновика
использует строгую валидацию не по назначению — латентно, на текущих FK/soft-delete 422 не
воспроизводится; (2) лишняя дорогая сборка полного профиля с аватаром ради проверки существования для
черновика; (3) пакетная сборка read-model полагается на ключ автора без guard — латентно, авторы
защищены FK `RESTRICT`; (4) дублирование разрешения упоминаний в двух Composer-ах; (5)
недокументированный обход шины в `PostViewAssembler`; (6) неточный «без N+1» в докблоке для разрешения
URL медиа. Обязательных правок нет. Регрессий от фиксов третьего круга (дедуп `mediaIds`, перенос
рассылки `post_mention` на публикацию, guard пустого `findByTexts`, `UserCollection::map()`) не
обнаружено — все четыре фикса на месте и корректны (подтверждено всеми ролями и кросс-CLI).

## Проблемы сверки с планом

Явных проблем по плану не найдено. Реализация покрывает все маршруты схемы B, контракты смежных

## Замечания

### 1. При публикации черновика рассылка использует строгую валидацию упоминаний не по назначению

Фикс третьего круга перенёс рассылку уведомлений об упоминаниях с момента создания черновика на момент
его публикации — это правильно, потому что до публикации запись невидима и ссылка из уведомления вела бы
в «не найдено». Но при публикации `notifyPostMentions` гонит уже сохранённый список упоминаний через
`resolveRecipients`, который при несовпадении числа найденных профилей с запрошенными бросает
`ValidationException` (422). Так как `PublishPostHandler` помечен `#[Transactional]`, такое исключение
откатило бы и `publish()`.

Важно: на текущей модели данных это исключение фактически **не воспроизводится**. Физическое удаление
пользователя каскадит (`post_mentions.user_id` FK `delete: CASCADE`) и удаляет строку упоминания, поэтому
к моменту публикации её уже не будет в выборке; мягкое удаление (если оно есть) не фильтруется
`UserRepository::findByIds` — профиль всё равно вернётся, и счётчик сойдётся. То есть это **не**
работающая сейчас регрессия публикации, а структурная хрупкость: 422 на публикации стал бы возможен
только при будущем изменении политики профилей (скрывать удалённых) или порче данных (упоминание без
профиля).

Суть проблемы — семантическая: `resolveRecipients` отвечает за валидацию *входного* списка упоминаний
(момент создания, клиент прислал id), а рассылка по *уже сохранённым* упоминаниям должна быть «мягкой»
(разослать тем, кто существует, недоступных пропустить). Сейчас эти две роли смешаны в одном методе.

Технические детали:

- **Тип:** `quality` (латентный `bug` при изменении политики профилей/порче данных)
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/Post/PostContentComposer.php:148-165` (`notifyPostMentions`)
  → `resolveRecipients` (строки 205-220, бросает `ValidationException` при `count !== count`).
  Путь вызова: `PublishPostHandler::handle` (`PublishPostHandler.php:53`).
- **Что подтверждает проблему:** `notifyPostMentions` собирает получателей из сохранённых `PostMention` и
  передаёт их в `resolveRecipients` со строгой проверкой полноты — методику, предназначенную для
  валидации входного списка при создании. Тест
  `PublishPostHttpTest::testPublishingDraftNotifiesMentionedUsers` покрывает только happy-path.
- **Как исправить:** `resolveRecipients` по своей ответственности — валидация *входного* списка
  упоминаний (проверка полноты `count !== count` имеет смысл при создании, когда клиент прислал id).
  В `notifyPostMentions` он используется не по назначению: рассылка идёт по *уже сохранённым*
  упоминаниям, и здесь нужна «мягкая» выборка профилей без проверки полноты — недоступные тихо
  пропускаются. Создание черновика уже отвалидировало упоминания (422), поэтому на публикации строгая
  проверка избыточна. Практически: в `notifyPostMentions` заменить `resolveRecipients(...)` на выборку
  без `count`-проверки (как уже делает `attachMentionsAndNotify` в `CommentComposer` для мягкого пути).
- **Тесты:** отдельный тест не обязателен, пока кейс не воспроизводится на текущей модели данных;
  при появлении политики «скрывать удалённых из профилей» добавить HTTP-кейс «черновик с упоминанием →
  упомянутый удалён → публикация владельцем возвращает 200, уведомление уходит только существующим».

### 2. Для черновика список получателей упоминаний вычисляется и отбрасывается

При сохранении упоминаний для черновика код сначала ходит в модуль `User` за профилями всех упомянутых,
а затем, обнаружив что запись — черновик, выходит без рассылки, не используя полученные профили. То есть
на создание каждого черновика с упоминаниями делается лишний батч-запрос профилей, результат которого
выбрасывается.

Это не баг: запрос заодно выполняет нужную валидацию «упомянутый существует» (422 на несуществующего при
создании), поэтому полностью убрать его нельзя. Но получать полный профиль (с разрешением URL аватара
через Media) только ради проверки существования — избыточно: для черновика достаточно более дешёвой
проверки наличия пользователей.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/Post/PostContentComposer.php:122-141` (`attachPostMentions`):
  `resolveRecipients` (строка 130) вызывается до проверки `status === Draft` (строка 136); для черновика
  результат не используется.
- **Что подтверждает проблему:** при `PostStatus::Draft` метод доходит до строки 138 (`return`), так и
  не передав `$recipients` в `notifyMentions`. `resolveRecipients` внутри вызывает
  `GetUserPublicProfilesHandler`, который, помимо выборки пользователей, для каждого разрешает URL
  аватара через Media — это работа, не нужная для черновика.
- **Как исправить:** для валидации существования упоминаний при создании достаточно лёгкой проверки
  «все id найдены» (количество найденных пользователей == количество запрошенных) без сборки полного
  профиля с аватаром. Полный профиль собирать только когда действительно идёт рассылка (опубликованная
  запись). Это сохранит валидацию 422 и уберёт лишнюю работу для черновиков.
- **Тесты:** существующие кейсы создания черновика/опубликованной записи с упоминаниями остаются
  зелёными; отдельный тест не обязателен (поведение не меняется, меняется только стоимость).

### 3. Пакетная сборка read-model полагается на ключ автора без guard (латентная хрупкость)

В пакетной сборке (лента записей и листинги комментариев/ответов) карта авторов строится только по
найденным профилям (`GetUserPublicProfiles` молча опускает отсутствующих), а представление каждого
элемента берёт автора по ключу `userId` напрямую, без проверки наличия. Если профиль автора не вернётся,
доступ к несуществующему ключу даст `undefined array key` → неконтролируемая 500.

На текущей модели данных это не воспроизводится: автор записи/комментария защищён FK
(`posts.user_id`/`comments.user_id` `delete: RESTRICT` — пользователя с записями нельзя удалить
физически), а мягкое удаление `UserRepository::findByIds` не фильтрует. Поэтому это латентная хрупкость
под будущую политику «скрывать удалённых из профилей», а не текущий баг. Заметна асимметрия: одиночное
чтение (`fromPost`/`fromComment` → `GetUserPublicProfile`) при отсутствии профиля получает честную 404
(`NotFoundException`), а пакетное чтение тихо полагается на наличие ключа.

Технические детали:

- **Тип:** `quality` (латентный `bug` при изменении политики профилей)
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/View/PostViewAssembler.php:95` (`fromPosts`) и `:424`
  (`originalViewsByPost`); тот же паттерн в `CommentViewAssembler.php:59` (`fromComments`) —
  `$authors[...->value()]` без guard. Карты строятся в `authorViews` только по вернувшимся профилям
  (`PostViewAssembler:172-182`, `CommentViewAssembler:109-119`).
- **Что подтверждает проблему:** `authorViews` кладёт в карту только профили из
  `GetUserPublicProfilesQuery`, а тот по контракту опускает отсутствующих. При отсутствующем ключе PHP
  отдаёт `undefined array key` → 500.
- **Как исправить:** в пакетных путях обрабатывать отсутствие автора явно (пропуск элемента или
  заглушка-автор), либо гарантировать наличие профиля и бросать понятное доменное исключение, как в
  одиночном пути. Привести одиночный и пакетный пути обоих ассемблеров к единому поведению.
- **Тесты:** отдельный тест не обязателен, пока кейс не воспроизводится; добавить вместе с политикой
  скрытия удалённых пользователей.

### 4. Дублирование `resolveRecipients`/`profile` в двух Composer-ах с захардкоженным ключом

`PostContentComposer` и `CommentComposer` содержат побайтово одинаковые приватные методы
`resolveRecipients` и `profile`, включая захардкоженный ключ перевода `'app.posts.mention_user_not_found'`.
Логика проверки упоминаний и подтягивания профиля задублирована: при изменении правила проверки или
ключа перевода нужно править оба места, и легко пропустить одно.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/Post/PostContentComposer.php:205-228` и
  `app/src/Modules/Posts/Application/Post/CommentComposer.php:118-141`.
- **Что подтверждает проблему:** оба метода идентичны (тот же `GetUserPublicProfilesQuery`, та же
  проверка `count !== count`, тот же ключ `'app.posts.mention_user_not_found'`, тот же `profile`).
- **Как исправить:** вынести разрешение получателей упоминаний и сборку профиля в один общий
  прикладной сервис (например `MentionRecipientResolver` в `Posts/Application`), переиспользуемый обоими
  Composer-ами. Естественно объединяется с п.1: у сервиса два режима — строгий для валидации *входного*
  списка упоминаний (создание) и мягкий для рассылки по *уже сохранённым* (публикация). Тогда ключ
  перевода и правило проверки живут в одном месте.

### 5. Прямой вызов `FindMediaUrlHandler` в `PostViewAssembler` без обоснования инварианта

`PostViewAssembler` инжектит `FindMediaUrlHandler` и вызывает его напрямую (минуя `QueryBus`), как и
`UserPublicProfileAssembler`. Но в `UserPublicProfileAssembler` это явно обосновано в докблоке (обёртка
шины теряет `null` из вывода типов, а контракт «медиа недоступно → null → дефолт» нужно сохранить без
try-catch). В `PostViewAssembler` того же обоснования у обхода шины нет: докблок `mediaItem` объясняет
поведение мягкой деградации, но не сам факт прямого вызова. Это не баг, а пробел документации инварианта
и расхождение в консистентности межмодульных вызовов.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/View/PostViewAssembler.php:47` (инъекция),
  `:267` (`mediaItem` — прямой `findMediaUrlHandler->handle()`).
- **Как исправить:** добавить в докблок `PostViewAssembler` (или метода `mediaItem`) ту же причину
  прямого вызова `FindMediaUrl`, что и в `UserPublicProfileAssembler` (теряемый `null` через шину),
  чтобы обход `QueryBus` был осознанным и единообразно задокументированным контрактом.

### 6. Заявленный «без N+1» неточен для разрешения URL медиа

Докблок `PostViewAssembler` обещает, что «в листингах авторы, флаги likedByMe, медиа и теги собираются
пакетно (без N+1)». Это верно для выборок из БД (`post_media`, `post_tags`, авторы, лайки берутся одним
батчем на страницу), но разрешение URL каждого вложения идёт отдельным вызовом `FindMediaUrlHandler` на
каждое медиа (`mediaItem`), а тот читает медиа по одному. То есть на странице с медиа-тяжёлыми записями
число вызовов разрешения URL растёт линейно с числом вложений — формально это N+1 на уровне URL, не
покрытый обещанием докблока. Тест `GetUserFeedHttpTest` проверяет тело ответа, но не число вызовов
разрешения URL.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/View/PostViewAssembler.php:265-283` (`mediaItem` —
  `findMediaUrlHandler->handle()` на каждое вложение); докблок класса (`:31-37`) обещает «без N+1».
- **Что подтверждает проблему:** батч-методы покрывают только выборку строк; URL разрешается поэлементно.
  Отдельного батч-контракта разрешения URL в `Media` сейчас нет.
- **Как исправить:** либо уточнить докблок (батч относится к выборкам из БД, URL разрешается поэлементно
  из-за отсутствия батч-контракта в `Media`), либо при необходимости завести в `Media` пакетный сценарий
  разрешения URL. Минимально — снять переоценку «без N+1» в формулировке докблока.
