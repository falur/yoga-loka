# Ревью: Удаление оригинала медиа с сохранением конверсий

## Оценка

**90/100.** Реализация почти дословно следует плану: новая команда, доменный предикат `isFinalized()`, расширенные guard-ы записи ошибок, разведённая семантика запросов и три ключа локалей — всё на месте, тесты закрывают перечисленные планом сценарии. Критичных багов и нарушений правил, требующих обязательной правки, не найдено. Снижение оценки — за набор мелких, не блокирующих пробелов, которые вскрыло мета-ревью: несколько тестов фиксируют контракт слабее, чем могли бы (лог-контекст, идемпотентный no-op, пути удаления/конверсии, ключ исключения в одном из новых кейсов), и за пару наблюдений по качеству/единообразию (дублирование тел двух доменных методов, предикат через `||` вместо исчерпывающего `match`). Все пункты — «на усмотрение автора».

## Проблемы сверки с планом

### 1. Состав лог-контекста завершения не закреплён тестом

План в разделах «Логирование» и «Целевой алгоритм» (шаг 8) фиксирует `logging_strategy: debug_precise` с явным составом контекста завершения: debug-лог «Оригинал медиа удалён» с ключами `mediaId`, `userId`, `storage`, `path` (camelCase, без сырых VO). В коде это сделано верно (`RemoveMediaOriginalHandler.php:75-80`) — расхождения реализации с планом нет. Проблема узкая: состав контекста описан планом как часть контракта `debug_precise`, но ни один тест его не закрепляет — везде используется `NullLogger`, поэтому при будущем рефакторинге случайное удаление `userId`/`storage`/`path` или передача сырого VO не уронит ни один тест.

Это последовательный стиль модуля: остальные хендлеры (`ProcessMediaHandlerTest` и др.) логи тоже не проверяют через spy. Поэтому замечание — про тестовую страховку точно описанного планом контракта, а не про дефект кода.

Технические детали:

- **Статус:** код соответствует плану; не закреплено тестом
- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php:75-80` — лог завершения; `tests/Feature/Modules/Media/Application/RemoveMediaOriginalHandlerTest.php:209` — `new NullLogger()`
- **Как исправить:** опционально — в одном успешном кейсе подменить `NullLogger` на spy/`createMock(LoggerInterface::class)` и проверить вызов `debug` с ключами `mediaId/userId/storage/path`. Если команда сознательно не покрывает логи (как остальные хендлеры модуля) — оставить как есть: это в рамках принятого стиля.

## Замечания

### 1. Идемпотентный no-op не проверяет отсутствие записи в БД

Команда идемпотентна: повторный вызов на уже `readyOriginalRemoved`-медиа делает ранний `return` ДО `deleteObject` и ДО `persist`+`run()`. Код это поведение реализует корректно. Тест `testIsIdempotentWhenOriginalAlreadyRemoved` проверяет только `expects(self::never())->method('deleteObject')` и поля результата, но не закрепляет, что в БД ничего не переписалось.

Это не риск текущего поведения (ранний `return` до записи уже гарантирует no-op), а только слабая тестовая фиксация: если кто-то позже передвинет `return` ниже записи, тест по состоянию объекта в памяти этого не заметит.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Application/RemoveMediaOriginalHandlerTest.php:180-198`
- **Как исправить:** при желании — перечитать медиа из репозитория после вызова и сравнить `updatedAt` до/после (повторного `persist` быть не должно). Основная гарантия (нет S3-вызова) уже проверена.

### 2. Новый кейс `CheckMediaAttachableHandlerTest` не проверяет ключ исключения

Добавленный этим diff-ом кейс `testRejectsReadyOriginalRemovedMedia` проверяет только класс `ValidationException`, без `expectExceptionMessage('app.media.not_ready')`. Все новые кейсы `RemoveMediaOriginalHandlerTest` и оба новых 404-кейса `GetMediaUrlHandlerTest` ключ проверяют — несимметрично; план в фазе 1 требовал закреплять конкретный контракт ошибки, а не только класс.

(Существующие, не тронутые этим diff-ом кейсы без `expectExceptionMessage` — `GetMediaUrlHandlerTest::testRejectsMediaThatIsNotReady`, `GetAudioWaveformHandlerTest::testRejectsNonReadyMedia` — вне scope diff; их план явно велел «оставить как есть».)

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Application/CheckMediaAttachableHandlerTest.php:72-87`
- **Как исправить:** добавить `$this->expectExceptionMessage('app.media.not_ready')` к новому кейсу.

### 3. Регрессионные/успешные кейсы проверяют факт вызова, но не пути

Два места фиксируют только число вызовов файлового сервиса, но не сами пути, поэтому не отличают «удалён правильный объект» от «удалён не тот»:

- `RemoveMediaOriginalHandlerTest::testRemovesOriginalOfImageMediaKeepingConversion` захватывает аргументы `deleteObject` и сверяет путь оригинала — это эталон. А video/audio success-кейсы и `GetMediaUrlHandlerTest::testReturnsConversionUrlForReadyOriginalRemovedMedia` проверяют только результат/число, без сверки, что URL конверсии строится по пути конверсии, а не оригинала.
- `DeleteMediaHandlerTest::testDeletesReadyOriginalRemovedMediaConversionsAndIdempotentOriginal` проверяет `exactly(2)` вызова `deleteObject`, но не то, что среди удаляемых путей есть путь конверсии и исторический путь оригинала.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Application/RemoveMediaOriginalHandlerTest.php:66-100`; `GetMediaUrlHandlerTest` (кейс конверсии для `ReadyOriginalRemoved`); `DeleteMediaHandlerTest.php:154-173`
- **Как исправить:** при желании — там, где важна корректность пути, захватывать аргументы (как в image success-кейсе) и сверять путь конверсии/оригинала, а не только число вызовов.

### 4. `ProcessMediaHandlerTest` no-op не закрепляет неизменность полей ошибки

`testIsNoOpWhenMediaAlreadyOriginalRemoved` (главный тест защиты финализированного состояния) проверяет только неизменность `status`, но не `processingAttempts`/`processingError` — а именно поздняя запись ошибки (через `recordTemporary/PermanentProcessingError`) и была риском, ради которого guard расширен на `isFinalized()`. Тест не упадёт, если handler случайно запишет ошибку до `isFinalized()`-гарда.

Технические детали:

- **Тип:** `tests`
- **Рекомендация:** на усмотрение автора
- **Где:** `tests/Feature/Modules/Media/Application/ProcessMediaHandlerTest.php:254-276`
- **Как исправить:** добавить ассерты неизменности `processingAttempts`/`processingError` для `ReadyOriginalRemoved`-медиа.

### 5. Дублирование `app.media.not_ready` в двух ветках `GetMediaUrlHandler`

После рефактора ключ `'app.media.not_ready'` встречается в `GetMediaUrlHandler` дважды: в `conversionUrl()` (не-финализированное медиа) и в ветке оригинала (не-ready). Обе ветки семантически разные и обе нужны — план это и предписывал. Правило «не плодить технические константы» прямо разрешает оставлять такие строки рядом с использованием, пока их немного. Это наблюдение про устойчивость к будущему переименованию, а не нарушение.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Application/Query/GetMediaUrl/GetMediaUrlHandler.php:54,75`
- **Как исправить:** оставить как есть (соответствует rules «не плодить технические константы») либо, если ключ начнёт переиспользоваться шире, вынести в одну приватную фабрику исключения.

### 6. Дублирование тел `recordTemporaryProcessingError` и `recordPermanentProcessingError`

После расширения guard-ов оба доменных метода `Media` стали побайтно идентичными по реализации: `if ($this->isFinalized()) return;` → `status = ProcessingFailed` → `processingAttempts->increment()` → `processingError = ...` → `touch()`. Различаются только докблоки. При будущей правке логики фиксации ошибки (новое поле, лог) легко обновить один и забыть второй; тест на симметричный no-op это не поймает.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Domain/Entity/Media.php:182-208`
- **Как исправить:** при желании вынести общее тело в приватный `recordProcessingError(MediaProcessingError $processingError)` и вызывать его из обоих публичных методов, сохранив их как точки доменного контракта.

### 7. `isFinalized()` собран через `||`, а не исчерпывающий `match`

`isFinalized()` написан как `return $status === Ready || $status === ReadyOriginalRemoved;`. Правило проекта предписывает для enum исчерпывающий `match` без `default`: при таком стиле добавление нового `MediaStatus` стало бы compile-time ошибкой PHPStan, тогда как текущий `||` молча вернёт `false` для нового статуса.

Нюанс местного стиля: соседний предикат `isReady()` тоже написан одиночным `===` (`return $status === MediaStatus::Ready;`), то есть `isFinalized()` следует уже принятому в файле паттерну для предикатов. Поэтому это пограничная стилистика, а не однозначное нарушение — отсюда «на усмотрение».

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/Domain/Entity/Media.php:250-256`
- **Как исправить:** при желании переписать предикат на исчерпывающий `match ($this->status)` по всем веткам `MediaStatus`, чтобы расширение enum было защищено PHPStan. Если выбран единый стиль предикатов через `===` — оставить как есть для единообразия с `isReady()`.

### 8. README: переход статусов описан линейной цепочкой

В README строка статусов читается как `waitingUpload → uploaded → ready → readyOriginalRemoved` — как единая обязательная цепочка, хотя `readyOriginalRemoved` — опциональная терминальная ветка, в которую переводит только явная команда `RemoveMediaOriginal`. Ниже текст поясняет это корректно, поэтому путаница маловероятна — это небольшая неоднозначность заголовочной строки, не ошибка документации.

Технические детали:

- **Тип:** `docs`
- **Рекомендация:** на усмотрение автора
- **Где:** `app/src/Modules/Media/README.md` — раздел «Статусы и обработка ошибок», строка с цепочкой статусов
- **Как исправить:** при желании пометить последний переход как опциональный, например `ready (→ readyOriginalRemoved опционально)`.
