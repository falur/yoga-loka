# Ревью: Рефакторинг Media URL-сервисов, RemoveMediaOriginal и config-independence

## Оценка

**87/100.** Аккуратный крупный рефакторинг: URL-сервис вынесен за контракт в Infrastructure, добавлен опциональный статус удаления оригинала с идемпотентными доменными переходами, Application отвязан от `*Config`. Изменение сопровождается подробными докблоками, синхронной правкой `arch.md`/`rules.md`/README и широким покрытием (unit + feature + kernel + HTTP-интеграция). Мета-ревью выявило одно обязательное нарушение правила — ветвление по enum через `if/else` вместо исчерпывающего `match` в новом файле `MediaUrlService` (замечание 3), — и один архитектурный блокер, обязательный перед подключением `RemoveMediaOriginal` к реальному триггеру: порядок «удалить объект в хранилище → зафиксировать статус» без надёжного after-commit-шага (замечание 4). Остальные замечания — на усмотрение автора и касаются осознанно принятых компромиссов, которые стоит держать на виду.

## Замечания

### 1. Устойчивость ленты к отсутствующему медиа переехала из кода в инвариант БД

Раньше сборка вложения ленты сначала искала медиа по идентификатору и, если его не было, просто пропускала вложение — чтение записи не падало. Теперь код обращается к загруженной сущности медиа напрямую как к обязательной связи. Если строки медиа под вложением вдруг не окажется, чтение свойства уронит весь запрос (500 на ленте и на карточке поста), а не пропустит одно вложение.

Практически сейчас такая ситуация недостижима: внешний ключ вложения на медиа стоит с запретом удаления используемого медиа (ON DELETE RESTRICT), и это закреплено тестом; состояния «оригинал удалён» и «ещё не готово» дают безопасный null и обрабатываются корректно. Риск проявится только если инвариант кто-то ослабит: миграция снимет RESTRICT, появится жёсткое удаление в обход сценария или ручная чистка данных. Практического вреда сегодня нет, но стоит осознавать, что защита ленты теперь держится не на коде, а на схеме БД.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Application/View/PostViewAssembler.php` — метод `mediaItem()`, обращение к `$postMedia->media`; `app/src/Modules/Posts/Domain/Entity/PostMedia.php:60-68` — non-nullable `#[BelongsTo(target: Media::class, ...)]`; FK RESTRICT в миграции `app/database/migrations/20260617.160942_0_create_posts_domain_tables.php`.
- **Что подтверждает проблему:** свойство `public private(set) Media $media;` объявлено без nullable; при отсутствии связанной строки Cycle оставит связь неинициализированной и доступ бросит `Error`. Прежний путь через `findById(...) -> null -> пропуск` был устойчив к отсутствию строки.
- **Как исправить:** осознанно оставить, добавив к связи явную пометку «безопасно только благодаря FK RESTRICT» (докблок это уже частично делает), либо, если нужна защита в коде, грузить связь как nullable и вернуть null-skip — но это расходится с документированным foundational-контрактом `Media`, поэтому предпочтителен первый вариант.
- **Тесты:** ветка «оригинал удалён → вложение исчезает, attachmentType=none» уже покрыта `tests/Feature/Modules/Posts/Http/GetPostHttpTest.php`; инвариант удаления — `testCannotDeleteMediaReferencedByPostMedia`. Дополнительный тест не требуется.

### 2. Верхняя граница срока presigned-ссылки задана числом в двух местах и синхронизируется только комментарием

Максимум срока presigned-ссылки скачивания (7 суток) проверяется в конфиге и одновременно продублирован из доменного value object, который держит тот же предел. Их согласованность обеспечивается только комментарием «менять синхронно», а тест на превышение тоже опирается на соседнее захардкоженное число. Если предел в value object однажды изменят, ни анализатор, ни тесты об этом не сообщат: конфиг молча начнёт отвергать значения, которые домен уже принимает, или наоборот. Риск небольшой и разовый, но это лишняя точка ручной синхронизации, которую легко забыть.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Shared/Infrastructure/Configuration/Media/MediaConfig.php` — проверка `$presignedTtlSeconds > 604_800`; дублирует `MediaPresignedTtl::MAX`; `tests/Kernel/Shared/Infrastructure/Configuration/MediaConfigTest.php` — `testRejectsPresignedTtlAboveUpperBound` хардкодит `604_801`.
- **Что подтверждает проблему:** комментарий в конструкторе `MediaConfig` прямо просит «держать синхронно» с константой VO; прямой импорт запрещён (константа `protected` и завёл бы зависимость `Shared/Infrastructure → Modules/Media/Domain`), поэтому связь держится текстом.
- **Как исправить:** вынести предел в единый доступный обоим сторонам источник — публичную границу домена (сейчас `MediaPresignedTtl::MAX` объявлена `protected const`, поэтому напрямую из конфига/теста не читается; нужен публичный аксессор — `public const` или `public static function maxSeconds()`). Вариант «тест-мост, который берёт максимум у VO и проверяет, что конфиг отвергает `max + 1`» без такого аксессора невыполним: `protected const` из теста не прочитать.
- **Тесты:** при выборе тест-моста — сначала открыть предел публично, затем обновить `MediaConfigTest`; иначе оставить осознанно.

### 3. Ветвление по видимости медиа сделано через if/else, а не исчерпывающим match

Правила проекта требуют для enum исчерпывающий `match` без ветки по умолчанию, чтобы добавление нового варианта ловилось статическим анализом. Здесь выбор способа построения ссылки (прямая публичная или подписанная со сроком) делается условием «если публичная — …, иначе — подписанная» — это диспетчеризация поведения по значению enum, а не guard-clause предусловия, поэтому правило применимо напрямую. `MediaUrlService.php` — новый файл в этом же дифе (статус `A`), а `resolverFor()` написан с нуля: это не перенос паттерна из удалённого кода, а свежее нарушение безусловного правила rules.md «Enum — исчерпывающий `match` без default». Практический риск сегодня низкий (у `MediaVisibility` ровно два значения, обе ветки покрыты тестом), но правило оговорок не имеет: если появится третий вариант видимости, он молча уйдёт в приватную ветку и получит presigned-ссылку без явного решения, и статический анализ этого не поймает.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** `править обязательно`
- **Где:** `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php` — `resolverFor()` (`if ($visibility === MediaVisibility::Public) ... else ...`).
- **Что подтверждает проблему:** безусловное правило `rules.md` «match вместо switch / Enum — исчерпывающий match без default»; файл новый (`A`), метод написан заново, значит нарушение вносится этим дифом.
- **Как исправить:** заменить `if/else` на `match ($visibility)` с явным перечислением всех вариантов `MediaVisibility` (Public → прямой резолвер, Private → presigned).
- **Тесты:** обе ветки (public/private) уже покрыты в `FindMediaUrlHandlerTest`; менять тесты не нужно.

### 4. Удаление оригинала фиксирует статус после физического удаления объекта — окно битой ссылки без надёжного after-commit-шага

Добавлен сценарий удаления оригинала медиа с сохранением конверсий (проверка владельца, требование хотя бы одной готовой конверсии, идемпотентность). Сам факт, что команда пока не подключена ни к одному входу (ни маршрут, ни консоль, ни очередь, ни outbox), — не проблема: это осознанная заготовка. Проблема — в порядке операций, который станет боевым при подключении: `deleteObject(...)` в хранилище выполняется до доменного перехода `markReadyOriginalRemoved()` + `run()`, без транзакции и без автоматического повтора. Пока переход не довыполнен (сбой между удалением объекта и flush), статус остаётся `ready`, и любой запрос ссылки на оригинал (`FindMediaUrl`/`FindMediaOriginalUrl`/лента/аватар) вернёт ссылку на уже удалённый объект — окно битой ссылки. Это прямо расходится с принципом `arch.md`: отложенные шаги, которым нужна гарантированная доставка после commit-а, идут через outbox, а не «эффект до фиксации состояния». Докблок Handler-а сам честно фиксирует компромисс. Пока входа нет, живого бага нет, но перед подключением к реальному триггеру порядок обязателен к пересмотру — иначе первый же боевой вызов сможет отдавать битые ссылки.

Технические детали:

- **Тип:** `architecture`
- **Рекомендация:** `обязательно перед подключением к триггеру` (сейчас неактивно — команда не вызывается; при появлении любого входа это блокер по `arch.md`, а не опция)
- **Где:** `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php` — нет `#[Transactional]`, `deleteObject(...)` выполняется до `markReadyOriginalRemoved()` + `run()`.
- **Что подтверждает проблему:** докблок Handler-а сам описывает окно битой ссылки и отсутствие авто-повтора; принцип `arch.md` про outbox для надёжных after-commit-шагов. `deleteObject` идемпотентен по 404 (проверено: `S3MediaFileService::deleteObject` ловит `S3Exception` и на not-found делает no-op), поэтому повтор команды после частичного сбоя безопасен — но повтор никем не гарантирован, окно битой ссылки сохраняется до следующего вызова.
- **Как исправить:** при подключении к триггеру перевести физическое удаление объекта в after-commit-шаг (outbox), чтобы статус фиксировался в транзакции, а удаление объекта происходило после commit с повторами.
- **Тесты:** сценарий покрыт на уровне Handler (`RemoveMediaOriginalHandlerTest`); интеграционного теста нет по причине отсутствия входа — это ожидаемо для заготовки.

### 5. Лента на каждой странице подгружает все конверсии медиа, хотя использует только оригинал

Репозиторий вложений жадно грузит image/video/audio-конверсии вместе с каждым медиа, но сборка ленты сейчас строит ссылку только на оригинал и конверсии не читает. Это не N+1 и не лишняя подпись presigned-ссылок на конверсии в ленте (оригинал резолвится из уже загруженной сущности), а дополнительные строки конверсий, добираемые тем же eager-запросом и не попадающие в ответ. Это документировано как задел под будущий показ превью (постер видео, миниатюры) и намеренно завязано на `arch.md`, поэтому убирать eager-load нельзя как обычную оптимизацию. Но как осознанную текущую стоимость архитектурного решения это стоит зафиксировать: пока фичи превью нет, лента несёт лишние выборки строк, растущие с числом вложений на странице.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Repository/PostMediaRepository.php` — `->load('media.imageConversions')`/`videoConversions`/`audioConversions` в обоих методах; `PostViewAssembler::mediaItem()` вызывает только `getOriginalUrl(...)`.
- **Что подтверждает проблему:** докблок репозитория сам отмечает, что конверсии сейчас не читаются и eager-load держится «под планируемый показ превью».
- **Как исправить:** осознанно оставить до появления фичи превью или сузить eager-load до оригинала (синхронно с правкой `arch.md`, отдельной задачей).
- **Тесты:** не требуется.

### 6. Happy-path тест удаления оригинала для видео не проверяет возвращённый результат

Три позитивных сценария `RemoveMediaOriginalHandlerTest` симметричны по смыслу, но проверяют разное. Для image и audio тест захватывает результат `handle()` и утверждает `MediaResult` (`$result->status === ReadyOriginalRemoved`, `$result->mediaId`), а для видео вызывает `handle(...)` без присвоения и проверяет только состояние сущности. Бага это не создаёт, но ослабляет фиксацию контракта возврата для видео и делает набор тестов несогласованным — при регрессе в `MediaResult::fromEntity` для видео-ветки тест промолчит.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `tests/Feature/Modules/Media/Application/RemoveMediaOriginalHandlerTest.php` — `testRemovesOriginalOfVideoMediaKeepingConversionAndPoster` вызывает `handle(...)` без захвата `$result`; ср. image (`assertSame(..., $result->status)`, `assertSame($media->id->value(), $result->mediaId)`) и audio с теми же проверками `$result`.
- **Что подтверждает проблему:** видео-тест не содержит утверждений по `$result`, тогда как соседние позитивные тесты их содержат.
- **Как исправить:** захватить `$result` в видео-тесте и добавить те же два `assertSame` по `status`/`mediaId`, что и в image/audio.
- **Тесты:** это и есть правка теста.
