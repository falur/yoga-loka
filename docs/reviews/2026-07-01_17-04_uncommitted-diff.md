# Ревью: Рефакторинг Media URL-сервисов, RemoveMediaOriginal и config-independence (2-й круг)

## Оценка

**92/100.** Второй круг доводки того же крупного дифа. Обязательное замечание первого круга
(ветвление по видимости через `if/else` вместо исчерпывающего `match`) устранено: `MediaUrlService`
теперь диспетчеризует резолвер `match ($visibility)` без `default`, presigned-ветка вынесена в
`presignedResolverFor()`. Принятые optional-правки первого круга тоже на месте: видео happy-path тест
`RemoveMediaOriginalHandlerTest` проверяет возвращённый `MediaResult`, а связь `PostMedia::$media`
несёт докблок про инвариант FK RESTRICT. Новый код (enum `MediaConversionKind`,
`MediaConversionsChecker`, `existsReadyForMediaId` в репозиториях конверсий, `MediaUploadPlanner`,
резолверы URL, `LocaleResolver`) правилам и архитектуре не противоречит: guard-clause-переходы,
именованные аргументы, read-only репозитории через `count()`, отсутствие примитивов в Entity,
`declare(strict_types=1)` и trailing commas на месте.

Явных обязательных нарушений во втором круге не найдено. Оба свежих замечания — `на усмотрение
автора` и касаются поверхности, оставшейся без потребителя, и асимметрии в пакетной загрузке.
Ранее отклонённые с обоснованием пункты (№2 дублирование предела presigned-TTL, №5 eager-load
конверсий в ленте, №4 порядок «удалить объект → зафиксировать статус» в `RemoveMediaOriginal`)
повторно не поднимаю: новых содержательных аргументов против прежних отклонений нет. По №4 фиксирую
только статус: команда по-прежнему не подключена ни к одному входу, поэтому предусловие «перед
подключением к триггеру перевести `deleteObject` в after-commit outbox-шаг» остаётся открытым и
неизменным, а не новым замечанием.

## Замечания

### 1. Полносетевой путь FindMediaUrl построен, но в приложении его никто не вызывает

Модуль `Media` — foundational: у него нет своих HTTP-маршрутов, и сценарии он предоставляет другим
модулям как библиотечный API. В этом дифе появился крупный «полный набор ссылок»: запрос всех URL
медиа сразу — оригинал плюс все конверсии с их типами. Но оба реальных потребителя ссылок в этом же
дифе перешли на узкий путь «только оригинал»: лента `Posts` строит оригинал из уже загруженной
сущности, а аватар профиля идёт через отдельный запрос только оригинала. В итоге весь полносетевой
аппарат остался без единого вызова в коде приложения — он покрыт только модульным тестом.

Практического вреда сегодня нет: код корректен, протестирован и, как API foundational-модуля,
симметричен незадействованной пока команде удаления оригинала. Сам путь при этом уже задокументирован
как публичный API модуля: `arch.md` прямо называет `MediaUrlService::getUrls(Media)` путём полного
набора «оригинал + конверсии», а README описывает Query `FindMediaUrl` — то есть вопрос не в
отсутствии документации. Проблема в том, что это заметная новая поверхность (запрос, DTO набора,
коллекция ссылок конверсий с методом выбора по типу, отдельный enum вида конверсии, репозиторный
метод жадной загрузки), у которой сейчас нет ни одного runtime-потребителя, и это нигде не отмечено —
в отличие от команды удаления оригинала, чей докблок прямо оговаривает неподключённость к входу. Риск —
стоимость поддержки неиспользуемой поверхности и вероятность, что реальному потребителю в итоге
понадобится другой контракт, а этот придётся переделывать. Стоит либо явно отметить отсутствие текущего
потребителя рядом с уже существующим описанием API (README/докблок, как сделано для
`RemoveMediaOriginal`), либо отложить полносетевой путь до появления первого потребителя.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Media/Application/Query/FindMediaUrl/FindMediaUrlHandler.php`;
  `app/src/Modules/Media/Application/Dto/MediaUrlsResult.php`,
  `MediaConversionUrl.php`, `MediaConversionUrlCollection.php`;
  `app/src/Modules/Media/Domain/Enum/MediaConversionKind.php`;
  `app/src/Modules/Media/Repository/MediaRepository.php` — `findByIdWithConversions()`;
  реализация `MediaUrlService::getUrls()` в `Infrastructure/FileService/MediaUrlService.php`.
- **Что подтверждает проблему:** поиск по `app/src` не находит ни одной ссылки на `FindMediaUrlHandler`
  / `FindMediaUrlQuery` / `getUrls(` вне их собственных папок; у `Media` нет `#[Route]`-контроллеров;
  `PostViewAssembler` вызывает `getOriginalUrl`, `UserPublicProfileAssembler` — `FindMediaOriginalUrl`.
  Тесты на полный набор есть только в `tests/Feature/Modules/Media/Application/FindMediaUrlHandlerTest.php`.
- **Как исправить:** осознанно оставить как foundational-API и пометить это явно (README модуля уже
  описывает `FindMediaUrl`, но не отмечает отсутствие текущего потребителя), либо отложить
  полносетевой путь и связанные DTO/коллекцию/enum/репозиторный метод до первого реального вызова.
- **Тесты:** дополнительных не требуется; при отсрочке — удалить вместе с кодом.

### 2. В листинге профилей ссылка на аватар каждого пользователя разрешается отдельным запросом

Лента записей в этом дифе получила пакетную загрузку: вложения и их медиа грузятся одним набором
запросов на страницу, а URL строится в памяти — по вложению отдельного похода в базу больше нет.
Аватары в листинге профилей остались на прежней модели: сборка публичного профиля вызывается на
каждого пользователя, и для каждого непустого аватара выполняется отдельный поиск медиа по
идентификатору. На странице из N пользователей с аватарами это N отдельных запросов к медиа —
классический N+1 на уровне разрешения ссылок.

Это поведение существовало и до дифа (прежняя сборка так же ходила за медиа по одному — старый
`FindMediaUrl` использовал `findById` без конверсий), и относительно HEAD число запросов на аватар
не меняется: и до, и после — один `findById` без конверсий, поэтому это не регресс. При этом называть
изменение «удешевлением» относительно HEAD некорректно — выигрыш только внутридифовый: переключение
аватара на `FindMediaOriginalUrl` не даёт ему унаследовать загрузку конверсий, которую `FindMediaUrl`
получил в этом же дифе (`findByIdWithConversions`). Но появляется заметная асимметрия: тот же
рефакторинг URL-слоя дал `Posts` пакетный путь и даже репозиторный метод жадной загрузки, а листинг
профилей так и разрешает аватары поштучно, потому что пакетного «URL для набора медиа-идентификаторов»
контракта в `Media` по-прежнему нет. Риск — деградация времени ответа на выдаче профилей, растущая
линейно с размером страницы; проявится на реальном трафике списков.

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/User/Application/Query/GetUserPublicProfiles/GetUserPublicProfilesHandler.php`
  — `->map(fn(User $user) => $this->assembler->fromUser($user))`;
  `app/src/Modules/User/Application/Profile/UserPublicProfileAssembler.php` — `resolveAvatarUrl()`
  диспатчит `FindMediaOriginalUrlQuery` на каждого пользователя, а обработчик делает
  `mediaRepository->findById(...)`.
- **Что подтверждает проблему:** `FindMediaOriginalUrlHandler::handle()` выполняет один
  `findById` на вызов; ассемблер вызывается в `->map(...)` по каждому пользователю страницы. Пакетного
  контракта разрешения URL по набору id в `Media` нет.
- **Как исправить:** осознанно оставить (аватар — одна дешёвая выборка по PK, набор ограничен размером
  страницы) либо, отдельной задачей, добавить в `Media` пакетный сценарий «URL оригиналов по набору
  медиа-идентификаторов» и собирать аватары листинга одним запросом, как это сделано для вложений ленты.
- **Тесты:** при добавлении пакетного пути — feature-тест на выдачу профилей, проверяющий число
  запросов/корректность аватаров; иначе не требуется.
