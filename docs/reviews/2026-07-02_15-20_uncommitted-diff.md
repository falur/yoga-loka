## Замечания

### 1. Документация обещает проверку верхней границы срока ссылки, которой в коде нет

Раньше срок жизни временной ссылки на скачивание («presigned TTL») ограничивался и снизу, и сверху одним объектом-значением: меньше 1 или больше 604800 секунд (7 суток — предел подписи хранилища) сразу давали ошибку. В этом изменении верхнюю границу убрали из объекта-значения и переложили на конфиг, но конфиг проверяет только значение по умолчанию при старте приложения. При этом README модуля по-прежнему утверждает, что если вызывающий передаст свой срок «вне диапазона 1..604800 → ошибка» и что «диапазон 1..604800 держит MediaPresignedTtl».

На практике теперь переданный вызывающим срок проверяется только на «больше нуля»: значение, например, в 700000 секунд пройдёт как валидное. Уточнение по итогам мета-проверки: это не приводит к «слишком долго живущей» ссылке и не является дырой безопасности — клиент хранилища не проверяет лимит подписи при генерации, поэтому ссылка построится, но хранилище отклонит её уже при запросе (S3 SigV4, ответ 403). То есть вместо чистой ошибки валидации вызывающий получит нерабочую ссылку, а поломка обнаружится только при использовании. Сейчас это латентно — ни один боевой потребитель не передаёт своё значение (аватар идёт со значением по умолчанию, полный набор `FindMediaUrl` пока никем не вызывается). Но документация даёт ложную гарантию: тот, кто позже подключит `FindMediaUrl` к HTTP и доверится строке README «вне диапазона → ошибка», не добавит проверку на границе — и вместо понятной 4xx-ошибки клиент получит подписанную ссылку, которую хранилище отвергнет при обращении.

Заодно стоит уточнить смежную неточность: докблоки и README описывают `FindMediaUrl`/`FindMediaOriginalUrl` как «не бросающие» (медиа недоступно → `null`), но это не абсолют — невалидный переданный срок (например, явный `0`) на приватном медиа даёт `InvalidDomainValueException` (500), а не `null`. Это намеренно и покрыто тестом, но текст про «best-effort → null» без оговорки вводит в заблуждение.

Нужно привести к согласованности: либо вернуть проверку верхней границы на путь переопределения (чтобы гарантия из README была правдой), либо убрать из README утверждение про «1..604800 → ошибка» и «диапазон держит MediaPresignedTtl», честно описав, что переопределение проверяется только снизу, а верхнюю границу держит лишь значение по умолчанию из конфига.

Технические детали:

- **Тип:** `docs` (расхождение код↔документация публичного контракта README; смежно validation)
- **Рекомендация:** `править обязательно`
- **Где:**
  - `app/src/Modules/Media/README.md:26` — «вызывающий может переопределить `presignedTtlSeconds` (явный `0`/вне диапазона 1..604800 → ошибка)».
  - `app/src/Modules/Media/README.md:175` — «диапазон 1..604800 держит `MediaPresignedTtl`».
  - `app/src/Modules/Media/Infrastructure/FileService/MediaUrlService.php:114` — `MediaPresignedTtl::fromInt($presignedTtlSeconds ?? $this->mediaConfig->presignedTtlSeconds)`.
  - `app/src/Modules/Media/Domain/ValueObject/MediaPresignedTtl.php:24-32` — `assertValid` проверяет только `< 1`.
  - `app/src/Shared/Infrastructure/Configuration/Media/MediaConfig.php:38-46` — верхняя граница `> 604800` проверяется только для поля конфига (значение по умолчанию), не для override.
- **Что подтверждает проблему:** тест `MediaValueObjectTest::testPresignedTtlRequiresPositiveWithoutUpperBound` явно фиксирует, что `MediaPresignedTtl::fromInt(604_801)` теперь **успешен**; из провайдера убрана строка `MediaPresignedTtl => [604_800, 604_801]`. Значит override со значением > 604800 не отвергается, вопреки README.
- **Как исправить:** выбрать одно из двух. (а) Согласовать документацию с кодом: в README заменить «вне диапазона 1..604800 → ошибка» на «меньше 1 → ошибка; верхнюю границу держит только значение по умолчанию конфига», и не приписывать полный диапазон `MediaPresignedTtl`. (б) Либо восстановить гарантию: валидировать верхнюю границу и на override (например, единая доменная проверка диапазона presigned-TTL, применяемая и к значению из конфига, и к переопределению, чтобы «7 суток» жили в одном месте и срабатывали для обоих путей).
- **Тесты:** если выбран вариант (б) — добавить в `FindMediaUrlHandlerTest`/`FindMediaOriginalUrlHandlerTest` кейс «override > 604800 → ошибка»; если (а) — тестов не требуется, но убедиться, что README не противоречит существующему `testPresignedTtlRequiresPositiveWithoutUpperBound`.

### 2. Добавлен рабочий, но нигде не подключённый функционал (RemoveMediaOriginal и полный набор FindMediaUrl)

Команда удаления оригинала `RemoveMediaOriginal` и «полный» путь `FindMediaUrl` (оригинал + все конверсии, метод `getUrls`) реализованы, задокументированы и покрыты тестами, но ни один боевой сценарий их не вызывает: у команды нет ни контроллера, ни консольной команды, ни outbox-шага, а `getUrls`/`FindMediaUrl` не потребляются ничем в `app/src` (лента и аватар используют только узкий `getOriginalUrl`). Это осознанный «foundational»-задел под будущее (оба класса честно помечены в докблоках как пока не подключённые), но правило проекта требует такой код хотя бы явно отметить, чтобы он не забылся как «мёртвая» поверхность и не разошёлся с реальностью к моменту подключения.

Отдельно у `RemoveMediaOriginal` есть заявленный в докблоке компромисс порядка «удалить объект в хранилище → затем зафиксировать статус» без транзакции и без гарантированного повтора: при сбое между удалением и записью статуса остаётся короткое окно, когда запрос ссылки на оригинал вернёт ссылку на уже удалённый объект. Пока команда не подключена к триггеру — это неактуально, но именно поэтому важно, чтобы к моменту подключения компромисс был пересмотрен (вариант из докблока — вынести удаление в outbox-шаг после commit-а перехода).

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:**
  - `app/src/Modules/Media/Application/Command/RemoveMediaOriginal/RemoveMediaOriginalHandler.php` — нет боевого вызывающего.
  - `app/src/Modules/Media/Application/Query/FindMediaUrl/FindMediaUrlHandler.php` — `getUrls`-путь без потребителя.
- **Что подтверждает проблему:** поиск по `app/src` показывает вызовы только внутри самих определений и тестов; докблоки прямо пишут «пока не подключена к прямому запуску пользователем» и «не вызывается ни одним потребителем в app/src».
- **Как исправить:** решение автора — оставить как задел (тогда зафиксировать в roadmap/issue, чтобы отследить подключение и пересмотр порядка удаления в S3 у `RemoveMediaOriginal`) или отложить внесение до появления реального потребителя. Код трогать не обязательно.
- **Тесты:** имеющегося покрытия достаточно; при подключении к HTTP/console добавить интеграционный тест роута (правило «каждый роут покрыт интеграционным тестом»).

### 3. Лента подгружает конверсии, которые сейчас не использует

Репозиторий вложений записей теперь eager-грузит все конверсии медиа (`media.imageConversions`/`videoConversions`/`audioConversions`) на каждую страницу ленты, но сборщик представления строит только ссылку на оригинал (`getOriginalUrl`) и к конверсиям не обращается вовсе. То есть каждая страница ленты платит за три дополнительные загрузки связей на каждое вложение, результат которых сразу отбрасывается.

Это сознательный задел «под планируемый показ превью», прямо разрешённый архитектурой и снабжённый комментарием в репозитории. Замечание не про нарушение, а про то, что цена платится уже сейчас, а выгода — только в будущем: стоит либо подтвердить, что задел оправдан, либо отложить eager-load конверсий до момента, когда превью реально начнут показывать (синхронно с правкой `arch.md`, как и предписывает комментарий).

Технические детали:

- **Тип:** `performance`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Repository/PostMediaRepository.php:30-33,54-56` (три `->load('media.*Conversions')`); потребитель `app/src/Modules/Posts/Application/View/PostViewAssembler.php` (`mediaItem` → `getOriginalUrl`, конверсии не читаются).
- **Что подтверждает проблему:** `mediaItem()` использует только `originalUrl`; ни один путь ленты не читает `MediaUrlsResult.conversions`.
- **Как исправить:** оставить как задел (подтвердив осознанность и синхронность с `arch.md`) либо сузить eager-load до `media` без конверсий до появления показа превью.
- **Тесты:** отдельных не требуется; при сужении обновить ожидания в `PostMediaRepositoryTest`.

### 4. Включение правила `single_quote` в php-cs-fixer шире темы изменения

В конфиг форматирования добавлено правило `single_quote`, применяющееся ко всему проекту, тогда как остальной diff сфокусирован на модуле Media/локали/VO. В самом наборе изменений под это правило попали лишь две строки в тестах. Если в кодовой базе есть другие двойные кавычки у простых строк, следующий прогон форматтера в CI выдаст массовый несвязанный diff (или упадёт на проверке), уже после этого коммита.

Замечание низкой уверенности: возможно, проект и так писался в одинарных кавычках и правило лишь закрепляет статус-кво. Стоит убедиться, что `php-cs-fixer` на всей базе не даёт дополнительных правок помимо вошедших в diff.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `.php-cs-fixer.dist.php:12` (`'single_quote' => true`).
- **Что подтверждает проблему:** правило глобальное, а тема diff — Media; проверить полноту применения без запуска форматтера нельзя.

- **Тесты:** не требуются (изменение тулчейна).

### 5. Связь `PostMedia.media` — обязательное свойство, которое `create()` не инициализирует

У вложения записи появилось поле-связь на сущность медиа, объявленное как обязательное (не допускающее пустоты). При этом фабрика создания вложения его не заполняет — оно осмысленно только после того, как строку подняли из базы вместе с медиа. Сейчас все пути чтения ленты грузят медиа сразу (eager), поэтому связь всегда на месте и всё работает. Но это хрупкая конструкция: любой будущий путь, который прочитает вложение без «жадной» загрузки медиа и обратится к этому полю, получит либо скрытую доп-загрузку по одной строке (та самая N+1), либо прямую ошибку обращения к неинициализированному свойству — а на только что созданном через фабрику объекте обращение к полю упадёт всегда.

Это не баг сегодняшнего кода (докблок поля подробно всё описывает, а FK с запретом удаления держит инвариант на уровне схемы), а скрытая мина под будущие изменения. Стоит либо оставить как есть с явным осознанием риска, либо подстраховать инвариант, чтобы обращение к незагруженной связи не давало «тихую» N+1 или неожиданную ошибку.

Технические детали:

- **Тип:** `quality`
- **Рекомендация:** `на усмотрение автора`
- **Где:** `app/src/Modules/Posts/Domain/Entity/PostMedia.php` — `public private(set) Media $media` (обязательное, non-nullable); `create()` инициализирует `mediaId`, но не `media`.
- **Что подтверждает проблему:** запись идёт по колонке `mediaId`; сущность `media` доступна только после ORM-гидрации с eager-load. Обращение к `->media` на объекте из `create()` до гидрации бросит `Error` (неинициализированное типизированное свойство).
- **Как исправить:** решение автора. Варианты: оставить с явной пометкой «только после eager-load» (уже есть в докблоке); либо рассмотреть защиту от случайного доступа без загрузки. Правка не обязательна, пока все пути грузят связь eager.
- **Тесты:** дополнительно можно закрепить регрессом «доступ к `media` без eager-load», но при текущем контракте это скорее документирование, чем необходимость.

### 6. Англицизмы в новых докблоках и комментариях

В новых комментариях и докблоках встречаются кальки с английского, для которых в правилах проекта требуется обычное русское слово: «foundational» (есть «базовый»), «best-effort» («по возможности»), «реиспуск», а в тестовых комментариях — «changeset», «short-circuit». Это не влияет на работу кода, но правило «без англицизмов» распространяется на человекочитаемый русский текст, включая комментарии и докблоки.

Оговорка: часть терминов в проекте уже устоялась как идиомы (`no-op`, `staging`, `eager`), поэтому речь про точечную стилистическую чистку новых мест, а не про сплошную замену.

Технические детали:

- **Тип:** `rules`
- **Рекомендация:** `на усмотрение автора`
- **Где:** докблоки `FindMediaUrlHandler`, `FindMediaOriginalUrlHandler`, `MediaUrlService`, `RemoveMediaOriginalHandler`; докблок связи в `Posts/Domain/Entity/PostMedia.php`; отдельные комментарии в новых тестах.
- **Что подтверждает проблему:** правило `docs/rules.md` «Без англицизмов» требует русских аналогов в комментариях/докблогах; перечисленные слова имеют общеупотребимые русские замены.
- **Как исправить:** заменить кальки на русские аналоги в новых местах; устоявшиеся идиомы можно оставить.
- **Тесты:** не требуются.
