# Правила проекта

## Работа над задачей

- До изменения кода прочитай `docs/arch.md`, `docs/rules.md`, `docs/references.md` и применимые карточки из `docs/business.md`.
- До реализации сформулируй проверяемый результат; для многошаговой задачи дай короткий план с проверкой каждого шага.
- Меняй только строки, необходимые для задачи; не исправляй соседний код без отдельного запроса.
- Не удаляй старый неиспользуемый код, если он не стал неиспользуемым из-за текущего изменения.
- Не выдавай предположение за факт; значимую неясность или компромисс сообщи до реализации.

## Язык и Git

- Отвечай пользователю на русском языке простыми словами.
- Комментарии, сообщения исключений и записи журнала пиши на русском языке без ненужных англицизмов.
- Пользовательские ошибки возвращай на языке пользователя через существующий механизм переводов.
- Сообщение коммита пиши на русском языке в формате Conventional Commits; тип и область оставляй на английском.
- Не добавляй AI-агента в авторы, соавторы, подписи коммитов и описание pull request.

## PHP и типы

- Каждый PHP-файл, входящий в PHPStan, начинай с `declare(strict_types=1)`.
- Не используй `mixed` в проектных сигнатурах и PHPDoc; неизвестные внешние данные сузь на границе системы.
- Не используй вложенные массивы, tuple и array shape как проектный контракт; замени их именованным DTO, объектом-значением или коллекцией.
- Для списка указывай `list<T>`, для однородной карты — `array<string, T>` или `array<int, T>`.
- Сравнивай значения только через `===` и `!==`.
- Не используй `switch`; применяй исчерпывающий `match` без `default` для enum.
- В многострочных списках ставь завершающую запятую.
- При двух и более обычных аргументах, а также при необязательном или логическом аргументе используй именованные аргументы; исключение допустимо только для несовместимых имён параметров стороннего API и должно быть погашено точечно.
- Не используй `assert()`; проверяй условие явно и бросай типизированное исключение.
- Не оставляй закомментированные блоки, недостижимые ветки и созданный текущим изменением мёртвый код.

## Данные и границы системы

- Вызов `env()` размещай только в файле массива конфигурации: в `app/config/<name>.php` для общего runtime или в `Modules/{Module}/Infrastructure/Configuration/<name>.php` для конкретного модуля.
- Для новой секции конфигурации добавь в модуль-владелец типизированный корневой `<Name>Config`, реализующий `TypedConfig`, и тест его преобразования. Общая конфигурация без владельца остаётся в `Shared/Infrastructure/Configuration`.
- Входящие HTTP-данные принимай через Spiral Filter; не принимай ассоциативный массив или `ServerRequestInterface` в контроллере.
- Ряд выборки превращай в объект фабрикой `{Name}Data::fromDatabaseRow()`; Reader и остальной код ключи ряда не читают.
- Имя таблицы и колонки в Cycle Entity, Repository и Reader бери из `{Entity}Columns`; строковый литерал имени таблицы или колонки в запросе не пиши.
- API-ответ возвращай типизированным Response и Resource, а не ассоциативным массивом.
- Все сериализуемые ключи вне базы данных пиши в `camelCase`; имена таблиц и колонок PostgreSQL — в `snake_case`.
- Не называй таблицу и колонку зарезервированным словом SQL.
- Не добавляй секреты, токены, коды входа, персональные данные и содержимое приватных файлов в журнал, исключение или ответ 500.
- Не используй ручной SQL в коде приложения и тестах; в миграции он допустим только когда schema/query builder не выражает операцию и причина записана рядом.
- При изменении схемы добавь миграцию в `Infrastructure/Persistence/Migration` модуля-владельца; не редактируй уже применённую миграцию и не меняй таблицы другого модуля. В миграции имена таблиц и колонок пиши строковым литералом.
- При изменении публичного HTTP API обнови сгенерированную OpenAPI-спецификацию и тест её генерации.
- Не подавляй PHPStan, тест или предупреждение целиком; исключение должно быть точечным, содержать причину и минимальный путь.

## Именование архитектурных классов

- Domain Entity называй `{Name}`, Cycle Entity — `{Name}CycleEntity`.
- Domain Repository называй `{Name}Repository`, его реализацию Cycle — `Cycle{Name}Repository`.
- Mapper называй `{Name}Mapper`; направления преобразования — `toDomain()` и `toCycleEntity()`.
- Каталог имён колонок называй `{Entity}Columns`, имя таблицы в нём — `TABLE`, Typecast — `{Value}Typecast`.
- Начальную фабрику Entity называй бизнес-действием, например `register()` или `place()`; восстановление из хранения — `restore()`.
- Классы сценария называй `{Action}Command`, `{Action}Query`, `{Action}Handler` и при необходимости `{Action}Result`.
- Публичный интерфейс заканчивай на `Contract`, его реализацию в `Infrastructure/PublicApi` — на `Provider`, межмодульный DTO — на `Dto`.
- Reader называй `{Name}Reader`, его реализацию Cycle — `Cycle{Name}Reader`.
- Данные чтения называй `{Name}Data`, их набор — `{Name}DataCollection`, страницу — `{Name}PageData`.

## Коллекции

- Набор доменных значений передавай именованной типизированной коллекцией, а не голым массивом или `Collection`.
- Если значение уже является коллекцией, используй её методы и не делай промежуточный переход `коллекция -> массив -> коллекция`.
- Для преобразования типизированной коллекции в список используй `mapToList()`; не применяй его к карте, где ключ несёт смысл.
- Для курсорной страницы используй `WhenSelect::cursorById()` и `CursorSlice::fromOverfetched()`, пока эти общие примитивы остаются в проекте.

## Тесты и проверки

- Исправление ошибки начинай с теста, который воспроизводит ошибку; новую ветвь поведения покрывай положительным, отрицательным и граничным сценарием.
- Каждый HTTP-маршрут покрывай интеграционным тестом.
- Сохраняй 100% покрытие кода приложения.
- Тест одного модуля размещай в его `Tests`; в глобальном `tests` оставляй только сквозные и межмодульные проверки.
- Тесты приложения запускай только в Docker командой `make test`; не запускай `composer test` с хоста.
- PHPStan приложения запускай только в Docker командой `make phpstan`.
- Перед завершением изменения кода запусти `make qa`.
- Для быстрой проверки чистой доменной логики используй `make test-unit`; тест из этого набора не должен поднимать Spiral, базу данных, Redis, MinIO, очередь или сеть.
- Для дублёра, у которого не проверяется факт вызова, используй `createStub()`; mock используй только когда тест проверяет взаимодействие.
- Тесты и PHPStan каждого изменённого пакета из `packages/*` запускай внутри этого пакета через `composer -d packages/<package> test` и `composer -d packages/<package> phpstan`.
